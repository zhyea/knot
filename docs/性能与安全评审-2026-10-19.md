# 性能与安全评审 — knot（2026-10-19）

> 范围：只读评审 `knot-server`（8 模块）+ `knot-front`（Vue3/TS）。
> 方法：源码通读 + 实证 grep（无修改、无构建）。结论均附 `文件:行号` 证据。
> 门禁现状（来自 2026-10-18 巡检）：后端 669 例单测 BUILD SUCCESS、前端 `vue-tsc` exit 0、`vite build` exit 0。

---

## 0. 结论速览

| 维度 | 总体判断 |
|------|----------|
| 安全架构 | **基础扎实**：消费者 API Key 鉴权 + 管理端「登录 JWT → 接口级权限」双层、默认拒绝；CORS 显式源 + 禁凭据；AES-256-GCM 随机 IV；无 Jackson 多态反序列化、无 `Runtime.exec`、无路径穿越。 |
| 安全缺口 | **1 项高**：生产可用开发默认密钥（JWT / 凭证加密），仅告警不拦截。 |
| 安全缺口 | 中：数值字段无范围校验（无 `@Min/@Max/@Range`）；AES 密钥由口令 SHA-256 派生无盐。低：网关鉴权无防爆破限流；强随机数阻塞；CORS 默认含 localhost。 |
| 性能 | 网络层与流式设计良好（连接池、显式超时、StreamingResponseBody）。**主要隐患在线程模型**：网关请求线程 `Thread.sleep` 退避；Redis 档在途读为同步 GET 且按池 N 次串行。Comparator 副作用已证实为低危（命中缓存）。 |

## 1. 安全发现

### 🔴 P0 — 生产可使用「开发默认密钥」（仅告警，不拦截）

两份核心密钥在环境变量缺失时**回退到源码硬编码的默认值**，且只打一行 WARN，不阻止启动：

- **JWT 签名密钥** `knot-common/.../auth/JwtKit.java:26-46`
  - `DEV_DEFAULT_SECRET = "knot-ai-gateway-jwt-secret-key-must-be-at-least-256-bits-long!"`
  - `buildKey()`：`secret == null` 时用默认值，仅 `log.warn(...)`。
  - 后果：若生产未注入 `KNOT_JWT_SECRET`，任何人可用源码里的公开密钥**伪造管理员 JWT**（登录态、权限全绕过）。
- **凭证加密密钥** `knot-service/.../config/CredentialProperties.java:13-19` + `crypto/CredentialEncryption.java:17-21`
  - `encryptionKey` 默认 `DEV_DEFAULT_KEY = "knot-dev-credential-encryption-key"`。
  - `isDevDefaultKey()` 只用于 `log.warn(...)`，无 fail-fast。
  - 后果：若生产未注入 `KNOT_CREDENTIAL_ENCRYPTION_KEY`，所有落库的供应商凭据（API Key）可用源码里的公开口令**批量解密**——任何拿到数据库只读权限的人都能还原明文凭据。

**修复建议（强烈）**：在 `JwtKit.buildKey()` 与 `CredentialEncryption` 构造器中，当 `active profile ∈ {prod, default}` 且命中开发默认值时**直接抛异常中断启动**（参考 `isDevDefaultKey()` 已有判定）。本地 dev 才允许放行。这是全仓唯一可让「部署疏漏」直接变成「全线失守」的单点。

### 🟠 P1 — 数值字段无范围校验（`@Min/@Max/@Range` 全局为 0）

- grep 全仓 `@Min|@Max|@Range|@DecimalMin|@DecimalMax`：**0 命中**。
- 字符串字段已有 `@NotBlank/@Size`（如 `RoutingRule.java:16-40`、`ModelPool.java:12-22`、`ProviderProfileItem.java:10-13`），覆盖较好。
- 但**数值字段无约束**：重试 `maxAttempts`/`multiplier`、配额 `limit`、超时秒数、计费 `cost`/`price`、在途阈值等。

**风险**：
- 例如把路由重试 `maxAttempts` 设成极大值 → 上游抖动时网关对单请求重试成百上千次，演变为**自我 DoS / 上游轰炸**。
- 配额 `limit` 设负数或 0 → 绕过限流/限额逻辑。
- 计费/超时字段越界 → 下游解析异常或静默错误记账。

**修复建议**：对所有入站 DTO 的数值字段补 `@Min`/`@Max`/`@Positive`/`@DecimalMin`，并确认每个 `@RequestBody` 都带 `@Valid`（`@Valid` 已普遍使用，但建议扫一遍确认无遗漏——重点看 `GatewayOutage`、各类 `updateStatus` 之外的自定义请求体）。`GlobalExceptionHandler` 已处理 `ConstraintViolationException`（`knot-admin/.../GlobalExceptionHandler.java:3`），400 返回链路现成。

### 🟠 P2 — AES 密钥由口令 SHA-256 直接派生，无盐、无 KDF 迭代

`AesGcmCipher.deriveKey`（`knot-common/.../crypto/AesGcmCipher.java:39-49`）：

```java
MessageDigest.getInstance("SHA-256").digest(passphrase.getBytes(UTF_8));
```

- 无 salt、无 PBKDF2/Argon2 迭代。单一全局密钥。
- 若 `KNOT_CREDENTIAL_ENCRYPTION_KEY` 口令强度弱，离线暴力（SHA-256 极快）可在极短时间内穷举出密钥，进而解密全部凭据。
- 与 P0 叠加：开发默认口令就在源码里。

**修复建议**：改用 `PBKDF2`/`Argon2` 带随机盐（盐随密文一起存储，当前 `ENC:` 格式已预留扩展位）；并通过部署规范强制口令长度/熵。最低限度：P0 的 fail-fast 必须落地，杜绝开发默认口令进入生产。

### 🟡 P3 — `SecureRandom.getInstanceStrong()` 在加密热路径阻塞

`AesGcmCipher.encrypt`（`AesGcmCipher.java:69-70`）每次加密取 12 字节 IV 用 `getInstanceStrong()`。
- 在部分 Linux 内核上 `/dev/random` 会**阻塞**直至熵池充足，导致管理端保存凭据的请求线程卡顿/毛刺。
- GCM 的 12 字节 IV 不需要「强」随机，`new SecureRandom()`（非阻塞）即可。

**修复建议**：改为 `new SecureRandom()`；`getInstanceStrong()` 留作可选。

### 🟡 P4 — 网关鉴权失败无防爆破 / 限流

`AbstractGatewayRequestTemplate.extractApiKey` + `RoutingResolver`（`runtime/AbstractGatewayRequestTemplate.java:205-210`、`routing/RoutingResolver.java:80-101`）对无效 Key 返回 401，但**无针对鉴权失败的限流/锁策略**。攻击者可持续枚举消费者 Key。

**修复建议**：在网关入口对「按 IP / 按 Key 前缀」的鉴权失败做滑动窗口限流（复用已有的 traffic 限流骨架）；或统一返回 401 且不区分「Key 不存在 / 禁用 / 规则未绑定」以避免信息泄露（当前错误信息已较细，见下）。

> 附带：错误信息泄露面。`RoutingResolver` 对各类失败返回不同文案（"Consumer API key not found" / "is disabled" / "Routing rule is not available"）。虽非严重，但可统一为泛型 401 文案减少枚举辅助。

### 🟡 P5 — CORS 默认源含 localhost:5173（生产需显式覆盖）

`GatewayCorsConfiguration.java:23` 默认 `allowedOrigins = http://localhost:5173,http://127.0.0.1:5173`。
- 设计本身正确：显式源列表、`allowCredentials(false)`、未启用通配（注释已说明因网关接收 API Key）。
- 但若生产未设置 `knot.gateway.cors.allowed-origins`，开发源被放行。凭据非 Cookie，浏览器无法自动附加，实际影响有限，属**配置卫生**项。

**修复建议**：生产 profile 下将默认源置空或显式列出前端域名；CI 校验该配置非空。

## 2. 性能发现

### 🟢 已具备的良好设计（基线，不应破坏）

- **上游 HTTP 层**：Apache HC5 池化（`UpstreamRestClientConfiguration.java:37-68`），`maxTotal=200`/`maxPerRoute=50`（默认），连接/读/取连接三类超时齐全（`GatewayUpstreamClientProperties.java:23-54`，`connectionRequestTimeout=5s` 杜绝池耗尽时无限排队）。
- **流式转发**：网关响应走 `StreamingResponseBody`（`ProxyStreamingBody`，8KB 分块，`upstream/stream/ProxyStreamingBody.java`），大体积 LLM 输出**不整块进内存**。
- **Redis 故障口径 fail-hard**：`RedisModelLoadStore` 不可用时抛 `RedisUnavailableException` → 503，而非静默按 0（避免负载均衡退化为「全不拥塞」），符合既定红线。
- **超时齐全**：`RestClientDecisionsTransport`（5s/30s）、`RoutingRuleService`（5s/120s）、`GatewayOutageService`（5s）、`OpenRouterModelSyncProvider`（connect 15s）。

### 🟠 P6 — 网关请求线程 `Thread.sleep` 同步退避（热路径阻塞）

`GatewayRequestHandler.sleepQuietly`（`runtime/GatewayRequestHandler.java:353-363`）：
- 上游可重试失败时，在 **servlet（Tomcat） worker 线程**上 `Thread.sleep(delayMs)` 做退避，再重试。
- 高并发 + 多次重试 + 非可忽略延迟时，会**占满 worker 线程池**，拖累无关请求。
- 这是网关主链路，风险高于同类（见 P7）。

**修复建议**：退避改为非阻塞——用 `WebClient` + `Mono.delay` / `Schedulers` 调度重试，或把重试交给独立调度器，让请求线程立即释放。至少确认 `BackoffCalculator` 的最大延迟与 `maxAttempts` 上限被收敛到较小值。

### 🟡 P7 — `JevBillingJudge` 429 退避 `Thread.sleep`

`knot-service/.../support/JevBillingJudge.java:122-128`：裁判限流 429 时在当前线程 `Thread.sleep(RETRY_BACKOFF_MS)` 后退避重试一次。
- 该路径是管理端**离线计费裁判**（非网关热路径），影响小，但属同一反模式。

**修复建议**：同 P6，非阻塞延迟；或至少确认 `RETRY_BACKOFF_MS` 为小值。

### 🟠 P8 — Redis 档「在途」读为同步 GET，且按池 N 次串行（仅 `redis` 档）

- `RedisModelLoadStore.inflight`（`load/RedisModelLoadStore.java:84-97`）每次是**同步** `cache.value(...)` GET。
- 调用点有两处：
  1. `RoutingResolver.targetLoad`（`routing/RoutingResolver.java:215-229`）——`LEAST_LOAD` 排序下，由 `Comparator.comparingLong(this::targetLoad)`（同文件 :204）在排序过程中**反复调用**（O(n log n) 次），每次对池内每个启用条目各做一次 `inflight` GET。
  2. `RoutingResolver.resolvePoolCandidates`（:295-309）——`modelPoolSelection.order` 的 lambda 对**每个候选**各做一次 `inflight` GET，单池 N 次串行。
- 仅当 `knot.load.store=redis`（多节点全局口径）时成立；默认 `caffeine` 档为内存 Map 读，可忽略。

**修复建议**：
- 在 `targetLoad`/`resolvePoolCandidates` 中**预取**一次池内所有模型的在途值到 `Map`，排序/选路只读 Map（消除 Comparator 副作用 + 重复读，见 P9）。
- 用 `MGET`/pipeline 批量取池内 N 个在途值，替代 N 次串行 GET。
- 该优化只在 redis 档有意义；caffeine 档无需动。

### 🟡 P9 — `RoutingResolver.orderTargets` 的 Comparator 副作用（低危，已核实）

`routing/RoutingResolver.java:204`：`Comparator.comparingLong(this::targetLoad)` 在排序中调用带副作用的方法。
- 早期怀疑是 N+1；**核实后降级**：`targetLoad` 依赖 `listModelPoolItemsByPoolCode`（Caffeine `LoadingCache`，10min 写过期，`GatewayDataService.java:192-194`）与 `inflight`。默认 caffeine 档开销可忽略；redis 档代价见 P8。
- 真正问题是**代码异味**：Comparator 应无副作用；且按 P8 预取后顺带消除。

**修复建议**：排序前先 `Map<String,Long> loadByTarget = ...` 预计算，再 `comparingLong(loadByTarget::get)`。纯健壮性/可读性改进，非性能瓶颈（单规则目标数 n 极小）。

### 🟡 P10 — 网关入站请求体无显式大小上限

消费者 `/v1/**` 代理端点直接转发请求体到上游，未设显式 max body size（Spring Boot 对非 multipart 无默认硬限；Tomcat 默认 `max-swallow-size` 仅控制「读弃」量）。
- 风险：客户端可发超大 prompt / 大图，占用内存与上游带宽（流式读取可缓解内存，但不限制上游被打）。

**修复建议**：在网关入口 Filter 设请求体大小上限（如 10–50MB，按业务定），超限直接 413。

## 3. 优先级行动表

| 优先级 | 项 | 工作量 | 影响 |
|--------|----|--------|------|
| **P0** | 生产 fail-fast 拦截开发默认密钥（JWT + 凭证） | 小 | 杜绝部署疏漏导致全线失守 |
| P1 | 数值字段补 `@Min/@Max/@Range` + 确认全量 `@Valid` | 中 | 防自我 DoS / 配额绕过 / 计费异常 |
| P2 | 凭证密钥改 PBKDF2/Argon2 + 随机盐 | 中 | 弱口令下防离线穷举 |
| P6 | 网关退避改非阻塞（释放 worker 线程） | 中 | 高并发下避免线程池耗尽 |
| P8 | Redis 档在途读预取 + MGET 批量 | 中 | 多节点部署下降低热路径延迟 |
| P3/P7 | 随机数与退避改非阻塞 | 小 | 去除请求线程毛刺 |
| P4/P5/P9/P10 | 防爆破限流 / CORS 生产置空 / Comparator 预取 / 请求体上限 | 小–中 | 加固与卫生 |

## 4. 评审边界（声明未覆盖项）

本评审聚焦**性能**与**安全**两个维度，且为只读源码级，未做动态渗透/压测。以下未深入，供后续专项：
- 并发竞态：Kafka 发布（`WarehousePublisher`/`KafkaPublisher`）、流量记账与在途计数在并发下的精确性。
- 资源泄漏：连接/流关闭路径（已见 try-with-resources，未逐路径验证）。
- 前端安全：`knot-front` 的输入转义、XSS、token 存储（`localStorage` vs 内存）、路由守卫完备性。
- 依赖供应链：`mvn` 第三方库 CVE（建议接 `dependency-check`）。
- 数据库层：已在 2026-10-18 巡检确认 MyBatis `${}` 注入 0 命中、逻辑删除覆盖健康，本次未重复。
