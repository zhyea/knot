## 三、数据契约（对齐方案 §4.3，按 2026-09-30 评审结论修订）

方案类型**不**写进 configJson（由版本列 `pricing_plan` 表达）—— 因此 `pricing.type` **不设**，避免与 `pricing_plan` 双写产生不一致。

> ⚠️ **`pricing` 只描述「价」怎么变，不含任何模式专属字段**。下面示例里的 `basePrices` 属于 **TOKEN 模式**的基础价格（由模式层产出），不是高低峰方案的一部分；换成 REQUEST 就是 `defaultUnitPrice`、换成 VIDEO 就是 `defaultUnitPrice` + `resolutionPrices`，而 `pricing` 这段**一字不改**。

```json
// 示例：billingMode=TOKEN + pricingPlan=PEAK_OFF_PEAK（首期唯一开放的组合）
{
  "defaultUnitPrice": 0.002,
  "basePrices": {
    "input": 0.28, "output": 0.42, "cacheRead": 0.07,
    "cacheWrite": 0.28, "cacheWrite5m": 0.28, "cacheWrite1h": 0.28
  },
  "pricing": {
    "rateMode": "MULTIPLIER",
    "timezone": "UTC",
    "phases": [
      {
        "condition": {
          "weekdays": ["MONDAY","TUESDAY","WEDNESDAY","THURSDAY","FRIDAY"],
          "windows": [ { "start": "01:00", "end": "04:00" }, { "start": "06:00", "end": "10:00" } ],
          "holidayPolicy": "OFF_PEAK",
          "makeUpWorkdayPolicy": "OFF_PEAK"
        },
        "phase": "PEAK",
        "multiplier": 1
      },
      { "condition": { "type": "DEFAULT" }, "phase": "OFF_PEAK", "multiplier": 0.8 }
    ]
  }
}
```

| 字段 | 约束 |
|---|---|
| ~~`pricing.type`~~ | **已删除**：方案类型由版本列 `pricing_plan` 表达，JSON 内不重复 |
| `rateMode` | 首期固定 `MULTIPLIER`（不做「分别维护低峰单价」） |
| `timezone` | **保留字段，当前白名单仅 `UTC`**（预留后续放开 IANA 时区）。保存时越界即拒绝；**禁止 `+08:00` 这类固定偏移** |
| `phases` | 至少 1 项；**首项为高峰，末项必须是 `condition.type=DEFAULT` 的兜底低峰** |
| `condition.weekdays` | ISO `DayOfWeek` 名（Java 枚举），拒绝未知值 |
| `condition.windows[].start/end` | 统一换算到「当天 0 点起算分钟数轴」比较：`start` 为 `HH:mm`（**不接受 `24:00`**），`end` 为 `HH:mm` **或特例 `24:00`**（= 次日 0 点，数轴 1440）；`start < end`；**禁止跨午夜**（`22:00–02:00` 拆两行）；`00:00–00:00` 不代表全天。换算唯一出口 `BillingConfig.windowRangeOf`，校验与判定共用 |
| 同一 condition 内时段 | 不得重叠；相邻首尾相接（`01:00–04:00` + `04:00–06:00`）允许 |
| `phase` / `multiplier` | `phase` ∈ PEAK / OFF_PEAK；`multiplier` 满足 `0 < v <= 1` |
| `holidayPolicy` | 首期固定 `OFF_PEAK`（节假日整日低峰，覆盖星期/时段） |
| `makeUpWorkdayPolicy` | `OFF_PEAK` / `FOLLOW_WEEKDAY_WINDOWS`；**多条高峰规则必须完全一致**（判定器只读第一条，不一致即拒绝保存，不做静默忽略） |

版本号行为不需要额外代码：`buildUniqHash()` 已把 `pricingPlan` 与 `configJson` 计入（`BillingService.java:415-427`），改 pricing → 新 hash → 新版本；改回旧配置 → 命中历史 hash → `activateVersion` 回退（`:382-391`）。

### 3.1 模式与方案是正交的两层（先讲清楚边界）

| 层 | 回答什么 | 谁负责 | 本方案是否改动 |
|---|---|---|---|
| 计费模式 `billingMode` | 用量怎么提、明细有哪些、基础价长什么样 | `BillingModeEnum` + `BillingMode*Calculator` | **不动** |
| 进阶方案 `pricingPlan` | 命中什么条件、单价怎么调 | `PricingPlanEnum` + 方案对象 | 本方案只加 `PEAK_OFF_PEAK` 一个 |

由此推出三条约束，实现时必须守住：

1. **`pricing` 里不出现任何模式专属内容**（没有 `input/output/cache*`、没有 `resolution`、没有 `perRequest`）。模式层怎么涨价跌价由它自己定，方案层只输出 `phase` + `multiplier`。
2. **「首期只支持 TOKEN」是能力矩阵的声明，不是数据结构的限制**。它落在 `PricingPlanEnum.java:19,25` 的 `supportedBillingModes(BillingModeEnum.TOKEN)`，由 `BillingService.validateRule()` 的 `plan.supports(mode)` 校验（`:443-446`），并由 `BillingService.listModeCapabilities()` 过滤后下发给前端（`:103-107`）。**放开到新模式的动作只有一步**：在枚举的 `supportedBillingModes` 里加一项 —— 不动 `BillingModeEnum`、不动 `pricing` 结构、不动版本表。
3. **价格解析有两条路径，高低峰将来要能同时覆盖**（当前领域接口 `BillingConfig.PricingPlan` 就是这么分的）：

   | 路径 | 谁在用 | 方法 |
   |---|---|---|
   | 分项价 | TOKEN | `resolvePrice(PriceKind, usageAmount, fallback)`（`BillingConfig.java:145`） |
   | 单一价 | REQUEST/IMAGE/AUDIO/VIDEO/EMBEDDING | `resolveDefaultPrice(fallback)`（`:148`） |

   ⚠️ 第三条有个**当前实现的坑**：`VideoBillingModeCalculator.java:54` 对「命中分辨率价」的分支**绕过了 PricingPlan**（直接取 `config.resolutionPrice`），只有兜底才走 `resolveDefaultPrice`。所以未来 PEAK_OFF_PEAK 若放开到 VIDEO，必须先把分辨率价这条支路也纳入倍率，否则会静默漏乘。

## 四、判定与价格逻辑

```text
local = occurredAt(ZoneId(pricing.timezone))        // 当前 timezone 恒为 UTC，即 local = occurredAt(UTC)
if  holiday(local.date)                                        -> OFF_PEAK  reason=HOLIDAY
elif makeUpWorkday(local.date) && makeUpWorkdayPolicy==OFF_PEAK -> OFF_PEAK reason=MAKE_UP_WORKDAY
elif ∃ rule ∈ phases(first, PEAK):
        local.dow ∈ rule.weekdays ∧ local.time ∈ [w.start, w.end) -> PEAK   reason=PEAK_WINDOW
else                                                            -> OFF_PEAK  reason=DEFAULT

// 基础价由「模式层」决定，方案层只在其上乘倍率：
//   TOKEN    -> resolvePrice(kind, usageAmount, fallback)      // basePrices / tier / defaultUnitPrice
//   其它模式 -> resolveDefaultPrice(fallback)                  // defaultUnitPrice
basePrice(mode) = 模式层解析出的基础单价
final           = basePrice(mode) × phase.multiplier           // BigDecimal
cost            = usage / unitSize × final
```

**关键取舍**：

1. 高低峰不持有价格，只对**模式层产出的基础单价**乘系数 —— 与上层「低峰＝基础价×倍数」语义一致，也让阶段四的「阶梯 × 高低峰」串联变成自然扩展。因为不碰模式层，它对 REQUEST/IMAGE/AUDIO/VIDEO/EMBEDDING 是**同一套代码**，首期只是不开放这些组合。
2. **时段按 UTC 解释**（`timezone` 字段保留、当前只允许 `UTC`，为后续放开 IANA 时区留口子）。管理员需自行把业务本地时段换算成 UTC 填写 —— DeepSeek 这类供应商公布的就是 UTC 时段，首期直接照抄即可。
3. **节假日日期按日历自身口径判定，不随 `timezone` 漂移**：中国法定节假日按 `Asia/Shanghai` 日期判定（`kb_holiday_calendar.holiday_date` 存的就是日历日期）。
   ⚠️ 由此产生一条已知边界：UTC 时段与北京日期在 `16:00–24:00 UTC`（次日 `00:00–08:00` 北京时间）会落在不同自然日，例如 `2026-09-30T17:00Z` 在北京已是 10-01 国庆 → 判定为节假日低峰，即使它落在工作日时段内。**首期接受该语义并在页面摘要里明示**；若日后要求"节假日也按 UTC 日期"再改。

## 七、验收清单（对应方案 §11）

- 能创建/编辑 PEAK_OFF_PEAK 规则，刷新后 `pricingPlan` 与 `configJson.pricing` 完整回显。
- 重叠时段、跨午夜、空星期、`timezone` 非 `UTC`、倍率 >1 或 ≤0、`start=24:00`、多条高峰规则调休策略不一致、缺失日历版本 → 拒绝保存。
- 时段一律按 UTC 解释；页面摘要明示「时段按 UTC，节假日按中国日历日期」。
- 判定：工作日窗口内 PEAK；工作日窗口外 OFF_PEAK；周末 OFF_PEAK；节假日全天 OFF_PEAK 且**覆盖**工作日窗口；调休按 `makeUpWorkdayPolicy`。
- 跨自然日边界：`2026-09-30T17:00Z`（北京 10-01 国庆）判定为节假日低峰，符合 §四 取舍 3 的既定语义。
- 边界：`01:00` 命中 `01:00–04:00`；`04:00` 不命中。**`end=24:00` 覆盖到当日最后一刻**（`23:59` 仍命中 `01:00–24:00`），修正原先 `23:59` 封顶导致每天最后一分钟错价低峰的问题。
- 配置页「至午夜」开关即写 `24:00`；列表高低峰列与明细抽屉对**全部**高峰规则取并集展示（不再只取第一条）。
- 价格：低峰单价 = 基础单价 × multiplier，BigDecimal、6 位小数无 double 误差。
- 版本：改 `pricing` 出新版本；改回旧配置命中历史 hash 回退。
- **正交性**：能力矩阵对 TOKEN 下发 `PEAK_OFF_PEAK`、对其余模式不下发；前端切换模式到 REQUEST/IMAGE/… 时，当前方案自动回退 FIXED；后端直接提交 `REQUEST + PEAK_OFF_PEAK` 应被 `plan.supports(mode)` 拒绝。
- 既有 TOKEN/REQUEST/…/CUSTOM 与 TIERED 方案金额与改动前完全一致。
