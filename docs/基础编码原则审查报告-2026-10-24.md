## 2. 🔴 Blocker 明细

### O 开闭 —— 新增一类东西要改一片

| 扩展点 | 需同步修改的位置 |
|---|---|
| 新增协议 | `RoutingRuleService.java:90` `DEBUGGABLE_PROTOCOLS`、`MediaProtocolExecutor.java:19`、`TextGenerationProtocolExecutor.java:19`、`UsageExtractorRegistry` 的 protocol if 链、`RoutingTestBillingVerdictService.java:144` 镜像 switch、前端 `ModelFormDrawer.vue:842` + `RoutingRuleTestDrawer.vue:972` 两份归一函数 —— **共 6+ 处** |
| 新增异常族 | `GatewayExceptionHandler`（9 个 `@ExceptionHandler`）、`ErrorMsgDto.of()`（8 分支）、`GatewayTrafficMsgDto.statusOf()`（4 分支）—— **三棵树** |

### D 依赖倒置 —— 两处，性质不同

**(a) `adapter` 反向依赖 `dal`（编译期）**
`knot-adapter/pom.xml` compile 依赖 `knot-dal`；7 个主类 import `org.chobit.knot.gateway.entity.*`：
`UpstreamRequestContext`、`NormalizedUsageContext`、`UsageNormalizationSupport`、`AbstractBillingModeCalculator`、`SimpleBillingModeCalculator`、`TokenBillingModeCalculator`、`VideoBillingModeCalculator`（另 5 个测试类）。
适配层是协议/计费语义层，不应知道表映射实体。

**(b) 业务类自建外部客户端**

| 位置 | 判定 |
|---|---|
| `RoutingRuleService.java:175` `RestClient.builder()` | 🔴 管理面 CRUD 服务持有 HTTP 客户端，与 S 违反叠加 |
| `GatewayOutageService.java:54` `RestClient.builder()` | 🔴 故障探测应归专门 Runner，不该由 Service 自建 |
| `OpenRouterModelSyncProvider.java:38` `HttpClient.newBuilder()` | 🟡 专职外部同步 Provider，可接受但应抽公共 Support |
| `RestClientDecisionsTransport.java:34` | ✅ 已在 `service.support`，是合理的 transport 封装 |

### DRY —— 四组重复

| 组 | 实证 |
|---|---|
| 错误码字面量 | `ErrorMsgDto` 8 处 + `GatewayTrafficMsgDto` 3 处，共 **11 处手写字符串**，而 `GatewayErrorTypeEnum`（含 `TIMEOUT_ERROR`）从未被引用 |
| 协议集合 | 见 O |
| `snapshot()` 兜底模式 | 8 个 Service 全是 `try { dto=getById(id); return JsonKit.toMap(dto); } catch (BusinessException e) { return null; }` |
| 前端协议归一 | `normalizeProtocolCode` 在两个组件各写一份 |

### E1 无假成功 —— 两处，第二处是原方案漏的

| 位置 | 问题 |
|---|---|
| `BillingService.java:398` | `reconcile()` 返回 `0,0,"DONE"`，前端显示"对账完成" |
| `ModerationGuard.java:111` | `log.warn("MASK action is not implemented yet, falling back to FLAG")` —— **用户在管理台配了 MASK，实际从未生效**，且只有日志知道，调用方看到的响应与 FLAG 无异 |

### E5 测试真的在跑

|---|---|

## 6. 与原治理方案的差异

### 原方案有误或需修订（6 项）

| 原方案 | 修订 |
|---|---|
| P0-2 插件超时定为 P0，且用 `Future.get` + virtual thread + 信号量 | **降级 P1**（8 个插件全为本地内存操作，无阻塞源、无故障证据）；**形态改为** `Mono<Void>` + 复用既有 `MdcContextSupport`，否则会在 Gateway 阶段阻塞 Netty event loop |
| P1-3 把 protocol→extractor 搬进 `ModelApiProtocolEnum` | 与 2026-10-23「计费去兜底」立规反向。拆两件事：**(a)** 抽 `UsageExtractorResolver` 消灭镜像（赞成）；**(b)** protocol 猜测的收敛目标是**移除**而非搬迁 |
| P1-3 同节要求删 `canonical()` | 与 (b) 内部矛盾——`canonical()` 恰是别名归一的正当位置，二者必须二选一 |
| P1-2 `BillingService` 拆分 | 降为**按需**；其中 `calculateUsageDetail` 删除已拍板可立即执行 |
| P0-1 删除面 3 处 | 实际 8 处 + `data.sql` 3 行种子 + `NumericStatusEnumContractTest` 引用 |
| I 接口隔离被列为疑似违反 | **改判合规**：`PluginDispatchContext` 只有 3 个成员，"上下文字段多"是误判 |

## 8. 建议处置顺序

**第一批（上线前，低成本 + 已拍板）**：对账下线（E1）、`calculateUsageDetail` 删除、`routingRuleConverter` 删除、`row.status ?? "ENABLED"`、CI 加 `npm test`（E5，全场性价比最高）、`ErrorMsgDto` 复用 `GatewayErrorTypeEnum` + timeout 分支（O/DRY，约 10 行）。

**第二批（上线前后均可，需先拍板取值）**：`RoutingResolver` / `PluginDispatcher` 补单测（E5）、`ModerationGuard` MASK 要么实现要么显式声明不支持（E1）、timeout 三出口取值（`type`/`httpStatus`/`stage`/`statusOf` 四个子项）。

**第三批（上线后，结构性）**：`adapter → dal` 依赖倒挂整改（D，12 文件，纯机械的字段下沉）、`RoutingRuleService` 拆分（S + D 叠加）、`UsageExtractorResolver` 去重（O/DRY）、8 处 `snapshot()` 抽公共 Support（DRY）、前端抽屉拆分（S）。

**第四批（按需）**：其余巨型文件、`canonical()`、缓存边界、`DefaultPluginDispatcher` 迁出。
