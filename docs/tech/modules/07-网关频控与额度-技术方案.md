# 网关频控与额度控制（技术方案）

> 落地日期：2026-10-04，字段简化 2026-10-05　范围：`knot-gateway.traffic`　状态：已实现（单节点）／多节点代码就绪，改配置即可切换
>
> **多窗口额度（B1 子表版，设计中）**：在基线单窗口额度之上，让每个 resource 挂多套「不同统计窗口」的额度配置。详见第 9 节——核心是**新增一张 resource↔额度策略关联子表**（`kb_resource_quota_bindings`），`kb_quota_policies` 保持单窗口不动。

## 1. 背景与现状

改造前 `GatewayTrafficGuard` 是一份「能跑但不完整」的实现：

| 问题 | 说明 |
|---|---|
| 计数容器无界 | `ConcurrentHashMap` 只增不删，冷资源的窗口计数永久驻留堆内 |
| 窗口靠除法定界 | `System.currentTimeMillis() / windowMillis`，条目不随窗口过期，靠覆盖写复用对象 |
| 额度是空壳 | `checkQuota` 直接 `return true`，`kb_quota_policies` 配了也不生效 |
| 无法多节点 | 计数只在进程内，多副本部署时每个节点各自统计，总配额被放大 N 倍 |
| 策略字段过载 | 一张限流表塞了秒 / 分钟 / 时段三种窗口，一张额度表塞了日 / 月请求数与累计 token，配置项多且互相重叠 |

策略数据本身是齐的：`kb_rate_limit_policies` / `kb_quota_policies` / `kb_resource_traffic_policies`
三表 + `ResourceTrafficPolicySupport` 读写 + `GatewayDataService` 的 Caffeine 缓存（10 分钟过期）。
缺的是**运行时的计数与判定**。

## 2. 分层

```
GatewayRequestHandler          调用方：拿判定结果抛异常，成功后上报用量
        │
GatewayTrafficGuard            业务判定：检查哪些资源、限额多少、超了算什么原因
        │
        ├── TrafficPolicySource         策略来源：GatewayDataService（库 + 10 分钟缓存）
        └── TrafficCounterStore         计数抽象：addAndGet(key, delta, expireAtMillis) / get(key)
                ├── CaffeineTrafficCounterStore   单节点（默认）
                └── RedisTrafficCounterStore      多节点（knot.traffic.store=redis）
```

Guard 有两个可替换依赖：**策略从哪来**（`TrafficPolicySource`）与**计数存哪去**（`TrafficCounterStore`）。
前者让 Guard 不再绑死 `GatewayDataService`，单测可直接喂固定策略；后者决定单节点还是多节点。

抽象的下限定在「**一次调用完成一次原子累加**」，而不是「读出来再加回去」：

- Caffeine 侧用 `cache.asMap().compute`，Caffeine 对同一 key 的计算是排他的，不会丢计数；
- Redis 侧用一段 Lua（`INCRBY` + `PEXPIREAT`），天然原子；
- 业务语义（限多少、算不算超）一律留在 Guard，存储层只认「键 + 增量 + 过期时刻」。

两种实现共用同一套键（由 `TrafficCounterKeys` 生成），切换只改 `knot.traffic.store`。

## 3. 口径定义（2026-10-05 简化）

### 3.1 分层：每层只配一类策略

`TrafficResourceTypeEnum` 是分层的单一来源，`supportsRateLimit()` / `supportsQuota()` 决定该层认哪类策略：

| 资源层 | 限流（RPM / TPM） | 限额（token / 成本） |
|---|---|---|
| `MODEL` 模型 | ✅ | — |
| `ROUTING_RULE` 路由规则 | ✅ | — |
| `APP` 应用 | — | ✅ |
| `PROVIDER` 供应商账户 | — | ✅ |
| `ROUTING_CONSUMER` 消费者 | — | ✅ |

Guard 的 `checkResources` 按上表决定走哪条判定链；`ResourceTrafficPolicySupport.save`
在写入侧同样按层过滤，防止给模型层挂上额度策略这类脏绑定。

> 语义：**限流是速率约束**（防瞬时打爆，关心每分钟多少），**限额是总量约束**（防预算超支，关心窗口内累计多少）。
> 两者维度不同、窗口不同，混在一层反而互相干扰。

### 3.2 限流（RateLimitPolicy）

`record RateLimitPolicy(int rpm, int tpm)`，两项都是「每分钟」口径，无窗口字段。

| 字段 | 窗口 | 计数时机 | 判定 |
|---|---|---|---|
| `rpm` 每分钟请求数 | 固定 1 分钟（epochMinute） | **请求进入即 +1**（不论上游成败） | `已用量 > 限额` 即拒 |
| `tpm` 每分钟 token | 固定 1 分钟 | 上游成功后 + 本次 token（**事后累加**） | `已用量 >= 限额` 即拒 |

TPM 只能事后累加——请求发出前拿不到 token 数，因此超限在**后续请求**上拦住。
与 RPM 的 `>` / `>=` 差异正是这个原因：RPM 事前 +1，第 N+1 次请求时 used=N+1 > N 即拒；
TPM 事后累到 N 时第 N 次请求已经发出去了，只能从下一次开始拒。

固定窗口而非滑动窗口：窗口序号由 `epochMillis / 60000` 得出，不依赖时区与本地时钟，
多节点天然一致，Redis 上单键即可表达。

### 3.3 限额（QuotaPolicy）

`record QuotaPolicy(long maxTokens, BigDecimal costLimit, String currency, String window)`

| 字段 | 含义 |
|---|---|
| `maxTokens` | 窗口内 token 上限；`0` = 不限 |
| `costLimit` | 窗口内成本上限；`NULL` 或 `0` = 不限。**配置 4 位小数**（DB `DECIMAL(18,4)`、前端 `precision=4`） |
| `currency` | 成本币种（`USD` / `CNY`），策略自带 |
| `window` | 统计窗口：`MINUTE` / `HOUR` / `DAY` / `WEEK` / `MONTH`，默认 `MONTH` |

判定：`已用量 >= 限额` 即拒。**事后累计**——请求前只判断，请求成功后才累加，
因此上游失败与 failover 重试不消耗额度（failover 走到下一个目标时，前一个失败目标不记账）。

token 来源：`UsageAccounting.totalTokens()`，优先取计费结果，无计费规则时退回上游用量输入。
成本来源：`NormalizedUsage.totalCost()`。

**币种不做汇率换算**：只有本次计费结果的币种与 `policy.currency()` 一致（`equalsIgnoreCase`）时才累加成本，
币种不符则跳过成本维度（token 维度照常累计）。理由是网关不持有汇率表，跨币种折算需要引入
汇率快照与生效时间，超出本次范围；要精确请配同币种规则。

**窗口标识与过期**（`QuotaWindowEnum`，按 `knot.traffic.zone` 时区换算）：

| 窗口 | `windowId` 形态 | 过期时刻 |
|---|---|---|
| `MINUTE` | `yyyyMMddHHmm` | 截断后 +1 分钟 |
| `HOUR` | `yyyyMMddHH` | 截断后 +1 小时 |
| `DAY` | `yyyyMMdd` | 次日零点 |
| `WEEK` | 本周周一的 `yyyyMMdd` | 下周一零点 |
| `MONTH` | `yyyyMM` | 次月一号零点 |

窗口结束即清零：换窗口就是换键（键里带 `windowId`），旧键随 TTL 自然消失，无清理任务。

## 4. 键设计

```
<prefix>:rl:<TYPE>:<id>:RPM:<epochMinute>
<prefix>:rl:<TYPE>:<id>:TPM:<epochMinute>
<prefix>:qt:<TYPE>:<id>:TOKENS:<windowId>
<prefix>:qt:<TYPE>:<id>:COST:<CURRENCY>:<windowId>
```

- 资源类型取 `TrafficResourceTypeEnum`：`APP` / `MODEL` / `PROVIDER` / `ROUTING_RULE` / `ROUTING_CONSUMER`；
- 限流键按分钟翻页，限额键按窗口翻页，**都不需要后台清理任务**；
- 成本键带币种：同一资源可以并存 USD 与 CNY 两套成本计数（策略换了币种不会串味）；
- 成本按**纳元（1e-8）整数**计数（`QuotaDimension.toScaledAmount`），避开浮点误差，
  同时契合 Redis `INCRBY` 的整数语义。**缩放因子必须与计费侧一致**：
  `AbstractBillingModeCalculator.cost` 产出的是 `setScale(8, HALF_UP)`，所以计数也取 1e-8；
  用 1e-6 会把第 7、8 位小数截断成 0，表现为「明明花超了却一直不超限」。
  换算写成 `movePointRight(8).setScale(0, HALF_UP)`，**不能用 `setScale(8, …)`**——
  后者只改小数位数，`new BigDecimal("10.00")` 结果仍是 10 而非 10^8。
  `long` 计数上界对应约 922 亿元，远超任何配额场景。

> **配置精度（4 位）与计数精度（1e-8）是两回事，别一起降。**
> 成本上限只要求配到 `0.0001` 粒度（预算口径够用），但内部计数必须保留 8 位：
> 若把 `COST_SCALE` 降到 4，单次成本 1e-8 会被截断成 0、永不累加，
> 就等于退回到两轮前修掉的「明明花超了却一直不超限」。
> 单测 `fourDecimalLimitKeepsEightDecimalCounting` 守住这条边界。

## 5. 实现要点

### 5.1 Caffeine（默认）

- **逐键过期**：限流键 1 分钟、限额键按窗口，用 `Expiry` 按条目自身携带的过期时刻算 TTL，
  而不是全局统一的 `expireAfterWrite`；
- **有界**：`maximumSize`（默认 20 万）兜底，冷资源不会撑爆堆；
- **同步维护**：`executor(Runnable::run)`，过期 / 淘汰时机确定，不往公共线程池排队；
- **扩展性**：`Clock` 与 `Ticker` 可从构造器注入，单测用固定时钟推进时间。

局限：计数只在进程内有效，多副本部署时各节点各自计数。

### 5.2 Redis（多节点）

`knot.traffic.store=redis` + `spring.data.redis.*` 即可启用，Lua 保证累加与过期设置的原子性
（拆成两条命令时，进程在中间崩掉会留下永不过期的键）。

Redis 故障时默认 **fail-open**（记 warn 日志后按「未产生用量」处理），避免缓存层故障打挂网关；
需要严格管控时设 `knot.traffic.fail-open=false`。

## 6. 调用链改动

`GatewayRequestHandler.proxyWithFailover`：

1. `checkRouting` → 应用 / 路由规则 / 消费者；被拒即抛异常；
2. 逐个候选目标 `checkTarget` → 目标模型 / 供应商账户；被拒则跳到下一个候选；
3. 上游成功 → `record(routing, target, usage, context)`：限流层累加 TPM，限额层累加 token 与成本；
4. 全部候选都被流量策略拒绝 → 抛第一个拒绝原因；没有候选目标 → 抛 `NO_ROUTING_TARGET`。

用量来源 `usageOf(ProxyResult)`：`UsageAccounting.totalTokens()` 取 token，
`normalized().totalCost()` / `normalized().currency()` 取成本与币种，缺计费结果时用 `TrafficUsage.EMPTY`。

新增错误码：`ProxyErrorCodeEnum.QUOTA_EXCEEDED` + `GatewayErrorTypeEnum.QUOTA_ERROR`
+ `GatewayQuotaException`，与频控的 `RATE_LIMIT_EXCEEDED` 区分开，调用方可分别处置。

拒绝原因细分（`TrafficRejectReason`）：`RATE_LIMIT_RPM` / `RATE_LIMIT_TPM` /
`QUOTA_TOKENS` / `QUOTA_COST`，便于管理端区分是哪个维度触顶。

## 8. 已知限制

| 限制 | 说明 |
|---|---|
| 单节点计数会放大额度 | N 副本各计各的，实际放行量是配额的 N 倍；要精确就切 `store=redis` |
| 进程重启清零 | Caffeine 是内存计数，重启后窗口内用量从 0 重新累计 |
| 固定窗口有边界突刺 | 相邻窗口交界处理论上可达 2 倍限额；需要更平滑再换滑动窗口 |
| TPM 有一次放行延迟 | 事后累加的代价：超限的那个请求已发出，下一个请求才被拦 |
| 跨币种不换算 | 币种不符时成本维度不累计；需要折算要引入汇率快照 |
| 额度未落库 | 用量不写库，管理端查不到历史用量；如需审计口径再接用量落库 |
| 管理端查不到当前用量 | 计数在 Redis / 内存里，管理端列表不展示已用量；要展示需提供查询接口 |

## 9. 多窗口额度重构（B1 子表版）：资源-额度策略关联子表

### 9.1 目标与取舍

基线的额度是「**一个 resource 绑定一个单窗口 QuotaPolicy**」（`quota_policy_code` 单列 1:1）。
需求是「每个 resource 支持一组不同统计窗口的限额配置」——即同一个 resource 可以同时有
「每分钟 1 万 token」和「每月 100 万 token」两套上限。

**B1 子表版的核心判断**：`kb_quota_policies` 本来就是一个窗口的额度包（token + 成本上限），模型不动；
要让 resource 挂多个这样的单窗口策略，用一个**关联子表**表达 resource → quota_policy 的 1:N，
比 JSON 数组更规范（可索引、可查询、无解析、可加外键约束）。这是上一版「绑定表 JSON 数组」
的等价实现——应用层契约（`List<QuotaPolicy>`）与判定逻辑完全不变，只是存储从 JSON 列换成子表。

> 之前否决 C 方案（新增 `kb_quota_policy_limits` 子表 + 把 QuotaPolicy 拆成扁平
> `(维度,窗口,上限)` 列表 + 引入 `QuotaLimit` 类）的理由不变：那是把「limit」单独成类、
> 改动 `kb_quota_policies` 形状，概念冲突。**B1 子表版不碰 `kb_quota_policies` 的形状**，
> 只新增一张「resource 与单窗口 quota policy 的关联表」，二者本质不同。

### 9.2 表结构 diff（对比基线）

| 对象 | 基线 | B1 子表版 | 说明 |
|---|---|---|---|
| `kb_quota_policies` | `max_tokens` / `cost_limit` / `currency` / `quota_window` 单窗口 | **不变** | 每行 = 一个窗口的额度策略（token + 成本上限） |
| `kb_resource_traffic_policies` | 含 `quota_policy_code VARCHAR(64)` 单列 | **删除 `quota_policy_code` 列 + `idx_resource_traffic_quota` 索引**（仅留 `rate_limit_policy_code`） | 额度改由子表承载，本表只锚定限流 |
| `kb_resource_quota_bindings`（**新增**） | — | `resource_type` / `resource_code` / `quota_policy_code` + 唯一键 `(resource_type, resource_code, quota_policy_code)` | resource 1:N 挂 quota 策略；每元素 = 一个统计窗口下的额度 |

**结构性改动**：删绑定表的 quota 列 + 新增一张关联子表。其余表、枚举、判定口径全部沿用基线。

### 9.3 表形态

```sql
-- 绑定表：删 quota_policy_code，仅锚定限流
CREATE TABLE IF NOT EXISTS kb_resource_traffic_policies (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  resource_type VARCHAR(32) NOT NULL COMMENT 'APP / MODEL / PROVIDER / ROUTING_RULE / ROUTING_CONSUMER',
  resource_code VARCHAR(128) NOT NULL COMMENT '资源业务码（按 resource_type 指向对应表的 code），非主键 id',
  rate_limit_policy_code VARCHAR(64) DEFAULT NULL COMMENT '频控策略业务码（kb_rate_limit_policies.policy_code），非主键 id',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_resource_traffic (resource_type, resource_code),
  KEY idx_resource_traffic_rate (rate_limit_policy_code)
);

-- 新增：resource 与额度策略的 1:N 关联子表
CREATE TABLE IF NOT EXISTS kb_resource_quota_bindings (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  resource_type VARCHAR(32) NOT NULL COMMENT 'APP / PROVIDER / ROUTING_CONSUMER（仅这些层配额）',
  resource_code VARCHAR(128) NOT NULL COMMENT '资源业务码（按 resource_type 指向对应表的 code），非主键 id',
  quota_policy_code VARCHAR(64) NOT NULL COMMENT '额度策略业务码（kb_quota_policies.policy_code），非主键 id',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_rqb_resource_policy (resource_type, resource_code, quota_policy_code),
  KEY idx_rqb_policy (quota_policy_code)
);
```

要点：

- 额度从「绑定表单列」迁到子表后，绑定表只负责限流（`rate_limit_policy_code`），两张表各管一类策略，职责清晰。
- 子表唯一键 `(resource_type, resource_code, quota_policy_code)` 在存储层杜绝「同一 resource 同一窗口配额重复绑定」；
  `idx_rqb_policy` 供按 policy 反查 / 回收孤儿。
- **`kb_quota_policies` 完全不动**：它本就是单窗口额度包，B1 子表版只是让 resource 能引用多个它的行。

### 9.4 policy code 生成与读写

- **写路径**（resource 保存额度，提交 `List<QuotaPolicy>`）：每个窗口生成**稳定 code** `<resourceType>-<resourceId>-QT-<window>`
  （如 `PROVIDER-1-QT-MONTH`），按 code **幂等 upsert** `kb_quota_policies`（存在则 update，否则 insert）；
  再按「本次窗口集合」整组替换该 resource 在 `kb_resource_quota_bindings` 的行
  （先删不在集合内的旧绑定，再批量插入新绑定）；被删绑定对应的 `<type>-<id>-QT-` 前缀 quota policy 行一并删除（无孤儿）。
- **读路径**：`ResourceTrafficPolicySupport.loadBatch` 按 `(resource_type, resource_codes)` 查子表 →
  收集 policy 码 → `QuotaPolicyMapper.listByCodes` → 按 resource 组 `List<QuotaPolicy>`。
- **种子数据**可直接引用既有 policy 码（如 `PROVIDER-1-QT`），不强制走自动生成规则。

校验：`QuotaWindowEnum.fromCode` 兜底非法窗口为 `MONTH`；同一 resource 同一窗口不允许重复
（子表唯一键天然杜绝）；非法维度/窗口在判定时跳过而非判死（沿用基线 `QuotaDimension` 口径）。

### 9.5 迁移脚本（幂等）

文件：`docs/database/migration/2026-10-12-quota-policy-multi-window.sql`（**重写为 B1 子表版**）。

1. **撤销 C 残留**（仅对「曾跑过 C 方案」的库生效，全部带 `IF EXISTS` 守卫）：
   - `DROP TABLE IF EXISTS kb_quota_policy_limits`；
   - `kb_quota_policies` 缺 `max_tokens` / `cost_limit` / `currency` / `quota_window` 则 `ADD COLUMN IF NOT EXISTS` 补回
     （基线本就有，C 才删；补齐保证列一致）。
2. **建子表**：`CREATE TABLE IF NOT EXISTS kb_resource_quota_bindings`（见 9.3）。
3. **绑定表迁 quota 到子表**：若 `kb_resource_traffic_policies` 仍有 `quota_policy_code` 列：
   - 把现有每行 `quota_policy_code` 非空值插入子表 `(resource_type, resource_code, quota_policy_code)`；
   - `ALTER TABLE ... DROP COLUMN quota_policy_code`；
   - `DROP INDEX idx_resource_traffic_quota`（MariaDB 不随列删索引）。
4. 对全新库：`schema.sql` 直接建出 B1 子表版形态，迁移里 1/3 的 `IF EXISTS` 分支全部空跑，幂等安全。

> 执行顺序不变：**先跑迁移，再启应用**。`schema.sql` 的 `CREATE TABLE IF NOT EXISTS` 不会改已有列，
> 不跑迁移会报 `Unknown column`。

### 9.8 判定口径（全部沿用基线，B1 不重写）

- 窗口标识 / 过期（`QuotaWindowEnum`，按 `knot.traffic.zone` 时区）→ 不变；
- 成本纳元（1e-8）整数计数、与计费侧 `setScale(8)` 对齐 → 不变；
- 币种不做汇率换算（不符则跳过成本维度）→ 不变；
- 下游失败 / failover 重试不记账（事后累加）→ 不变；
- 429 `error.detail` 保留 `window` 字段（每个 QuotaPolicy 自带 window，命中即带出）→ 不变。

B1 只解决一件事：**同一 resource 可配多套窗口额度**，其余机制零改动。
