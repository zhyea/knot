# knot 网关接入 AI 编程/办公客户端（Codex / WorkBuddy / Qoder / Cursor）技术方案

> 版本：2026-10-05 初版
> 范围：基于 `D:/MyDevelop/JDevelop/workspace/knot` 现有网关代码，设计让 Codex / Cursor / WorkBuddy / Qoder 等工具通过 knot 网关统一调用模型的分阶段方案。
> 目标：在**不破坏现有 `Rule` 头 + `Bearer` 鉴权模型**的前提下，让只能配置 `base_url` + `api_key` 的客户端无感接入，并具备模型发现、按模型选择、计费/用量/流式闭环能力。

---

## 1. 目标与范围

**核心目标**：把 knot 网关作为统一模型出口，供 AI 编程/办公客户端接入。客户端侧通常只能配置：

- `base_url`（指向网关）
- `api_key`（网关消费者的 secret_key）
- 部分客户端可配置 `model` 列表或自定义请求头

**关键约束（来自现有代码）**：

- 网关强制要求两个头：`Authorization: Bearer <secretKey>`（已支持）+ `Rule: <ruleCode>`（`AbstractGatewayRequestTemplate.validateRequestHeaders` L99-101，缺则抛 `GatewayInvalidRequestException("Rule header must not be blank")`）。
- 网关**忽略**客户端请求体里的 `model` 字段，恒用路由候选目标的上游模型覆盖（`GatewayRequestHandler.proxyWithFailover` L103-104：`requestBody.put(MODEL, candidate.upstreamModelCode())`）。
- 路由按 `consumerId + ruleCode` 解析（`RoutingResolver.resolveByRule` L41-81），一条 rule 绑定一个 app 与一组候选模型/模型池。

**本方案解决的问题**：客户端发不出 `Rule` 头 → 无法接入。解决办法是「消费者绑定默认路由规则，缺 `Rule` 头时回退」，并补齐模型发现与按模型选择能力。

**不在本方案范围**（明确划界）：

- Qoder 仅支持预设供应商 BYOK，**不支持任意 Base URL**，除非 Qoder 开放自定义 endpoint，否则无法直接接入（见 §6）。
- WorkBuddy 个人版仅支持内置国产模型自定义 Key，**仅企业版/私有化部署**支持自定义 Base URL，才适用本方案。

## 3. 客户端协议约束对比

| 客户端 | 可配置项 | 能否发自定义头 | 能否自定义 Base URL | 协议偏好 | 接入可行性 |
| --- | --- | --- | --- | --- | --- |
| **Codex CLI** | `openai_base_url` 或 `[model_providers.<id>]`（含 `base_url`/`env_key`/`wire_api`/`requires_openai_auth`） | 否（仅能经 `model_providers` 间接配） | 是（任意 URL） | `chat` 或 `responses`（可配 `wire_api`） | ✅ 高（配置 `wire_api=chat` 即通） |
| **Cursor** | Settings → Override OpenAI Base URL + OpenAI API Key | 否 | 是（全局覆盖） | OpenAI chat/completions | ✅ 高 |
| **WorkBuddy** | 内置国产模型自定义 Key；企业版支持私有化/SSO/审计 | 视部署形态 | 仅企业版/私有化 | OpenAI 兼容 | ⚠️ 受限（需企业版） |
| **Qoder** | 仅预设供应商（DeepSeek/智谱/Kimi/MiniMax 等）BYOK | 否 | **否**（不支持任意 Base URL） | 内置 | ❌ 暂不可（待产品开放） |

**核心障碍抽象**：Codex/Cursor/WorkBuddy(企业版) 都满足「能配 base_url + api_key」，唯一缺的是 `Rule` 头。Qoder 连 base_url 都不让配，属于产品能力边界。

## 4. 核心设计决策

### 决策 D1 — 消费者绑定默认路由规则（解决 G1）
- `kb_routing_consumers` 新增 `default_rule_code VARCHAR(32) DEFAULT NULL`。
- `Rule` 头改为**可选**（`required = false`）。缺省时由 `RoutingResolver` 回退到该 consumer 的 `default_rule_code`。
- 解析顺序：`resolveByRule(secretKey, ruleCode)` → 若 `ruleCode` 为空，取 `consumer.getDefaultRuleCode()`；两者皆空才抛 `GatewayInvalidRequestException`。
- **安全**：泄露的 key 仅能触达该 consumer 的默认规则（最小权限），与原 `Rule` 头显式指定等价收紧，不放松现有边界。

### 决策 D2 — 新增 `/v1/models` 列表端点（解决 G2/G5）
- 新增 `GatewayModelCatalogController`，`@RequestMapping("/openai/v1")`，`GET /models`。
- 按 `Authorization` 解析 consumer → 取默认规则（或 `Rule` 头指定）→ 列出该规则下候选模型的**暴露名**。
- 暴露名 = `kb_models.model_code`（或别名）。返回 OpenAI 兼容结构：`{ object:"list", data:[ { id, object:"model", owned_by } ] }`。
- 客户端（尤其 Codex）会拿 `model` 名与 `/v1/models` 比对，必须一致。

### 决策 D3 — 请求体 `model` 驱动候选选择（解决 G3/G5）
- 在 `proxyWithFailover` 中：先读取 `bodyModel = requestBody.get("model")`。
- 若 `bodyModel` 命中某候选的 `model_code` / `upstream_model` / 别名，则**优先该候选**并置于 failover 首位；否则维持原「首候选优先」行为（向后兼容内部客户端）。
- 选中候选后仍以 `candidate.upstreamModelCode()` 覆盖上游请求体 `model`（协议适配所需），但**客户端看到的模型名与网关内部 model_code 解耦**。

### 决策 D4 — RESPONSES 协议处理策略（缓解 G4）
- **v1（推荐落地）**：指导 Codex 配置 `wire_api = "chat"`，使其走 `/openai/v1/chat/completions`（CHAT_COMPLETIONS）。网关已有完整 chat/completions 链路，无需新增转码。
- **v2（Phase 4）**：实现 `ResponsesToChatCompletionsAdapter`（请求转码 + SSE 响应归一化），使 `wire_api=responses` 的客户端也能对接仅支持 chat/completions 的上游。当前 `OpenAiCompatibleRequestAdapter` 仅声明支持 RESPONSES，未做转码（仅 Anthropic/Zhipu 适配器内有 `responsesToMessages`），v2 需补齐。

### 决策 D5 — Qoder/WorkBuddy 受限客户端的处置
- WorkBuddy：企业版/私有化确认支持自定义 Base URL 后，套用 D1-D3，等同 Codex/Cursor。
- Qoder：当前产品不支持任意 Base URL，**本方案不强行接入**；建议两条路径：① 推动 Qoder 开放自定义 endpoint；② 若 Qoder 后续支持 OpenAI-compatible 自定义供应商，则复用 D1-D3。划为「观察项」，不占用实施排期。

## 5. 分阶段实施计划

> 门禁纪律（沿用项目约定）：改码 → 全量 grep 残留 → 三门禁（`mvn package` / `vue-tsc` / `vite build`）→ 真实 jar 冒烟 → 清理冒烟数据，零残留。

### Phase 0 — 数据模型与路由回退（解决 G1）
**改动**：
1. `knot-admin/src/main/resources/db/schema.sql`：`kb_routing_consumers` 增加 `default_rule_code VARCHAR(32) DEFAULT NULL COMMENT '缺 Rule 头时回退的默认路由规则 code'`，并加 `KEY idx_consumers_default_rule(default_rule_code)`。
2. 新增幂等迁移脚本 `docs/database/migration/2026-10-05-consumer-default-rule.sql`（先跑迁移再 package）。
3. `RoutingConsumerEntity` 增加 `defaultRuleCode` 字段；`GatewayDataService.getConsumerBySecretKey` 返回体携带该字段。
4. `AbstractGatewayRequestTemplate.validateRequestHeaders`（L94-103）：移除 `ruleCode` 必填校验（保留 apiKey 校验）。
5. `RoutingResolver.resolveByRule`（L41-81）：`ruleCode` 为空时回退 `consumer.getDefaultRuleCode()`；两者皆空才抛错。
6. Controller 的 `@RequestHeader(value = GatewayHeaders.RULE)` 改为 `required = false`（`GatewayTextController` 三处 + `GatewayAnthropicController`）。

**验证**：
- `mvn -f knot-server/pom.xml package`（含测试）BUILD SUCCESS。
- 冒烟：用现有 consumer 的 secret_key 但不带 `Rule` 头调用 `/openai/v1/chat/completions` → 命中默认规则返回 200；带 `Rule` 头仍按指定规则；两者皆无 → 400。

### Phase 1 — `/v1/models` 列表端点 + 模型别名（解决 G2/G5）
**改动**：
1. 新增 `GatewayModelCatalogController`（knot-gateway），`GET /openai/v1/models`。
2. `RoutingResolver` 新增 `listModelCatalog(secretKey, ruleCode)`：解析 consumer → 规则 → 候选模型，返回暴露名列表（含 `model_code` 与可选别名）。
3. `kb_models` 复用 `model_code` 作为暴露名；如需友好别名，新增可选 `alias` 列（迁移脚本独立）。
4. 返回 OpenAI 兼容 JSON。

**验证**：
- `mvn package` 通过。
- 冒烟：`curl -H "Authorization: Bearer <key>" <gateway>/openai/v1/models` 返回该 consumer 默认规则下的模型列表；`model` 字段名与客户端配置一致。

### Phase 2 — 请求体 `model` 驱动候选选择（解决 G3）
**改动**：
1. `GatewayRequestHandler.proxyWithFailover`（L92 循环前）：读取 `bodyModel`，在候选列表里定位匹配 `model_code`/`upstream_model`/别名的候选，置顶 failover 顺序；未命中则维持原序。
2. 保持「选中后以 `upstreamModelCode()` 覆盖上游 body.model`」不变。

**验证**：
- 单测：构造含多候选的规则，验证 `model` 命中第二候选时优先调用它；`model` 缺失/不匹配时维持首候选。
- 冒烟：同一 key 分别传 `model: "model-a"` / `"model-b"`，确认打到不同上游。

### Phase 3 — 客户端配置手册（解决 G6）
**产出**：本文 §6 的配置片段 + 单独 `docs/tech/客户端接入配置手册.md`，覆盖 Codex / Cursor / WorkBuddy(企业版) 的逐步操作、推荐 `wire_api`、模型名与 `/v1/models` 对齐说明、常见问题（401/400/模型不存在）。

### Phase 4 — RESPONSES 协议端到端闭环 + Qoder 评估（解决 G4）
**改动**：
1. 新增 `ResponsesToChatCompletionsAdapter`：输入 Responses API 请求体 → 输出 chat/completions 请求体；流式响应 SSE 归一化回 Responses 事件流。注册到 `UpstreamRequestAdapterRegistry`（ORDER 介于 Passthrough 与 OpenAiCompatible 之间）。
2. `UpstreamProxyClient.resolveBinding`（L166）对 RESPONSES 协议在无专属绑定时回退 chat/completions 绑定。
3. 评估 Qoder 是否开放自定义 endpoint，更新 §6 可行性结论。

**验证**：
- 单测：Responses 请求体转 chat/completions 结构正确；流式事件可还原。
- 冒烟：Codex 配置 `wire_api=responses` 经网关调通。

## 6. 各客户端配置示例

### Codex CLI（`~/.codex/config.toml` 或 `config.json`）
```toml
# 方式 A：直接覆盖 OpenAI base url（走 chat/completions）
[model_providers.knot]
base_url = "https://<gateway-host>/openai/v1"
api_key = "<consumer-secret-key>"
wire_api = "chat"            # v1 推荐，规避 Responses 转码
requires_openai_auth = true

# 方式 B（Phase 4 后）：原生 Responses
[model_providers.knot]
base_url = "https://<gateway-host>/openai/v1"
api_key = "<consumer-secret-key>"
wire_api = "responses"
requires_openai_auth = true
```
> 无需配置 `Rule` 头：网关按 consumer 的 `default_rule_code` 自动路由。模型名取自 `/v1/models`。

### Cursor（Settings → Models）
- 勾选 **Override OpenAI Base URL**，填入 `https://<gateway-host>/openai/v1`
- **OpenAI API Key** 填 `<consumer-secret-key>`
- 模型名填 `/v1/models` 返回的任一 `id`（如 `model-a`）
> Cursor 全局覆盖，发不出 Rule 头，依赖 D1 默认规则回退。

### WorkBuddy（企业版/私有化）
- 在模型设置中将供应商 Base URL 指向 `https://<gateway-host>/openai/v1`，API Key 填 `<consumer-secret-key>`。
- 个人版不支持自定义 Base URL，不适用本方案。

### Qoder
- 当前**不支持任意 Base URL**，仅预设供应商 BYOK。**暂不可接入**，列为观察项。

## 7. 风险与验收

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 默认规则误配 | `default_rule_code` 指向禁用/无候选的 rule | `resolveByRule` 沿用现有 NO_ROUTING_TARGET 校验；admin 界面创建 consumer 时强制关联默认规则 |
| 模型名不一致 | 客户端 `model` 与 `/v1/models` 暴露名不符 → Codex 拒绝启动 | Phase 1 暴露名与客户端配置严格对齐；文档明确 |
| RESPONSES 转码不全 | v1 若误用 `wire_api=responses` 到 chat-only 上游 | v1 强制 `wire_api=chat`；Phase 4 才放开 |
| 多会话并发改码 | 并行会话互相 commit/占 jar | 按约定单会话推进；冒烟前重跑 `-DskipTests` package |
| 缓存导致规则不生效 | `GatewayDataService` 缓存 10min | 改 `default_rule_code` 后等待缓存过期或重启网关再冒烟 |

**验收标准（Phase 0-3 完成即可宣告 Codex/Cursor 可用）**：
1. Codex（`wire_api=chat`）与 Cursor 配 base_url+key 后，能列出模型并正常对话/流式输出。
2. 网关侧按 consumer 记录用量、计费、频控/额度，与原生 `Rule` 头接入行为一致。
3. 三门禁全绿 + 真实 jar 冒烟通过 + 冒烟数据清理零残留。
