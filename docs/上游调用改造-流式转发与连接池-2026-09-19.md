# knot-gateway 上游调用改造：流式转发 + 连接池 + 超时

日期：2026-09-19
范围：`knot-server/knot-gateway`（含 `knot-common` / `knot-adapter` 的少量配套改动）

## 一、问题与根因

| # | 问题 | 位置（改造前） | 后果 |
|---|---|---|---|
| 1 | 流式 SSE 被强制缓冲 | `AbstractUpstreamProtocolExecutor.java:57-59` 用 `.retrieve().body(String.class)` 把整个上游响应读成 String | `stream:true` 变成"等上游全部生成完才返回"：首 token 延迟等于整包耗时、响应体整份驻留堆内存、worker 线程全程占用 |
| 2 | 无连接池 | `GatewayApplication.java:25-28` 仅 `builder.build()`，默认 `SimpleClientHttpRequestFactory`（JDK HttpURLConnection） | 每请求新建 TCP + TLS，握手开销全额付出，无连接复用 |
| 3 | 无超时 | 同上未设任何超时 | 上游挂起 → 永久占住线程 → 线程池耗尽雪崩 |

## 二、改造内容

### 2.1 HTTP 客户端：Apache HttpClient 5 池化 + 有界超时

- `knot-gateway/pom.xml`：新增 `org.apache.httpcomponents.client5:httpclient5`（版本由 Boot 3.3.4 管理为 5.3.1）。
- 新增 `config/GatewayUpstreamClientProperties.java`（前缀 `knot.gateway.upstream`）。
- 新增 `config/UpstreamRestClientConfiguration.java`，替换 `GatewayApplication` 里的裸 `restClient` bean：
  - `PoolingHttpClientConnectionManager`：`maxConnTotal=200`、`maxConnPerRoute=50`、连接 TTL 5 分钟、`validateAfterInactivity=10s`。
  - `ConnectionConfig`：建连超时 5s、**Socket 读超时 120s**（相邻两个数据包之间的最大静默时间，非整包总时长）。
  - `RequestConfig`：取连接超时 5s；`contentCompressionEnabled=false`（解压器会引入缓冲，且压缩过的 SSE 易被中间层攒包）。
  - 连接管理器声明为 shared，生命周期由 Spring bean 管理，避免重复关闭。

> 为什么不设 `RequestConfig.responseTimeout`：HC5 中该值语义与"整包响应超时"存在歧义，一旦理解错会把长流掐断。改为只依赖语义明确的 `ConnectionConfig.socketTimeout`。

### 2.2 流式转发

- 新增 `upstream/stream/UpstreamStreamResponse.java`：持有未读取的响应体流 + 原始 `ClientHttpResponse`，`close()` 后连接才归还连接池。
- 新增 `upstream/stream/ProxyStreamingBody.java`（实现 `StreamingResponseBody`）：读一行写一行并立即 flush；SSE 场景逐事件累计用量，在上游 `data: [DONE]` 之前插入 `data: {"knot_usage":...}`。
- `AbstractUpstreamProtocolExecutor`：`execute()` 按 `stream == true` 分流到 `executeStreaming()`，用 `exchange(fn, false)` 只消费响应头，响应体留作流式读取；非 2xx 仍读错误体并抛 `GatewayUpstreamException`，**首字节之前的失败依旧参与 failover**。
- `TextGenerationProtocolExecutor.supportsStreaming()` 返回 true（chat / responses / messages / completions），其余协议保持整包缓冲。
- `ProxyResult` 增加 `streamResponse` 组件（保留 4 参构造兼容）。
- `GatewayRequestHandler.applyUsageAccounting()`：流式结果直接返回 `ProxyStreamingBody`，并在返回前写响应头（`Content-Type` 取上游值、UTF-8、`Cache-Control: no-cache`、`X-Accel-Buffering: no`）。

**关键约束**：必须返回裸 `StreamingResponseBody`，不能包 `ResponseEntity`。控制器方法声明返回 `Object`，Spring 依据返回值的**运行时类型**挑选处理器；包成 `ResponseEntity` 后 `getGeneric(0)` 解析为 `Object`，`StreamingResponseBodyReturnValueHandler` 不会命中，会退化成消息转换器查找并报 500。已用反射实测确认（`getParameterType()` 返回运行时类）。

### 2.3 用量统计

- `UsageExtractorRegistry` 抽出 `extract(body, eventStream, context, adapter)`，新增 `extractEvent(eventData, context, adapter)`：按单个 SSE 事件提取，复用与整包完全相同的提取器与归一化链路（含 `streamUsageExtractor`）。
- 流式转发逐事件提取并取 token 数更大的一份，与整包 `mergeMax` 语义对齐。

### 2.4 配置

`knot-gateway/src/main/resources/application.yml`：

```yaml
spring:
  mvc:
    async:
      request-timeout: 600s   # 流式走 Servlet 异步写，容器默认仅 30s 会掐断长流

knot:
  gateway:
    upstream:
      connect-timeout: 5s
      connection-request-timeout: 5s
      read-timeout: 120s
      time-to-live: 5m
      validate-after-inactivity: 10s
      max-total-connections: 200
      max-connections-per-route: 50
      streaming-enabled: true        # 出问题可置 false 退回整包缓冲
      stream-buffer-size: 8192
      content-compression-enabled: false
```

## 三、验证

1. **全量编译**：`mvn -f knot-server/pom.xml clean compile` → `BUILD SUCCESS`（8 个模块，无告警新增）。
2. **流式转发实测**（对已编译产物跑真实用例，非 mock）：
   - SSE + 注入用量：`knot_usage` 事件正确插在 `data: [DONE]` 之前，其余内容逐行原样转发，上游响应已 `close()`（连接归还池）。
   - SSE 不注入用量：输出与输入**逐字节相等**。
   - 非 SSE（`application/json`）：走字节拷贝，输出与输入**逐字节相等**。
3. **Spring 返回类型分派**：反射实测 `ServletInvocableHandlerMethod.getReturnValueType()` 返回的 `MethodParameter.getParameterType()` 为运行时类，故 `Object` 声明的控制器返回 `StreamingResponseBody` 能被 `StreamingResponseBodyReturnValueHandler` 命中（该处理器内部走 `WebAsyncUtils.startCallableProcessing`，请求线程被释放）。

## 四、已知取舍与后续项

- **流式一旦开始转发即无法 failover**：响应头已发出，只能中断。首字节之前的错误仍会切换候选目标。
- **异步写线程无界**：`StreamingResponseBody` 走 MVC 的 `SimpleAsyncTaskExecutor`，每条流占一个线程（不再占 Tomcat worker）。若需限流，可注册独立的 `mvcTaskExecutor` bean 或开启虚拟线程（需升到 JDK 21 并把 `java.version` 提上去）。
- **异步线程丢失 MDC / `GatewayTraceContext`**：`GatewayTraceFilter` 在请求线程返回时即清理 ThreadLocal，流式写期间的日志无 traceId。
- **用量依赖上游上报**：与整包模式一致，上游未在 SSE 中下发 `usage`（多数需 `stream_options.include_usage=true`）时，`knot_usage` 不会出现。
- **插件可观测性**：`GATEWAY_RESPONSE` / `UPSTREAM_RESPONSE` 两个阶段在流式下拿到的是流对象而非响应文本。
