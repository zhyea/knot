# 视频（VIDEO）计费规则不足之处盘点

> 日期：2026-10-27　范围：`knot-server`（adapter 提取层 / calculator / common BillingConfig / gateway）+ `knot-front` 计费规则表单
> 方法：逐文件读源码实测，结论均附 `文件:行号`；**未经运行时验证的推断已显式标注「推断」**。
> 相关文档：`docs/视频计费规则类型化方案-2026-10-26.md`、`docs/VENDOR_KLING计费方案-2026-10-26.md`、
> `docs/维度分档价方案-2026-10-26.md`。

---

## 0. 结论先行

**当前的视频计费不是「支持的厂商少」，而是三层各有塌方：**

1. **提取层拿不到信号** —— 键表写死厂商字段名，主流厂商（尤其 Kling 与所有「提交任务 + 轮询」型厂商）
   的关键字段一个都命中不了，且**命中不了时没有报错、没有告警**。
2. **维度体系只有三根半轴** —— 分辨率 / 有声 / 有无输入视频有了，**宽高比、输出段数、时长套餐**没有；
   而 `FIXED` 方案下前端**连有声轴都配不出来**。
3. **错配一律静默** —— 维度键拼错、分辨率名不识别、用量异常，全部悄悄回落默认价或兜底值。
   这套系统缺的不是算法，是**「不知道就说不知道」的能力**。

优先级建议：**A1 / A2 / A5 / D1 / D2 属资损，先做；B 组是表达力，按厂商接入节奏补。**

## 2. 🔴 资损项（优先）

### A1 输入视频时长取不到 → 数量与分量双向失真

**证据**

```java
// knot-adapter/.../usage/extractor/MediaUsageReaders.java:47-51
static long inputDurationSeconds(Map<String, Object> requestBody) {
    return MapNumberUtils.firstLong(requestBody,
            "input_duration_seconds", "input_video_seconds", "input_duration", "input_video_duration",
            "source_duration", "source_video_seconds");
}
```

键表里没有一个字段是主流厂商实际用的：Kling 传 `video` / `video_url` / `task_id`，
可灵视频续写传 `video_id`，图生视频传 `image`。**实际值恒为 0。**

**两条后果（互相独立，别混为一谈）**

| 后果 | 代码位置 | 说明 |
| --- | --- | --- |
| **计费量只算输出** | `VideoBillingModeCalculator.java:435`（`quantity`）、`:270`（Kling 分支取值） | `OUTPUT_PLUS_MAX` 的判定是 `inputSeconds > 0`，输入秒为 0 → 恒走「无输入」分支。Kling 4.0「有输入 = 输出×2」**完全失效 → 少收一半** |
| **输入视频分量永不启用** | `VideoBillingModeCalculator.java:118-119` | 门控是 `video.inputDurationSeconds() > 0`，为 0 时整个分量跳过 |

> ⚠ 注意：2026-10-26 那轮加的 `hasInputVideo = inputDurationSeconds > 0 || reference`
> （`VideoBillingModeCalculator.java:386`）只修好了**「取哪一档价」**——
> 因为 `reference` 还能从请求体的 `reference_*` 键兜住部分厂商。
> **计费量那条轴没修好**，因为 `reference` 是布尔，拿不出秒数。这是本轮新发现，此前讨论没点到。

### A2 完全不支持「提交任务 + 轮询」的异步模式

**证据**：全仓 Java 搜索 `task_id` / `taskId` / `轮询` 在**上游调用与用量链路上零命中**
（命中项全在 `knot-admin` 的内部定时任务：`ScheduledTaskResult`、`ScheduledTaskSchedulerService`）。
`knot-gateway/.../upstream/protocol/AbstractUpstreamProtocolExecutor.java:151-163` 的整包路径：
一次请求 → 一个响应体 → 立刻提取用量 → 计费。**没有第二条采集时机。**

**后果链（这条最隐蔽）**

```
提交型厂商返回 HTTP 200 {"task_id": "..."}（不含 usage）
  → VideoUsageExtractor 提取出 durationSeconds=0，但 pixels>0（请求里声明了 resolution）
  → UsageExtractorRegistry.java:147 hasPositiveNumber(rawUsage) == false  → 不判 MISMATCH
  → UsageExtractorRegistry.java:123 item.billing().isEmpty() …
     VideoBillingUsage.isEmpty() = tokens.isEmpty() && durationSeconds<=0 && pixels<=0
     （VideoBillingUsage.java:44-46）→ pixels>0 ⇒ false ⇒ **连 warn 都不打**
  → VideoBillingModeCalculator.java:435 quantity(0,…) → output = 1L
  → 稳稳计 1 秒的钱
```

钉住这个行为的既有测试就是 `VideoBillingModeCalculatorTest.java:735-741`
（`shouldBillAtLeastOneSecondWhenDurationMissing`，断言 `0.5`）——
**「至少一秒」对「时长缺失」是合理的，但同一条路径把「整条视频还没生成」也一并兜成 1 秒。**

> 附：非 2xx 不会走到计费（`AbstractUpstreamProtocolExecutor` 先抛异常），这条没问题，别算进来。

> **处置状态（2026-10-27 修订）**：曾设计 `VideoUsageStage`（`UNKNOWN/SUBMITTED/COMPLETED`）
> 放进 `VideoBillingUsage` 做阶段闸门，**已撤销** —— robin 判定「和数据提取有关，但和计费无关」。
> 计费模型只回答「量是多少、按哪一档」，不回答「这份量该不该出账」。
> 因此 A2 **仍开放**，且解决位置从「计费闸门」改判为「提取层不出量」：
> 提交回执应当提取出 `VideoBillingUsage.empty()`（而不是「档位名非空 + 时长 0」），
> 让 `UsageExtractorRegistry` 现有的 MISMATCH 策略接手。这条与 A1（输入视频时长拿不到）
> 一起决策：两者都是「知道有事、不知道量」，需要同一套缺失语义。

### A5 秒数是 `long`，小数秒被截断

**证据**

```java
// knot-common/.../util/MapNumberUtils.java:46-62
public static Long longValue(Object value) {
    if (value instanceof Number number) { return number.longValue(); }        // 直接截断
    if (value instanceof String text)   { return new BigDecimal(normalized).longValue(); } // 直接截断
```
配合 `firstLong` 要求 `parsed > 0`（`:14-25`），以及 `quantity()` 的 `outputSeconds > 0 ? … : 1L`
（`VideoBillingModeCalculator.java:435`）：

| 上游真值 | 落到这边 | 结果 |
| --- | --- | --- |
| `5.9` 秒 | 5 | 少收 15% |
| `0.5` 秒 | 0 → 兜底 1 | **多收 100%** |

没有四舍五入、没有小数保留、也没有「你这真是秒吗」的单位判别
（若某厂商把 `duration` 报成毫秒，`firstLong` 会当成秒 → **1000 倍多收**，此项属推断，未实测到具体厂商）。

### D1 / D2 两类静默错价

| 项 | 证据 | 现象 |
| --- | --- | --- |
| D1 维度键拼错 | `BillingConfig.java`（`dimensionPrice` 逐级去尾查表） | `720P:SOUND`、`:AUDIO:REFERENCE`（顺序颠倒）、空档位名 —— 在 `FIXED` / `TIERED` / `PEAK_OFF_PEAK` 下一律**静默回落 `defaultUnitPrice`**。只有 `DIMENSION_TIERED` 拦（`validateDimensionTiered`） |
| D2 分辨率名不识别 | `VideoBillingModeCalculator.java:491` `normalizeResolution` 的 `default -> StringUtils.upperCase(text)` | 厂商自造档位名 / `auto` 之类非档位值会原样大写变成 `"AUTO"`，配不上价 → 回落默认价，**全程无日志** |

两者叠加的实际表现：「价配好了、看着也生效了、那档价从未命中过」。

## 3. 🟡 表达力缺失

### B4 `FIXED` 下前端配不出有声轴 ← robin 那句「支持得不够好」的具体所指

`modes/BillingModeVideoConfig.vue` 的通用档位表只有三列：**档位名 / 单价 / 含参考输入**。
要配「有声」必须切到 `VENDOR_KLING` 或 `DIMENSION_TIERED`（共用 `billing/ResolutionTierTable.vue`）。

于是形成一条**很不自然的产品路径**：配阿里云万相这种「分辨率 × 声音」二维价表，
必须选一个叫「厂商定制(Kling)」或「维度分档价」的方案，而 Kling 那个组件还会强制写
`quantityMode` 并吞掉输入侧分量。

> 建议方向：**把「按维度分档」从「一种方案」降级为「档位表的一种形态」**——
> 即 FIXED/TIERED/PEAK_OFF_PEAK 都能选用三维整表，`DIMENSION_TIERED` 只保留「拼键严格校验」这一增量。
> 这条是产品层面的判断，需 robin 拍板，不在本次盘点里实施。

### B5 `INPUT_IMAGE:` 键表单写不出

后端支持（`BillingConfig.java:211` `INPUT_IMAGE_PREFIX`、`VideoBillingModeCalculator.java:135`），
**前端只在 `VENDOR_MINIMAX` 分支写 `INPUT_VIDEO:`**（`BillingRuleFormDialog.vue:777-783`）。
「输入图片按分辨率分档」只能手写 `config_json`。

### B1 / B2 / B3 三个缺失维度

| 维度 | 现状 | 谁需要 |
| --- | --- | --- |
| 宽高比 | 全仓无 `aspect_ratio` 相关代码（grep 零命中） | 横屏 / 竖屏异价的厂商 |
| 输出段数 | 无任何产出数量读取；`imageCount` 只读**输入** | 一次请求出多段视频 |
| 时长套餐 | 无「5s / 10s 包」概念 | 按固定时长打包定价的厂商 |

### C1 无非 1 / 10ⁿ 单位 → 折算全靠人

`BillingUnitEnum` 只有 `PER_SECOND / PER_IMAGE / PER_REQUEST / PER_TOKEN / 1K / 1M`，
`unitSize()` 全是 1 / 1e3 / 1e6。Kling「对口型 0.5 元 / 5 秒」必须在配置期折成每秒 0.1。
前端只在 Kling 组件里写了一句提示文字，**没有任何校验拦得住把 0.5 直接填进每秒单价**——写错就是 5 倍。

### C2 无免费额度

`BillingConfig.VideoConfig` 只有 `freeInputImages`（`BillingConfig.java:200`、`:241-242`）。
阿里云万相「免费额度 50 秒」这类**输出侧免费额度**完全无法表达，
也没有任何「周期内额度」的数据载体（这是计费域的整体缺口，不只视频）。

### C3 一条规则只有一个单位基数

`AbstractBillingModeCalculator.java:43-45`：`unitSize` 对整条规则只有一个值。
token 量纲下输入侧分量直接被关掉（`VideoBillingModeCalculator.java:117-118` 的 `!tokenQuantity` 门控）。
「输出按秒 + 输入按 token」这类混合口径表达不了。

### D3 无用量合理性兜底 / 对账告警

grep `maxDuration / durationCap / 合理性 / 上限` 在 adapter 与 `common/model` 均零命中。
异常用量（例如某次 extract 到了 1000 秒）照单全额计费，没有熔断也没有告警。

## 5. 处置建议（按性价比排序，供 robin 拍板）

| 序 | 动作 | 覆盖 | 代价 |
| --- | --- | --- | --- |
| 1 | **给 `inputDurationSeconds` 补厂商键**：`video` / `video_url` / `video_duration` / `duration`（并做 ms ↔ s 判别） | A1 | 小；但要与「不猜协议语义」红线对齐，建议做成**按厂商 `apiProtocol` 声明式取键**而非加进通用键表 |
| 2 | **区分「无用量」与「有像素但无时长」**：后者必须打 error 级日志 + 明细打标（而非计 1 秒） | A2 / D2 | 小，纯止血；先让问题可见 |
| 3 | **小数秒**：`VideoBillingUsage` 的时长改 `BigDecimal`（或 `long` 毫秒）存真值，落到 SIDE 时再决定取整策略 | A5 | 中；改 record 会碰多处构造与测试 |
| 4 | **把 `validateDimensionTiered` 的键形状校验开放给所有方案**（至少 FIXED） | D1 | 小；但要评估存量配置的存量错键会一次性暴露成保存失败 |
| 5 | 异步任务采集：**双阶段计费**（提交记一次 BP/占位、结果出来后补差） | A2 | 大；牵动 gateway 请求模型与 Kafka 消息协议 |
| 6 | 档位表形态解耦（见 §3 B4 的建议方向） | B4 | 中；属产品决策，先对齐再做 |

**缓解手段（已存在，用起来）**：后端 `previewBillingRule` + 前端 `PricingPreviewDrawer.vue` 已有试算能力。
建议把新接厂商的**首笔真实请求**先过一遍试算再放行——它能挡住 D1 / D2 这类「配得出但算不对」，
但**挡不住 A 组（提取层压根没拿到信号）**，因为试算输入的用量本身就是错的。

## 6. 明确「不算不足」的项（避免后续重复讨论）

- **非 2xx 上游失败不计费**：`AbstractUpstreamProtocolExecutor` 在提取前就抛异常，链路正确。
- **「至少一秒」兜底本身**：对「确实拿到了视频但时长字段缺失」是合理的；问题只在于它同时吞掉了 A2 那种「压根没产出」。
- **`hasInputVideo` 判据**：2026-10-26 已统一（`:386`），「选择哪一档价」这条轴已修好——
  **只剩「量是多少」那条轴没修**，别把这当成做过了。
- **QWEN 孤种绑定**：无实现类、恒回落透传，已另单登记，不属视频计费范畴。
