# 高低峰计费（PEAK_OFF_PEAK）方案评审与实施计划

> 分层修订：高低峰是计费模式之上的进阶定价方案，不新增 `BillingModeEnum`。本文涉及“模式”的旧表述统一按 `billingMode + pricingPlan` 理解；完整模型见《计费规则优化方案：计费模式与进阶方案分层》。

评审日期：2026-09-28 ｜ 评审对象：《高低峰计费规则编辑页面设计方案》
评审方式：逐条对照 knot-server / knot-front 现有代码与库表，**本次未修改任何代码**

---

## 一、总体结论

| 维度 | 判定 |
| --- | --- |
| 方案本身 | **可行**。语义清晰（左闭右开、判定优先级、倍率模式），数据契约与现有 `configJson` + 版本化机制兼容。 |
| 能否按原文一次性落地 | **不能**。有 3 处与现状冲突（载荷 `name`/`providerId`、方案能力未拆分）、1 处架构前提不成立（网关热路径计算器不按 `billingMode` 路由）、1 处无落点（账单明细表不存在）。 |
| 建议节奏 | **拆两期**。首期＝「规则配置 + 后端校验 + 判定引擎 + 预览接口」；二期＝「请求计费明细表 + 账单留痕 + 灰度」。否则第 3 条设计目标（每笔可追溯）在首期无法验收。 |

## 二、方案假设 vs 代码现状（逐条核对）

| # | 方案说法 | 代码现状 | 判定 |
| --- | --- | --- | --- |
| 1 | 增加 `PricingPlanEnum.PEAK_OFF_PEAK` | 现有 `BillingModeEnum` 只表达基础计量模式；下拉框目前取 DB 枚举 `billing_mode`（`BillingRuleFormDialog.vue:63-69`，分类在 `data.sql:498`） | ⚠ **需要拆分模式和方案能力**，不能把高低峰加入 `billing_mode` |
| 2 | 请求载荷含 `name` | `BillingRuleDto`（`BillingRuleDto.java:6-27`）无 `name`；`kb_billing_rules` 也无该列（`schema.sql:573-586`，已按 2026-09-28 重构 DROP） | ❌ 方案 8.4 与 §5「规则名称」已过时，删除 |
| 3 | 请求载荷 `providerId: 1` | 现行为 `providerCode`（`BillingRuleDto.providerCode`；`kb_billing_rules.provider_code`） | ❌ 过时，改 `providerCode` |
| 4 | 模式与方案能力接口需返回新方案 | 现有 `BillingService.listModeCapabilities()` 只遍历 `BillingModeEnum.values()`（`BillingService.java:96-105`） | ⚠ 需新增 `supportedPricingPlans`，不能依靠基础模式枚举自动生效 |
| 5 | 任何配置变更都要生成新版本 | `buildVersionCode()` 把 `configJson` 计入 MD5（`BillingService.java:351-367`），`updateRule()` 按 versionCode 变化建版（`:175-183`） | ✅ **天然满足**，§12.1 无需额外代码 |
| 6 | `unitPrice` 存高峰输入单价 | 前端 `primaryUnitPrice()` 对 TOKEN 已取 `inputUnitPrice`（`BillingRuleFormDialog.vue:370-374`） | ✅ 作为基础价格沿用；高低峰方案只保存峰谷判定和倍率，不新增模式单价字段 |
| 7 | 沿用 `configJson`，首期不建专用表 | `kb_billing_rule_versions.config_json` 为 JSON 列（`schema.sql:595`） | ✅ 可行；`condition` 放在具体价格明细中，阶梯保持 `ladder[].condition + ladder[].unitPrices` |
| 8 | 「在计费引擎中实现时区转换与判定」 | 网关热路径的 calculator **由 extractor 决定，不看 billingMode**：`UsageExtractorRegistry.java:54-70` 传的是 `extractor.calculator()`，`DefaultUsageExtractor.calculator()` 是构造注入的固定实例 | 🔴 **架构前提不成立**。新增模式不会自动路由到新计算器，必须显式改接线 |
| 9 | 判定使用请求发生时间 | `NormalizedUsageContext(rule, usage, requestBody)` 无时间字段（`NormalizedUsageContext.java:9-20`）；`UpstreamRequestContext` 也无（`UpstreamRequestContext.java:10-18`） | ⚠ 需给 context 补 `occurredAt`（首期取 `Instant.now()`） |
| 10 | 节假日日历缓存 | 网关热路径零 DB：`GatewayDataService` 用 Caffeine 缓存计费规则（`GatewayDataService.java:184`） | ⚠ 日历必须同口径缓存，**禁止请求内查库** |
| 11 | 明细留 `occurredAt`/`billingPhase`/日历版本等 | `schema.sql` 全库无请求记录表 / 成本明细表（只有 `kr_plugin_execution_logs`） | 🔴 **无落点**，首期必须新建表或推迟到二期 |
| 12 | 新增 `POST /api/billing/rules/{id}/preview` | `AdminAuthorizationInterceptor` 默认拒绝，无绑定即 403 | ⚠ 必须补 `ks_api_permission_bindings`（`gen_api_bindings.py` + `apply_bindings.py`，插在授权块之前） |
| 13 | 价格 BigDecimal 语义 | `kb_billing_rule_version_items.unit_price DECIMAL(18,6)`；`config_json` 是 JSON 列，Jackson 默认走 double | ⚠ 后端解析必须走 `BigDecimal`/`asText()`；现有 `jsonDecimal()` 是字符串扫描（`BillingService.java:543-572`），能取嵌套 key 但脆弱，新逻辑建议用 POJO 解析 |
| 14 | 新增独立模式组件 | `modes/*.vue` 只接 `props.form`，真正的 JSON 拼装在父组件 `buildConfigJson()` 按 mode 分支（`BillingRuleFormDialog.vue:336-368`） | ⚠ 新组件之外，父组件也要加分支 |
| 15 | IANA 时区下拉 | 按既有约定：非 `ModelType`/`ModelApiProtocol` 的枚举一律留 DB；但 IANA 全量 600+ 条不适合塞 `ks_enum_configs` | ⚠ 待决策：建议**前端静态常用时区列表 + 后端 `ZoneId.of()` 校验** |

## 三、对方案 §17「待评审决策」的建议答案

| # | 问题 | 建议 | 理由 |
| --- | --- | --- | --- |
| 1 | 方案编码 | 定 `PEAK_OFF_PEAK`，归入 `PricingPlanEnum` | 与基础计费模式解耦 |
| 2 | 低峰价格模式 | 首期**只开倍率**，`rateMode` 固定 `MULTIPLIER` | 与方案 §6.3 一致，避免两套价格源不一致 |
| 3 | 节假日数据来源 | **DB 表 + 一次性导入脚本**（`kb_holiday_calendar`），不用外部服务 | 热路径零 DB 要求必须可缓存；外部服务会引入可用性依赖（方案 §13.2 自己也要求缓存兜底） |
| 4 | 调休工作日默认 | **按低峰处理**（`OFF_PEAK`） | 与 DeepSeek 示例语义一致 |
| 5 | 禁止跨午夜 | **维持禁止**，保存时校验 `start < end`，跨午夜必须拆两行 | 语义最简单，前端也好校验 |
| 6 | 时间精度 | **分钟** | 与 `HH:mm` 控件及方案一致 |
| 7 | `unitPrice` 语义 | 明确为**高峰输入单价**，不新增主表字段 | 与 TOKEN 现状一致，列表/排序/审计不受影响 |
| 8 | 长时音视频跨峰谷 | 首期**单一计费时点**，不做切分 | Token 请求天然单点；音视频留给后续 |
| 9 | 首期开放预览接口 | **开放**，但只做管理端调试，且复用后端判定引擎 | 方案 §11.3 已明确禁止前端另写一套日历算法 |

补充决策（方案未列但必须定）：

- **时区列表来源**：前端静态常用时区清单（UTC / Asia/Shanghai / America/New_York / Europe/London 等）+ 后端 `ZoneId` 白名单校验，不进 DB 枚举。
- **首期是否建请求明细表**：二期。首期只落地「规则 + 引擎 + 预览」，§12.2 的明细展示顺延。

## 四、实施计划

### 阶段 0：拍板（阻塞后续）

- 确认上表 9 + 2 项决策；确认首期不含明细表。
- 确认中国法定节假日 2026 版数据来源与导入责任人。
- 门禁：无代码改动。

### 阶段 1：契约与领域能力（后端）

| 步骤 | 落点 |
| --- | --- |
| 1.1 | 新增 `PricingPlanEnum.PEAK_OFF_PEAK`，并在能力矩阵中声明其支持的 `billingMode`/`unit` 组合 |
| 1.2 | 新增独立 `billing_pricing_plan` 字典（或由后端枚举下发）；`billing_mode` 只保留基础模式 |
| 1.3 | 新建配置模型 `PeakOffPeakConfig`（record）+ 校验器：时区 `ZoneId`、星期枚举、`HH:mm`、重叠检测、倍率 `(0,1]`、价格非负 |
| 1.4 | `BillingService.validateRule()` 增加「按 `pricingPlan` 校验对应价格明细的 `condition` 与价格参数」分支 |
| 1.5 | 建 `kb_holiday_calendar`（id / calendar_type / version / holiday_date / name / is_make_up_workday）+ 导入脚本 + 版本查询 DAO |
| 1.6 | 判定引擎 `PeakOffPeakResolver`：按方案 §9.1 优先级返回 `phase` + `reason` + `multiplier`，纯函数、可单测 |

验证门：`mvn -f knot-server/pom.xml clean package` EXIT=0；新增 `PeakOffPeakResolverTest` 覆盖工作日/周末/节假日/调休/边界 `01:00` 命中与 `04:00` 不命中。

### 阶段 2：管理页面（前端）

| 步骤 | 落点 |
| --- | --- |
| 2.1 | 新增 `BillingModePeakOffPeakConfig.vue`（时区/日历/时段列表/价格/摘要/时间轴/判定测试） |
| 2.2 | `BillingRuleFormDialog.vue`：`componentsByMode` 注册、`buildConfigJson()` 加分支、`primaryUnitPrice()` 加分支、模式切换保留字段 |
| 2.3 | 前端校验：空星期、跨午夜、同星期重叠、倍率越界；提交前 JSON 规范化 |
| 2.4 | 摘要 / 一周时间轴 / 判定测试（测试区调用后端预览接口，不内置日历算法） |

验证门：`vue-tsc --noEmit` EXIT=0（以 `npm run type-check` 为准）。

### 阶段 3：引擎接线 + 预览接口

| 步骤 | 落点 |
| --- | --- |
| 3.1 | **关键**：`UsageExtractorRegistry` 按 `rule.billingMode` 覆盖 calculator（或在 `TokenBillingModeCalculator` 内按 mode 分支），否则模式不生效 |
| 3.2 | `NormalizedUsageContext` 补 `occurredAt`（`Instant`，UTC） |
| 3.3 | `GatewayDataService` 增加节假日日历 Caffeine 缓存（键 = type+version），保证热路径零 DB |
| 3.4 | `POST /api/billing/rules/{id}/preview`，复用 `PeakOffPeakResolver` |
| 3.5 | 补 `ks_api_permission_bindings` + 前端 api 方法 |

验证门：`mvn clean package` EXIT=0；真启 admin jar（`--server.port=18080`）冒烟：创建 PEAK_OFF_PEAK 规则 → 回显完整 → 预览接口返回 `phase/reason/multiplier/prices`；冒烟数据当轮清理。

### 阶段 4（二期）：明细与灰度

- 新建请求计费明细表（occurredAt / billingTimezone / billingPhase / ruleVersionId / calendarVersion / rateMultiplier / effectivePrices / usage / amount）。
- 成本明细页展示方案 §12.2 字段；版本差异对比与回滚。
- DeepSeek 示例 + 一个非 UTC 时区示例联调；非关键模型灰度。

### 回归底线（每阶段都要满足）

- `TOKEN` / `CUSTOM` 等既有模式及固定价结果**不变**；旧 `TIERED` 数据按“基础模式 + `pricingPlan=TIERED`”转换。
- 计费规则列表、启停、删除保护、版本审计不受影响。
- 网关热路径不新增 DB 查询。
