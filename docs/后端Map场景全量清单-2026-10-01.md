## 1. 结论

Map 的使用总体合理。大多数命中点承载的是外部协议 JSON、动态扩展字段、运行时属性袋、索引或分组结果，改成 class/record 会丢失扩展性，或者只是把一个集合换成没有行为的包装对象。

Adapter 需要单独遵守“透传优先”原则：当前对接的 Adapter 以把用户请求送到上游为主，Map 在这里是协议边界上的请求载体，不是等待收敛的弱 DTO。兼容协议路径应尽量原样返回请求内容；只有跨协议或供应商协议明确要求时，才复制并修改必要字段。不能因为 Map 治理而先反序列化成通用 record/class，再重建请求体。

真正值得评估的是四组结构，固定程度不同：

1. 7 个 controller 的 `Map.of("available", boolean)`，可以统一为一个 `CodeAvailability` record，序列化 JSON 不变。
2. 六个内置插件日志位置当前用 Map 拼接 payload，应统一为固定 payload record；请求体和响应体等动态内容改用 `JsonNode` 原样保存，固定路由快照改为 `GatewayRoutingSnapshot` 类型。
3. `AbstractGatewayRequestTemplate:143` 的路由快照固定写入 7 个字段，适合抽象为 `GatewayRoutingSnapshot` class。
4. `BillingService` 中 4 个结构化写入点（外层 `detail`、TOKEN `parts`、非 TOKEN `parts`、版本指纹 payload）应分开处理。外层 `detail` 适合 record；TOKEN `parts` 已有稳定字段，适合定义 `TokenBillingParts` class，并至少补齐通用缓存写用量和成本；若该路径接入统一用量的细分，再按独立字段补 5m、1h 缓存写；非 TOKEN `parts` 仍是另一种形状；版本指纹应复制并归一化 `BillingRuleDto`，再用固定字段投影，避免魔数字符串键并保持 hash 兼容。

因此，“所有 Map 都应替换成 class/record”这个方向不成立；合理目标是只收敛固定、跨边界、需要字段约束的结构。

### 1.1 选择 `Map`、record 还是 class 的判断标准

| 选择 | 适用条件 | 本项目对应场景 |
|---|---|---|
| `Map<String, Object>` | key 集合未知、供应商可扩展、需要保留未建模字段，或只是局部组装/索引 | 上游请求体、`extra`、插件 attributes、凭据 JSON、分组表；插件日志 payload 不再属于此类 |
| `record` | 字段固定、主要用于只读传输或快照、没有生命周期和复杂变更行为；若包含 Map/List，另行处理其可变性 | `CodeAvailability`、`BillingUsageDetail` 外层、已经存在的 `PluginEvent` |
| `class` | 需要逐步构建、可变状态、校验方法、兼容旧 setter/框架绑定，或对象本身有明显行为；固定快照也可用 class 封装工厂和脱敏行为；需要计算派生值或兼容旧输出时也可优先 class | `GatewayModelRequest` 这类带 `@JsonAnySetter` 的请求对象、拟新增的 `GatewayRoutingSnapshot`、拟新增的 `TokenBillingParts`；不能仅为替换一个局部 Map 而新建 class |

record 只解决“字段有名字、类型可检查、组件引用不能重新赋值”这几个问题；它对组件内的 Map/List 不是深度不可变容器。需要不可变边界时仍要做防御性复制或使用不可变集合。record 也不会自动解决动态 JSON、版本兼容或哈希稳定性。对于包含动态 Map 的固定外层，可以使用“record 外壳 + Map 内核”；对于 TOKEN parts 这类字段已固定的嵌套对象，应继续使用具名类型。

本清单统计的是显式创建点，未把 `JsonKit.toMap(...)`、`JsonKit.fromJson(..., TypeReference<Map<...>>)` 等转换结果当成新的创建点；这些调用也不应机械改成 DTO，需要按对外合同和审计用途单独判断。

### 2.1 Adapter 专项原则：保留用户请求，最小化协议转换

Adapter 的首要职责是把用户请求按目标协议发送出去，而不是重新定义请求模型。对当前实现，建议把下面的约束作为后续重构的准入条件：

1. **兼容路径原样透传。** 当输入协议与上游协议兼容时，优先返回 `context.requestBody()`；不要为了使用 record/class 而重新序列化或重建 Map。
2. **转换路径只改必需字段。** 需要跨协议转换时，先复制 source，再移动、补充或删除目标协议明确要求的字段；保留未知字段和供应商扩展字段，除非目标协议明确禁止或转换本身必须移除。
3. **不原地修改用户请求。** `new LinkedHashMap<>(source)` 这类防御性复制可以保留；转换结果可以变化，但 `context.requestBody()` 的内容不能被 Adapter 原地改写。若转换需要修改嵌套 Map/List，还要复制将被修改的分支，不能把浅复制当成深复制。
4. **禁止以类型治理为由做隐式归一化。** 不应裁剪未知字段、擅自补默认值、改变 `null`/空值语义、重排字段，或把别名转换扩大成通用字段清洗。只有目标供应商合同明确要求的变化才允许发生。
5. **供应商专用请求体是例外，不是通用模板。** Qwen 图片请求、智谱图片请求等必须构造供应商结构时，可以使用 Map 组装目标 payload；这不意味着可以把所有 Adapter 都改成固定 DTO。
6. **record/class 只放固定外壳。** 可以为结果快照、事件信封、可用性响应等固定结构新增 record；不能用它替代动态上游请求体，也不能把未知字段丢进一组可空字段。

当前代码与这套原则基本一致：OpenAI 兼容路径和多数协议直接返回原请求；Anthropic、智谱在跨协议时复制 source 后做字段移动/删除，必要时补目标协议要求的默认字段；Qwen、智谱图片接口在供应商协议边界内重建必要结构。后续新增或修改 Adapter 时，应把“未知字段透传、原 Map 不变、输出只发生必要差异”作为回归检查点。

其中，Qwen 和智谱的图片请求目前是从 source 提取已识别字段后重新组装目标结构，不能把这两条路径误判为完整透传。如果目标供应商允许扩展字段，应补充明确的保留策略；如果目标协议只接受固定字段，则应在 Adapter 契约和测试中记录哪些字段会被有意丢弃。这样既能保持透传优先，也不会把供应商专用的结构转换误推广为全局字段裁剪规则。

建议每个 Adapter 至少覆盖以下回归场景：

- 输入包含未知字段时，兼容路径仍能发送该字段；
- `buildRequestBody` 返回后，原始 `requestBody` 没有被原地修改；
- 转换路径只改变协议转换明确涉及的字段；
- `null`、空字符串、空数组等值的行为保持既有合同；
- 供应商扩展字段在目标协议允许时仍能发送，明确不支持的字段有对应测试说明。

### 2.2 插件日志统一结构设计：固定 payload record + `JsonNode` 原始内容

本节是后续落码设计，本次只更新清单，不修改现有 Java 代码。

当前六个内置日志插件都先创建 `Map<String, Object> payload`，再把不同字段放进去。这种写法虽然已有 `PluginEvent` 事件信封，但 payload 的字段集合和类型仍由字符串键决定，日志消费者无法依赖稳定的 Java/JSON 结构。建议沿用现有 `PluginEvent` 事件信封，只把 `payload` 的类型收敛为一个受限的 payload 类型集合：

```java
public record PluginEvent(String eventType,
                          String traceId,
                          String traceparent,
                          String pluginInstanceCode,
                          String pluginCapabilityCode,
                          PluginStageCode stageCode,
                          String scopeType,
                          Long scopeRefId,
                          PluginLogPayload payload,
                          LocalDateTime occurredAt) {
}

@JsonTypeInfo(use = JsonTypeInfo.Id.NAME,
        include = JsonTypeInfo.As.PROPERTY,
        property = "payloadType")
@JsonSubTypes({
        @JsonSubTypes.Type(value = GatewayRequestPayload.class, name = "gateway-request"),
        @JsonSubTypes.Type(value = GatewayResponsePayload.class, name = "gateway-response"),
        @JsonSubTypes.Type(value = GatewayErrorPayload.class, name = "gateway-error"),
        @JsonSubTypes.Type(value = UpstreamRequestPayload.class, name = "provider-request"),
        @JsonSubTypes.Type(value = UpstreamResponsePayload.class, name = "provider-response"),
        @JsonSubTypes.Type(value = UpstreamErrorPayload.class, name = "provider-error")
})
public sealed interface PluginLogPayload
        permits GatewayRequestPayload, GatewayResponsePayload, GatewayErrorPayload,
                UpstreamRequestPayload, UpstreamResponsePayload, UpstreamErrorPayload {
}
```

六种 payload 的字段边界如下。字段名应直接成为 record 组件，禁止再退回字符串键；请求体和响应体属于原始 JSON，使用 `JsonNode` 保留结构和未知字段；路由快照使用固定的 `GatewayRoutingSnapshot` class，不用 Map 重建日志对象。

| payload record | 固定字段 | 动态内容承载 | 对应日志位置 |
|---|---|---|---|
| `GatewayRequestPayload` | `ruleCode`、`protocol`、`contentType` | `JsonNode requestBody`、`GatewayRoutingSnapshot routing` | `GatewayRequestLoggingPlugin.java:40` |
| `GatewayResponsePayload` | `ruleCode`、`protocol` | `JsonNode responseBody` | `GatewayResponseLoggingPlugin.java:36` |
| `GatewayErrorPayload` | `ruleCode`、`protocol`、`errorType`、`errorMessage` | `JsonNode requestBody` | `GatewayErrorLoggingPlugin.java:37` |
| `UpstreamRequestPayload` | `providerCode`、`modelCode`、`protocol`、`bindingProtocol`、`contentType` | `JsonNode requestBody` | `UpstreamRequestLoggingPlugin.java:36` |
| `UpstreamResponsePayload` | `providerCode`、`modelCode`、`protocol` | `JsonNode response` | `UpstreamResponseLoggingPlugin.java:36` |
| `UpstreamErrorPayload` | `providerCode`、`modelCode`、`protocol`、`errorType`、`errorMessage` | `JsonNode requestBody` | `UpstreamErrorLoggingPlugin.java:37` |

通过 Jackson 的 `payloadType` 判别值明确六种 payload，禁止消费者依赖字符串键猜测类型。`eventType` 和现有事件信封字段暂时保留，便于已有日志检索；新结构只替换 `payload` 的动态 Map，不改变 trace、插件、阶段和时间字段的含义。`scopeType` 是否从字符串改成 `PluginScopeType` 应单独评估，不要与本次 payload 收敛混在一起。

选择六种 payload record 而不是一个包含大量可空字段的“大日志 record”，是为了让每个阶段的字段约束在类型上成立：网关日志不应出现 provider 字段，上游日志不应依赖 routing 字段，错误日志才携带错误信息。`PluginLogPayload` 作为 sealed interface 仍是一个统一出口，`payloadType` 负责跨 sink 和跨语言消费者的稳定判别。

这项设计不要求把请求体本身类型化。`JsonNode` 只负责保存日志快照，既能避免 Map 拼装，又能保留上游协议的未知字段；它不是对用户请求做归一化或裁剪。日志序列化仍由 `LoggingPluginEventSink` 统一完成，Kafka 或其他 sink 可以消费同一个 `PluginEvent`。如果存在外部消费者依赖旧的 Map payload，应在 sink 或反序列化边界做兼容适配，不要让六个日志插件继续构建 Map。

后续落码前应验证：六类 payload 的 JSON 字段名稳定；`null` 错误字段仍按现有行为输出；请求/响应中的未知 JSON 字段不丢失；旧的 `eventType`、trace 和 scope 字段继续可检索；日志 sink 不再调用 `JsonKit.toJson(Map)`。

### 2.3 `AbstractGatewayRequestTemplate:143`：固定路由快照建议抽象为 class

`routingSnapshot` 当前固定写入 7 个字段：`ruleId`、`ruleCode`、`consumerId`、`returnUsageDetail`、`candidateCount`、`appId`、`department`，其中后两个字段只在路由信息存在时取值。这已经是一个明确的内部快照结构，不再是为了保留未知供应商字段而存在的动态 Map。

建议抽象为 `GatewayRoutingSnapshot` class，字段如下：

```java
public final class GatewayRoutingSnapshot {
    private final Long ruleId;
    private final String ruleCode;
    private final Long consumerId;
    private final boolean returnUsageDetail;
    private final int candidateCount;
    private final String appId;
    private final String department;

    public static GatewayRoutingSnapshot from(ResolvedRouting routing) {
        // 负责 null 安全地提取 routingInfo、app、department
    }
}
```

这里使用 class 的理由是把 `ResolvedRouting` 到日志快照的提取和 null 处理封装在 `from` 工厂中，并为后续增加脱敏或格式化行为保留空间。如果确认只需要不可变数据载体，也可以用同字段的 record；无论采用 class 还是 record，都不应再通过字符串键拼 Map。

配套调整范围包括：`routingSnapshot(...)` 返回 `GatewayRoutingSnapshot`；`GatewayPluginContext.routingSnapshot` 改为该类型；`GatewayRequestPayload.routing` 直接使用该类型。请求体 `GatewayPluginContext.requestBody` 仍保持 Map，因为它是用户请求的动态透传内容，与固定路由快照是两种不同语义。

该位置的处理意见为：**建议改为 `GatewayRoutingSnapshot` class；保留 7 个固定字段和 JSON 字段名，补充 null 路由、空候选列表、无 app/department 三类序列化测试。**

## 5. 固定结构候选的逐项判断

### 5.1 `CodeAvailability`：适合 record

7 个 controller 都返回同一个 JSON 形状：`{"available": true}`。可以新增共享类型：

```java
public record CodeAvailability(boolean available) {
}
```

将 `return Map.of("available", value)` 改为 `return new CodeAvailability(value)`，Jackson 默认仍输出同样的 `available` 属性。该改动不改变前端 JSON 合同，但会改变 controller 方法的 Java 声明类型；落地前应确认没有测试或其他 Java 调用方依赖 `Map` 返回类型，并补一次 controller 序列化测试或接口冒烟。

这是唯一一组可以直接、低风险、一次性统一的 Map。

### 5.2 `BillingService.calculateUsageDetail`：外层 detail 适合 record

`BillingService.java:382` 固定写入 10 个字段：模型、规则身份、计费模式、币种、单位、单位大小、用量和总成本。外层结构具有明确边界，建议使用 `BillingUsageDetail` record。

当前仓库内没有找到 `calculateUsageDetail` 的 controller 或其他调用点，因此它目前更像预留的服务能力。落地前应先确认 API/调用方是否已经在外部使用；如果没有稳定消费者，可以先只记录候选，不急于新增公共 DTO。

它的 `usage` 当前按计费模式变化：TOKEN 是 token/cost 字段，其他模式只有 `amount`。`TokenBillingParts` 可以先作为计费计算内部 class；如果外部结果仍要求既有 Map/JSON 形状，则只在结果边界做一次字段映射，保留原有字段名。不要为了容纳两种形状而引入带大量可空字段的统一类型，也不要把动态 usage 输入反向收敛成 DTO。

### 5.3 TOKEN `parts`：适合定义内部 `TokenBillingParts` class，并补齐缓存写

`BillingService.java:434-441` 的字段集合是固定的，不是供应商请求体，也不是按 ID 建索引。这里可以定义服务内部的 `TokenBillingParts` class；建议使用 `private static final class`，字段设为 `final`，通过构造器一次性建立，避免继续用字符串键表达结构。选择 class 而不是把字段散落在 `Map` 中，是因为它可以把“输入侧非缓存 token”“缓存读写 token”“各项金额”和“总成本”放在同一个领域对象中，并在构造器或方法中维护派生值和非负约束。

建议的最小字段类型如下：

```java
private static final class TokenBillingParts {
    private final long inputTokens;
    private final long outputTokens;
    private final long totalTokens;
    private final long cacheReadTokens;
    private final long cacheWriteTokens;
    private final BigDecimal inputCost;
    private final BigDecimal outputCost;
    private final BigDecimal cacheReadCost;
    private final BigDecimal cacheWriteCost;
}
```

这里的类型不能混用：`inputTokens`、`outputTokens`、`totalTokens`、`cacheReadTokens`、`cacheWriteTokens` 都是 token 数量，使用 `long`；`inputCost`、`outputCost`、`cacheReadCost`、`cacheWriteCost` 都是金额，使用 `BigDecimal`。不要把缓存写 token 声明为 `BigDecimal`，也不要用 `Object`、`String` 或可空的 `Map` 代替。`inputTokens` 仍表示原始输入总量，不能为了扣除缓存写而改名或覆写；class 可以提供 `uncachedInputTokens()` 这类派生方法，按 `max(0, inputTokens - cacheReadTokens - cacheWriteTokens)` 得到可按普通输入价计费的数量。若为了兼容外部 JSON 需要包装类型，包装应发生在序列化边界，内部计算仍以 `long` 和 `BigDecimal` 为准。

当前 `BillingService.java:434-441` 缺少缓存写的四个关键环节：

1. 从 usage 读取 `cacheWriteTokens`，并沿用 `BillingUsage` / `MapNumberUtils` 的缓存写别名和嵌套字段语义；
2. 读取 `BillingConfig.PriceKind.CACHE_WRITE` 对应的缓存写单价；
3. 计算并写入 `cacheWriteCost`；
4. 计算普通输入 token 时扣除缓存写 token，并把缓存写成本纳入总成本。

因此，当前代码的 `inputCost = cost(inputTokens - cacheReadTokens, ...)` 和 `inputCost + outputCost + cacheReadCost` 都不能作为完整的 TOKEN 计费口径。文档这里只记录缺失和目标结构，不修改代码；后续落地必须与已经存在的 `TokenBillingModeCalculator`（其缓存写 token 为 `long`、缓存写金额为 `BigDecimal`）保持一致。

缓存写还有一层不能混淆的明细语义：统一用量模型中的 `cacheWrite`、`cacheWrite5m`、`cacheWrite1h` 均为 `long` token 数，其中 `cacheWrite5m` / `cacheWrite1h` 任一大于 0 时，普通 `cacheWrite` 归 0，三者不是可随意相加后再塞回一个字段。若该计费路径需要保留 5m/1h 明细，应在 class 中增加 `long cacheWrite5mTokens`、`long cacheWrite1hTokens` 及对应的 `BigDecimal cacheWrite5mCost`、`BigDecimal cacheWrite1hCost`；在定价解析明确区分这两种价格前，不得把它们静默当成普通 `cacheWrite` 计价。当前 `BillingConfig.PriceSet` 已有 `cacheWrite5m` / `cacheWrite1h` 字段，但 `PriceKind` 只有通用 `CACHE_WRITE`，这是需要单独确认的计费语义缺口。

还要区分模型层和计费层的字段：`BillingUsage.cacheWriteTokens` 当前是计费输入的 `Long` 组件，进入计算器后按 `long` 使用；统一 `ModelUsage.InputTokens` 的 `cacheWrite` / `cacheWrite5m` / `cacheWrite1h` 是对外用量的 `long` 字段；`BillingConfig.PriceSet.cacheWrite` / `cacheWrite5m` / `cacheWrite1h` 则是价格，必须按 `BigDecimal` 处理。当前 `BillingUsage.from(Map)` 只抽取通用缓存写别名，没有 5m/1h 独立组件，因此文档不能把统一用量的细分字段误写成现成的计费输入。

### 5.4 非 TOKEN `parts`：保持独立形状

`BillingService.java:462` 只有 `amount`，不应与 TOKEN class 合并成一个带大量可空字段的“大杂烩”类型。当前没有稳定消费者要求它类型化，保留 Map 作为服务内部中间结果即可；若未来需要类型化，应单独评估 `SimpleBillingParts(long amount)`，不要让它反向约束 TOKEN class 的缓存字段。

### 5.5 版本指纹 payload：复制 `BillingRuleDto`，再做固定字段投影

`BillingService.java:518-523` 当前只把 5 个字段纳入 MD5：归一化后的 `billingMode`、`pricingPlan`、`currency`、`unit` 和规范化后的 `configJson`。这里可以复制 `BillingRuleDto` 实例并调整这 4 个字符串字段的值，使归一化结果有一个具名、可检查的承载对象；不要继续通过 `Map.put("billingMode", ...)`、`Map.put("pricingPlan", ...)` 这类魔数字符串键表达 DTO 字段。

`BillingRuleDto` 当前是 record，不能对原实例调用 setter 原地修改；这里的“copy”应是调用 canonical constructor 或具名工厂创建新实例，只替换 `normalizeBillingMode`、`normalizePricingPlan`、`normalizeCurrency`、`normalizeUnit` 的结果，其余字段沿用原 DTO。默认值、枚举 code 和字段选择都应复用已有方法/枚举，不要新增裸数字、裸字符串或按位置猜字段。

复制 DTO 后不能直接把完整 `BillingRuleDto` 序列化进指纹：DTO 还包含 `id`、规则编码、展示字段、状态、有效期等不参与版本内容判断的字段；把它们带入会改变当前 hash 语义。建议从归一化 DTO 读取上述 4 个字段，再与 `normalizeJsonText(request.configJson())` 产生的 JSON 值组装一个私有 `BillingVersionFingerprint` 类型，只保留这 5 个字段。该类型的字段名由 Java 成员决定，不再依赖散落的 Map key。

`BillingRuleDto.configJson` 是 `String`，而当前 `normalizeJsonText` 返回的是 canonical JSON 值（对象、数组、数字或 null）。因此 DTO 复制只承载可直接归一化的计费标量；`configJson` 必须在指纹投影中保持 JSON 值类型，不能先 `toJson` 成字符串再放回 DTO，否则序列化结果会从 JSON 对象变成带引号的字符串，破坏既有 MD5。若实现选择把 canonical JSON 文本写回 DTO，必须同步调整指纹序列化契约并迁移历史 hash，不能静默改变。

落地时至少验证：

- 归一化前后仅空白、大小写、默认值变化的请求仍得到既有 hash；
- 指纹 JSON 只包含这 5 个字段，字段顺序和 `null` 处理保持稳定；
- `configJson` 对象键排序、数组顺序和数字归一化保持现有 `canonicalizeJsonValue` 语义；
- DTO 新增展示字段或数据库字段不会进入 hash。

## 6. 不建议改成 class/record 的场景

| 场景 | 原因 |
|---|---|
| 上游 OpenAI/Anthropic/Qwen/Zhipu 请求体 | 供应商字段不同，且需要保留未建模扩展字段；record 会把协议变化变成频繁改类 |
| 网关事件、SSE 片段 | payload 是动态异构快照，当前仍保留 Map；插件日志已单独收敛为固定 payload record |
| `GatewayModelRequest.extra`、请求 attributes、插件 attributes | 本意就是扩展袋，调用链需要透传未知字段 |
| `Map.copyOf` 注册表和按 ID 索引 | Map 的 key/value 关系就是业务语义，class 只会包一层 |
| 分组、聚合和报表中间 Map | Map 是算法过程量，最终结果已经是 record/DTO |
| 凭据 JSON、模型能力 JSON、用户设置、枚举选项 | key 集合可配置或随供应商扩展，无法建立稳定字段集合 |
| 测试输入 Map | 测试的是上游原始 JSON 兼容性，改成 DTO 会削弱覆盖面 |

插件日志不再采用“固定事件信封 + `Map<String, Object>` payload”。应改为“固定事件信封 + 固定类型 payload record”：六个内置插件日志位置分别使用网关请求、网关响应、网关错误、上游请求、上游响应、上游错误六种 payload record；请求体和响应体使用 `JsonNode` 保存原始结构，路由快照使用 `GatewayRoutingSnapshot` class，不在日志插件中用 Map 拼装。

`GatewayTrafficGuard.rateCounters` 需要并发 Map；`TrafficCheckContext.providerResults` 只在单次网关请求内使用普通 `HashMap`，不应因为“限流”二字机械改成 `ConcurrentHashMap`。
