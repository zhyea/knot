# 上游原文口径横向排查

> 日期：2026-11-13
> 核查基线：当前工作区 `HEAD 8fd1a410`
> 关联文档：`docs/上游日志保真问题分析与方案-2026-11-13.md`
> 性质：**静态代码核查。未修改业务代码，未运行测试门禁。**

## 1. 结论

### 1.1 已修复的部分

当前代码已经解决了首轮报告中的两项核心日志缺口：

- `ProxyResult` 已同时保留 `responseBody`（适配后）与 `upstreamResponseBody`（供应商 wire 原文）。
- `UpstreamResponsePayload` 已区分两个 body；`UpstreamErrorPayload` 已带 `httpStatus` 与 `upstreamResponseBody`。
- 上游请求日志的契约已明确写成“客户端请求体，不是实际出站体”，不再声称是供应商收到的请求。

### 1.2 仍然存在的系统性问题

**证据字段仍在协议适配之后采样。**

最严重的问题不在日志插件，而在 `UsageAccounting.rawUsage` / `rawBody`：

```text
供应商 wire 原文
  └─ adapter.handleResponse
       └─ 适配后响应 body
            ├─ 客户端响应
            ├─ 计费提取器输入
            └─ UsageAccounting.rawUsage / rawBody（被错误地称为“上游原文”）
```

因此，即使上游响应日志里已经有了 wire 原文，同一日志里的 `usage.rawUsage`、Kafka 的 `upstream_usage`、
对外并列的 `usage`、计费裁判的 `upstreamUsage`，在跨协议绑定时仍然可能是网关适配后的 usage。

## 2. 同类问题矩阵

| 级别 | 位置 | 声称的语义 | 实际语义 | 主要影响 |
|---|---|---|---|---|
| 🔴 高 | `UsageAccounting.rawUsage` / `rawBody` | 上游原文，用于审计、对账、事后重算 | 同步整包链路上是 `adapter.handleResponse` 之后的 body | Kafka `upstream_usage`、JEV、路由测试计费证据失真 |
| 🔴 高 | 同步非流式响应的并列 `usage` | 上游原始 usage | 响应体自带的适配后 usage；计算出的 `rawUsage` 未注入 | 前端计费裁判拿到适配后 usage；跨协议时供应商 key 已变 |
| 🟡 中 | `ProxyStreamingFlux` 的 `usage.rawUsage` | 上游原始 usage | 从 `adapter.adapt(line)` 之后的 SSE 事件提取 | `knot_extend` 并列 usage、流式 Kafka 证据失真 |
| 🟡 中 | `GATEWAY_RESPONSE` / `GATEWAY_REQUEST` / `GATEWAY_ERROR` payload | “原始请求 / 原始响应 JSON” | 分别是适配后响应、客户端入口请求、可能已被目标模型覆盖的请求 | 日志消费者误判客户端实收与网关入口 |
| 🟡 中 | 异步 `UsageAccounting.rawBody` | 上游查询响应原文 | `queryBodyForUsage` 改写后的 body | `terminal_body` 仍是原文，但账目里的 rawBody 不是 |
| 🟡 中 | 异步任务查询异常日志 | 上游错误状态与错误体 | 只有异常 message 文本，结构化字段为空 | 查询 4xx/5xx 无法按状态码筛选 |
| 💭 低 | 上游请求日志的“实际出站体” | 供应商实际收到的请求 | 只有客户端请求体；适配器产物没有采集 | 契约已澄清，但跨协议排障仍缺最后一层证据 |
| 💭 低 | `PluginLogPayload` / `ModerationTextExtractor` / `ModerationEventSink` 文案 | “原始 JSON / 原始载荷” | 可能是适配后响应或已注入 `knot_extend` 的 Map | 主要是文档误导，不影响数据面 |

## 3. 逐项证据

### 3.1 `UsageAccounting.rawUsage` / `rawBody` 仍是适配后口径

代码链路：

1. `knot-server/knot-gateway/src/main/java/org/chobit/knot/gateway/upstream/protocol/AbstractUpstreamProtocolExecutor.java:154`
   执行 `adapter.handleResponse(buffered.body(), context)`。
2. 同文件 `:159` 把 `handledResponseBody` 传给 `usageExtractorRegistry.extract(...)`。
3. `knot-server/knot-gateway/src/main/java/org/chobit/knot/gateway/upstream/usage/UsageExtractorRegistry.java:104-113`
   从传入 body 中读取 `rawBody` 与 `rawUsage`。
4. 同文件 `:248` 构造 `UsageAccounting.of(rawUsage, rawBody, ...)`。
5. `knot-server/knot-adapter/src/main/java/org/chobit/knot/adapter/model/usage/UsageAccounting.java:12`
   与 `:21-23` 仍声称二者是“上游原文”。

这与当前 `ProxyResult` 的注释已经直接冲突：

- `knot-server/knot-gateway/src/main/java/org/chobit/knot/gateway/model/ProxyResult.java:22-24`
  已明确写明 `rawUsage` 是在**适配后** body 上提取的，不是 wire 原文。

典型字段改写：

- Anthropic Messages → OpenAI Chat：
  `knot-server/knot-adapter/src/main/java/org/chobit/knot/adapter/support/anthropic/AnthropicMessagesResponseSupport.java:119-124`
  重建 `id` / `created` / `model` / `finish_reason` / `usage`；
  `:280-295` 把 `input_tokens` / `output_tokens` 改写为 `prompt_tokens` / `completion_tokens` / `total_tokens`。
- Bedrock Converse → OpenAI Chat：
  `knot-server/knot-adapter/src/main/java/org/chobit/knot/adapter/support/aws/AwsBedrockConverseSupport.java:173-181`
  重建响应；
  `:209-228` 把 `inputTokens` / `outputTokens` / `totalTokens` / `cacheReadInputTokens` 改写为 snake_case。
- OpenAI Chat → Anthropic Messages：
  `AnthropicMessagesResponseSupport.java:214-224` 重建响应；
  `:339-349` 把 `prompt_tokens` / `completion_tokens` 改写为 `input_tokens` / `output_tokens`，且刻意不携带缓存键。

结论：PassThrough 绑定下 `rawUsage` 可能恰好等于供应商原文；跨协议绑定下不成立。

### 3.2 Kafka `upstream_usage` 直接消费这份适配后 usage

- `knot-server/knot-gateway/src/main/java/org/chobit/knot/gateway/kafka/msg/GatewayTrafficMsgDto.java:274-279`
  的 `upstreamUsageOf(...)` 直接返回 `usage.rawUsage()`。
- `docs/gateway-warehouse-kafka-message-protocol-2026-10-17.md:216`
  明确承诺“上游响应里那个 `usage` 对象原样、保留厂商键名”。
- `docs/standards/rules/60-business-rules.md:269-270`
  也把 `upstream_usage` 定义为“上游原文，只透传”。

后果：

- 数仓拿 `upstream_usage` 回溯归一化口径时，看到的其实可能是网关变换后的口径。
- 供应商私有 usage 字段如果在适配器里被丢弃，Kafka 消息里也不会有。
- “网关不下发规则内容，但原文足够复算”的契约前提在跨协议绑定下不成立。

### 3.3 计费裁判与 `upstreamUsage` 证据链同样受影响

同步链路：

- `knot-server/knot-gateway/src/main/java/org/chobit/knot/gateway/runtime/GatewayRequestHandler.java:586`
  取出 `result.usage().rawUsage()`；
- 非流式分支 `:590-599` 只注入 `knot_extend`，**没有**把这个 `rawUsage` 作为并列字段注入；
- 客户端响应体里原有的 `usage` 是适配后响应自带的 usage。

这意味着：

- `knot-front/src/composables/useBillingVerdict.ts:79-80`
  按 `knot_extend` 的同级 `usage` 取“上游原始 usage”，实际取到的是适配后响应里的 usage；
- `knot-server/knot-service/src/main/java/org/chobit/knot/svc/service/RoutingTestBillingVerdictService.java:88-94`
  把该值作为 `upstreamUsage` 与 `upstreamRawBody` 的证据；
- `knot-server/knot-service/src/main/java/org/chobit/knot/svc/service/support/BillingFactAssembler.java:137-152`
  从 `upstreamUsage` 读取 `cost` / `total_cost`；
- `knot-server/knot-service/src/main/java/org/chobit/knot/svc/service/support/JevBillingJudge.java:313-324`
  的提示词仍把 `upstreamUsage` 描述为“上游原始 usage”。

如果适配器丢弃了 `cost` 或供应商私有字段，影子链的上游成本校验会退化为 `SKIP`，
而界面上的“证据”仍看起来像供应商原文。

### 3.4 并列字段名存在冲突风险

- `knot-server/knot-common/src/main/java/org/chobit/knot/common/constants/AiPayloadFields.java:73-79`
  把 `RAW_USAGE` 定义成 `"usage"`，并注明“整包模式下与上游响应自带的 `usage` 同义覆盖（值相同）”。

这个前提只对透传或未改写的响应成立。跨协议时：

- 客户端响应里的 `usage` 是适配后 usage；
- `UsageAccounting.rawUsage` 可能是另一套键名；
- 两者不能同时放在同一个 `"usage"` 键下。

所以同步非流式不能直接“补一个 rawUsage 到 usage 键”，否则会覆盖客户端依赖的适配后 usage，
或者造成不同绑定下同一字段语义不同。

### 3.5 流式 usage 也在适配后采样

- `knot-server/knot-gateway/src/main/java/org/chobit/knot/gateway/upstream/stream/ProxyStreamingFlux.java:166`
  先执行 `adaptedLines(adapter, stream, line)`；
- `:171-181` 遍历适配后的行，并从 `SseLineSupport.dataOf(current)` 提取 usage；
- `:357-359` 把 `value.rawUsage()` 作为并列 `usage` 注入 `knot_extend`。

典型改写：

- `AnthropicStreamSupport.java:228-243` 把 Anthropic 的 `output_tokens` 合成 OpenAI `completion_tokens`；
- `AnthropicStreamSupport.java:517-522` 在 Chat → Messages 方向合成 `input_tokens` / `output_tokens`。

因此流式 `rawUsage` 与整包 `rawUsage` 一样，都是适配后口径。

### 3.6 网关请求 / 响应日志仍有“原始”措辞

当前 payload 注释：

- `knot-server/knot-plugin/src/main/java/org/chobit/knot/plugin/log/GatewayRequestPayload.java:9`
  写“原始请求 JSON”；
- `GatewayResponsePayload.java:7` 写“原始响应 JSON”；
- `GatewayErrorPayload.java:7` 写“原始请求 JSON”；
- `PluginLogPayload.java:12` 写“请求/响应体等原始 JSON 用 `JsonNode` 原样保存”。

实际分发点：

- `knot-server/knot-gateway/src/main/java/org/chobit/knot/gateway/runtime/AbstractGatewayRequestTemplate.java:161`
  在入口阶段分发 `GATEWAY_REQUEST`；
- `:193` 在 `applyUsageAccounting(...)` 之后分发 `GATEWAY_RESPONSE`；
- `:213` 在终态异常时分发 `GATEWAY_ERROR`。

具体差异：

1. `GATEWAY_REQUEST` 看到的是客户端入口请求体；这在语义上是“客户端原文”，不是供应商请求。
2. `GATEWAY_RESPONSE` 看到的是最终网关响应：
   - 未开启用量详情时是适配后 JSON 字符串；
   - 开启时是已注入 `knot_extend` 的 Map；
   - 流式时是 `GatewayStreamingResponse`，没有实际 SSE 正文。
3. `GATEWAY_ERROR` 在候选尝试之后执行。`GatewayRequestHandler.java:439-441` 的
   `withTargetModel(...)` 会原地覆盖 `exchange.requestBody()` 的 `model`；
   因此上游阶段失败时，错误日志里的 `requestBody` 可能已经是最后一个候选的上游模型，
   不再是客户端入口原文。

这不是数据面改写，但会让日志消费者按错误字段语义得出错误结论。

### 3.7 异步路径是“部分原文”，不能笼统算正确

保持原文的部分：

- `knot-server/knot-gateway/src/main/java/org/chobit/knot/gateway/async/AsyncTaskQueryPluginDispatcher.java:58-62`
  查询响应日志记录 `responseBody` 原文；
- `AsyncTaskRunner.java:284-290` 落库 `terminal_body` 仍用 `polling.rawBody()`；
- `AsyncTaskViewSupport.java:92-100` 的并列 `rawUsage` 从 `terminal_body` 读取。

失真的部分：

- `knot-server/knot-gateway/src/main/java/org/chobit/knot/gateway/async/AsyncTaskCompletion.java:93-95`
  在调用提取器前执行 `queryBodyForUsage(...)`；
- `:107-118` 会创建顶层 `usage` 覆盖键并重新序列化 body；
- `UsageExtractorRegistry` 随后把这个 body 作为 `rawBody` 存进 `UsageAccounting`。

因此异步侧应区分：

| 证据 | 是否原文 |
|---|---|
| `terminal_body` | 是 |
| `AsyncTaskQueryResponse.upstream_body` | 是 |
| 查询响应插件日志 | 是 |
| 异步 `UsageAccounting.rawBody` | 否，已按 `usage_path` 加工 |
| 异步 `UsageAccounting.rawUsage` | 通常仍来自原 usage 对象，但位置/覆盖关系可能被加工 |

### 3.8 异步查询异常缺结构化上游证据

- `knot-server/knot-gateway/src/main/java/org/chobit/knot/gateway/async/AsyncTaskQueryClient.java:126-128`
  把状态码和错误体拼进 `IllegalStateException` 的 message；
- `UpstreamPluginContextSupport.java:30-51` 只从 `GatewayUpstreamException` 解出
  `httpStatus` 与 `upstreamResponseBody`；
- 因此异步查询失败时，插件日志里 `httpStatus` / `upstreamResponseBody` 仍为 null，
  只能从 `errorMessage` 字符串里人工提取。

### 3.9 文案层面的同类问题

- `ModerationTextExtractor.java:56-59` 仍写“上游原始 JSON 字符串，也可能是已注入 `knot_extend` 的 Map”；
  实际 `GATEWAY_RESPONSE` 阶段拿到的是适配后响应，不是上游原始响应。
- `ModerationEventSink.java:10` 用“请求/响应/错误的原始载荷”概括 `PluginLogWriter`，
  与网关阶段的实际语义不一致。

这些不影响数据面，但会让后续维护者继续用错误的“原始”前提写代码。

## 4. 候选修复方案

### 4.1 优先方案：把“证据”和“提取输入”拆开

核心原则：**计费提取继续吃适配后 body；审计证据必须从 wire body 取。**

非流式：

1. 保留 `ProxyResult.upstreamResponseBody`（已存在）。
2. `UsageExtractorRegistry` 继续用 `handledResponseBody` 做 billing / usage 提取。
3. 在构造 `UsageAccounting` 时，用 `buffered.body()` 重新读取 `rawBody` / `rawUsage` 覆盖证据字段。
4. 保留现有 `billing` / `usage` / `normalized`，不回退计费口径。

流式：

1. 在 `adaptedLines(...)` 之前旁路原始 SSE 行。
2. 原始 usage 的提取按**上游/绑定协议**选规则，不能再按客户端协议选提取器。
3. 原始事件与适配事件分别累计：
   - 适配事件 → billing / usage / `knot_extend`；
   - 原始事件 → `rawUsage` / `rawBody` / 对账证据。
4. 若暂时无法实现原始流式提取，至少不要把适配后 usage 继续标成“上游原文”，
   并显式输出“流式原始 usage 不可用”的证据状态。

### 4.2 同步非流式的并列 usage 需要先解决键冲突

可选方案：

- 方案 A：新增真正独立的 `upstream_usage` 键，保留响应体里的 `usage` 为客户端适配口径。
- 方案 B：不新增并列键，明确“客户端响应里的 usage 就是适配后 usage”，
  同时删除“并列 usage 等于上游原文”的契约表述。

不能继续假设 `RAW_USAGE = "usage"` 在跨协议时与响应自带 usage 同值。

### 4.3 日志 payload 校准

- `GatewayRequestPayload`：改成“客户端入口请求体，路由前快照”。
- `GatewayResponsePayload`：改成“网关最终响应投影，可能含 `knot_extend`；流式无正文”。
- `GatewayErrorPayload`：改成“终态错误时的请求体快照”；若需客户端入口原文，
  在 `GatewayExchange` 中另存一份不可变入口快照。
- `PluginLogPayload`：删除“原始 JSON”总称，按 payload 分别说明来源。

### 4.4 异步计费证据

- 给 `UsageExtractorRegistry` 增加显式的 `evidenceBody` 参数，或增加
  `UsageAccounting.withEvidence(rawUsage, rawBody)`。
- `AsyncTaskCompletion.charge(...)` 继续用 `queryBodyForUsage(...)` 给提取器，
  但 `rawBody` 使用调用方传入的 `polling.rawBody()` 原文。
- 异步查询失败改用可结构化解析的异常类型，或直接把 status / body 作为上下文参数传给插件。

## 6. 建议处理顺序

1. 先修 `UsageAccounting.rawUsage` / `rawBody`，因为影响 Kafka、数仓、计费裁判，已经超出日志范畴。
2. 再定同步非流式并列 usage 的字段契约，解决 `"usage"` 键冲突。
3. 再处理流式原始 usage；这一项需要上游协议感知的提取路径。
4. 最后校准网关日志文案、异步 rawBody 和异步查询异常结构化。
