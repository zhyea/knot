# 上游 curl 命令技术方案

> 2026-10-22 · robin 拍板三项：**网关实况复现**语义 / 挂载**路由测试抽屉「上游」tab** / SigV4 走**结构占位 + awscurl 提示**

## 1. 背景与语义

管理台路由测试抽屉（`RoutingRuleTestDrawer.vue`）现有「curl」tab 展示的是**调网关自身**的命令（gatewayBaseUrl + `Rule` 头 + 消费者密钥，`RoutingRuleService.buildTestCurl` 生成）。缺的是**上游视角**：网关实际转发给供应商的请求长什么样。

本方案交付的「上游 curl」= **网关实况复现**：按真实链路相同的顺序（适配器解析 URL → 鉴权策略拼头 → 请求体经协议适配器转换）渲染一条等价 curl，用于：

- 测试失败时隔离「网关问题 vs 上游问题」（直连上游复跑同一条请求）
- 观察协议适配器对请求体做了什么（如 MESSAGES → chat completions 字段搬家、Bedrock Converse 转换）
- 新供应商接入时验证凭据与端点

明确**不做**：请求执行期埋点捕获真实发出的字节（理由见 §6 风险 R1）。

## 3. 总体设计

### 3.1 生成位置：service 层，复用 adapter catalog

在 `prepareTestInvocation`（同步/流式共用的准备步骤）内扩展：构造 `UpstreamRequestContext` → 按真实链路相同顺序渲染 curl → 随 `RoutingTestPreparation` / `RoutingTestResult` 下发。**不新增端点、不动网关热路径、零权限绑定改动**（与 AWS 方案 D9 同思路）。

渲染顺序严格对齐 `AbstractUpstreamProtocolExecutor`：

```
1. adapter = requestAdapterCatalog.resolve(binding.requestAdapter 或 OPENAI_COMPATIBLE)
2. path    = adapter.resolvePath(context, protocol.defaultPath())
3. baseUrl = adapter.resolveBaseUrl(context)          // model.baseUrl 优先，AWS 推导兜底
4. headers = new HttpHeaders()
             authApplierCatalog.resolve(account.authApplier).apply(headers, context)
             headers.setContentType(adapter.resolveContentType(context))
5. body    = adapter.buildRequestBody(context)        // 协议转换后的真实请求体
6. curl    = 拼装（JSON → -d；multipart → -F，复用 buildMultipartCurl 既有写法）
```

### 3.2 新组件：`RoutingUpstreamCurlSupport`

落 `service.support` 子包（遵循 10-backend-java §4：support 后缀 + routing 域前缀）。职责只有「把 context 渲染成 curl 字符串」；注入 `RequestAdapterCatalog` + `UpstreamAuthApplierCatalog`（两个 catalog 均已在 adapter 模块且 service 已依赖）。

`RoutingRuleService.buildTestCurl` 保持不动（网关 curl 与上游 curl 两个关注点，分别收口）。

### 3.4 SigV4 占位形态（robin 拍板：结构占位 + awscurl 提示）

SigV4 签名含时间戳、每次不同，无法预生成。策略分支：

- **静态头策略**（BEARER / ANTHROPIC_API_KEY / NO_AUTH）：真实凭据入 curl（与既有网关 curl 带 consumer secretKey 明文的先例一致，见 R2）
- **AWS_SIGV4**：Authorization / X-Amz-Date / X-Amz-Security-Token 三头用占位符，URL 用真实推导端点（`AwsBedrockEndpointResolver` 同款逻辑），并附 awscurl 等价命令提示：

```bash
# knot 占位版（签名头需本地签署）
curl -X POST 'https://bedrock-runtime.us-east-1.amazonaws.com/model/<upstream_model>/converse' \
  -H 'Authorization: AWS4-HMAC-SHA256 Credential=<AK_ID>/<DATE>/us-east-1/bedrock/aws4_request, SignedHeaders=host;x-amz-date, Signature=<SIGNATURE>' \
  -H 'X-Amz-Date: <YYYYMMDDTHHMMSSZ>' \
  -H 'Content-Type: application/json' \
  -d '{...转换后的 converse 请求体...}'

# 或直接用 awscurl（推荐）
awscurl --service bedrock --region us-east-1 -X POST \
  'https://bedrock-runtime.us-east-1.amazonaws.com/model/<upstream_model>/converse' \
  -d '{...}'
```

Access Key ID 一并占位（`<AK_ID>`）：authConfig 整体加密存储，保守起见不向 curl 里泄任何凭据组分。

## 4. 挂载点交互（路由测试抽屉）

现有 tab 结构：请求预览（preset/headers/curl）× 响应（summary/body/stream）。

- 新增 tab「上游」，与「curl」tab 并列，位置在 curl 之后
- 内容 = `displayUpstreamCurl`（测试后回填；测试前空态「执行测试后生成」——协议转换在前端无知识，不做本地预览）
- 复用 `ShellCodeBlock.vue`（language="bash"），零新组件
- tab 文案明示：**含上游密钥，仅管理员可见，勿外传**

「网关」tab（现有 curl）行为不变：测试前本地实时预览、测试后回填服务端值。

## 6. 风险与红线

| # | 风险 | 对策 |
|---|---|---|
| R1 | 执行期捕获真实字节（含真实签名）需改网关热路径 + 跨模块传参，且签名头回传即泄露 AK/SK | 不做。准备期复现 + SigV4 占位已覆盖 robin 选定语义 |
| R2 | 静态头策略 curl 含上游 apiKey 明文 | 仅 admin 会话可见（测试抽屉本身已要求权限）；tab 文案明示；**不进任何日志**（secretKey 既有注释口径：仅用于转发与 curl 展示） |
| R3 | 「实况」打折扣：body 是准备期转换而非真实发出字节 | 转换函数与真实链路同一份（`adapter.buildRequestBody`），差异仅在签名与 traceparent；traceparent 用占位 `00-<trace_id>-01` 风格 |
| R4 | AWS 端点推导与真实链路分叉 | 直接调 `adapter.resolveBaseUrl(context)`，与 executor L86 同入口，零分叉 |
| R5 | IMAGE_EDITS 的 `-F` 里 `@文件路径` 是服务端本地路径，用户机器上不一定存在 | 沿用 `buildMultipartCurl` 既有行为（`new File(text).exists()` 判断），加注释说明 |
