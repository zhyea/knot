# 插件元数据单一来源重构（2026-10-25）

> 起因：robin 追问「`instance_code` 双口径是什么意思」→「如果没有历史包袱，这个问题怎么处理更好」→「执行修复」。
> 前置批次：`docs/包结构迁移修复-2026-10-25.md`（本批修的是它暴露出的第二层问题）。

## 0. 结论

`kb_plugin_instances` 重新定位为 **「`PluginDescriptor` 的物化 + 运维开关」**：

- 派生列（code / name / capability / extension / stage / orderNo / timeout / version / pluginType）**每次启动全覆盖写**；
- 运维列（`status` / `is_deleted`）**永不覆盖**；
- `data.sql` 不再预置插件种子；`deriveInstanceCode` / `firstSegment` 两条启发式删除。

修复后「DB 里存着需要人工迁移的 FQCN」这整类风险消失——上一批写的那份 entrypoint 迁移脚本对新库不再必需（只对已被污染的既有库有意义）。

门禁：后端 **1047 例 0 失败**，前端 `vue-tsc` 双通道通过，另加三个定向探针（详见 §5）。

## 1. 问题不在命名，在权威边界

原设计里同一个字段有两条赋值路径：

| 路径 | 来源 | 产出 |
|---|---|---|
| 种子行 | `db/data.sql` 手写 8 条 `INSERT IGNORE` + 显式 id | 人类可读短码（`gateway-request-log`） |
| 启动补建 | `PluginReconcileRunner.deriveInstanceCode()` 拼 `capability-extension-stage` | 机器长码（`provider-request-response-log-upstream_exchange-upstream_response`，65 字符） |

同一个插件叫什么**取决于它是被预置的还是被补建的**。再叠加「`data.sql` 改值对既有库无效（主键冲突静默跳过）」，就出现了上一批那个 P0：换包名 → 旧 entrypoint 匹配不上 → 全判孤儿 + 重复插入 + 派生码超列宽打挂启动。

根因是这张表**同时想当两样东西**，却没有失效机制。所以修法不是把派生名改好看，而是把边界划死。

同一段代码里还有四个字段同病（`instance_name` 拼 `SYNC:capability:stage`、`plugin_code` 取能力码首段拼 `builtin-xxx` 且丢掉 `-audit` 后缀、`plugin_name` 直接抄能力码、`capability_name` 抄能力码），全部随 `deriveInstanceCode` 一起删除。

## 2. 方案

### 2.1 `PluginDescriptor` 成为插件元数据唯一来源

```java
public record PluginDescriptor(String code,               // "gateway-request-log"
                               String name,               // "网关请求日志插件"
                               String capabilityCode,     // "gateway-request-response-log"（能力族，可共享）
                               PluginExtensionPoint extensionPoint,
                               PluginStageCode stageCode,
                               int orderNo) {}            // 100 审计 / 200 敏感词
```

- 元数据本来就是编译期已知的，让类自己声明，比运行期反推可靠。
- `capabilityCode` 保留：它是**能力族**（一族的请求/响应/异常三态各是一个实例），分发器按「能力码 + 扩展点 + 阶段 + 上下文类型」四要素匹配，不能用实例级 `code` 替代。
- `orderNo` 进描述符：它表达执行语义（审计必须先落、敏感词必须后判），不是运维可调配置。原先写死在 data.sql 的 100/200 靠注释解释。

### 2.2 reconcile 从「只插不更」改「幂等 upsert」

```sql
insert into kb_plugin_instances (... ) values (..., 1, 0, 0)
on duplicate key update
  instance_code = values(instance_code), instance_name = values(instance_name),
  version = ..., capability_code = ..., extension_point = ..., stage_code = ...,
  order_no = ..., timeout_ms = ..., plugin_type = ...,
  orphaned = 0
  -- 故意不出现 status / is_deleted
```

以 `entrypoint` 为稳定键。update 段只列派生列，`status` / `is_deleted` 一个都不出现——**用户停用过的插件不能被重启重新打开**。

### 2.3 `entrypoint` 加唯一键

原来它不仅没有唯一键，连普通索引都没有；reconcile 靠 `listAll()` 全表拉进内存匹配，upsert 无从谈起。新增 `uk_plugin_instances_entrypoint`（`VARCHAR(255)` utf8mb4 = 1020B < InnoDB 3072B 上限）。

### 2.4 写库前校验三项

`code` 非空 / 全局唯一 / 不超列宽（64）。这三类错误原先只能等 MySQL 在插入时报出来（判例：65 > 64 直接 `DataTruncation` 打挂上下文）。现在启动第二秒指名报错，报错信息带 entrypoint。

选 upsert 而非「先 UPDATE 再 INSERT 若 0 行」的另一个理由：admin 与 gateway **两个 app 都会跑这个 runner**，并发启动时 upsert 是 DB 级原子操作，两段式会撞唯一键。

## 3. 删除清单（附零引用证据）

| 删除项 | 证据 | 理由 |
|---|---|---|
| 列 `plugin_code` / `plugin_name` | 后端仅 `PluginService.toBindingView` 透传进 `PluginBindingView`，而该 record 的这两个字段**无人读取**；前端 grep 零命中 | 「插件包」分组概念在 2026-10-13 单表收口后已压成「能力族 → 实例」两级 |
| 列 `capability_name` | 仅 Entity / Dto / 测试引用，无读取方；种子值还是能力码的中文副本 | 冗余副本 |
| 列 `source_type` | 仅 Entity / 测试；schema 注释已写「动态 jar 插件确认不支持」 | 死概念 |
| 列 `config_json` | 仅 Dto / Item 声明，从未写入也从未读取（`toBindingView` 注释已写明「配置改由 Nacos 下发」） | 不为将来预留 |
| 列 `concurrency_limit` | 代码零引用，仅 insert 里写死 0 | 死列 |
| 索引 `idx_plugin_instances_package_status` | 依赖被删列 | — |
| 索引 `idx_plugin_instances_capability_status` | 无任何查询用它（`list` 的关键词过滤是 `like '%x%'`，走不了索引） | 死索引 |
| `PluginReconcileRunner.deriveInstanceCode` | 唯一调用点即自身 | 启发式反推，产出必然与手写值不等价 |
| `PluginReconcileRunner.firstSegment` | 同上 | 同上 |
| `PluginPackageStatusEnum` | 只被 `NumericStatusEnumContractTest` 枚举清单引用；类注释指向已 DROP 的 `kb_plugin_packages.status` | 表已不存在 |
| `data.sql` 插件种子段（40 行） | — | 单一来源后无需预置，且种子+`INSERT IGNORE` 正是 entrypoint 漂移的根源 |

保留：`timeout_ms`（分发器尚未读取，但有在办事项「3.1 插件超时」，属于真实待落地设计，非「将来」预留）；`version`（前端列表展示，由 reconcile 写统一常量）。

### 定向探针（`@SpringBootTest` 真启 + 真库查表）

全量套件只覆盖了 upsert 的 **UPDATE** 分支（库里 8 行一直在），所以补了三个探针：

| # | 探针 | 期望 | 实测 |
|---|---|---|---|
| 1 | **插入分支**：清空 `kb_plugin_instances` 后启上下文 | 自动补出 8 行，code/name/orderNo 全对 | ✅ 8 行，`gateway-request-log` 等码正确、名称 8/9 字符、orderNo 100/200 |
| 2 | **幂等**：再启一次 | 行数仍 8，不产生重复 | ✅ rows_total = 8 |
| 3 | **边界双向**：手工把某行 `status` 改 0、`instance_name` 改成「运营商改过的名字」，再启上下文 | `status` 保持 0（运维权威不被覆盖）+ `instance_name` 被改回描述符值（代码权威每次重写） | ✅ status=0 保留；`instance_name` HEX 还原为「网关请求日志插件」 |

探针 3 是关键——它同时证明「代码权威会覆盖」和「运维权威不会覆盖」，只测一边等于没测。

## 6. 既有库升级顺序

**先跑 `docs/database/migration/2026-10-25-plugin-entrypoint-package-migration.sql`，再启新 jar。**
