# knot 性能瓶颈与潜在 Bug 审查

- **审查日期**：2026-09-18
- **审查范围**：`knot-server` 网关请求热路径（转发 / 路由解析 / 限流 / 凭证加解密 / 外部模型同步）
- **审查方法**：逐文件静态走读核心热路径 + 全局模式扫描（HTTP 客户端 / 并发 / 缓存 / 正则 / ObjectMapper）
- **说明**：本文只覆盖「性能瓶颈」与「潜在 Bug」两个维度，安全与规范问题参见 `docs/审计报告-2026-09-16.md`，不重复罗列。所有结论均附 `文件:行号`，可逐条复核。

---

## 总体判断

> **代码骨架干净（SQL 零注入、分层清晰、Caffeine 缓存已就位），但「网关转发这条最关键的热路径」存在三处系统性性能缺陷：且限流/配额有一处隐蔽的「桩实现」会让人误以为配额生效。** 这几点不修，网关无法承受生产级流量。

## 一、性能瓶颈

### 🔴 P0 — 阻断级（不修无法上量）

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| 1 | **流式 SSE 被强制缓冲** | `knot-gateway/.../upstream/protocol/AbstractUpstreamProtocolExecutor.java:57-59`：`.retrieve().body(String.class)` 把整个上游响应（含 `text/event-stream`）读进一个 `String` 再返回；`accept(JSON, TEXT_EVENT_STREAM)` 声明了流式却没实现流式转发 | `stream:true` 的 chat 请求被变成「等上游全生成完才返回」，首 token 延迟优势归零；整段响应驻留内存（并发下 GC 压力大）；servlet 线程被占用整个生成周期 |
| 2 | **RestClient 无连接池** | `knot-gateway/.../GatewayApplication.java:25-28`：`public RestClient restClient(RestClient.Builder builder){ return builder.build(); }` 未指定 `ClientHttpRequestFactory`，默认走 `SimpleClientHttpRequestFactory`（JDK `HttpURLConnection`），**每次请求新建 TCP+TLS 连接，不复用** | 跨公网 TLS 握手 50~200ms/请求，高频网关吞吐被握手开销主导，连接数无法收敛 |
| 3 | **RestClient 无超时** | 同上 Bean 未设 `connectTimeout` / `readTimeout`，默认 `-1`（无限） | 上游挂起 → worker 线程永久阻塞 → 线程池耗尽 → **网关雪崩**；这是生产最危险的单点 |

**修复方向（同一次改动即可覆盖 #1/#2/#3）**：
- 将 `restClient` Bean 改为带池化的实现，例如：
  ```java
  @Bean RestClient restClient(RestClient.Builder b){
      return b.requestFactory(new HttpComponentsClientHttpRequestFactory(
          PoolingHttpClientConnectionManagerBuilder.create()
              .setMaxConnTotal(400).setMaxConnPerRoute(100).build()))
          .build();
  }
  ```
- 超时：connect 3~5s；非流式 read 设有限值；流式 read 走独立长超时或不设。
- 流式转发改用 `ResponseSpec.exchangeToFlux(...)` / 零拷贝将上游字节流直接写入 `HttpServletResponse` 输出流，真正实现边收边发。

### 🟡 P1 — 重要

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| 4 | **同步阻塞转发 + 无异步** | `knot-gateway/.../controller/GatewayTextController.java:26-33` 是同步 `@PostMapping`，`handleRequest` 同步返回；`@EnableAsync` 未用于网关转发 | 每个请求占一个 Tomcat 线程直到上游返回（可能数十秒）；Tomcat 默认 200 线程，并发长请求超限即拒绝。应与 #1/#2/#3 一起改为异步/响应式 |
| 5 | **路由解析 N+1（冷路径）** | `knot-gateway/.../routing/RoutingResolver.java:193-199`：`resolvePoolCandidates` 在 `.filter()` 中对每个 pool item 调用 `dataService.getModelById(item.getModelId())` | 热路径被 `GatewayDataService` 的 Caffeine 兜底，但 3min refresh / 10min expire 时，一个含 N 个 item 的 model pool 会瞬时触发 N 次 DB 查询。建议改为批量 `listModelsByIds(ids)` 一次查回 |
| 6 | **Caffeine 无容量上限 + 缓存空值（穿透）** | `knot-gateway/.../service/GatewayDataService.java:233-237`：`builder()` 只配 `expireAfterWrite`/`refreshAfterWrite`，**无 `maximumSize`**；`optionalCache`（222-224）缓存 `Optional.ofNullable(loader.apply(key))`，**把查不到的结果也缓存 10min** | ① 不同 id 的缓存条目只按时间过期、无容量上界，内存随 key 基数增长；② **缓存穿透**：攻击者用大量不同的不存在 id 打请求，每个 key 都是新 miss → 每次都查 DB → DoS 向量；③ 资源删除后空条目仍占内存直到过期 |

**修复方向（#6）**：
- 所有 `builder()` 增加 `.maximumSize(...)`（如 5000）；
- 空值缓存改用短 TTL（`expireAfterWrite(1m)`）或布隆过滤；
- 考虑 `expireAfterAccess` 让冷 key 优先淘汰。

## 二、潜在 Bug

### 🟡 功能 / 正确性

| # | 问题 | 证据 | 危害 |
|---|---|---|---|
| 7 | **配额检查是桩，永不拦截** | `knot-gateway/.../traffic/GatewayTrafficGuard.java:78-84`：`checkQuota(...)` 直接 `return true` | `quota_policies` 表配置后**完全不生效**，运维以为配额已开实则形同虚设。这是隐蔽的功能性 Bug（审计报告从「桩实现」角度提过，但未点出「配额失效」这一具体后果） |
| 8 | **限流是单 JVM 内存计数** | `GatewayTrafficGuard.java:26`：`rateCounters` 是进程内 `ConcurrentHashMap` | 多实例部署时每个节点各自计数，整体限流形同虚设；横向扩容反而放大超限风险 |
| 9 | **固定窗口 2× 突发** | `GatewayTrafficGuard.java:106-121`：`WindowCounter` 按 `currentTimeMillis()/windowMillis` 切窗，窗口切换即归零 | 在窗口边界（如 0.9s 与 1.1s 各来满额）可在极短时间内通过约 2× limit，无法平滑限流 |
| 10 | **rateCounters 永不清理** | 同上，`ConcurrentHashMap` 无 evict | 资源（model/provider/app/consumer）被删除后，对应计数 entry 永久残留（上界受资源数约束，属慢泄漏） |
| 11 | **请求 `stream` 字段被完全忽略** | `AbstractUpstreamProtocolExecutor.java:57-59` 不读取请求体的 `stream` 字段，一律缓冲返回 String | 客户端请求 `stream:true` 实际收到一次性完整响应（甚至可能被错误解析为 SSE 文本串）；既破坏流式契约，也可能导致 usage/格式解析出错 |

### 💭 nit / 次要

| # | 问题 | 证据 | 说明 |
|---|---|---|---|
| 12 | **`SecureRandom.getInstanceStrong()` 可能阻塞** | `knot-common/.../crypto/AesGcmCipher.java:70`：加密时取强随机 IV | Linux 熵不足时 `/dev/random` 会 stall；影响「凭证保存」路径（管理端批量保存）。建议改为 `new SecureRandom()`（12 字节随机 IV 的碰撞概率可忽略，GCM 安全性足够）。注：`decrypt` 不取随机，网关热路径不受影响 |
| 13 | **缓存 loader 内嵌入 `LocalDateTime.now()`** | `GatewayDataService.java:96-97`：`activeBillingRuleByIdCache` 的 loader 用 `billingRuleMapper.getActiveByRuleId(ruleId, LocalDateTime.now())`，key 仅为 `ruleId` | 同一 ruleId 在 10min 缓存期内，「是否生效中」始终基于缓存加载时刻的 now 判断，配置变更最多延迟 10min 生效（与整体缓存一致，但此处语义更易踩坑） |
| 14 | **`JsonKit.mapper()` 每次返回 copy** | `knot-common/.../util/JsonKit.java:64-66`：`return mapper.copy();` | `ObjectMapper` 本身线程安全、应全局复用单例；每次 copy 产生新实例 + 新内部缓存，属不必要分配。`toJson/fromJson/parse` 等静态方法复用单例无碍，仅 `mapper()` 这一处浪费 |
| 15 | **方法内 `Pattern.compile`** | `knot-service/.../service/ExternalModelService.java:238-239`：循环/每次调用都重新编译正则 | 经典反模式；但该路径是后台模型同步（低频），影响有限。`GatewayTraceContext.java:13` 已正确用 `static final Pattern`，可参照改为常量 |

## 三、修复优先级（按 ROI）

1. **🔴 网关转发三连（#1/#2/#3/#4）** —— 一次改 `GatewayApplication.restClient` Bean + 流式转发实现即可，是「能不能上生产」的门槛。
2. **🟡 配额/限流收口（#7/#8/#9）** —— `checkQuota` 至少先接上逻辑；多实例场景引入 Redis 令牌桶或明确「单实例部署」约束。
3. **🟡 缓存加固（#6）** —— `maximumSize` + 空值短 TTL，防穿透与内存增长。
4. **🟡 路由 N+1（#5）** —— 批量 `listModelsByIds`。
5. **💭 次要清理（#11/#12/#13/#14/#15）** —— 随相关模块迭代顺手修。
