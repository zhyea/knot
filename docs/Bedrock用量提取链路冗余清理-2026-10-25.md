# Bedrock 用量提取链路冗余清理 — 2026-10-25

## 结论

`BedrockConverseUsageSupport` 与 `BedrockConverseUsageExtractor` 整体删除，Bedrock Converse 的用量口径收敛为「请求适配器响应转换一次决策 + DEFAULT-TOKEN 提取器读取转换产物」。robin 提出质疑（两方法分属不同领域、usage 转换后无需专用提取器），核查后两个观点全部成立，且实际情况更彻底：专用提取器依赖的 camelCase 解析分支在生产链路不可达。

## 证据链

整包路径的调用顺序（`AbstractUpstreamProtocolExecutor.java:158-163`）：

```
上游 Converse 原始响应（usage = camelCase）
  → adapter.handleResponse()                    ← usage 经 toOpenAiUsage 转成 OpenAI snake_case
  → usageExtractorRegistry.extract(handledBody) ← 提取器拿到的是【已 OpenAI 化的 body】
```

1. **camelCase 主分支不可达**：`BedrockConverseUsageSupport.fromResponse` 的 camelCase 解析只在上游原始响应上有效，而提取器的输入恒为 `handleResponse` 产物。流式路径亦不可达（`streamSupported()=false`，永远走整包）。影子链同样不可达：`RoutingTestBillingVerdictService.java:87` 喂给提取器的是 `{"usage": upstreamUsage}`，upstreamUsage 来自前端上报的 knotExtend.usage，也是网关处理后的 OpenAI 形状。
2. **回落分支与 DEFAULT-TOKEN 逐字同构**：回落即 `TokenBillingUsage.fromResponse(body)`，与 `DefaultTokenUsageExtractor.extractUsage` 完全同构；`TokenBillingUsage.from` 的别名表（`TokenBillingUsage.java:60-72`）本就收 `cache_read_input_tokens` / `cache_write_input_tokens`，即 `toOpenAiUsage` 的产出形状。
3. **Support 类「两处口径收口」注释是伪命题**：`toOpenAiUsage` 吃 Converse 原生响应（适配器域），`fromResponse` 吃转换后的响应（计费域），两个方法从不在同一份数据上工作，无处漂移可防。

1. **R2 语义决策挂错位置**：原 `fromResponse` 注释「inputTokens 是否已含缓存，待实测」在生产链路永不生效，真实决策点早在 `toOpenAiUsage`。现 R2 说明随内联搬到适配器类注释与规范 §8.3，位置与生效路径一致。
