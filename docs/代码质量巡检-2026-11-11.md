## 4. 🟡 运行时高风险

### 🟡-1 请求可控键进入无容量上限缓存

**证据**

- `GatewayConfigCacheService.java:63` 起的多个 `LoadingCache` 未设置容量上限。
- 同一类 `:300` 的统一构造器只有 `expireAfterWrite` / `refreshAfterWrite`；只有计费规则缓存单独设置了 `maximumSize`。
- `RoutingSecretKeyGenerator.java:25` 对 secret key 只校验 `sk-` 前缀和非空。
- `RoutingResolver.java:138` 会为任意符合该弱格式的 key 查询消费者，并缓存空结果。
- `RoutingResolver.java:145` 还会为合法消费者下任意 `Rule` header 查询并缓存未命中结果。

**影响**

攻击者可用大量不同的 `sk-*` 值和规则 code 制造缓存条目，导致堆内存持续增长，并把缓存未命中转化为数据库查询放大。TTL 只限制单条存活时间，不限制 TTL 窗口内的基数。

**修复建议**

1. 所有请求可控缓存设置 `maximumSize` 或 `maximumWeight`。
2. secret key 按生成格式校验固定长度与字符集，拒绝任意 `sk-任意后缀`。
3. 评估是否缓存鉴权失败；如需防穿透，应使用单独的、有界的短 TTL 负缓存。

### 🟡-2 候选成功后异常会泄漏在途计数

**证据**

- `GatewayRequestHandler.java:301` 在候选开始前调用 `modelLoadStore.enter(loadKey)`。
- `GatewayRequestHandler.java:320` 在上游成功后调用 `trafficGuard.record(...)`。
- `GatewayRequestHandler.java:345` 只捕获 `GatewayUpstreamException`。
- `GatewayRequestHandler.java:361` 与 `:369` 才包含常规定时释放路径。
- `RedisCache.java:84` 会把 Redis 运行时错误包装为 `RedisUnavailableException`。

`trafficGuard.record`、`outageTracker.recordSuccess`、写响应头或指标代码如果抛出非 `GatewayUpstreamException`，所有 `leave` 路径都会被绕过。流式路径虽然由 `ProxyStreamingFlux` 的 `doFinally` 负责最终释放，但那只发生在候选成功并建立流响应之后；候选成功前抛异常仍会泄漏。

**影响**

`LEAST_LOAD` 依赖在途计数。计数只增不减会让后续选模持续偏向错误目标，且故障恢复后仍可能残留脏负载，表现为长期路由偏斜。

**修复建议**

把“enter 后的 release”收口到单个 `doFinally` 或资源作用域，并保证释放幂等。增加一条测试：让 `trafficGuard.record` 抛出 `RedisUnavailableException`，断言候选链结束后在途计数归零。

### 🟡-3 admin 全局异常泄露内部异常原文

**证据**

- `GlobalExceptionHandler.java:134` 返回 `"系统内部错误: " + e.getMessage()`。

**影响**

SQL、表名、类名、序列化异常或配置片段可能直接暴露给管理端调用方。即使需要登录，也不应把内部异常文本当作对外响应。

**修复建议**

对外返回稳定通用文案与关联 ID；异常详情只进日志，并按关联 ID 支持排查。若已有统一错误码体系，应优先复用。

### 🟡-4 默认 `local` profile 削弱启动安全守卫

**证据**

- `knot-admin/src/main/resources/application.yml:8` 默认激活 `local`。
- `knot-gateway/src/main/resources/application.yml:8` 默认激活 `local`。
- `BootstrapSecurityGuard.java:27` 把 `local` 列为非生产 profile。
- `SqlInitModeGuard.java:29` 同样把 `local` 视为非生产。
- `application-local.yml:8` 提供默认数据库账号口令。
- `application-local.yml:12` 默认 `KNOT_SQL_INIT_MODE=ALWAYS`。
- `application-local.yml:22` 提供开发默认凭证加密密钥。
- `data.sql:23` 提供 `admin/admin123` 种子。

**影响**

这是**条件性阻断**：如果部署侧严格强制 `SPRING_PROFILES_ACTIVE=prod`，风险可被外部配置压住；但仓库默认行为不是 fail-closed。一旦漏设 profile，应用就可能按 local 启动、使用默认密钥、执行 schema/data，并保留默认管理员凭据。生产部署是否强制注入 `prod` 本轮未验证。

**修复建议**

从打包配置移除默认 `active: local`，改由显式运行参数启用本地 profile；启动守卫应以“未显式声明非生产”为拒绝条件，而不是只要 active profiles 中出现 local 就放行。生产侧同时强制 `KNOT_SQL_INIT_MODE=NEVER`。

### 🟡-5 Redis 计数的 fail-hard 契约与实现不一致

**证据**

- `RedisTrafficCounterStore.java:18` 类注释声明 fail-hard。
- 同文件 `:56` 在 Lua 返回 `null` 时静默返回 `delta`。
- 同文件 `:68` 对非数字脏数据返回 0。
- `RedisModelLoadStore.java:76` 与 `:82` 对 `null` 返回 0。
- `RedisCache.java:84` 已保证 Redis 连接类故障本身会上抛，问题集中在“脚本返回 null / 脏值”的语义兜底。

**影响**

频率或额度可能少计，且没有错误日志或指标；这与类注释“宁可全拒并报警”冲突。多节点下会表现为限额被静默放宽。

**修复建议**

明确区分“键不存在”和“脚本/序列化异常”。正常缺失可返回 0；异常 `null` 和脏值应上抛或至少产生显式错误指标与高等级日志，不能按成功增量或零用量继续。

### 🟡-6 未预期异常被统计成 `upstream_error`

**证据**

- `GatewayErrorDescriptor.java:96` 把所有未识别异常映射为 `UPSTREAM_ERROR`。
- `GatewayErrorTypeEnum.java:3` 没有 `INTERNAL_ERROR` 类型。
- `GatewayErrorDescriptorTest.java:131` 用测试钉住了这个行为。

**影响**

网关自身缺陷、空指针、序列化错误等会被数仓统计为上游失败，导致告警指向错误方向，上游健康度与网关缺陷无法分离。

**修复建议**

新增内部错误类型并同步响应、数仓消息和测试口径。修改测试不是“改绿”，而是修正错误的契约。

### 🟡-7 流式单行上限可被大 chunk 绕过

**证据**

- `ProxyStreamingFlux.java:216` 只在当前 chunk 完全没有换行时检查 `MAX_LINE_BYTES`。
- 同文件 `:225` 对有换行的大块直接构造完整字符串。
- 同文件 `:226` 再对整块执行 `split`。

如果单个 chunk 含换行且整体超过 1MB，长度保护不生效，仍会构造大字符串和大量行对象。正常 SSE 不应出现此形态，但畸形上游或异常代理可能触发。

**修复建议**

对每个完整行和残留 tail 都做长度检查；优先使用增量扫描，避免先构造超大完整字符串再拆分。补充“含换行但总长度超限”的测试。

### 🟡-8 Caffeine 自动刷新未指定专用执行器

**证据**

- `GatewayConfigCacheService.java:303` 配置 `refreshAfterWrite` 但没有指定 executor。
- `ModerationWordResource.java:59` 同样未指定 executor。
- 回源分别会触发 MyBatis/JDBC 查询。
- 项目的阻塞段专用调度器在 `GatewayAsyncConfiguration.java:30` 配置。

**影响**

Caffeine 默认刷新执行器是公共执行器。阻塞 JDBC 在公共池上执行，会与普通计算任务争抢线程；在数据库抖动时可能放大全局阻塞。其行为不符合项目已有的“阻塞段离开事件循环并使用专用池”口径。

**修复建议**

为缓存刷新显式指定独立、有界、可监控的执行器，并明确拒绝策略。不要直接复用 Netty event loop；也不应无限排队。

### 🟡-9 fail-open 与记账失败缺少真正监控出口

**证据**

- `ModerationWordResource.java:93`、`:98`、`:103` 的 fail-open 状态只有 getter。
- `GatewayRequestHandler.java:625` 的 `usageRecordFailures()` 只有定义与测试读取。
- `GatewayMetrics.java:24` 起只有频控拒绝、上游失败、failover、摘除跳过和代理延迟指标。

**影响**

敏感词资源不可用时系统按设计 fail-open，但监控系统只能靠日志检索；流式记账失败导致配额被绕过时同样没有 Prometheus 指标。这与项目对“高风险决策必须可观测”的要求不符。

**修复建议**

注册 Gauge/Counter，至少暴露 fail-open 次数、持续时间、最后成功版本、流式记账失败次数，并接入现有告警面板。日志保留，但不应作为唯一观测手段。

## 5. 🟡 架构与可维护性

### 🟡-1 Controller 薄守门存在覆盖盲区

**证据**

- `ControllerThinGuardTest.java:24` 说明守门只覆盖 `JsonKit`、`new LinkedHashMap`、`switch` 三类。
- 同文件 `:41` 是三条正则规则。
- `UserController.java:71` 与 `:114` 在 controller 内手工拼装 12 字段 DTO，并填多个 null。
- `AppController.java:45` 在 controller 内补默认分页。
- `ControllerThinGuardTest.java:57` 仍登记 `RoutingRuleController`、`DepartmentController` 两个存量违规。
- `OutageAdminController.java:43` 位于 `outage/admin`，不在薄 Controller 扫描目录内。

**判断**

手工 DTO 转换和默认分页不一定是严重业务越界，但说明“转换、参数归一、归属处理”仍能穿透现有守门。守门通过只能证明三类模式没有新增，不能证明 Controller 已经全部变薄。

**建议**

优先把 `UserController` 的手工 DTO 拼装移入 converter；把查询默认值归一移入对应 service 参数对象。再扩充守门的扫描范围或规则，至少覆盖“controller 内 new DTO / 多 null 构造 / 目录外控制器”。

### 🟡-2 前端 API 类型约束偏弱，测试代码被类型检查排除

**证据**

- `knot-front/tsconfig.json:43` 排除 `**/*.test.ts` 与 `**/*.spec.ts`。
- `knot-front/src/api/http.ts:116` 起的请求函数默认 `T = any`。
- `knot-front/src/types/index.ts:10` 的 `PageResult<T = any>` 默认弱类型。
- `knot-front/src/types/index.ts:152` 仍保留 `Record<string, any>`。
- 测试中存在 `StatusTag.test.ts:27` 这类 `as unknown as boolean` 强断言。

**影响**

生产代码的弱泛型会掩盖响应结构错误；测试代码不进入类型检查，使 mock 和强断言可以在 CI 下长期积累。Vitest 只证明运行时路径通过，不证明类型契约正确。

**建议**

先在高风险域（权限、路由、计费、状态切换）使用显式响应泛型；再增加独立测试 tsconfig 或在 CI 单独检查测试目录。不建议一次性全仓消灭 `any`，但应守住新增 API。
