## 2. 系统性隐患（本轮最高价值发现）

### S1 · `JsonKit.toJson` 失败静默返 `null`，46 个生产调用点无统一防护

- 语义定义：`knot-common/.../util/JsonKit.java:77-86` —— `catch (Exception)` → `log.error` → **`return null`**，不抛。
- 团队已吃过一次亏并只修了一处：`AsyncTaskRunner.java:444-447` 注释明写「空账（`isEmpty`）时 `of()` 返回 null，此时必须落 SQL NULL 而不是 `JsonKit.toJson(null)`」。
- **未治理的高危点**（失败即落库为 NULL / 发出 null / 加密丢失）：

| 调用点 | 后果 |
|---|---|
| `KafkaPublisher.java:65` | payload=null → `send(topic,key,null)` 可能成 tombstone，死信不写（详见 P1-1） |
| `svc/.../support/ProviderCredentialSupport.java:199-205` | `encryptConfig` 返回 null → `setEncryptedConfig(null)`（详见 P1-3） |
| `gateway/.../async/AsyncTaskSupport.java:132-134` | `requestBody`/`spec`/`context` 三字段落库为 NULL（详见 P1-5） |
| `adapter/.../anthropic/AnthropicStreamSupport.java:171,196,205,225,232,322,330` | SSE 行内容变 `data: null`，下游解析异常 |
| `gateway/.../upstream/stream/ProxyStreamingFlux.java:314` | 同上 |
| `gateway/.../runtime/GatewayRequestHandler.java:700` | `usageData = "data: " + null` → 返回 `data: null` 给客户端 |
| `common/.../model/{Ejection,Retry,Sticky}Policy.java:127/118/73` | 策略 JSON 静默丢失 → 回落默认策略 |

- ⭐ **修复工具已存在**：`JsonKit.toJsonOrThrow`（`JsonKit.java:95`，受检 `JsonProcessingException` 上抛），`BillingService.java:441`、`RoutingRuleController.java:273` 已在用。
- **建议（不需一次性全改）**：按「失败是否可静默」二分——落库 / 发送 / 加密 / 对外响应**必须**改 `toJsonOrThrow` 或显式判 null 后抛领域异常；纯日志与展示类可保留 `toJson`。配一条守门测试钉住分类。

## 3. P1（高优先级，建议发布前收口）

### P1-1 · Kafka 序列化失败绕开死信分支，可能发 tombstone

- `JsonKit.java:77-86` 失败返 null 不抛 → `KafkaPublisher.java:63-74` 的 `catch (RuntimeException)` **永远抓不到序列化失败**。
- 随后 `kafkaTemplate.send(topic, key, null)`：异步回调仍可能成功，`sent` 照常自增，**死信不写**。
- 违反本类自述契约（`KafkaPublisher.java:22-24`：「序列化失败 → dropped + debug；任何情况下不丢消息」）。
- **修法最小**：改 `toJsonOrThrow` + 显式处理 null；补一个不可序列化 `Msg` 的测试（断言：不调 `send`、`dropped+1`、不写脏 payload）。当前 `KafkaPublisherTest` 未覆盖。

### P1-2 · 计费配置非法 / 模式错配时热路径静默出零账

- `BillingConfig.java:435-443` `fromJsonOrNull` 把非法 JSON 吞成 null。
- `TokenBillingModeCalculator.java:70-74` `planOf` 注释自认「config_json 解析失败（null）时各分项价按 0 出账」；`:31-35` 非 token 用量到达本计算器直接返零额 + 空明细，**无日志**。
- `SimpleBillingModeCalculator.java:34-38`（CUSTOM）空配置 → `unitPrice` 置零；`BillingService.java:119-126` 预览同样映射为零价。
- 与 `docs/standards/rules/60-business-rules.md:132,221`「静默记零账是红线」冲突。正常保存路径有校验不等于安全：历史脏数据 / 直接改库 / 迁移错误 / 模式与提取器错配都会走到这里。
- **修法**：三选一 —— 规则加载/版本发布时严格解析并拒绝启用；运行时抛 `BusinessException`；无法阻断时返回带 `degraded` 标记的零账并 `log.error`。

### P1-3 · 凭据加密失败被静默写成 NULL（用户看到"保存成功"）

- `ProviderCredentialSupport.java:199-205`：`encryptConfig` → `JsonKit.toJson` 失败返 null → `!hasText(json)` → `return null`。
- `:99` `entity.setEncryptedConfig(encryptConfig(authConfig))` 直接落 null，`:96` status 仍为 ENABLED 并 update。
- 结果：**接口返回成功，凭据实际丢失**，且没有任何告警。属 S1 的一个具体爆点。

### P1-4 · 流式用量记账失败被吞 → 配额/频控漏记

- `GatewayRequestHandler.java:641-645`：`catch (Exception e)` 仅 `log.error("Failed to record streaming usage for rule={}")`，无 rethrow、无兜底计数。
- 影响：`trafficGuard.record(...)` 的 TPM / token 配额 / 成本配额**整体漏记**（Kafka 事件在 `:614` 另行发布不受影响）。这是实时拦截侧，等于「限额被静默绕过」的口子。

### P1-5 · 异步任务入参静默落 NULL，后续无法重建上下文

- `AsyncTaskSupport.java:132-134`：`requestBody` / `spec` / `context` 三处用 `JsonKit.toJson`。`spec`、`context` 是 POJO，序列化失败即任务行以 NULL 落库，轮询时无法重建上下文。

### P1-6 · 前端授权状态存在两套互不兼容的表示

- 后端 wire 已确认：`AdminModuleEntity.java:13` / `AdminMenuEntity.java:21` / `AdminPermissionEntity.java:18` 的 `status` 均为 **`Integer`**（1/0），故视图侧写法是对的。
- `useAuthorizationManagement.ts:882` `previousStatus = row.status ?? "ENABLED"`、`:886-887` `nextStatus = enabled ? "ENABLED" : "DISABLED"` —— **乐观更新写入字符串**。
- `AuthorizationResourceView.vue:23,55`（等 4 处）判定用 `row.status === EnabledStatus.ENABLED`（`=== 1`，见 `constants/status.ts:12-15`）。
- 后果两点：① `:888` 写入字符串后 `=== 1` 变 false，**开关视觉回弹**，直到 `reload()` 拉回数字才恢复；② `:884` 的 `previousStatus === nextStatus` 幂等短路在「数字 vs 字符串」下**永不成立 = 死代码**，重复切换会重复发请求。
- 同时违反 `constants/status.ts:5-7` 自陈的「禁止 truthy、一律用 `===` 与本文件常量比较」约定。

### P1-7 · 口令策略只在前端

- `ForcePasswordChangeView.vue:69-73` 要求至少 8 位；后端 `UserService.java:95-102`（`forcePasswordChange`）与 `:184-192`（`createUser`）只校验非空 + 72 字节上限。
- 绕过前端直接调 API 可创建 1 位密码。密码策略应收口到服务端。

### P1-8 · 日志插件正文无脱敏（默认已关闭，风险面缩小但未消除）

- `PluginLogWriter.java:24-29` 用 `log.info` 输出完整 `payload`；`GatewayRequestPayload.java:10-14` / `GatewayResponsePayload.java:8-10` / `Upstream*Payload.java` 直接持有 `JsonNode` 正文，无截断、无字段白名单。
- ⚠️ **已降级的那半**：插件默认启用（upsert `status=1`）在基线 `c006a7e` 属实，但 `039517dc`（opt-in 改造）已改为 `0` + schema `DEFAULT 0` + 迁移脚本。**"默认泄露"已不成立**，故从 P0 降为 P1。
- 一旦运维在管理端启用日志插件，仍会全量落 prompt / 模型输出。建议：正文走字段白名单 + 截断，禁止直接序列化 `JsonNode`。

### P1-9 · 敏感词审核在词库不可用时 fail-open

- `ModerationWordResource.java:27-28,58-64` 捕获 `RuntimeException` 后返回 `List.of()`；`ModerationGuard.java:74-80` 见空快照即放行。
- 这是 `40-plugin.md` 明文登记的设计选择（可用性优先），**不是守门漏报**。但对 AI 网关而言 DB 一次抖动即可摘除内容审核能力，且只有 WARN、无 metric。
- 建议：明确风险接受人；补「fail-open 次数 / 持续时长 / 词库版本」三项指标；或改为沿用上一份成功快照。
