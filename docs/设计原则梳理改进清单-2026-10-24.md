- **根除假成功（本次删除的真正重点）**：删 `MASK` 枚举值；删 `ModerationActionEnum.ofOrDefault`（静默兜底）与无调用方的 `codes()`；`PluginProperties` 加 `@PostConstruct` 启动校验——`action` 写错（含拼错、含已移除的 `MASK`）直接 `IllegalStateException` 启动失败，不再等到请求进来按默认值静默跑。

### §4.6 计费 / 路由数值正确性审查 — 结论（2026-10-25）

审查口径：不审代码优雅度，只看**会不会算错钱**。逐面核查了 8 条数值链路，**发现并修复 1 个静默 1000 倍错价缺陷**，其余 7 面判定干净（附证据）。

**① 已修复缺陷：计费单位「缺失兜底」与「模式默认」双源头（1000× 错价）**

| 位置 | 旧行为 | 后果 |
|---|---|---|
| `AbstractBillingModeCalculator.normalizeUnit` | 单位空白 → 硬编码 `1K_TOKENS`（基数 1000） | 热路径算钱，分母错 1000 倍 |
| `BillingService.normalizeUnit` | 同上硬编码 | 落库写入错口径 |
| `kb_billing_rule_versions.unit` 列 | `NOT NULL DEFAULT '1K_TOKENS'` | 漏给单位即静默落 1K |
| `BillingModeEnum.defaultUnit()` | `VIDEO/AUDIO→PER_SECOND`、`TOKEN/EMBEDDING→1M_TOKENS`、`IMAGE→PER_IMAGE`、`REQUEST→PER_REQUEST` | 权威口径，但无人调用 |

同一件事两份定义。**任何绕过管理端表单的写入**（脚本导入、直连改库、新接入方、未来新端点）都会拿到 1000 倍错的金额：VIDEO 规则漏配单位 → 每秒价再除 1000（**少收**）；TOKEN 规则漏配单位 → 拿不到声明的 1M_TOKENS（**多收**）。且编译、单测、类型检查全绿。

修复：
- `BillingModeEnum.normalizeUnit(String)` 成为**唯一**归一化出口（空白 / 非法编码 / 模式不支持 → 都取 `defaultUnit()`）。
- 三个计算器 `unitSize(rule, mode)` 显式传自己的 `mode()`，不再用规则列空值兜底；`BillingService` 三处落库调用改走同一出口。
- schema 去掉 `DEFAULT '1K_TOKENS'`：单位正确值随 `billing_mode` 变，**不存在万能默认值**，漏给即插入失败胜过静默错价。
- 回归测试：`BillingModeUnitNormalizationTest`（13 例，含 8 模式全枚举不变量）+ `MediaBillingCalculatorTest.shouldBillPerSecondWhenVideoRuleMissesUnit`（数值证据：10 秒 × 0.5 应为 5.0，旧行为 0.005）。

**② 判定干净（有证据，不建议再动）**

| 面 | 证据 |
|---|---|
| 成本计数精度 `QuotaDimension.COST_SCALE=12` | 编码 `movePointRight(12).setScale(0,HALF_UP)` 与解码 `BigDecimal.valueOf(v,12)` 严格互逆；`MAX_SCALED_AMOUNT` 恰为 `Long.MAX_VALUE/1e12`，越界显式抛错不静默溢出；6 位小数单价 × 1 token ÷ 1e6 = 1e-12 不被抹平（`GatewayTrafficGuardTest` 已覆盖） |
| 金额字符串契约 | `plainMoney` 全工程唯一出口，`toPlainString` 永不出科学计数法；无 8 位定标，小额不归零（`tinyCostIsPlainDecimalNotScientificNotation`） |
| 除法精度 | `unitSize` 全为 10 的幂（1 / 1e3 / 1e6），`用量 × 单价 ÷ 基数` 恒定除尽；`DECIMAL128` 仅为未来非 10 幂基数兜底，实际不参与 |
| 明细自洽 | `cost = tokens × price(每百万) ÷ 1e6` 与 `BillingFactChecks ③` 同式，实测无尾差 |
| 阶梯档位边界 | `[from, to]` 双闭、按整数 token 命中、配置期校验 `from > previousTo` 无重叠、开放档必须最后 |
| 高低峰窗口 | 唯一换算出口 `windowRangeOf` → 分钟数轴 `[start,end)`，`24:00` = 1440 端点，不跨午夜、无 off-by-one |
| 路由排序数值 | `PRIORITY` 降序→稳定键升序；`LEAST_LOAD` 负载升序→权重降序；`WEIGHTED` 为 Efraimidis-Spirakis `u^(1/w)` 降序（w≤0 排末）；`RANDOM` 为正确 Fisher-Yates |

**③ 顺带收口（非缺陷，防后续误判）**
- 折扣值 `double` → `BigDecimal`（DTO/VO），与 `DECIMAL(10,4)` 同型，消除 `1e400→Infinity→NumberFormatException→500` 的健壮性缺口；前端 `el-input-number` 补 `:precision="4"`，避免 0.01 步进的浮点尾数原样提交。

行数只说明"文件长"，不说明"值不值得拆"。拆分的收益是**降低未来每次改动的成本**，所以真正要排的是：

风险分 = 当前行数 × 改动提交次数

**为什么放弃原计划的 `ModelDiscountSupport`（与原 ③ 结论不同，附证据）**

原计划把折扣簇（6 成员 / 约 70 行）一并抽出，实测后判定**收益为负**：

1. 折扣策略与模型 CRUD 处于**同一抽象层级**（都是聚合根的子资源 CRUD），端点就挂在 `ModelController` 的 `/api/models/{code}/discount-policies` 下；
2. 只抽私有方法、对外保留 public 委托 → 方法数只降 2，调用链反而多一跳；
3. 让控制器直连新 `@Service` → 必须改 `@modelService.discountPolicyAuditSnapshot(#p1)` 这条 **SpEL 字符串**。它编译期不校验，`ModelControllerTest` 只有 `contextLoads()` 也捕不到，赌的是运行期；
4. 对比刚拆掉的绑定簇：它是**子表持久化实现细节**，与聚合根不同层级，且是 `ModelApiBindingMapper` 的唯一使用者 → 拆得干净、零委托。

→ 沉淀判据：**跨抽象层的持久化细节必拆；同抽象层的子资源 CRUD 不拆**（除非它自己已成规模）。这也把 ④ 的「不拆」从「行数/提交次数」推到了「抽象层级」这一维权衡上。
