# 上游 trace 打通 — 双向对账设计

> 日期：2026-10-17 ｜ 状态：设计（未实现，待 robin 批准后进入工程）
> 关联：`docs/gateway-warehouse-kafka-message-protocol-2026-10-17.md`、`docs/gateway-warehouse-data-model-2026-10-17.md`

## 1. 背景与结论

knot 全链路 trace_id 已落地（W3C traceparent，生成/解析/MDC/数仓 key 四要素齐备），**出站方向已经打通，回站方向是断的**：上游返回的 request-id 头在网关出站链路被整体丢弃。结果是——向供应商提工单时，我们只能给出自己的 trace_id，对方系统里查不到，客服认的只有**他们回的 id**。

**本设计目标：从"单向发牌"变为"双向对账"**——出站带 trace（已有），回站把上游 id 抓回来与 traceId 绑死，落数仓、进日志、可检索。

## 3. 总体方案

| 编号 | 动作 | 层 | 动 DDL | 动前端 |
|---|---|---|---|---|
| B | 上游响应头白名单捕获 + attempt 级绑定（**核心**） | gateway 出站 + 数仓消息 | 否 | 否 |
| A | 出站加发 `X-Knot-Trace-Id`（轻量）；供应商级 `trace_header_name`（完整，仅设计） | executor | 完整版需要 | 完整版需要 |
| C | 响应回传 `X-Knot-Upstream-Request-Id` | 入口响应 | 否 | 否 |
| D | 工单协同 SOP | 文档 | 否 | 否 |

推荐顺序：**B → A(轻量) → D**；C 单独评估（对外租户场景默认关闭）；A 完整版等轻量版验证供应商配合度后再上。

## 4. 方案 B 详设（核心）

### 4.1 白名单头清单

不按供应商分支，固定一个 union 集合，命中即记（name + value）。**禁止全量透传**——上游响应头可能含 `set-cookie`、鉴权回显等敏感内容。

| 头名 | 供应商 | 确定性 |
|---|---|---|
| `x-request-id` | OpenAI 及多数 OpenAI 兼容厂商 | 高（通行事实标准） |
| `request-id` | Anthropic、智谱等 | 高 |
| `apim-request-id` | Azure OpenAI（APIM 出口） | 高 |
| `x-acs-request-id` | 阿里云百炼 / DashScope | 高（阿里云开放 API 通用头） |
| `X-Tt-Logid` | 火山方舟 / 字节系 | 高（字节基础设施通用 logid） |
| `cf-ray` | Cloudflare 出口（自建/反代链路） | 高 |
| `traceparent` | 上游回显（少数厂商） | 高 |
| `x-ms-region` | Azure OpenAI 区域标识 | 中 |
| 其余（腾讯混元、DeepSeek、Moonshot、MiniMax 等） | — | **待实测**：接入时用 curl 打一次上游，从响应头实录补齐白名单 |

> 原则：白名单只增不减；新增供应商时实测头名后追加，不允许临时放开全量抓取。

### 4.2 捕获点（三处，缺一不可）

1. **非流式成功路径**：`AbstractUpstreamProtocolExecutor` 当前 `spec.body(...)` 直接拿字符串，拿不到 response 对象。需改为 `.exchange((request, response) -> { 快照头; return body })`，同时落 body + headers。
2. **流式成功路径**：`toStreamResponse()`（同文件 `:126-145`）已持有 `ClientHttpResponse`，在构造 `UpstreamStreamResponse` 时**立即快照白名单头**——注意快照必须在 `response.close()` 之前（close 见 `UpstreamStreamResponse.java:61-66`）。
3. **异常路径**：`RestClientResponseException.getResponseHeaders()`（executor `:71-77` catch 块）。**排障工单 90% 发生在错误场景**，这一处优先级实际最高。

### 4.3 数据契约

**网关内部**：

- `UpstreamExchangeSnapshot`（新类型，gateway 出站域）：`traceId` / `traceparent` / `upstreamRequestId` / `upstreamLogId` / `upstreamHeaders`（白名单 map，只进日志不进数仓）/ `httpStatus`。
  - `upstreamRequestId` = 白名单中 request-id 类头的归一值（`x-request-id` → `request-id` → `apim-request-id` → `x-acs-request-id` 优先序）。
  - `upstreamLogId` = `X-Tt-Logid` 等字节系 logid（与 request-id 是两套东西，都值得留）。
- `GatewayUpstreamException` 增加 `upstreamRequestId` / `upstreamLogId` 可空字段（异常路径无 snapshot，从 catch 块直接提取）。
- `ProxyResult` / `UpstreamStreamResponse`：流式侧在 `UpstreamStreamResponse` 增加 `headers()` 访问器（返回快照）；非流式侧由 executor 把 snapshot 传给上游插件 context。

**数仓消息**（对齐 data-model 文档 §3 attempt 事件，新增两列）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `upstream_request_id` | string 可空 | §4.1 归一值；无白名单命中为 NULL |
| `upstream_log_id` | string 可空 | 字节系 logid，其余厂商为 NULL |

Kafka attempt 消息扩展示例：

```json
{
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f0...",
  "attempt_seq": 1,
  "target_code": "gpt-4o-mini",
  "upstream_model_code": "gpt-4o-mini-2024-07-18",
  "outcome": "upstream_failure",
  "upstream_http_status": 503,
  "upstream_error_code": "UPSTREAM_ERROR",
  "upstream_request_id": "req_abc123",
  "upstream_log_id": null,
  "error_stage": "upstream_call"
}
```

**日志**：`UpstreamRequestLoggingPlugin` / `UpstreamResponseLoggingPlugin` / `UpstreamErrorLoggingPlugin`（`knot-plugin/builtin/`）在日志行追加 `upstream_request_id`——这些插件已带 traceId（`UpstreamPluginContext` 已有），补一个上游 id 字段即可。

### 4.4 为什么是 attempt 级而不是 request 级

一次请求可能 failover 多个候选、候选内多重试，每个 attempt 打的是不同上游、拿回不同 id。挂 request 级会丢链。attempt 事件已有 `attempt_seq`（data-model §3），天然是 attempt 级字段。

## 5. 方案 A：出站头增强

**轻量版（推荐先做）**：executor 在 `traceparent` 之外加发 `X-Knot-Trace-Id`（裸 trace_id，无 W3C 格式要求）。价值：愿意配合的供应商可直接用自定义头检索，零配置成本。改动 = `AbstractUpstreamProtocolExecutor.java:204` 区域多一行 header。

**完整版（仅设计，不实现）**：`kb_providers` 增加 `trace_header_name` 列（默认 `traceparent`，可空=关闭），executor 从 provider 配置读取头名。需要：DDL 迁移 + admin 表单 + provider 查询链路。触发条件：轻量版上线后统计到某供应商明确要求特定头名再上。

## 6. 方案 C：客户端可见性

响应头增加 `X-Knot-Upstream-Request-Id`，风格对齐现有 `X-Knot-Model` / `X-Knot-First-Token-Time`（`constants/GatewayHeaders.java:16-27`）。

**边界**：内部/自用网关可默认开；对外租户多租场景默认关（透出上游 id 有信息暴露面），做成配置开关。

## 7. 方案 D：工单协同 SOP

零代码。提工单模板五要素：

1. knot `trace_id`（我们侧全链路检索键）
2. `upstream_request_id` / `upstream_log_id`（对方侧检索键）
3. 时间窗（UTC + 时区标注）
4. `model_code` / provider code
5. 请求体脱敏摘要（禁带用户原文/PII）

> 对供应商做 otel/traceparent 直接对接**不可行**：无一货一商支持外部 trace 注入检索，通行做法就是 request-id 双向绑定。traceparent 照发（成本已付），但别指望对方认。

## 8. 风险与边界

| 风险 | 对策 |
|---|---|
| 上游响应头含敏感内容泄进数仓 | 白名单硬编码 + code review；`upstream_headers` map 只进日志，数仓只要两个归一标量 |
| 流式路径 close 后头失效 | 快照时机写进单测：构造 `UpstreamStreamResponse` 时即快照，close 后再取返回空 |
| 非流式改 exchange() 破坏现有 body 读取 | 保持 body 读取逻辑不变，仅包一层 exchange；回归非流式 + 流式两条冒烟 |
| failover 多 attempt 混淆 | attempt 级字段，测试断言：二连 failover 时两条 attempt 消息各带各自 upstream id |
| JDK25+Mockito 限制 | 出站链路测试替身用子类覆写（项目铁律） |

## 9. 验收标准

1. 单测：白名单归一（x-request-id 优先序）、流式快照时序、异常路径提取、failover 两 attempt 各自绑定。
2. 冒烟：真实打一家上游（或录制头），断言 attempt 消息含上游 id；4xx/5xx 场景同样断言。
3. grep 残留：`upstream_request_id` 全链路贯通（executor → snapshot → exception → 数仓消息 → 插件日志）。
4. 全量门禁：`mvn -f knot-server/pom.xml test` + 前端不受影响（B 不动前端）。

## 10. 落地顺序

1. B 核心（executor 三处捕获 + snapshot 类型 + 数仓两字段 + 插件日志）
2. A 轻量（`X-Knot-Trace-Id` 一行）
3. D SOP 文档
4. C 开关设计后单独排期
5. A 完整版（触发条件见 §5）
