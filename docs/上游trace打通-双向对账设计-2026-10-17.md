# 上游 trace 打通 — 双向对账设计

> 日期：2026-10-17 ｜ 状态：设计（未实现，待 robin 批准后进入工程）
> 关联：`docs/gateway-warehouse-kafka-message-protocol-2026-10-17.md`、`docs/gateway-warehouse-data-model-2026-10-17.md`

## 1. 背景与结论

knot 全链路 trace_id 已落地（W3C traceparent，生成/解析/MDC/数仓 key 四要素齐备），**出站方向已经打通，回站方向是断的**：上游返回的 request-id 头在网关出站链路被整体丢弃。结果是——向供应商提工单时，我们只能给出自己的 trace_id，对方系统里查不到，客服认的只有**他们回的 id**。

**本设计目标：从"单向发牌"变为"双向对账"**——出站带 trace（已有），回站把上游 id 抓回来与 traceId 绑死，落数仓、进日志、可检索。

### 1.1 目的锚点与范围边界（robin 2026-10-18 拍板）

> **目的唯一**：落 request_id 是为了**网关侧与供应商侧联合分析/定位问题**（提工单、对账、查链路）。不是为了给 knot 的调用方（客户端）提供可见性。

由此确定的三条硬边界：

1. **客户端方向彻底排除**——原「方案 C：响应头回传 `X-Knot-Upstream-Request-Id`」**已作废**（见 §6）。网关响应头不新增任何上游标识，`constants/GatewayHeaders.java` 不动。理由：客户端既看不懂也不需要这个 id，而对外租户场景透出上游内部标识本身就是多余的信息暴露面。
2. **消费方只有两个**：① 数仓（Kafka 流量事件 `attempts[]`，供离线分析与按 trace_id 检索）；② 网关日志（三个上游日志插件，供排障第一步 grep）。两者都只服务于「我们内部」与「和供应商对接」这两个场景，不对外透出。
3. **因此不必做开关**：不透客户端就无需「默认关闭」的配置项；字段恒可空即可表达"没有"，不存在需要人工关闭的场景。**不加 `knot.upstream.*` 之类的新配置**。

联合排查的固定检索路径（写进 SOP，见 §7）：

```
报障 trace_id（或业务侧给出的 X-Knot-Sticky-Key / 时间窗）
      │
      ├─► 网关日志：grep traceId → 插件日志行自带上游 id（秒级，第一选择）
      └─► 数仓：按 trace_id 取流量事件 → attempts[] → 目标 attempt 的
           upstream_request_id / upstream_log_id（离线、可聚合）
      │
      └─► 提工单给供应商：trace_id + upstream id + 时间窗 + model_code
```

## 4. 方案 B 详设（核心）

### 4.1 白名单头清单

不按供应商分支，固定一个 union 集合，命中即记（name + value）。**禁止全量透传**——上游响应头可能含 `set-cookie`、鉴权回显等敏感内容。

| 头名 | 供应商 | 确定性 |
|---|---|---|
| `x-request-id` | OpenAI 及多数 OpenAI 兼容厂商 | 高（通行事实标准） |
| `request-id` | Anthropic、智谱等 | 高 |
| `apim-request-id` | Azure OpenAI（APIM 出口） | 高 |
| `x-acs-request-id` | 阿里云百炼 / DashScope | 高（阿里云开放 API 通用头） |
| `X-Tt-Logid` | 火山方舟 / 字节系 | 高（字节基础设施通用 logid） |
| `cf-ray` | Cloudflare 出口（自建/反代链路） | 高 |
| `traceparent` | 上游回显（少数厂商） | 高 |
| `x-ms-region` | Azure OpenAI 区域标识 | 中 |
| 其余（腾讯混元、DeepSeek、Moonshot、MiniMax 等） | — | **待实测**：接入时用 curl 打一次上游，从响应头实录补齐白名单 |

> 原则：白名单只增不减；新增供应商时实测头名后追加，不允许临时放开全量抓取。

### 4.2 捕获点（三处，缺一不可）

1. **非流式成功路径**：`AbstractUpstreamProtocolExecutor` 当前 `spec.body(...)` 直接拿字符串，拿不到 response 对象。需改为 `.exchange((request, response) -> { 快照头; return body })`，同时落 body + headers。
2. **流式成功路径**：`toStreamResponse()`（同文件 `:126-145`）已持有 `ClientHttpResponse`，在构造 `UpstreamStreamResponse` 时**立即快照白名单头**——注意快照必须在 `response.close()` 之前（close 见 `UpstreamStreamResponse.java:61-66`）。
3. **异常路径**：`RestClientResponseException.getResponseHeaders()`（executor `:71-77` catch 块）。**排障工单 90% 发生在错误场景**，这一处优先级实际最高。

### 4.3 数据契约

**网关内部**：

- `UpstreamExchangeSnapshot`（新类型，gateway 出站域）：`traceId` / `traceparent` / `upstreamRequestId` / `upstreamLogId` / `upstreamHeaders`（白名单 map，只进日志不进数仓）/ `httpStatus`。
  - `upstreamRequestId` = 白名单中 request-id 类头的归一值（`x-request-id` → `request-id` → `apim-request-id` → `x-acs-request-id` 优先序）。
  - `upstreamLogId` = `X-Tt-Logid` 等字节系 logid（与 request-id 是两套东西，都值得留）。
- `GatewayUpstreamException` 增加 `upstreamRequestId` / `upstreamLogId` 可空字段（异常路径无 snapshot，从 catch 块直接提取）。
- `ProxyResult` / `UpstreamStreamResponse`：流式侧在 `UpstreamStreamResponse` 增加 `headers()` 访问器（返回快照）；非流式侧由 executor 把 snapshot 传给上游插件 context。

**数仓消息**（⚠ 2026-10-18 口径更新：数仓已由「三事实表」/「两层 Kafka 消息」合并为**单条流量事件**，`GatewayTrafficMsgDto`（schema `knot.gateway.traffic/1.0`，单 topic `knot-gateway-traffic-event`）；attempt **不再是独立消息**，而是 `attempts[]` 内嵌数组的一行。以下两字段已并入权威协议文档 `docs/gateway-warehouse-kafka-message-protocol-2026-10-17.md` §3 attempts 字段规则）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `upstream_request_id` | string 可空 | §4.1 归一值；上游无匹配头、或 `attempt_no=0`（未发起调用即被频控/摘除跳过）为 NULL |
| `upstream_log_id` | string 可空 | 字节系 logid（`X-Tt-Logid` / `cf-ray`），其余厂商为 NULL |

`attempts[]` 一行示例（成功与失败 attempt **均带**这两个字段；排障工单 90% 在错误场景，失败 attempt 的 id 最关键）：

```json
{ "seq": 1, "target_code": "gpt-4o-mini", "priority": 1, "is_primary": true,
  "outcome": "upstream_failure", "attempt_no": 1, "max_attempts": 2,
  "upstream": { "http_status": 503, "error_code": "UPSTREAM_ERROR", "retry_after_ms": null },
  "upstream_request_id": "req_abc123", "upstream_log_id": null,
  "counted_for_ejection": true }
```

**代码落地边界**：协议已定，`AttemptMsgDto`（record，SnakeCase 自动转 JSON）**尚未含这两字段**，随本设计「方案 B」批次一并落地（executor 三处捕获 + `GatewayUpstreamException` 带字段 + `AttemptMsgDto` 加两可空 String + 埋点从 `CallTraceContext` 取数填充）。向后兼容追加，schema 版本号不变、不改主题名。

**日志**：`UpstreamRequestLoggingPlugin` / `UpstreamResponseLoggingPlugin` / `UpstreamErrorLoggingPlugin`（`knot-plugin/builtin/`）在日志行追加 `upstream_request_id`——这些插件已带 traceId（`UpstreamPluginContext` 已有），补一个上游 id 字段即可。

### 4.4 为什么是 attempt 级而不是 request 级

一次请求可能 failover 多个候选、候选内多重试，每个 attempt 打的是不同上游、拿回不同 id。挂 request 级会丢链。`GatewayTrafficMsgDto` 的 `attempts[]` 每行自带 `seq`，天然是 attempt 级字段。

> 顶层（request 级）**不另设** `upstream_request_id`：合并后单次请求只有一条消息，`hit` 指向真正承接的那个目标，其对应的上游 id 从 `attempts[]` 中 `outcome=success` 那一行取即可，再在顶层冗余一列反而容易两边打架。数仓检索路径固定为：`trace_id` → 消息 → `attempts[]` → 目标 attempt 的 `upstream_request_id`。

## 5. 方案 A：出站头增强

**轻量版（推荐先做）**：executor 在 `traceparent` 之外加发 `X-Knot-Trace-Id`（裸 trace_id，无 W3C 格式要求）。价值：愿意配合的供应商可直接用自定义头检索，零配置成本。改动 = `AbstractUpstreamProtocolExecutor.java:204` 区域多一行 header。

**完整版（仅设计，不实现）**：`kb_providers` 增加 `trace_header_name` 列（默认 `traceparent`，可空=关闭），executor 从 provider 配置读取头名。需要：DDL 迁移 + admin 表单 + provider 查询链路。触发条件：轻量版上线后统计到某供应商明确要求特定头名再上。

## 6. ~~方案 C：客户端可见性~~（已作废）

> **robin 2026-10-18 拍板：「落 request_id 的目的是便于网关和供应商联合分析问题，不用考虑客户端。」**

原方案：响应头增加 `X-Knot-Upstream-Request-Id`，风格对齐现有 `X-Knot-Model` / `X-Knot-First-Token-Time`（`constants/GatewayHeaders.java:16-27`），并做「对外租户默认关闭」的开关。

**作废依据**：

1. 该 id 的唯一用途是网关↔供应商联合排查，客户端既看不懂也不需要；透出它对订正问题毫无帮助。
2. 响应头是**对外**面：上游内部标识（部分厂商还带地域/网关节点信息）不经网关抽象直接暴露给调用方，属于无收益的信息暴露。
3. 加了就得配开关、写文档、考虑多租差异——为一处没有收益的东西付三份成本。

**连带结论**：`constants/GatewayHeaders.java` **不再新增任何上游标识常量**；`AbstractGatewayRequestTemplate` 的响应头设置区不动；对外 wire 协议文档 `docs/gateway-output-message-protocol-2026-10-17.md` **零改动**。上游 id 的两个消费方只剩数仓消息（§4.3）与网关日志（§4.3 末）。

## 7. 方案 D：工单协同 SOP

零代码。提工单模板五要素：

1. knot `trace_id`（我们侧全链路检索键）
2. `upstream_request_id` / `upstream_log_id`（对方侧检索键）
3. 时间窗（UTC + 时区标注）
4. `model_code` / provider code
5. 请求体脱敏摘要（禁带用户原文/PII）

> 对供应商做 otel/traceparent 直接对接**不可行**：无一货一商支持外部 trace 注入检索，通行做法就是 request-id 双向绑定。traceparent 照发（成本已付），但别指望对方认。

## 8. 风险与边界

| 风险 | 对策 |
|---|---|
| 上游响应头含敏感内容泄进数仓 | 白名单硬编码 + code review；`upstream_headers` map 只进日志，数仓只要两个归一标量 |
| 流式路径 close 后头失效 | 快照时机写进单测：构造 `UpstreamStreamResponse` 时即快照，close 后再取返回空 |
| 非流式改 exchange() 破坏现有 body 读取 | 保持 body 读取逻辑不变，仅包一层 exchange；回归非流式 + 流式两条冒烟 |
| failover 多 attempt 混淆 | attempt 级字段，测试断言：二连 failover 时 `attempts[]` 两行各带各自 upstream id |
| JDK25+Mockito 限制 | 出站链路测试替身用子类覆写（项目铁律） |

## 9. 验收标准

1. 单测：白名单归一（x-request-id 优先序）、流式快照时序、异常路径提取、failover 两 attempt 各自绑定。
2. 冒烟：真实打一家上游（或录制头），断言 `attempts[]` 那一行含上游 id；4xx/5xx 场景同样断言（5xx 的 id 来自 `RestClientResponseException` 响应头，与成功路径两条分支必须都验）。
3. grep 残留：`upstreamRequestId` 全链路贯通（executor 三处捕获 → `UpstreamExchangeSnapshot` / `GatewayUpstreamException` → `AttemptMsgDto`（JSON `upstream_request_id`）→ 三个日志插件）。
4. 全量门禁：`mvn -f knot-server/pom.xml test`；**必须补 `AttemptMsgDto` 字段断言 + `GatewayTrafficMsgDtoTest` 用例**（一成功一失败两个 attempt 各自带各自的 id，`attempt_no=0` 必为 null）；B 不动前端、`GatewayHeaders` 不新增常量（§1.1 边界 1），这两条用作反向断言。
