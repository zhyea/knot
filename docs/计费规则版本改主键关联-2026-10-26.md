# 计费规则版本改按规则主键关联（rule_code → rule_id）

- 日期：2026-10-26
- 决策人：robin
- 涉及层：schema / data.sql / knot-dal / knot-service / 迁移脚本 / 规范

## 1. 结论

`kb_billing_rule_versions` 与 `kb_billing_rules` 之间**不再用 `rule_code` 关联，改按主键 `rule_id`**。

版本是规则主体的**从属明细**（与主体同生命周期、不可独立存在），不属于「跨聚合业务绑定」，
因此不受「跨表绑定存 code 不存 id」约束——那条红线的判据是**是否跨聚合**，不是「是否两张表」。
改造后：规则编码在**没有供应商模型绑定**时可自由修改，版本行不再参与改码守卫。

## 2. 原设计的两个实际缺陷（不是理论风险）

原实现 `VersionJoin` 用 `v.rule_code = br.code`，`BillingService.assertCodeChangeAllowed`
把「版本行数」也算进引用计数：

1. **规则编码恒不可改**：新建规则必然生成一条版本行（`createRule → createVersion`），
   于是 `countVersionsByRuleCode(oldCode) ≥ 1` 恒成立，`CodeBindingSupport` 恒抛 409。
   前端 `codeBlockedByBinding` 只按 `boundModelCount` 判断（未绑模型时可编辑），
   与后端口径**不一致**：用户能编辑、能提交，必然收到「已被 1 处引用」。
2. **改码会把版本行改成孤儿**：`updateRule` 先 `syncVersion(newCode)` 再 `update` 主体。
   按 code 查版本时，改码后 `getLatestVersion(newCode)` 返回 null → 走 `createVersion`
   另插一条 `v1`，旧版本行仍留 `rule_code = 旧码`，旧码被永久占用（`uk_billing_rules_code`
   是物理行唯一，同码无法再建），旧配置悬空。即使绕过守卫，这也是必然发生的静默损坏。

两个缺陷同源：**把「可改的业务标识」当成了内部外键**。

## 3. 改动清单

| 层 | 位置 | 改动 |
|---|---|---|
| schema | `knot-admin/src/main/resources/db/schema.sql` | 版本表 `rule_code VARCHAR(64)` → `rule_id BIGINT NOT NULL`；三个索引前导列改 `rule_id` |
| data.sql | 同目录 `data.sql` | 版本种子 5 行改 `rule_id`（1..5，与规则种子 id 对齐） |
| entity | `BillingRuleVersionEntity` | `ruleCode:String` → `ruleId:Long` |
| mapper | `BillingRuleMapper.java/.xml` | `getLatestVersion` / `maxVersionSeq` 入参改 `ruleId`；`VersionJoin`、两处 `inner join` 改 `br.id = bv.rule_id`；**删除** `countVersionsByRuleCode`（版本行不再是引用方） |
| service | `BillingService` | `createVersion/syncVersion` 改按 `ruleId`；`updateStatus` 取版本改按 `id`；`assertCodeChangeAllowed` 只统计 `kb_models` 绑定 |
| 迁移 | `docs/database/migration/2026-10-26-billing-rule-version-rule-id.sql` | 加可空列 → 按 code 回填 → 收紧 NOT NULL → 先删旧索引再删列 → 重建索引；含孤儿行/重复版本预检与 3 条 POSTCHECK |
| 规范 | `10-backend-java.md` §5、`30-database-sql.md` §5 | 为「存 code 不存 id」补反向口径：聚合内从属明细按主体主键绑定 |

**未改动（语义本就正确）**：计费入口 `getActiveByRuleCode(ruleCode)` 仍按 code 查主体
（模型绑定 `kb_models.billing_rule_code` 存的就是 code），只是 join 版本的条件换成主键；
对外 DTO / 前端 / Kafka 归因（`versionCode`）零改动，前端 `codeBlockedByBinding`
按 `boundModelCount` 判断的口径现在与后端一致了。

**无历史兼容逻辑**：代码中不存在 `rule_code` 兼容分支、双写或回填兜底；存量库只走一次性迁移脚本。

## 4. 冲突检查（迁移安全性）

- 唯一键 `(rule_code, version_code)` → `(rule_id, version_code)`：rule_code 与 rule_id 在本库是
  一对一映射（版本表回填 `JOIN br.code = v.rule_code`），因此**不存在新增唯一冲突**。
- 反向不成立的历史脏数据只有一种：`rule_code` 在主体表已不存在（历史改码遗留孤儿行）。
  迁移脚本 PRECHECK-1 会列出并要求人工处理；回填后 POSTCHECK-1 未清空则 NOT NULL 收紧失败（保护生效）。
- 本机 `knot` 库实测：迁移前 5 行版本、0 孤儿；迁移后每规则 1 行版本、`rule_id NOT NULL`、
  三条索引前导列均为 `rule_id`、启用规则无缺版本（POSTCHECK-3 为空）。

### 4.1 首次迁移路径的真库验证（临时库 `knot_mig_verify`，已 DROP）

在旧结构上手工造 2 条规则 + 3 条版本（其中 `GHOST_CODE` 为孤儿），分三段验证：

| 轮次 | 场景 | 结果 |
|---|---|---|
| 1 | 含孤儿版本行 | PRECHECK-1 报出 `version_id=3 rule_code=GHOST_CODE` → POSTCHECK-1 `null_rule_id_rows=1` → `MODIFY NOT NULL` 失败（`Data truncated for column 'rule_id' at row 3`），迁移中断，未破坏已有数据 |
| 2 | 清掉孤儿行后重跑 | 全绿：POSTCHECK-1 `null_rule_id_rows=0`，每规则 1 行版本 |
| 3 | 已迁移库再执行（幂等） | 全绿：预检/回填走「已迁移，跳过」动态分支，索引与列操作走 `SELECT 1` 分支，无 `Unknown column` |

> 首版脚本此处在第 1 条语句即失败：三条预检与回填 UPDATE 都直接引用 `rule_code`，
> 列被删后重复执行报 `Unknown column 'rule_code'`。已改为用 `@has_rule_code_pre`
> 判断 + `PREPARE/EXECUTE` 动态执行——**凡是引用「本脚本自己会删掉的列」的语句，
> 都必须动态化**，否则幂等性在第一次执行成功那一刻就失效。

## 5. 新增测试

`BillingServiceCodeChangeTest`（4 例）守护三个故障模式：

1. 只有版本行、无模型绑定 → 允许改码，且**原地覆盖**版本（`never insertVersion`）；
2. 有模型绑定 → 仍 409，且不落任何写操作（模型绑定存 code，改码会静默掉绑）；
3. 无版本行 → 新建版本行携带 `ruleId`，版本号序号按 `ruleId` 统计；
4. 编码未变 → 不查绑定计数（避免「只改价格」被自身引用误伤）。

## 7. 沉淀的判据

**code 与 id 的取舍看「聚合边界」，不看「表的数量」**：

- 跨聚合引用（模型→计费规则、路由规则→目标、插件实例→能力码）→ 存 code，编码即业务契约；
- 聚合内从属明细（规则版本、明细行、快照）→ 存主体主键，主体编码保持可改。

反例特征：某表恒有一行（初始版本/初始明细）却被计入「改码引用计数」——
这几乎必然意味着**关联用错了键**，因为「恒存在」的从属关系不该能阻止主体改标识。
