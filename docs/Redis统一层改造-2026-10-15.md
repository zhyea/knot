## 1. 方案演进（重要）

本任务中途被 **robin 两次纠偏**，最终口径与初版提案不同。这部分保留下来是为了说明**为什么删掉了一批已通过门禁的代码**。

| 阶段 | 提案 | 结果 |
|---|---|---|
| 初版 | 三档 `caffeine` / `redis` / `fallback`，通用降级状态机 | 已实现并通过门禁 |
| 纠偏 1 | 「单节点 Caffeine、多节点适配器，由配置选」——**没改骨架**，但我擅自加了 `fallback` 第三档 | 骨架保留，多余档位被删 |
| 纠偏 2（最终） | **Redis 不降级**：出错抛异常 + ERROR 日志报警；**摘除纯本地缓存** | 当前代码 |

**最终口径的三条硬规则**：

1. **`redis` 档一律 fail-hard**：Redis 不可用 → 抛 `RedisUnavailableException` → 网关 **503** + **ERROR 日志**，无任何静默放行。
2. **报警通道就是 ERROR 日志**：全仓无 webhook / Notifier / 邮件设施，运维靠日志采集配规则（按 `domain` / `operation` / `key` 关键字）。
3. **摘除状态纯进程内 Caffeine**：无 store 开关。

## 2. 为什么要删掉已通过门禁的降级机制

 robin 的判断：**「Redis 承担的职责如果降级会产生损失」**。逐条对照代码验证，成立：

| 存储 | 若按放行值静默处理 | 实际损失 |
|---|---|---|
| 频控计数 `TrafficCounterStore` | 计 0（等于未产生用量） | 多节点实际限额悄悄涨到「配置值 × 节点数」，**直接超发且无感知** |
| 在途负载 `ModelLoadStore` | 记 0（等于不拥塞） | 所有模型被看成不拥塞，`LEAST_LOAD` 退化成权重序，**已过载模型继续被加压** |

补充证据：三个存储的调用方**全部裸调、无一处 catch**——`GatewayTrafficGuard.java:137`、`GatewayRequestHandler.java:195`、`OutageTracker.java:53`。这意味着 fail-open 一旦生效就是**完全静默**的，没有任何环节会发现。

结论：**宁可全拒 + 报警让人来决策，不可静默劣化。** 降级「保住功能」的代价是把故障变成看不见的损失。

## 3. 落地结构

```
gateway/redis/                          ← 统一层（4 类，比初版少 4 类）
├── RedisCache                 门面：脚本执行 / 读值 + 异常分类 + ERROR 日志节流（无 fail-open 入口）
├── RedisUnavailableException  唯一异常类型 → GatewayExceptionHandler 映射 503
├── RedisStoreModeResolver     模式归一（新键 → 旧键 → 默认），已删除 failOpen/probeInterval 归一
└── RedisStoreModes            模式常量表（只有 caffeine / redis）
```

各域侧：

| 域 | 实现 | 装配 |
|---|---|---|
| traffic | `RedisTrafficCounterStore`（无 failOpen 参数） | `TrafficCounterConfiguration` 两档分支 |
| load | `RedisModelLoadStore`（无 failOpen 参数） | `ModelLoadStoreConfiguration` 两档分支 |
| outage | **仅** `CaffeineTargetOutageStore` | `OutageStoreConfiguration` 无 store 开关 |

### 摘除为何可以纯本地

摘除表达的是「**本节点自己观察到的异常**」（超时率 / 异常率 / 慢信号），本就不需要跨节点共享。放 Redis 只会让 Redis 故障**同时打掉网关的自我保护能力**——摘除失效意味着坏模型继续被加压。

代价（已在代码注释与规范中标注）：多节点下各节点各摘各的，某节点摘掉的模型其他节点可能仍在用。这是**有意取舍**：「摘除口径不全局」比「Redis 故障导致全链路无保护」安全得多。

## 4. 错误码与 HTTP 映射

新增 `GatewayErrorTypeEnum.STORAGE_UNAVAILABLE`（`storage_unavailable`），`GatewayExceptionHandler` 新增 handler 返回 **503**。

**刻意不复用** `UPSTREAM_ERROR`：上游不可用是「模型服务的问题」，存储不可用是「网关自己的 Redis 挂了」，两者处置完全不同（一个可换节点/重试，一个必须先修 Redis），日志告警也需分别配规则。

### 固化进单测的红线

`RedisCacheFailHardTest` 用反射断言**门面不得重新出现 `evalOr` / `valueOr` / `hashEntriesOr` / `deleteOr` / `ping`**——这些方法一旦被加回，就意味着有人重新引入了 fail-open 语义或降级探针。

`RedisStoreModeResolverTest.legacyFallbackFailsFast` 断言**存量 `fallback` 配置必须启动失败**（抛 `IllegalStateException`），宁可启动失败也不静默忽略。

## 6. 配置契约（部署须知）

```yaml
knot:
  redis:
    traffic: { store: caffeine|redis, key-prefix: knot:traffic, zone: Asia/Shanghai }
    load:    { store: caffeine|redis, key-prefix: knot:load, ttl-seconds: 300 }
    outage:  { key-prefix: knot:outage, expire-grace-ms: 60000 }   # 无 store，永远 Caffeine
spring.data.redis:
  host / port / password / timeout / connect-timeout
```

**已删除的配置项**：`knot.redis.fail-open`、`knot.redis.recover-probe-interval-ms`、`knot.redis.outage.store`。

⚠ **存量部署若有 `KNOT_OUTAGE_STORE=redis` 或 `fallback`**：outage 段的 store 项已失效（会被忽略，日志提示改回 caffeine）；但 `traffic` / `load` 段若配了 `fallback`，**网关会启动失败**并报出原值——这是刻意的，需运维改回 `caffeine` 或 `redis`。

旧键仍生效并打 WARN：`knot.traffic.store` / `knot.load.store`。
⚠ 各域 `store` 字段必须保持 `null` 默认值——null 才代表「未显式设置」，否则旧键兼容失效。
