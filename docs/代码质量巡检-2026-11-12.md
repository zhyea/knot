### 🟡-1 `GET /api/docs/openapi.json` 在默认拒绝下不可达，文档却标“已上线”

**证据链**：

- `application.yml:30-32` 将 springdoc 文档路径设为 `/api/docs/openapi.json`。
- springdoc 2.6.0 的 `OpenApiWebMvcResource` 是 `@RestController` + `@GetMapping`（`javap` 核实），会被 Spring 注册为 `HandlerMethod`。
- `WebMvcConfig.java:31-43` 对 `adminAuthorizationInterceptor` 的 `addPathPatterns("/api/**")` 没有豁免 `/api/docs/openapi.json`。
- `AdminAuthorizationInterceptor.java:39-46` 对 `HandlerMethod` 取 `BEST_MATCHING_PATTERN_ATTRIBUTE`，然后调用 `AuthorizationAccessService.validateApiAccess`。
- `AuthorizationAccessService.java:40-42` 在 `ks_api_permission_bindings` 查不到绑定就直接抛 `ForbiddenException`。
- `data.sql:264` 起的 `INSERT IGNORE INTO ks_api_permission_bindings` 块中，实测 **没有任何 `/api/docs/*` 绑定**；`WebMvcConfig` 白名单中也没有该路径。
- 前端/文档：`docs/prd/modules/10-API文档管理.md:19` 与 `docs/tech/modules/10-API文档管理-技术方案.md:11` 仍标“✅ 已上线”。

**结论**：带合法 JWT 访问 `GET /api/docs/openapi.json` 时，`AuthInterceptor` 通过后仍会被接口级授权判为 403；不带 JWT 则是 401。**文档标注的“已上线”不成立。**

**归因与边界**：

- 删除 `ApiDocController` 与 `POST /api/docs/*` 绑定本身是正确的：删除前也只有 `POST` 绑定（id 54/55），`GET` 从来没有绑定或白名单，所以这是**存量缺陷**，不是本次删除新引入的回归。
- 但本次删除后，权限 `system:doc:view`（`data.sql:153`，id 58）**已没有任何端点消费点**；要么补 `GET /api/docs/openapi.json` 绑定，要么把该路径加进 authorization 白名单，否则权限表里留着一个永远用不上的权限。
- `ApiPermissionBindingCoverageTest.java:51` 只扫 `org.chobit.knot.admin.controller` 下的自有 controller；springdoc 的 controller 在第三方包里，不在扫描范围，因此守门测试无法兜住这个 403。

**建议修复**：

1. 在 `data.sql` 增加 `GET /api/docs/openapi.json` → `system:doc:view` 的绑定，并给既有库写幂等迁移（`INSERT IGNORE` 或 `ON DUPLICATE KEY` 语义，注意唯一键是 `http_method + path_pattern`）。
2. 或者把 `/api/docs/openapi.json` 加入 `adminAuthorizationInterceptor` 的 `excludePathPatterns`，仍保留 `AuthInterceptor` 的 JWT 校验；若选这条，需同步更新 `ApiPermissionBindingCoverageTest` 的 `WHITELIST`。
3. 把 springdoc 路径纳入覆盖率守门：至少断言 `springdoc.api-docs.path` 对应的 GET 路径“已绑定或在白名单”，避免第三方 controller 继续成为盲区。
4. 若 API 文档本次不打算交付，则应把 PRD/tech 的“已上线”改为“未实现/未接入”，不要保留错误状态。

### 🟡-2 流式收尾：`loadRelease` 抛异常会截断用量记账与流量事件

**证据链**：

```java
// GatewayRequestHandler.java:621-627
Runnable onComplete = () -> {
    if (loadRelease != null) {
        loadRelease.run();
    }
    recordStreamingUsage(context, routing, terminalUsage.get());
};
```

```java
// GatewayRequestHandler.java:628-634
Runnable base = onComplete;
onComplete = () -> {
    base.run();
    publishTraffic(context, exchange, terminalUsage.get(), firstTokenWriter.elapsedMillis(), null);
};
```

- `ProxyStreamingFlux.java:87-93` 在 `doFinally` 中调用 `onComplete.run()`，没有异常隔离。
- `RedisModelLoadStore.java:70-81` 的 `enter` / `leave` 走 `RedisCache.eval`；`RedisCache` 的故障口径是 fail-hard，Redis 不可用时抛 `RedisUnavailableException`。
- `GatewayRequestHandler.java:344-348` 的 `ATTR_LOAD_RELEASE` 先 `releaseDeferred.set(false)`，再 `releaseLoad.run()`；`releaseLoad` 在 `GatewayRequestHandler.java:302-307` 先 CAS 置位再调用 `leave`。

**后果**：

1. 流式响应已经提交后，`leave` 抛异常 → `recordStreamingUsage` 不执行 → TPM / token 配额 / 成本记账被跳过；
2. 外层 `publishTraffic` 也不执行 → 终态流量事件丢失；
3. `leave` 抛异常时 CAS 已置位、`releaseDeferred` 已置 false，后续兜底不会再重试 → 在途计数只能等 TTL 过期（默认 300 秒）才恢复，期间 `LEAST_LOAD` 选路会持续偏向脏负载；
4. 异常发生在 Reactor `doFinally` 回调里，至少不会回滚已提交响应，但会被 Reactor 丢弃/记录，调用方可能看到连接异常，且没有业务侧告警。

**第二个窗口：延迟释放没有 owner**：

- `GatewayRequestHandler.java:357` 在候选成功返回前 `releaseDeferred.set(true)`。
- 候选 Mono 的 `doFinally`（`:389-396`）此时会跳过释放。
- 之后 `AbstractGatewayRequestTemplate.java:163-166` 调 `onProxyResult` → `GatewayRequestHandler.java:553-562` 调 `streamResponse`；`streamResponse` 在 `:613` 先 `prepareStreaming`。
- 如果 `streamResponse` 构造阶段（例如 `prepareStreaming` 的 `MediaType` 非法）抛异常，流还没订阅、`doFinally` 还没挂上，`loadRelease` 没有 owner，在途计数同样泄漏。

**测试缺口**：

- `GatewayRequestHandlerLoadReleaseTest` 覆盖的是非流式候选成功后 `trafficGuard.record` 抛 Redis 异常；
- `GatewayRequestHandlerStreamingTrafficTest` 只直接调用 `recordStreamingUsage`，没有覆盖“流式 `leave` 抛异常”或“`streamResponse` 构造抛异常”；
- 因此这两条代码路径成立，但**本轮没有补反向故障注入测试**。

**建议修复**：

1. 把收尾三步分别隔离：`loadRelease`、`recordStreamingUsage`、`publishTraffic` 各自 `try/catch`，任何一步失败都不得阻断后续；`loadRelease` 失败要单独计数/打点，不能只靠 Reactor 日志。
2. 在 `streamResponse` 构造阶段用 `try { ... } catch (RuntimeException e) { releaseLoad.run(); throw e; }` 明确归还延迟释放；或把 `ATTR_LOAD_RELEASE` 的生命周期收敛到响应写出的 `Mono.doFinally`，保证“延迟释放”总有 owner。
3. 增加故障注入测试：`ModelLoadStore.leave` 抛 `RedisUnavailableException`，断言 `recordStreamingUsage` / `publishTraffic` 仍执行、在途最终可归零；再补 `prepareStreaming` 抛异常的构造期用例。
4. `releaseLoad` 的 CAS 不应在 `leave` 之前就不可逆置位；若要重试，可改为“成功后置位”或记录失败状态并由 TTL 兜底。

### 🟡-3 词库缓存刷新仍使用 `ForkJoinPool.commonPool()`

**证据**：

- `ModerationWordResource.java:68-74`：

```java
this.cache = Caffeine.newBuilder()
        .expireAfterWrite(EXPIRE_AFTER_WRITE)
        .refreshAfterWrite(REFRESH_AFTER_WRITE)
        .build(key -> {
            List<ModerationTerm> terms = moderationWordService.loadEnabledTerms();
            ...
        });
```

没有 `.executor(...)`。

- loader 调 `ModerationWordService.loadEnabledTerms()`，底层是 MyBatis / JDBC 阻塞查询。
- 对照 `GatewayConfigCacheService.java:289-295` 已显式 `.executor(refreshExecutor)`；`GatewayAsyncConfiguration.java:57-63` 提供专用 `gatewayConfigRefreshExecutor`。
- `GatewayConfigCacheServiceRefreshExecutorTest` 已守门配置缓存；`ModerationWordResourceTest` 没有等价的执行器断言。

**影响**：`refreshAfterWrite` 的后台刷新会回落到 `ForkJoinPool.commonPool()`；该池并行度通常等于 CPU 核数，一次慢查询会与并行流等 commonPool 使用者抢线程，并让同一窗口内的刷新排队。词库只有一个 key，频率低于配置缓存，所以影响面小于上一轮的配置缓存问题，但**同一类“阻塞 loader 不得进 commonPool”的约束没有一致落地**。

**建议**：给词库资源注入专用执行器（可复用 `gatewayConfigRefreshExecutor`，或独立单线程池）；补一个与 `GatewayConfigCacheServiceRefreshExecutorTest` 同型的 `refresh` 执行器探针。

### 🟡-4 Redis 存储的 fail-hard 契约与 null/脏值兜底不一致

**证据**：

- `RedisTrafficCounterStore.java:12-18` 类注释声明 fail-hard：Redis 不可用时抛异常，不能静默放行。
- `RedisTrafficCounterStore.java:50-54`：Lua 返回 `null` 时 `return delta`。
- `RedisTrafficCounterStore.java:58-68`：非数字脏值返回 `0L`。
- `RedisModelLoadStore.java:70-75`：Lua `null` 时 `return 0L`。
- `RedisModelLoadStore.java:102-115`：`null` / 空 / 非数字 / 负数统一按 `0`。

**边界**：

- `RedisCache` 对真正的 Redis 访问异常会包装成 `RedisUnavailableException` 上抛，这部分 fail-hard 是成立的。
- 正常“键不存在”返回 `null`，按 0 处理是合理语义，不能一律判故障。
- 问题在**异常/脏数据**与**正常缺失**没有区分：Lua 脚本行为异常、序列化异常、非数字值都静默变成 0/增量，没有 ERROR 日志、没有 metric、没有告警。对频控/额度来说，这等于在脏数据或脚本异常时少计、放行。

**建议**：

1. 明确区分“键不存在”和“值格式异常”：`get` / `parseInflight` 的 `NumberFormatException` 至少打 ERROR + 单调计数；若该值会影响安全额度，应抛 `RedisUnavailableException` 进入 503，而不是返回 0。
2. `addAndGet` / `enter` / `leave` 的 Lua `null` 不应静默返回 `delta` / `0`；至少记录异常并计数，或直接抛存储异常。
3. 给“Redis 正常缺失 / 脏值 / 脚本 null”三类写测试，断言语义不同；当前未见对应测试。

**定级说明**：上一轮复核已把这条从“fail-hard 契约破裂”降级为“异常路径可观测性不足”；本轮维持该判断，记 🟡 低优先级，不把它夸大成必然可利用的安全漏洞。

### 🟡-5 前端 SSE 401 可能误清管理端登录态

**证据**：

- `knot-front/src/api/http.ts:206-207`：

```ts
const {token, clearAllAuthState} = useAuth();
const usesAdminAuth = !requestHeaders.Authorization;
```

- `http.ts:337-345`：`xhr.status === 401 && usesAdminAuth && token.value` 时 `clearAllAuthState()` 并跳 `/login`。
- `http.ts:351-353` 也按 `usesAdminAuth` 决定是否弹管理端错误提示。
- 默认调试头来自 `useTestRequestComposition.ts:133-140`，其中 `Authorization` 是**消费者 API Key**，不是管理端 JWT。
- 调用链 `api/routing.ts:83-89` 的 `testRoutingRuleStream` 直接把这个头表传给 `postEventStream`；它本来就是网关消费者请求，不应按管理端会话处理。

**触发条件**：

1. 用户在调试抽屉 Headers 表格里删掉 `Authorization` 行；
2. 或把名称写成小写 `authorization` / 其他大小写变体；
3. 网关返回 401（确实是没有消费者凭据）。

此时 `usesAdminAuth` 变为 true，前端会清掉管理端 JWT 并强制跳登录——失败的是消费者调试请求，不应影响管理端会话。这个判断把“请求头是否存在”误当成“是否管理端认证”，是认证边界错误。

**建议**：

1. 不要用请求头名称推断认证类型。给 `postEventStream` 增加显式参数（如 `clearAuthOn401: boolean`），网关调试调用固定传 `false`；或直接把 401 清理逻辑从 `postEventStream` 移除（它只服务网关调试，管理端 Axios 拦截器已负责管理端会话）。
2. `postGatewayJson` 目前没有这段清理逻辑，二者行为也不一致；修复时应统一。
3. 补前端反向探针：构造“无 `Authorization` / 小写 `authorization` + 401”，断言**不**调用 `clearAllAuthState`、不跳登录；当前未找到 `postEventStream` 的对应测试。

### 💭-2 死信行格式未转义 `\t` / 换行

- `EventDeadLetterWriter.java:60-61` 以 `时间 \t topic \t key \t cause \t payload` 写单行。
- `causeOf`（`:87-...`）直接取异常 message；异常 message 若含 `\n` / `\t`，会把一条死信拆成多行或打乱字段。
- payload 是 JSON 序列化结果，换行通常已转义；topic 受 Kafka 命名约束；但 key 与 cause 没有显式清洗。
- 当前测试只断言 `line.contains(...)`，没有“cause 含换行/制表符仍保持单行可解析”的用例。

**建议**：对 `topic` / `key` / `cause` 做 `\t\r\n` 替换或转义；或改成“每行一个 JSON 对象”的稳定 JSONL，而不是裸 tab 分隔。死信是“数据不丢”的关键路径，建议至少补一条格式测试。

## 5. 已排除的误报 / 不再重复项

1. **`ModelApiBindingSupport.asyncProfileCodeOf` 的 `protocol` 空值路径**：该方法为 `private`，唯一调用点在 `toEntity` 内；`toEntity` 在 `:149-157` 已先拒绝空协议并 `fromCode` 校验非空，因此 `protocol.streamSupported()` / `matches` 不会收到 null。不记为缺陷。
2. **`AsyncTaskSupport.loadSpec` 的 `protocol == null` 分支**：注释明确“null 表示不做比对”；绑定查找 `bindingOf` 在协议匹配阶段已过滤，运行时不会把 null 协议当成异步。保持现状。
3. **`GatewayTrafficMsgDto` 的 `Map` 用法**：`upstreamUsage` 属于上游动态 payload，符合 `10-backend-java.md §5.1` 的允许场景；不按 B8 误报。
4. **前端 `status === 0`**：抽查的启用/禁用判断均为显式 `=== EnabledStatus.ENABLED` 或 `=== 0`，没有把 0 当 falsy 的写法。
5. **敏感词 fail-open**：`ModerationWordResource` 的 fail-open 是已登记业务语义，且有 `failOpenCounter` / gauge；本轮只报“刷新执行器缺失”，不把 fail-open 本身当缺陷。
6. **`ApiDocController` 删除**：删除占位端点方向正确；不要把“删除”本身当回归，问题是删除后 GET 文档仍无绑定/白名单。
7. **`GlobalExceptionHandler` 的 `ConstraintViolationException`**：返回的是参数校验信息，不是内部异常原文；与已修的通用 500 遮蔽不冲突。
8. **上一轮 🟡-2（候选成功后异常泄漏在途计数）**：当前已有 CAS + `doFinally` + 两个测试；不再重复报。流式收尾是另一个生命周期窗口，单列 §3.2。
