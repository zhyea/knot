# 维度分档价（`DIMENSION_TIERED`）方案与落地记录

> 日期：2026-10-26　范围：`knot-server`（common / adapter / service）+ `knot-front`
> 触发：robin 提出「视频计费通常按 **resolution + 是否输出声音 + 是否有输入视频** 三维分档，
> 目前默认视频计费规则对此支持得不够好；且这类分档规则应该成为一种**独立的计费方案**，
> 与阶梯计费 / 高低峰计费 / 厂商定制计费平级」。
> 同族文档：`docs/视频计费规则类型化方案-2026-10-26.md`（MiniMax）、
> `docs/VENDOR_KLING计费方案-2026-10-26.md`（Kling）。

---

## 1. 先诊断：到底是「不支持」还是「支持得不好」

结论：**键空间早就够用，真正缺的是「拼错没人管」和「第三维恒不命中」两件事。**

### 1.1 维度键空间（2026-10-25 已存在）

`VideoBillingModeCalculator#dimensionKeys(resolution, reference, sound)` 会按
「最具体 → 最宽泛」生成候选链，`BillingConfig#dimensionPrice` 取第一个命中：

```
档位:REFERENCE:AUDIO   有声 + 有输入视频
档位:REFERENCE         无声 + 有输入视频
档位:AUDIO             有声 + 无输入视频
档位                   无声 + 无输入视频
↓ 全部未命中
defaultUnitPrice
```

三维里「分辨率 × 是否输出声音」这两维在 `FIXED` 下本来就能配。

### 1.2 缺口一：第三维（有无输入视频）在通用路径上恒不命中

`VideoBillingUsage` **没有** `hasInputVideo` 字段，只有两个间接信号：

| 信号 | 键表 | 覆盖率 |
| --- | --- | --- |
| `reference`（布尔） | `input_reference` / `reference` / `reference_image` / `reference_video` / `reference_url` / `reference_images` | 只认 `reference_*` 命名的厂商 |
| `inputDurationSeconds`（长） | `input_duration_seconds` / `input_video_seconds` / `input_duration` / `input_video_duration` / `source_duration` / `source_video_seconds` | 主流厂商几乎恒为 0 |

而 Kling 的图生视频 / 视频续写传的是 `image` / `video` / `video_url`，**两个键表一个都不命中**。
通用路径此前直接用 `video.reference()`：这类请求会被判成「无输入视频」，
于是 `:REFERENCE` 档位价**永远取不到**，每条请求都按贵档多收。

> 这正是上一轮 `calculateVendorKling` 里 `hasInput = inputDurationSeconds > 0 || reference`
> 那条修复的由来——**同一个缺陷在通用路径上还留着一份**。

### 1.3 缺口二：维度键拼错是静默的

维度键是**自由文本**，取价是「逐级去尾找第一个命中」。于是：

| 配置 | 实际效果 |
| --- | --- |
| `720P:SOUND` | 无声/有声一律回落 `720P`，**配置看着生效、那档价从未命中** |
| `720P:AUDIO:REFERENCE` | 顺序颠倒，永远进不了候选链，同上 |
| `:AUDIO` | 空档位名，同上 |
| 只配 `INPUT_VIDEO:*` | 输出侧没有档位价，退化成固定价 |

`FIXED` 下这些都**不报错**。本方案把它们变成拒绝保存。

### 1.4 决策：新增独立方案而不是继续塞在固定价里

robin 拍板四项（2026-10-26）：

| # | 决策点 | 结论 |
| --- | --- | --- |
| 1 | 命名与覆盖面 | `DIMENSION_TIERED` **维度分档价**，仅 `VIDEO`（与 `TIERED` 按用量、`PEAK_OFF_PEAK` 按时间构成三根正交轴；不预设必须是分辨率，未来 IMAGE 分档也能进同族） |
| 2 | 「有无输入视频」信号怎么修 | **输入视频 ≡ 参考视频**（robin：本来就是同一维），参考**图**不属于这一维、走图片张数口径；**不动提取层**，在计算器侧统一判据 |
| 3 | 刚做的 `VENDOR_KLING` 是否吸收 | **不吸收**。Kling 更复杂（把「有输入」编码进单价 + 计费量口径二选一），独立保留；`VENDOR_MINIMAX` 同理 |
| 4 | 本轮范围 | **分批：先方案与前端**。本批 = 新增枚举 + 后端校验 + 统一判据 + 前端统一整表 |

## 2. 方案定位：三根正交的轴

| 方案 | 分档依据 | 解决什么 |
| --- | --- | --- |
| `TIERED` | **用量**（总 token / 秒数落哪一档） | Vidu Q2「首秒阶梯」 |
| `PEAK_OFF_PEAK` | **时间**（发生时点打几折） | Vidu 错峰半价 |
| `DIMENSION_TIERED` | **请求属性**（分辨率 × 有声 × 有无输入视频） | 阿里云万相「1080P 有声 0.5、720P 无声 0.15」 |

三者可叠加——分档价一律过方案层倍率链（`resolveDimensionPrice`），
这正是 2026-10-25 修掉「命中分辨率价直接 return 绕过方案层」那处旁路的收益。

> ⚠ `DIMENSION_TIERED` 的**取价算法与 `FIXED` 完全一致**（共用 `FixedPricing`），
> 本方案的真正增量是**保存期的强校验**。把它理解成「一种新的算钱方式」是错的。

## 3. 后端改动

### 3.1 `PricingPlanEnum`（knot-common）

新增第 6 个值，`supports(BillingModeEnum)` 数据驱动，能力矩阵自动下发：

```java
DIMENSION_TIERED("维度分档价", BillingModeEnum.VIDEO);
```

穷举点（**新增枚举值必须补齐，否则编译失败**）：

| 位置 | 处理 |
| --- | --- |
| `BillingConfig#pricingPlan` 工厂 | 与 `FIXED` / `VENDOR_MINIMAX` / `VENDOR_KLING` 并到同一 `case`（取价语义一致） |
| `TokenBillingModeCalculator#calculate` | 同上，`case FIXED, DIMENSION_TIERED, VENDOR_MINIMAX, VENDOR_KLING -> calculateFixed(...)` |
| `VideoBillingModeCalculator#calculate` | 走通用分量路径（无专属分支——专属分支会给通用路径复制一份，见 §6 反模式） |

### 3.2 `BillingConfig#validateDimensionTiered`（四类拦截）

```java
private String validateDimensionTiered() {
    // ① 档位表不能空：一张表没有 = 退化成固定价
    // ② 键形状必须合法：档位名非空 + 后缀 ∈ {"", ":AUDIO", ":REFERENCE", ":REFERENCE:AUDIO"}
    //    （INPUT_VIDEO: / INPUT_IMAGE: 前缀剥掉后按同一形状校验，手写 config_json 仍然合法）
    // ③ defaultUnitPrice 必填：档位未命中时的兜底，缺它 = 识别不了的请求免费出账
    // ④ quantityMode ∈ {SUM, OUTPUT_PLUS_MAX} 与 video.inputVideoPerSecond 不可并存
}
```

**为什么 ③ 是硬约束**：厂商档位不可枚举（768P、540P、2K、4K 及各厂商自造名），
总有配不到的档。命中链走到最后一步是 `resolveDefaultPrice`，
`defaultUnitPrice` 为 null 时会回落 `fallback`（= 0），**整笔 0 元出账**。

**为什么 ④ 是硬约束**：`SUM` / `OUTPUT_PLUS_MAX` 已经把输入秒折进输出量，
`inputVideoPerSecond` 再按分量单独收一次，同一批秒收两遍。
（`quantityMode=OUTPUT` 时二者并存是合法的——那就是 MiniMax 的结构。）

### 3.3 `VideoBillingModeCalculator#hasInputVideo`（统一判据）

```java
/**
 * 「有无输入视频」的唯一判据：上游确实回传了输入时长，或请求侧声明了参考输入。
 */
private static boolean hasInputVideo(VideoBillingUsage video) {
    return video.inputDurationSeconds() > 0 || video.reference();
}
```

调用点（**同一个事实只许有一份定义**）：

| 调用点 | 此前 | 现在 |
| --- | --- | --- |
| 通用路径 · 输出分量维度键 | `video.reference()` | `hasInputVideo(video)` ✅ |
| 通用路径 · 输入视频分量维度键 | `video.reference()` | `hasInputVideo(video)` ✅ |
| 通用路径 · 输入图片分量维度键 | `video.reference()` | `hasInputVideo(video)` ✅ |
| 通用路径 · 附加费触发 | `video.reference()` | `hasInputVideo(video)` ✅ |
| `calculateVendorKling` | 内联的 `inputDurationSeconds > 0 \|\| reference` | `hasInputVideo(video)` ✅ |

`calculateVendorMiniMax` 维持 `false, false`（MiniMax 无 reference / audio 折扣档，是刻意的）。

**探针**（`VideoBillingModeCalculatorTest#dimensionTieredShouldTreatReportedInputSecondsAsReferenceTier`）：
配置 `{"720P": 1.0, "720P:REFERENCE": 0.6}`，用量 `output=10s, input=3s, reference=false` → 期望 `6.0`。
若判据退回只看 `reference`，会得到 `10 × 1.0 = 10.0`（多收 67%）。

## 5. 真实价表对照（阿里云百炼 · 万相图生视频「基于首帧」）

| 模型 | 无声 | 有声 | 免费额度 |
| --- | --- | --- | --- |
| `wan2.6-i2v-flash` | 720P 0.15 / 1080P 0.25 元每秒 | 720P 0.30 / 1080P 0.50 元每秒 | 50 秒 |
| `wan2.6-i2v` | 720P 0.30 / 1080P 0.50 元每秒 | 720P 0.60 / 1080P 1.00 元每秒 | — |

表达成配置（口径 `OUTPUT`、输入侧留空、默认单价取一个兜底值）：

```json
{
  "defaultUnitPrice": 0.30,
  "resolutionPrices": {
    "720P": 0.15, "720P:AUDIO": 0.30,
    "1080P": 0.25, "1080P:AUDIO": 0.50
  }
}
```

两点从这份价表得到的外溢结论：

1. **「仅输出计费」才是默认**——首帧输入图完全不计费。
   这佐证 MiniMax「输入图片按张计费」是特例，不该反向污染通用模型。
2. 万相的声音字段是 **`audio`**，不在现有 `sound` 键表里
   （`generate_audio / with_audio / enable_audio / audio_enabled / sound`）。
   → 记为遗留（见 §7）。

## 6. 反模式：为什么不给 `DIMENSION_TIERED` 开一个专属计算分支

一度考虑过 `VideoBillingModeCalculator#calculateDimensionTiered`，最终否决：

- 通用路径已经做了「三维分档键 + 合成量 + 输入分量 + 附加费」，新分支只是**逐行复制**，
  唯一差异是 `hasInputVideo` —— 而那本身就是通用路径的**缺陷**（§1.2），
  正确做法是修通用路径，不是给新方案开一条「修好的副本」。
- 项目定式：**纯转发壳同样是冗余**；**跨类逐字重复先怀疑归属，不要先合并**。

同理，`计费量口径` 的选择器留在模式组件而不是搬进方案组件——
口径是「量」的轴，搬过去就是与模式组件再复制一份三选项列表。

## 7. 遗留（本轮刻意不动）

| # | 事项 | 风险 | 归属 |
| --- | --- | --- | --- |
| 1 | 万相声音字段是 `audio`，现有 `sound` 键表不含 | 万相的声档价**配了取不到**，恒按无声档出账 | 提取层（`MediaUsageReaders`）；robin 本轮明确「不动提取层」 |
| 2 | `reference` 键表把参考**图**与参考**视频**并成一个布尔 | 传参考图会命中 `:REFERENCE`（语义本应是「含输入视频」）→ 可能**多收** | 同上 |
| 3 | 万相 r2v「计费时长 = 输入视频时长（上限 5 秒）+ 输出视频时长」 | 第四种口径，`OUTPUT / SUM / OUTPUT_PLUS_MAX` 都无法表达（输入要**截断到上限**） | 待定，需 `VideoConfig` 再加一种 quantityMode |
| 4 | `inputDurationSeconds` 键表缺主流厂商字段（恒 0） | 已被 `hasInputVideo` 的 `reference` 分支部分兜住，但「既没 reference 键也没时长键」的请求仍判无输入 | 提取层 |
| 5 | `FIXED` 下的维度键拼错仍是静默回落 | 存量配置不会报错 | 只在 `DIMENSION_TIERED` 拦；存量是否巡检另开单 |
