## 1. 修复清单

### P0-1 · `@MapperScan` 指向已不存在的包（两个 app 都是）

| 项 | 内容 |
|---|---|
| 现象 | `@MapperScan("org.chobit.knot.gateway.mapper")`，实际包在 `org.chobit.knot.dal.mapper`（34 个接口）。字符串不参与编译校验 → 编译全绿、运行期一个 Mapper 都注册不上 |
| 修法 | 改 `@MapperScan(basePackageClasses = AppMapper.class)`。类引用参与编译校验，包再迁移编译期立即报错 |
| 文件 | `knot-admin/.../AdminApplication.java`、`knot-gateway/.../GatewayApplication.java` |

### P0-2 · 组件扫描范围不连续（两个 app 都是）

组件分散在 4 个**平行**顶级包，启动类却住在 `.admin` / `.gateway` 里，`@SpringBootApplication` 默认只扫自己及子包：

| 包 | 组件数 | 归属模块 | 原扫描状态 |
|---|---|---|---|
| `org.chobit.knot.admin.*` | controller/security/service/config/rw/auth | knot-admin | ✅ |
| `org.chobit.knot.gateway.*` | controller/routing/store/traffic/... | knot-gateway | ✅ |
| `org.chobit.knot.svc.*` | 56 个（service/aspect/auth/config/crypto/converter） | knot-service | ❌ 扫不到 |
| `org.chobit.knot.adapter.*` | 25 个（auth/protocol/usage） | knot-adapter | ❌ |
| `org.chobit.knot.plugin.*` | 12 个（builtin/moderation/components/runtime） | knot-plugin | ❌ |

无 `@ComponentScan` / `@Import` / `spring.factories` / `AutoConfiguration.imports` 兜底（已全量确认无 SPI 文件）。

**修法**：`@SpringBootApplication(scanBasePackages = "org.chobit.knot")`。

选 root 而非逐项列举 `.admin/.svc/.adapter/.plugin`：root 包名不随模块增删漂移，不必每加一个模块回来改两处。admin 与 gateway **不互相依赖**（已核 pom），所以上提不会误扫到对方。

> 等价替代方案：把启动类上提到 `org.chobit.knot` 根包（Spring Boot 官方布局），扫描规则隐式成立、连 `scanBasePackages` 都不用写。本次没选它，因为会牵动部署脚本里的 `Started AdminApplication` 日志断言、IDE 运行配置与 `spring-boot-maven-plugin` 的 mainClass 约定，收益不抵风险。若后续模块数继续增加，可以再做。

### P0-5 ·（分析遗漏，新发现）插件 entrypoint 存量数据未迁移 → 启动整屏孤儿 + 插库炸

这是本次修复里**唯一会导致生产事故**的一项，原分析把它错列为 P2「data.sql 类名是 DB 存量」。

**证据链**：

1. 插件实现类随迁移换了包：`org.chobit.knot.gateway.plugin.*` → `org.chobit.knot.plugin.*`（`git ls-tree e606fbd2` 实证）
2. `data.sql` 里 8 条 entrypoint 已同步改成新值，**但那段是 `INSERT IGNORE` + 显式 `id=1..8`** → 既有库主键冲突即**静默跳过**，旧值原封不动
3. `PluginReconcileRunner` 以 IOC 中 `PluginHandler` 的**类名**为权威键匹配 → 旧 entrypoint 一条都匹配不上 → 8 个插件全被判定「代码新增」
4. 实测后果三连：
   - 重复插入 8 行；其中 `deriveInstanceCode` 算出 `provider-request-response-log-upstream_exchange-upstream_response` = **65 字符** > `instance_code VARCHAR(64)` → `MysqlDataTruncation`，**上下文起不来**（本机库实测复现）
   - 已插入成功的 5 行 + 8 个旧行并存 → 插件列表重复
   - 8 个旧行会被标 `orphaned=1` → 前端整屏浅红

**修法（两层）**：

- 新增迁移脚本 `docs/database/migration/2026-10-25-plugin-entrypoint-package-migration.sql`：
  ① `UPDATE ... REPLACE(entrypoint,'org.chobit.knot.gateway.plugin.','org.chobit.knot.plugin.')`（幂等）
  ② 去重：同一 entrypoint 只保留 id 最小者（种子行，带用户改过的 status/名称；删的必然是 reconcile 自动插的长码行）
  ③ `ALTER TABLE kb_plugin_instances MODIFY instance_code VARCHAR(128)`
- `schema.sql` 的 `instance_code` 同步 64 → 128（`CREATE TABLE IF NOT EXISTS` 对新库生效，既有库靠上面的 ALTER）
- `data.sql` 插件段补了告警注释：entrypoint 是 IOC 稳定键，改值对既有库**无效**，必须另写迁移脚本

**部署顺序硬约束**：既有库必须**先跑迁移脚本，再启新 jar**。顺序反了就是上面第 4 步。

**本机库处置**：先只读核实（8 行旧 entrypoint + 5 行自动插入的重复行），再执行迁移（UPDATE 8 / DELETE 5 / ALTER），复核后为 8 行新 entrypoint、短码、零孤儿、列宽 `varchar(128)`。
