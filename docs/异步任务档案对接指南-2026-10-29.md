# 异步任务档案对接指南（视频协议）

> 面向「接一家新的异步上游（视频生成类为主）」。读完这一篇，你能在管理面自己配完一条档案，
> 让模型走「提交 → 轮询 → 回推」而不是等上游同步返回。
>
> 配套页面：**模型管理 → 异步任务档案**（`/model-management/async-task-profiles`）。
> （2026-10-30 从「路由管理」搬到「模型管理」，理由见第 6 节。）
> 事实来源永远是库里那一行；本文与页面里的「厂商模板」都只是「少打十几个字段」的起点。

---

## 1. 档案在链路里的位置

```
客户端 ──POST──▶ 网关 ──提交──▶ 上游（返回 task_id）
                    │
                    ├─ 落一行 kb_async_tasks（poll_spec_json = 提交那一刻的口径快照）
                    ├─ 回 202 + 任务句柄
                    │
   轮询节拍（分钟级 cron）─┬─▶ GET <query_path>?<{task_id}>
                    │        └─ 用快照里的表达式判终态
                    │             · 成功 → 取产物 → 归档 → 回调回推
                    │             · 失败 → 取失败原因 → 归档 → 回调回推
                    └─ 判不出终态 → 继续下一轮，直到次数上限 / 超时
```

**关键点：轮询用的是提交那一刻的快照，不是档案当前值。**

所以改档案不会让在途任务「半路换口径」（那会造成同一个任务前后判定不一致）；
但改完档案**只对之后提交的新任务生效**。排查线上问题时，先看任务行里的 `poll_spec_json`，
再看档案当前值——两者不一致是正常的。

| 东西 | 位置 | 谁改 | 影响面 |
|---|---|---|---|
| 档案（口径） | `kb_async_task_profiles` | 管理面 | 之后提交的新任务 |
| 任务实例（运行数据） | `kb_async_tasks` | 网关 | — |
| 快照（提交时口径） | `kb_async_tasks.poll_spec_json` | 网关（自动） | 单个任务 |

## 2. 档案的表达式与字段

| 列 | 作用 | 求值对象 | 缺它的后果 |
|---|---|---|---|
| `task_id_path` | 从**创建响应**取上游任务 ID | 创建响应 | 取不到 → 回落同步（不回 202） |
| `status_path` | 从**查询响应**取状态原文 | 查询响应 | 取不到 → 一直判「进行中」直到超时 |
| `status_succeeded` | 成功判定（布尔） | 查询响应 + 变量 `status` / `body` | 必填 |
| `status_failed` | 失败判定（布尔） | 同上 | 必填 |
| `status_running` | 进行中判定（布尔） | 同上 | 留空 = 除成功/失败外一律非终态 |
| `result_path` | 终态产物地址 | 查询响应 | 无产物（可空） |
| `result_url_field` | 产物是**对象数组**时取哪个字段 | — | 留空 = 元素本身必须是 URL 字符串 |
| `error_message_path` | 失败原因 | 查询响应 | 留空 = 沿用上游顶层 `message` |

> 判定的布尔表达式里有两个预置变量：`status`（= `status_path` 取到的原文）
> 和 `body`（= 整个查询响应对象，用于 `body.xxx` 这类写法）。取值类表达式直接写路径即可。

### 2.1 失败口径刻意不对称（重要）

| 表达式类型 | 取值失败时 | 原因 |
|---|---|---|
| **取值类**（`task_id_path` / `status_path` / `result_path` / `error_message_path`） | 回 `null`，继续跑 | 「这次没有」是常态，不该让整条链路炸 |
| **判定类**（`status_succeeded` / `status_failed` / `status_running`） | **抛异常**，任务判失败 | 判定表达式写错 = 口径本身是错的，继续轮询只会烧钱 |

写判定表达式时，任何可能抛的写法都要避开（例如对可能为 `null` 的字段先判空）。

### 2.2 判定顺序

**成功 → 失败 → 进行中**。成功判定先命中就不再看失败判定。
（同一份响应既满足成功又满足失败时，以成功为准——「拿到产物」比「报错」更符合事实。）
若状态既不匹配成功、也不匹配失败、且没配运行态，则按 RUNNING 继续轮询直到超时。

## 3. MVEL 2.5.2 的坑（2026-10-29 实测）

档案里的表达式跑在 **MVEL 2.5.2** 上，下面几条是实测结论，**不是**文档抄的：

| 想写 | ❌ 不行 | ✅ 这样写 |
|---|---|---|
| 多值包含 | `status in ('succeed','success')` | `['succeed','success'] contains status` |
| 取数组里每个元素的字段 | `data.task_result.videos.![url]` | `result_path = data.task_result.videos` + `result_url_field = url` |
| 转小写 | `lower(status)` | `status.toLowerCase()` |
| 过滤数组 | `videos.?[url != null]` | 取到数组后由后端逐项过滤（`result_url_field` 口径） |
| map / stream / lambda | `videos.collect{ url }`、`videos.stream().map(...)` | 不用（MVEL 2.5.2 直接 `CompileException`） |

另外两点：

- **大小写敏感**：`['succeed','success'] contains status` 是精确匹配，不含 `SUCCEEDED`。
  想宽匹配就自己写全：`['succeed','success','SUCCEEDED'] contains status`。
- **逗号列表不是数组**：`url1, url2` 在 MVEL 里是「语句序列」，能编译、但运行时取不到数组。
  **保存时的校验抓不到这条**（它能编译），只有**试跑（dry-run）**能暴露——
  试跑会把它判成「取不到产物 / 判定失败」。所以配完务必点「试跑」。

## 4. 厂商模板（新建时一键预填）

管理面「新建」时可选模板，预填后仍是独立配置（保存后改档案不会回写模板）。三个已内置：

### 4.1 可灵 Kling（文生视频）—— `KLING_TASK`

- 查询：`GET /v1/videos/text2video/{task_id}`
- 状态：`data.task_status` 取 `succeed` / `failed`
- 产物：`data.task_result.videos[]` 是**对象数组**，每个对象里的 `url` 是视频地址（`n ≥ 1`）
- 失败原因：`data.task_status_msg`

```
task_id_path      = data.task_id
status_path       = data.task_status
status_succeeded  = ['succeed','success'] contains status
status_failed     = status == 'failed'
status_running    = （空）
result_path       = data.task_result.videos
result_url_field  = url
error_message_path= data.task_status_msg
```

> 可灵一次生成多个视频，所以 `result_path` 指向数组、`result_url_field = url`——
> 这正是当初加 `result_url_field` 列的动机：原来只能吐一个标量地址，`n>1` 必丢产物。

### 4.2 火山方舟 即梦 / Seedance —— `ARK_VIDEO_TASK`

- 查询：`GET /api/v3/contents/generations/tasks/{task_id}`
- 状态四态：`queued` / `running` / `succeeded` / `failed`（加了 `cancelled` 也算失败）
- 产物：`content.video_url` 是**单个**字符串（无需 `result_url_field`）
- 失败原因：`error.message`

```
task_id_path      = id
status_path       = status
status_succeeded  = ['succeeded'] contains status
status_failed     = ['failed','cancelled'] contains status
status_running    = ['queued','running'] contains status
result_path       = content.video_url
result_url_field  = （空）
error_message_path= error.message
```

### 4.3 通用骨架（单产物）

适合「提交返回 id、查询返回 `status` + 单个 `url`」的接口。只填了占位，请按上游文档替换：

```
task_id_path      = data.id
status_path       = data.status
status_succeeded  = ['succeeded','SUCCEEDED'] contains status
status_failed     = ['failed','FAILED'] contains status
result_path       = data.url
result_url_field  = （空）
error_message_path= （空）
```

## 5. 试跑（dry-run）：保存前验一遍

档案表单底部有「试跑」面板：粘一段**上游查询响应 JSON**（成功态、失败态各验一次），
点试跑，后端用**和运行时完全相同的 `verdict(...)` 逻辑**求值，把结果摊开给你看。

返回字段（`AsyncTaskProfileDryRunVo`）：

| 字段 | 含义 |
|---|---|
| `upstreamTaskId` | 创建响应里按 `task_id_path` 取到的任务 ID |
| `status` | 查询响应里按 `status_path` 取到的状态原文 |
| `terminal` | 三值判定：`RUNNING` / `SUCCEEDED` / `FAILED`；**`null` 表示没能判定**（取不到状态或表达式报错） |
| `resultUrls` | 按 `result_path`（+ `result_url_field`）取到的产物，**可能多个** |
| `errorMessage` | 按 `error_message_path` 取到的失败原因 |
| `elapsedHint` | 一句话摘要（如「命中成功，2 个产物」） |
| `errors` | **阻断级**：表达式编译不过、判定返回非布尔、JSON 非法。这些在运行时会让任务判错或抛，必须改 |
| `warnings` | **提示级**：能跑通但结果可疑（典型是「状态既非成功也非失败，又没配运行态」，运行时只会轮询到超时）。不拦保存，但必须看见 |

> ⚠ **`terminal` 为 `null` 不等于「判成 RUNNING」**——前者是「没判定出来」，后者是「明确还在跑」。
> 前端两者渲染成不同行，别混。
>
> ⚠ **试跑是 HTTP 200，错误信息在 `errors` 数组里**，不在响应码。前端已按此处理；调接口时注意。

## 6. 数据库迁移与回滚

本次上线涉及两件事（幂等，可重复执行）：

1. `kb_async_task_profiles` 加两列：`error_message_path`、`result_url_field`（都在 `result_path` 之后，可空）。
2. 菜单 / 权限 / 接口绑定。

> ⚠ **2026-10-30 变更**：菜单 `model.async-task-profiles` 已从「路由管理」搬到**「模型管理」**（sort 80），
> 权限编码前缀随之从 `routing:` 改为 `model:`（id 159~162 不变）。理由是档案唯一的消费方是模型绑定
> （模型表单的「任务协议」下拉）。异步任务**实例**页仍在路由管理下。
> 存量库请用 `docs/database/migration/2026-10-30-async-task-profile-menu-to-model.sql`
> （只改 `db/data.sql` 对存量库无效：`INSERT IGNORE` + 显式 id 会被静默跳过）。

| 文件 | 作用 |
|---|---|
| `docs/database/migration/2026-10-29-async-task-profile-admin.sql` | 正向迁移（含 6 条迁移后自检 SELECT） |
| `docs/database/migration/2026-10-29-async-task-profile-admin-rollback.sql` | 回滚 |
| `docs/database/migration/2026-10-30-async-task-profile-menu-to-model.sql` | 菜单 / 权限搬到模型模块（存量库必跑） |
| `docs/database/migration/2026-10-30-async-task-profile-menu-to-model-rollback.sql` | 搬回路由管理 |

- 加列前查 `INFORMATION_SCHEMA.COLUMNS`，重复执行跳过（MySQL 5.7 不支持 `ADD COLUMN IF NOT EXISTS`）。
- 种子全部 `INSERT IGNORE` + 显式 id，与 `db/data.sql` 完全一致——重启时 `data.sql` 也插同一批 id，先到者生效，不产生第二份。
- 角色授权按 `permission_code` 关联，不依赖硬编码权限 id：`OPERATOR` / `ADMIN` 全量，`DEVELOPER` 只读（page + view）。
- 存量语义：两列都可空，老档案空着走原行为（失败原因沿用顶层 `message`、产物元素必须为标量），**不写数据迁移，不动在途任务**。

⚠ **回滚会丢掉已配置的失败原因表达式与产物字段名**，只在「本次上线完全没填过这两列」时安全。
