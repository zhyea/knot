## 五、补录建议（落地要点）

1. **授权 5 个 Controller 优先**：注解统一 `module="authorization"`（或细分为 `role`/`permission`/`module`/`menu`/`api-binding`），
   `operation` 用 `CREATE/UPDATE/DELETE`；`updateStatus` 用 `UPDATE` + `oldValueSpel/newValueSpel` 取快照。
2. **快照 SpEL 需要 service 支持**：现有模式是 `@xxxService.xxxAuditSnapshot(#p0)`（见 `UserService:161`、
   `ModelService:142`）。授权模块无快照方法，可先只记 `entityId/entityName/description`，
   或补 `auditSnapshot` 方法后再开 `recordOldValue/recordNewValue`。
3. **AuthController**：`login` 无 token 上下文（`operatorId` 来自 request attribute，登录时为空），
   建议 `entityName="#request.username"`、`operation="LOGIN"`；`logout` 同理。
4. **SpEL 参数名**：无 `-parameters` 编译保证时用 `#p0/#p1` 更稳（现有代码两种都在用，新写建议 `#p0`）。
5. 改完按既有流程：全量包 + 真启 jar 打一遍相关接口，确认 `ks_operation_logs` 有落行。

### 7.3 结论与注意点

- **新增能力全部正常**：落行、字段回填、旧/新值快照、失败留痕、查询/筛选/详情均可用。
- 行为约定（沿用切面既有实现，不是新增缺陷）：
  1. **UPDATE 且前后快照完全一致 → 不落行**（`OperationLogAspect#isNoChangeUpdate`），所以管理员重复提交相同表单不留痕；
     GRANT / EXECUTE / CREATE / DELETE 不受此过滤。
  2. 失败操作**会落行**并记 `status=2 + error_msg`；SpEL 取旧值失败仅 warn 吞掉，不影响主流程。

- 两处 `entity_name` 为空（无返回值可用，不影响可追溯性，可选增强）：
  `ScheduledTaskController#trigger`、`ExternalModelController#deleteItem / setIgnored`（这三处只有 `old_value` 里的实体快照可查）。
  若要补，需给 `ScheduledTaskService` / `ExternalModelService` 各加一个「查不到返回 null」的安全方法供 `entityName` SpEL 使用

## 九、该 bug 的修复（robin 拍板：改）

### 9.1 根因（比初报更深一层）

`ProviderProfileMapper.xml` 的 6 条引用检查**整体把「供应商档案 id」当成了「供应商账户 id / code」**：

| 旧 SQL | 问题 |
|---|---|
| `kb_provider_credentials where provider_account_id = #{providerId}` | 参数是档案 id，列要的是账户 id → 语义错 |
| `kb_provider_discount_policies where provider_account_id = #{providerId}` | 同上 |
| `kb_models where provider_account_code = (select code from kb_provider_accounts where id = #{providerId})` | 同上 |
| `kb_provider_model_mappings where provider_account_code = (... where id = #{providerId})` | 同上 |
| `kb_billing_rules where provider_code = (...)` | 表无此列 → **必 500** |
| `kb_provider_accounts where provider_code = (select code from kb_providers where id = #{providerId})` | 唯一没错的（绕一圈等价于直接按 code 查） |

### 9.2 改法（对齐「跨模块绑定存 code 不存 id」的既有约定）

- Mapper 接口：`countXxxByProviderId(Long)` → `countXxxByProviderCode(String)`（`@Param("providerCode")`），
  **删除** `countBillingRulesByProviderId`（`kb_billing_rules` 只有 `code / model_family / status /
  is_deleted / remark`，与供应商无关联；`BillingService#reconcile` 只是占位实现）。
- XML：按「档案 code → 账户 → 账户下的凭据 / 折扣策略 / 模型 / 映射」二级关联重写
  （`provider_account_id in (select id from kb_provider_accounts where provider_code = #{providerCode})`
   与 `provider_account_code in (select code ...)`），`kb_models` 保留 `is_deleted = 0`。
- Service：`delete` 先取实体拿 code 再检查；冲突时抛
  `BusinessException(ErrorCode.CONFLICT, "供应商档案下仍有关联账户或账户数据，无法删除")`
  （原来是无 message 的裸 CONFLICT，对齐授权模块「角色已绑定用户，无法删除」的写法）。
- 无 DDL 变更 → **不需要迁移脚本**。
