## 1. 背景

当前计费用量提取存在两条入口：

1. `UsageExtractorRegistry` 优先调用模型绑定配置的 `UsageExtractor`。
2. 提取器无结果时，`UsageExtractorRegistry` 回退到 `UpstreamRequestAdapter.extractUsage`。

相关位置：

- 适配器默认实现：`knot-adapter/.../adapter/request/UpstreamRequestAdapter.java:56`
- 注册表兜底：`knot-gateway/.../upstream/usage/UsageExtractorRegistry.java:80`
- Anthropic 覆写：`knot-adapter/.../adapter/request/AnthropicRequestAdapter.java:75`
- Bedrock 覆写：`knot-adapter/.../adapter/request/BedrockConverseRequestAdapter.java:191`

该设计已经失去合理性：

- `UsageExtractor` 已成为用量的唯一领域模型，适配器侧解析属于重复实现。
- Anthropic 与 Bedrock 的适配器覆写和各自提取器口径重复，存在双源漂移风险。
- 未知或错误的 `usage_extractor` 编码会被兜底逻辑掩盖，最终表现为「空用量/零计费」，而不是配置错误。
- 适配器职责从「请求/响应形态转换」扩散到「计费语义解析」，边界不清晰。

## 2. 目标与原则

### 2.1 目标

- 适配器不再解析计费用量。
- 用量提取只保留 `UsageExtractor` 一条链路。
- extractor 缺失、编码错误、提取结果违反契约时立即失败。
- 流式请求在开始转发前完成 extractor 预检，避免响应头已发出后才暴露配置错误。
- 清理因兜底逻辑产生的流式适配器依赖和测试桩。

### 2.2 设计原则

1. **单一事实来源**：计费用量只能由配置的 `UsageExtractor` 产出。
2. **适配器无计费语义**：`UpstreamRequestAdapter` 只负责请求/响应形态转换、路径与内容类型解析、流式能力声明。
3. **禁止静默归零**：提取器不存在或返回非法结果时抛错，不把错误降级为空用量。
4. **错误前置**：能预检的错误必须在上游请求或流式响应开始前暴露。
5. **区分空值与错误**：SSE 中间事件没有 `usage` 是正常协议行为；完整响应或明确带有 `usage` 的事件提取为空则属于异常信号。
6. **区分「未上报」与「未解析」**：上游没回 usage ≠ 网关解析不出来。二者必须走不同分支（§5.4）。

## 3. 范围

### 3.1 本次范围

- 删除 `UpstreamRequestAdapter` 的用量提取 API。
- 删除 Anthropic、Bedrock 适配器中的用量解析覆写。
- 收敛 `UsageExtractorRegistry` 的提取链路与错误语义（含三分支空用量判据）。
- **`UsageRawReader` 解析失败改为上抛**（`fromJson` → `fromJsonOrThrow`），使「非法 JSON」可被感知。
- 清理 `ProxyStreamingFlux`、`UpstreamStreamResponse` 中仅为兜底存在的适配器依赖。
- 调整 `BillingFactAssembler` 离线影子链的默认提取器回落（改为显式标记，不抛异常）。
- 更新相关单元测试与测试桩。

### 3.2 非目标

- 不修改计费规则三级回退：模型 `billing_rule_code` → 模型族精确匹配 → 默认规则。
- 不修改计费模式、价格计算器、金额格式或 `knot_extend` 输出契约。
- 不修改数据库表结构，不新增迁移脚本。
- 不修改前端。
- 不删除 `DEFAULT-TOKEN` 提取器；它是显式配置项，不是本次要移除的兜底路径。
- 不改动 `resolveExtractorCode` 的协议推断（IMAGE/VIDEO/AUDIO 按协议确定性选取，不是兜底）。

## 4. 现状与问题

### 4.1 当前链路

```text
上游响应
  → UsageExtractorRegistry
      → 解析配置的 UsageExtractor
          → 有 billing：归一化
          → 无 billing：UpstreamRequestAdapter.extractUsage
              → 再解析响应或 SSE
              → 仍然为空：生成空 billing / 空 normalized
```

### 4.2 主要问题

| 问题 | 影响 |
|---|---|
| 适配器与提取器重复解析 | 两处口径可能漂移，修一处漏一处 |
| 未知 extractor 编码被兜底 | 配置错误被伪装成空用量，问题延迟到对账才发现 |
| 空 billing 继续生成空账 | 计费静默归零，无法区分「上游未上报」和「网关解析失败」 |
| 流式事件逐条解析时才校验 extractor | 响应头可能已写出，配置错误无法通过 HTTP 状态反馈 |
| `UpstreamStreamResponse` 持有 adapter | 仅为兜底传递依赖，链路职责不纯 |
| 非法 JSON 被 `JsonKit.fromJson` 吞掉 | 解析失败与「上游没回 usage」无法区分（见 §4.4） |

### 4.3 关键证据：删兜底在正确配置下是零行为变化

三处口径逐字比对（这是本方案低风险的依据）：

| 场景 | 提取器实现 | 适配器兜底实现 | 结论 |
|---|---|---|---|
| DEFAULT | `DefaultTokenUsageExtractor:62`<br>`TokenBillingUsage.fromResponse(body)` | `UpstreamRequestAdapter:71`<br>`TokenBillingUsage.fromResponse(body)` | **逐字相同** |
| Bedrock | `BedrockConverseUsageExtractor:69`<br>`BedrockConverseUsageSupport.fromResponse(body)` | `BedrockConverseRequestAdapter:192`<br>`BedrockConverseUsageSupport.fromResponse(body)` | **逐字相同** |
| Anthropic | `AnthropicUsageExtractor`（同一出口） | `AnthropicRequestAdapter:77`<br>`fromResponse().withCacheCountedInInput()`<br>注释自认「与 AnthropicUsageExtractor 同一出口」 | 同源 |

推论：只要 binding 配对了 extractor，兜底分支产出的结果与提取器**恒等**，属于纯冗余。唯一有行为差异的场景是「提取器产出空、但适配器覆写能产出非空」——见 §11 风险表。

### 4.4 非法 JSON 当前不可感知

`UsageRawReader.readMap` → `JsonKit.fromJson`，而 `JsonKit:138-141` 是 `catch → log.error → return null`，**异常被吞**。

后果：上游返回非法 JSON 时，链路看到的是 `rawBody == null` → `rawUsage == null` → `billing` 空，与「上游没回 usage」**完全无法区分**。§5.4 的三分支判据依赖能区分这两者，因此必须先做 §6 Phase 2 第 1 步的 `fromJsonOrThrow` 改造。

`readBody` 生产调用点仅 `UsageExtractorRegistry:65` 一处（另有 3 处测试调用，传的都是合法 JSON），改造面很小。

## 5. 目标设计

### 5.1 职责边界

| 组件 | 职责 |
|---|---|
| `UpstreamRequestAdapter` | 请求体转换、路径与 Content-Type 解析、响应形态转换、流式能力声明 |
| `UsageExtractorCatalog` | 注册、索引和解析用量提取器 |
| `UsageExtractor` | 从上游响应和请求体中提取 `UsageExtractItem` |
| `UsageRawReader` | 读取原文载体，**解析失败上抛**（不再吞异常） |
| `UsageExtractorRegistry` | 选择 extractor、执行提取、归一化计费、管理失败语义 |
| `ProxyStreamingFlux` | 转发 SSE、逐事件提取用量、注入 `knot_extend`，不负责选择 extractor |

### 5.2 目标链路

```text
上游响应
  → UsageExtractorRegistry
      → UsageRawReader.readBody（解析失败即抛，不降级）
      → 解析并校验 UsageExtractor
          → 不存在：立即失败
          → 存在：执行 extractUsageBody
              → 返回 null：契约错误，立即失败
              → 返回 UsageExtractItem：按 §5.4 三分支判空后归一化
```

流式请求在建立上游流之前先执行一次 extractor 预检；预检失败时不发起上游请求。流开始后不再进行 extractor 存在性判断，只处理运行期提取结果。

### 5.3 错误语义（2026-10-24 修订）

> **初稿缺陷**：初稿把「整包响应提取结果为空」一律判为计费异常。这会误杀——`DEFAULT-TOKEN` 对不含 `usage` 的响应返回 `empty()` 是**合法常态**（大量供应商/接口不回 usage）。按初稿字面实施会把这些正常请求全部打成失败。

修订后的错误语义：

| 场景 | 处理方式 |
|---|---|
| 配置的 extractor 编码非空但无法解析 | 请求开始前抛异常，错误信息包含具体编码 |
| extractor 返回 `null`（或 `billing` 为 `null`） | 视为实现违约，直接抛异常 |
| 上游响应 JSON 无法解析 | 严格解析失败，抛异常（依赖 `UsageRawReader` 改造） |
| **响应本身不含 `usage` 字段，提取为空** | **合法零用量**，记 WARN + 指标，正常返回零账 |
| **响应含 `usage` 但提取结果为空** | **口径错配**，记 ERROR + 指标并抛异常 |
| SSE 中间事件不含 `usage` | 合法，不调用提取器，继续转发 |
| SSE 流结束仍无任何用量 | 记 WARN + 指标，不伪造空账（现状已不伪造） |

错误类型：

- 配置错误（extractor 不存在、编码非法）：`IllegalStateException` 或统一网关配置异常。
- 响应提取错误（JSON 非法、extractor 返回 null、应有用量却为空）：明确的计费提取异常，避免与普通业务校验混用。

具体异常类型在实施时结合现有错误码体系确定，不新增语义模糊的通用异常。

### 5.4 空用量三分支判据（新增，2026-10-24 二轮修订）

判据依赖 `rawUsage`（`UsageExtractorRegistry:66` 已取到，无需新增读取）。

**「能不能为空」由提取器声明，注册表不跨协议猜**：`UsageExtractor.allowsEmptyUsage()` 默认 `false`，
少数供应商的 usage 带本提取器不消费的字段（如 `reasoning_tokens`、媒体时长）导致 token 分项全零时，
由该提取器显式覆写为 `true` 放行。这遵循「协议语义由提取器边界一次性决定」的纪律。

「存在正数」由 `hasPositiveNumber` 判定——递归下钻嵌套字段，把「上游合法上报全零」排除在错配之外。

```text
extractor.extractUsageBody(...) 返回 item
  ├─ item == null 或 item.billing() == null ──→ 契约错误，抛异常，不生成账
  ├─ billing 非空 ──────────────────────────→ 正常归一化计费
  └─ billing 为空
       ├─ 提取器声明 allowsEmptyUsage() ──────→ 合法零用量 + WARN（如 TOKEN_ALLOW_EMPTY）
       ├─ rawUsage 无正数（缺失 / 全零）──────→ 合法零用量 + WARN
       └─ rawUsage 有正数 ──────────────────→ 口径错配：ERROR + 立即失败
```

```java
// UsageExtractorRegistry:98-112（实现）
if (item == null || item.billing() == null) {
    throw new IllegalStateException("UsageExtractor returned no result: " + extractor.code());
}
// 能否为空由提取器声明，不在这里跨协议猜
if (item.billing().isEmpty() && !extractor.allowsEmptyUsage() && hasPositiveNumber(rawUsage)) {
    log.error("usage extractor mismatch: extractor={} rawUsageKeys={}", ...);
    throw new IllegalStateException("UsageExtractor cannot read upstream usage: " + extractor.code());
}
if (item.billing().isEmpty()) {
    log.warn("upstream reported no usage: extractor={} protocol={} allowsEmpty={}", ...);
}
return normalize(item, rawBody, rawUsage, billingRule, requestBody, occurredAt, extractor.calculator());
```

### 5.5 fail-fast 的真实覆盖面（新增，澄清）

`resolveExtractorCode` 末行恒返回 `usageExtractorCatalog.defaultExtractor().code()`（`UsageExtractorRegistry:141`），因此：

- **未配置** extractor → 落到 `DEFAULT-TOKEN`，**永远解析成功**，fail-fast 不触发。
- **配了错误 code** → `resolve` 返回 null → fail-fast 触发。

结论：fail-fast 的风险面**只有「显式配了错误 code」这一种**。§9 的上线前扫描因此是必要且唯一的防线，不要以为它能兜住「未配置」。

### 5.6 现状已满足、无需新做的两条（新增，澄清）

初稿 §8.1 列了两条其实**代码里已经做到**的测试项，不必新做：

| 初稿测试项 | 现状 | 证据 |
|---|---|---|
| SSE 中间事件无 `usage` 时不调用提取器 | 已满足 | `ProxyStreamingFlux:192` 的 `!data.contains(USAGE_FIELD)` 门控 |
| SSE 流结束仍无用量不伪造空账 | 已满足 | `UsageState.usageLine()`（`ProxyStreamingFlux:261`）value 为 null 时返回 null，不注入 |

本批只需**补 WARN/ERROR 日志与指标**，不改行为。

> 顺带修正：上述门控用字符串 `data.contains("usage")` 判断，正文里出现该词会误判为「有用量事件」。建议改用 `UsageRawReader.readUsage(解析后的 map) != null` 做结构判断。此项可选，不阻断本方案。

## 6. 分阶段实施

### Phase 1：删除适配器兜底

1. 在 `UpstreamRequestAdapter` 中删除：
   - `extractUsage`
   - `extractUsageFromBody`
   - `extractEventStreamUsage`
   - `isEventStream`
   - `readMap`
2. 清理不再使用的 `BillingUsage`、`TokenBillingUsage`、`JsonKit`、`TypeReference`、`Map` 等 import。
3. 删除 `AnthropicRequestAdapter` 与 `BedrockConverseRequestAdapter` 的 `extractUsageFromBody` 覆写。
4. 全量 grep `extractUsageFromBody`、`extractEventStreamUsage`、`adapter.extractUsage`，确认无残留。

### Phase 2：收敛 Registry

1. **`UsageRawReader.readMap` 改用 `JsonKit.fromJsonOrThrow`**（`JsonKit:162`），使非法 JSON 上抛；`readBody` 相应声明抛出，由 registry 转成领域异常。
   > 前置步骤：§5.4 的三分支判据依赖它能区分「未上报」与「未解析」。
2. `UsageExtractorRegistry.extract` 和 `extractEvent` 去掉 `UpstreamRequestAdapter` 参数。
3. 删除 extractor 为空后的适配器回退分支。
4. 删除 `fallbackCalculator`。
5. 增加 `requireExtractor` 语义：解析失败直接抛异常，错误信息包含 extractor code。
6. 增加 `UsageExtractItem` 非空校验；返回 null 视为 extractor 契约错误。
7. 按 §5.4 接入三分支空用量判据（WARN/ERROR 日志 + 指标）。
8. 提取结果直接进入 `normalize`，不再生成 fallback item。

### Phase 3：流式前置校验与依赖清理

1. 在 `AbstractUpstreamProtocolExecutor.executeStreaming` 建立上游连接前调用 extractor 预检。
2. **预检只做 resolve，不执行提取**（此时没有 body 可提）。签名建议：
   `UsageExtractor<?> requireExtractor(boolean eventStream, UpstreamRequestContext context)`，
   与 `resolveExtractorCode` 复用同一套选择逻辑，避免两套实现。
3. `ProxyStreamingFlux` 调用注册表时只传 `eventData` 和 `context`。
4. 删除 `UpstreamStreamResponse` 中无其他用途的 `adapter` 字段、访问器和构造参数。
5. 更新所有 `UpstreamStreamResponse` 构造点及测试（编译期即可发现）。

### Phase 4：离线影子链对齐（改法已修订）

`BillingFactAssembler` 目前存在两处静默回落：

- `resolveExtractor` 在编码不存在时回落到 `defaultExtractor`（`:77`）。
- `extractUsage` 在 billing 为 null 时返回 `TokenBillingUsage.empty()`（`:86`）。

**初稿建议「直接暴露配置错误、抛异常」，评审否决。** 理由：`BillingFactAssembler` 是管理端**离线复算/影子链**，语义是「尽力算出来给你对照」，不是生产计费闸门。抛异常会让路由测试抽屉直接报错、用户看不到影子对照结果（`RoutingTestBillingVerdictService` 也依赖这条链）。

修订后的改法：**保留回落，但让回落可见**。

- 在 `BillingFact` 中显式标记回落来源（如新增 `extractorFallback` 布尔字段，或复用既有 `BillingRuleSource` 风格）。
- 提取结果为空/null 时照样产出 `BillingFact`，但标记 `usageAbsent`，由裁判层/UI 决定是否告警。
- 路由测试断言从「默认提取器仍能重算」改为「回落可见、错误配置可被识别」。

同样满足「错误配置可见」，且不炸链路。

## 8. 测试方案

### 14.6 二轮：允许空用量的提取器声明（2026-10-24）

第一轮用 `hasPositiveNumber` 把「上游合法上报全零」排除在错配之外，但那仍是注册表在跨协议猜语义。
按 §12 第 2 项与「协议语义由提取器边界一次性决定」的纪律，改为**提取器显式声明**：

| 改动 | 位置 |
|---|---|
| `allowsEmptyUsage()` default 方法，默认 `false` | `knot-adapter/.../usage/extractor/UsageExtractor.java` |
| 新建 `EmptyAllowedTokenUsageExtractor`（code `TOKEN_ALLOW_EMPTY`，`@Order(1)`）：取量口径与 `DEFAULT-TOKEN` 同一出口 `TokenBillingUsage.fromResponse`，唯一差别是声明允许全零 | `knot-adapter/.../usage/extractor/EmptyAllowedTokenUsageExtractor.java` |
| 门控改为 `!extractor.allowsEmptyUsage() && hasPositiveNumber(rawUsage)` | `knot-gateway/.../UsageExtractorRegistry.java:101` |

**用法**：上游 usage 含本提取器不消费的正数字段（如 `reasoning_tokens`、媒体时长）、
而 token 分项被读成 0 的供应商，把模型绑定的 `usage_extractor` 设为 `TOKEN_ALLOW_EMPTY` 即放行。

**边界**：它不解析新协议、不猜字段语义，只声明「这个模型允许全零」——因此是显式配置而非兜底，
也**不能**替代 camelCase 等场景去绑定专用提取器（`BEDROCK_CONVERSE`）。

**测试**：`allowsEmptyUsageWhenExtractorDeclaresIt`（声明允许 → 有正数也放行）、
`shouldDeclareEmptyAllowedOnTolerantExtractorOnly`（默认 false / 新类 true）、
`shouldShareTokenUsageSemanticsWithDefaultExtractor`（两者取量口径必须一致）。

门禁：BUILD SUCCESS，**852 用例**（111+3+36+135+152+110+305），日志 `audit/allowempty-test.log`。

### 14.7 三轮：提取失败的中断开关（2026-10-24）

**问题**：前两轮把 fail-fast 写死在 `UsageExtractorRegistry` 的三处 `throw` 里。上游协议变更导致成片失败时，
这是最坏的商业结果——上游已生成并计费，调用方却拿不到响应（我们付钱、用户没结果）。
需要部署级开关，但不能因此放松默认红线。

**口径（先对齐再动手）**

- 默认 `fail`：出厂仍让失败可见，静默零账不进默认路径。
- 覆盖面只有三处**提取失败**；**未知 extractor code 恒 fail-fast**——那是配置错误，
  降级它等于让该绑定下所有请求永久零账且无自愈路径。

**结构性改动（关键不是加开关，而是先收敛）**：三处失败原本各写各的 `throw`，直接加开关就要改三处，
后续每加一种失败情形还会漏改。改为「判定」与「处置」分离：

```
readBody 非法 JSON ──┐
item/billing 为 null ├─→ judgeExtractResult → ExtractFailure(原因+稳定 code) → applyFailurePolicy ─┬→ throw ISE
口径错配 ───────────┘                                                                        └→ UsageAccounting.degraded(...)
```

| 改动 | 位置 |
|---|---|
| 新建 `UsageExtractionProperties`（prefix `knot.gateway.usage`；字段 `onExtractFailure`，嵌套枚举 `OnExtractFailure{FAIL,DEGRADE}`；派生 `interruptOnFailure()`，`null` 按 FAIL） | `knot-gateway/.../config/UsageExtractionProperties.java` |
| 新建 `UsageExtractionConfiguration`（`@Configuration` + `@EnableConfigurationProperties`，同 `JevJudgeConfiguration` 模式） | `knot-gateway/.../config/UsageExtractionConfiguration.java` |
| 新建降级账目工厂 `degraded(rawUsage, rawBody)`：`billing` 空、`normalized`/`usage` 为 null，**保留上游原文** | `knot-adapter/.../model/UsageAccounting.java` |
| `extract(...)` 收敛三处失败为 `ExtractFailure`，加 `judgeExtractResult`（判定）与 `applyFailurePolicy`（唯一处置） | `knot-gateway/.../upstream/usage/UsageExtractorRegistry.java` |
| 删 `readRawBody`：其 try/catch 并入 `extract`，非法 JSON 从「直接抛」变成一种失败原因 | 同上 |
| yml 显式列出开关 + 注释（含「未知 code 不受影响」） | `knot-gateway/src/main/resources/application.yml` |

**降级产出的形状 = 既有「上游未上报 usage」分支**：`billing` 空 → `isEmpty()` 为 true →
`KnotExtendPayload.of` 返回 `null`（不出 billing 块），影子链侧 `BillingFactAssembler` 的 `usageAbsent` 自动为 true。
**零下游新管道**，因此没有新增行为风险面——这是选择「路由到既有合法零用量分支」而不是「新造一条降级数据流」的直接原因。

**日志**：两档都走 `log.error`，固定 5 项 `reason / extractor / protocol / rawUsageKeys / interrupt`；
