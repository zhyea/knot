## 2. 🔴 发布阻断项

### 🔴-1 后端测试夹具被 `.gitignore` 忽略，干净 checkout 必然红

**证据**

- `.gitignore:27` 使用通配 `*.json`。
- `knot-server/knot-service/src/test/java/org/chobit/knot/svc/service/external/XFusionAIModelSyncProviderTest.java:33` 依赖 `/external/xfusionai-pricing.json`；`:183-190` 找不到资源时直接断言失败。
- `git ls-files` 确认该夹具未入库；`git archive HEAD` 中同样不存在；本机 `knot-server/knot-service/src/test/resources` 目录也不存在。
- surefire：`Tests run: 11, Failures: 9`，9 条失败均以 `缺少测试夹具: /external/xfusionai-pricing.json` 收尾。

**影响**

任何干净 checkout / CI 都会在 `knot-service` 失败，导致 `knot-admin`、`knot-gateway` 的测试根本不执行。这不是“某个断言偶发”，而是测试资产未入库。

**修复建议**

1. 将夹具提交到 `knot-server/knot-service/src/test/resources/external/xfusionai-pricing.json`。
2. 收窄 `.gitignore` 的 `*.json`：至少增加白名单，或改成具体生成物路径；否则任何新增 JSON fixture 都会再次静默丢失。
3. 加一个“测试资源存在性”断言或 CI 探针，避免同类问题再次以 9 个红色用例的形式暴露。

### 🔴-2 `package-lock.json` 未入库，CI 的 `npm ci` 必然失败

**证据**

- `.gitignore:23` 忽略 `*/package-lock.json`，`:27` 又忽略 `*.json`。
- `.github/workflows/ci.yml:97` 把 `knot-front/package-lock.json` 当作缓存依赖路径；`:99-101` 执行 `npm ci`。
- 当前工作区有未跟踪的 `knot-front/package-lock.json`，所以本机 `npm ci --dry-run` 能继续；但用 `git archive HEAD knot-front` 导出的干净副本中锁文件缺失。
- 干净副本实测：`LOCK_MISSING`，`npm ci --dry-run` 返回 `EXIT=1`，报错首行为 `npm error code EUSAGE`，明确要求现有 `package-lock.json` 或 `npm-shrinkwrap.json`。

**影响**

1. CI 前端 job 在安装阶段即失败，后续单测、类型检查、构建全部不会执行。
2. 即使临时绕过 `npm ci`，没有锁文件也意味着依赖版本不可复现；同一份源码在 10-30 与 11-05 可能解析到不同 patch 版本，历史“类型检查全绿”的结论因此不可复用。

**修复建议**

1. 删除 `.gitignore` 中对 `package-lock.json` 的忽略，或为 `knot-front/package-lock.json` 增加明确的否定规则。
2. 用当前 `npm install` 生成锁文件并提交；确认 CI 的 Node 22/npm 版本能正常读取。
3. 保持 CI 使用 `npm ci`，不要退回 `npm install`；锁文件与 `npm ci` 是本项目前端可复现性的最低要求。

### 🔴-3 `RoutingRuleOutagePanel.vue` 的 4 个 `TS2345` 使类型门禁红

**证据**

- `knot-front/src/components/routing/RoutingRuleOutagePanel.vue:20,21,30,34` 在 Element Plus 表格 slot 中把 `DefaultRow` 直接传给要求 `OutageRow` 的函数。
- 组件内 `:88` 定义 `type OutageRow = GatewayOutageItem & { _acting?: boolean }`；`isEjected` / `formatCooldown` / `releaseOutage` 的参数均是 `OutageRow`。
- 当前 `vue-tsc` 与 `--noUnusedLocals` 都报 4 个同类错误；`vite build` 通过不代表类型门禁通过。

**影响**

前端 CI 的两道类型门禁都会红；由于 `package.json:10` 的 `build` 本身是 `vue-tsc --noEmit && vite build`，本地直接 `npm run build` 也会失败。当前 `npx vite build` 绿只说明“纯构建”能产出资源，不能作为可合入证据。

**修复建议**

在表格 slot 边界做一次显式的类型收窄（例如定义 `asOutageRow(row: DefaultRow): OutageRow`，只在边界处做一次受控断言），或在模板表达式中收窄；不要把业务函数的参数改成 `any` 来换绿。修复后同时跑 `vue-tsc --noEmit` 与 `type-check:strict`，并保留现有组件直测。

### 🔴-4 干净 checkout 的 CI 顺序拿不到自动生成的声明文件

**证据**

- `knot-front/vite.config.ts:11-18` 配置 `AutoImport` / `Components` 生成 `auto-imports.d.ts` 与 `components.d.ts`；`knot-front/tsconfig.json:40-41` 又显式把它们列入编译范围。
- `knot-front/.gitignore:3` 忽略 `*.d.ts`，两个声明文件均未入库。
- `.github/workflows/ci.yml:105-125` 的顺序是 `vitest → vue-tsc → type-check:strict → vite build`，类型检查早于会生成声明文件的 `vite build`。
- 用 `git archive HEAD knot-front` 导出干净副本（仅链接本地 `node_modules`）：初始两个 `.d.ts` 均缺失；跑完 `vitest run` 后仍缺失；此时 `vue-tsc --noEmit` 报 **35 个 `TS7006`**。再跑 `vite build` 后两个声明文件出现，类型检查收敛为前述 4 个 `TS2345`。
- `docs/standards/rules/20-frontend-vue.md:29` 已记录“`components.d.ts` 缺失会满屏 `TS7006`”，但 CI 当前顺序没有落实这个前置条件。

**影响**

即使修好 `package-lock.json`，干净 CI 仍会在类型检查阶段失败，且失败信息是 35 个隐式 `any`，会把真正的 4 个 `TS2345` 淹没。本地开发者因为工作区已经生成过 `.d.ts`，很难复现 CI 的首个错误面。

**修复建议**

1. 在 CI 的 `vue-tsc` 之前增加声明文件生成步骤；可以封装成独立的 `typegen` 脚本，避免先跑完整的 `vite build`。
2. 或者把 `components.d.ts` / `auto-imports.d.ts` 纳入版本库，并加“生成物漂移”检查；不要让类型门禁依赖开发者本地的偶然状态。
3. 固定并在 CI 文档中写清顺序：先生成声明，再跑类型检查，最后构建。

## 3. 🟡 建议项

### 🟡-1 默认 `local` profile 削弱了启动安全守卫

**证据**

- `knot-server/knot-admin/src/main/resources/application.yml:7-8` 与 `knot-server/knot-gateway/src/main/resources/application.yml:7-8` 都把 `spring.profiles.active` 硬编码为 `local`。
- `knot-server/knot-service/src/main/java/org/chobit/knot/svc/config/BootstrapSecurityGuard.java:27-28` 把 `local` 定义为非生产 profile；`:47-55` 仅在“没有任何非生产 profile”时拒绝开发默认密钥启动。
- `knot-server/knot-admin/src/main/resources/application-local.yml:7-8` 提供本地数据库默认账号口令，`:22` 提供开发默认凭证加密密钥；`knot-server/knot-gateway/src/main/resources/application-local.yml` 同样有 `knot-dev-credential-encryption-key`。
- `knot-server/knot-admin/src/main/resources/application-local.yml:11-12` 的 `KNOT_SQL_INIT_MODE` 默认 `ALWAYS`；`knot-server/knot-admin/src/main/java/org/chobit/knot/admin/config/SqlInitModeGuard.java:45-50` 对非生产 profile 直接放行。
- `knot-server/knot-admin/src/main/resources/db/data.sql:21-25` 包含 `admin/admin123` 种子管理员。
- 两个 Dockerfile 只在注释中写“生产必须设置 `SPRING_PROFILES_ACTIVE=prod`”（`knot-admin/Dockerfile:12-17`、`knot-gateway/Dockerfile:12-18`），没有在镜像层强制。

**影响**

若部署时漏设 `SPRING_PROFILES_ACTIVE=prod`，应用会按 `local` 启动：默认密钥守卫认为是非生产环境而放行，SQL 初始化守卫也放行；如果此时数据源环境变量已指向真实库，就会带来默认管理员口令、重复执行 schema/data、开发密钥误用等组合风险。这是**条件性阻断**：部署侧已严格强制 `prod` 时可降级，但仓库自身没有把这个前提变成不可绕过的代码约束。

**修复建议**

1. 不在通用 `application.yml` 中硬编码 `local`；让 `local` 必须显式激活。
2. 把“没有 active profile”也按生产处理，或至少让安全守卫在 profile 为空时 fail-closed。
3. 为 `BootstrapSecurityGuard` 与 `SqlInitModeGuard` 补回归测试；本轮 `rg` 未找到对应测试类。

### 🟡-2 零账与 fail-open 路径缺可观测面

**证据**

- `knot-server/knot-adapter/src/main/java/org/chobit/knot/adapter/usage/calculator/TokenBillingModeCalculator.java:31-35`：非 token 用量到达 TOKEN 计算器时直接返回零金额，注释说明是热路径取舍。
- `knot-server/knot-adapter/src/main/java/org/chobit/knot/adapter/usage/calculator/SimpleBillingModeCalculator.java:35-38`：`config == null` 时按 `BigDecimal.ZERO` 计价。
- `knot-server/knot-gateway/src/main/java/org/chobit/knot/gateway/runtime/GatewayRequestHandler.java:647-672`：流式记账失败只累加 `usageRecordFailures` 并打日志；全仓未找到该计数的 Micrometer 消费点。
- `knot-server/knot-gateway/src/main/java/org/chobit/knot/gateway/service/support/ModerationWordResource.java:69-89`：词库异常时 fail-open 为空列表；虽有 `failOpenCount` / `failOpenSinceMillis` / `lastVersion` 访问器，但未接入 Micrometer。`40-plugin.md` 已登记 fail-open 设计，因此这里不把它当“隐藏 bug”，问题在可观测性。

**影响**

这些路径符合“避免阻断热响应”的可用性取舍，但若没有指标，线上无法区分“正常零价/零用量”和“计费或审核能力已被绕过”。尤其流式记账已经明确会跳过配额/成本，现有 `AtomicLong` 只在对象内部，不能作为告警面。

**修复建议**

补 `usage.accounting.failure`、`moderation.fail_open`、`moderation.last_success.age` 等 Micrometer 指标，并加告警阈值；对“模式与提取器错配”的零账路径，至少在日志/指标中带上规则码、计费模式和提取器类型。

### 🟡-3 `JsonKit` 的静默失败仍是系统性债务

**证据**

- `knot-server/knot-common/src/main/java/org/chobit/knot/common/util/JsonKit.java:77-87`：`toJson` 失败记日志后返回 `null`。
- 同文件 `:105-128`：`fromJson` 失败同样返回 `null`。
- 静态统计：生产代码 `JsonKit.toJson` 47 个调用点、`toJsonOrThrow` 5 个、`fromJson` 35 个。

**判断**

不能把这 47 个调用点一律判错：日志、审计摘要、可选字段可能允许 best-effort。但落库、发消息、权限、计费和异步任务上下文等“失败即改变业务结果”的调用点应逐步收口到 `toJsonOrThrow` 或显式错误类型。旧报告中 Kafka、凭据、异步任务三处已经修复，说明治理路径有效，但剩下的是**分类治理**，不是一次性替换。

**建议**

按“失败后会发生什么”给调用点分级：落库/消息/计费/权限为必须抛；日志/调试为可降级；补一个静态守门或调用点清单，防止新代码继续默认使用 `toJson`。

### 🟡-4 前端 API 层类型约束偏弱

**证据**

- `knot-front/src/api/http.ts:116-145` 的 `get` / `postQuery` / `post` / `put` / `del` 全部默认 `T = any`。
- `knot-front/src/types/index.ts:10,16,152,155,174` 的 `PageResult` / `ListResponse` / `Dict` / `SelectOption` / `QueryFn` 默认 `any`；`knot-front/src/composables/usePageList.ts:15` 也默认 `T = any`。
- 静态统计：API 目录共约 221 个导出函数/别名，约 174 个直接返回未带泛型参数的请求封装，只有约 13 个调用点显式给出泛型；生产代码中实际 `any` 默认约 11 处。

**判断**

这不是当前 4 个 `TS2345` 的直接原因，但会让“类型检查通过”覆盖不到大量响应结构：新 API 很容易在调用点退化为 `any`，`vue-tsc` 只能守住模板边界，守不住数据契约。10-30 报告“生产代码 `any` 为 0”的结论与当前代码不符。

**建议**

优先把 `http.ts` 默认值从 `any` 改为 `unknown` 或要求显式泛型，再按域补响应 DTO；不建议为了消灭 `any` 做一次性大迁移，先守住新增 API 和状态/权限/计费这些高风险域。

### 🟡-5 Controller 薄守门存在扫描范围缺口

**证据**

- `knot-server/knot-gateway/src/test/java/org/chobit/knot/gateway/ControllerThinGuardTest.java:45-46` 只扫描 `src/main/java/org/chobit/knot/gateway/controller`。
- `knot-server/knot-admin/src/test/java/org/chobit/knot/admin/ControllerThinGuardTest.java:57-59` 明确把 `RoutingRuleController`、`DepartmentController` 登记为存量违规；守门通过只能说明“没有新增”，不能说明这两处已经是薄 Controller。
- `knot-server/knot-gateway/src/main/java/org/chobit/knot/gateway/outage/admin/OutageAdminController.java:67-78` 在 controller 内做列表查询、过滤和响应映射；`:87-108` 做字段校验、trim、状态操作和日志；`:125-130` 的 `requireText` 还做了 `trim()`。
- 按 `docs/standards/rules/10-backend-java.md:209-238`，controller 只允许参数绑定、委托、HTTP 语义；trim、查询/过滤和字段级映射应在 Runner/Service/Support。该类的只读 GET 有规范允许的管理面例外，但“GET 例外”不等于“可以承担业务逻辑”。

**影响**

外部入口包守门通过，不代表所有 `*Controller` 都薄；当前扫描口径会漏掉 `outage.admin`、`async.admin` 这类同包外的管理面 Controller。随着管理面继续增长，可能形成第二套业务层。

**建议**

把守门扫描从“固定 `controller` 目录”升级为“所有以 `Controller` 结尾的类，配合显式、可审计的框架例外”；先把 `OutageAdminController` 的查询/过滤/校验搬到对应 Runner/Support，再扩展守门。

### 🟡-6 测试覆盖仍呈“组件多、路由少”结构

**证据**

- 前端共 34 个测试文件、477 例，单测本身通过。
- `knot-front/src/views` 有 33 个 `.vue`，但只有 `DashboardView.test.ts` 一个 route-level 测试。
- 超过 500 行且无同名前缀测试的组件/布局包括 `knot-front/src/layouts/MainLayout.vue`（541 行）、`knot-front/src/components/provider/ProviderAccountFormDrawer.vue`（507 行）、`knot-front/src/components/model/ModelPoolFormDrawer.vue`（504 行）。

**判断**

这是 S8（测试缺口），不是“前端没有测试框架”。现有测试对组件细节覆盖不错，但页面级装配、路由守卫、抽屉打开/提交/失败回滚等跨组件路径仍可能只有 E2E 才能发现。

**建议**

优先补 `MainLayout` 的路由/权限装配测试，以及两个表单抽屉的提交失败与 loading 回滚测试；复杂组件测试按行为断言，不要把实现细节锁死在快照里。

### 🟡-7 日志插件仍保留正文泄露面

**证据**

- `knot-server/knot-plugin/src/main/java/org/chobit/knot/plugin/log/PluginLogSupport.java:28-35` 默认策略是 `truncated`；`:63-71` 只做截断，不是去除敏感字段。
- `knot-server/knot-plugin/src/main/java/org/chobit/knot/plugin/log/PluginLogWriter.java:24-29` 仍把 `JsonKit.toJson(payload)` 整体写入 INFO 日志。

**判断**

插件默认 opt-in 已降低暴露面，但“启用后默认落 512 字符正文”仍可能包含 prompt、模型输出或凭据字段。属于旧报告 P1-8 的残留风险，不宜称为完全脱敏。

**建议**

默认改为 `none` 或字段白名单；确需排障时通过短时开关切到 `full`，并在配置层加显式告警。
