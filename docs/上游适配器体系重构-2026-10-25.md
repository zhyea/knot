## 1. 背景与决策链

robin 就适配器体系连续下达四组指令，全部落地：

| # | 指令 | 落地形态 |
|---|---|---|
| 1 | 命名结构「供应商+原协议+To+新协议」 | `<供应商>+<原协议>+<新协议>+UpstreamAdapter`，泛化转换免供应商段 |
| 2 | 不存在单一请求/响应适配，应然用 UpstreamAdapter | 接口改名 `UpstreamRequestAdapter` → `UpstreamAdapter`，明确**双向角色**注释 |
| 3 | 除透传外一个适配器只服务一种协议 | 一适配器一协议（`protocol()` 单元素集）；Anthropic 一拆三、Bedrock 一拆四 |
| 4 | 流式与非流式处理要在接口约定层分开 | `handleStreamEvent`（流式逐事件）与 `handleResponse`（整包）双钩子，见 §3 |

配套决策：DB 列名 `request_adapter` 不变（改列牵动 schema + mapper + 前端，零收益）；Bedrock 四拆而非保留单适配器（职责边界优先，复用走 Support）。

## 3. 流式契约（接口约定层分开）

| 契约 | 位置 | 内容 |
|---|---|---|
| `handleStreamEvent` | `UpstreamAdapter.java` | default 透传；入参是 `data:` 之后的事件数据（与用量提取同粒度） |
| 与 `handleResponse` 的分工 | 同上 javadoc | 前者只服务流式逐事件、后者只服务整包；两条路径的转换产物都同时喂客户端转发与用量提取（同构） |
| 接线 | `ProxyStreamingFlux.transform` | data 行一律过适配器 → 提取（看 `appendUsage`）→ 重组行；`[DONE]` 检测用原始数据 |
| 取适配器 | `UpstreamStreamResponse` | 重新持有 adapter 字段（2026-10-23 计费去兜底时曾移除，本次以「流式响应适配需要在场」为由恢复），执行器 `executeStreaming` 创建时传入 |

关键口径：**响应适配是协议正确性，不受 `appendUsage`（计费注入开关）gate**——转换不挂在开关下，只有用量提取看开关。测试 `adaptsStreamEventEvenWithoutUsageInjection` 固化该语义。

Bedrock 族 `streamSupported=false`（上游 EventStream 二进制帧恒走整包），不存在「流式响应转换丢失」问题；Messages/泛化方向响应侧本透传，流式零损失。
