### B. 流式收尾异常截断记账与事件

**复核后的精确结论**（比巡检原文更窄，但都成立）：

- `recordStreamingUsage` 自己已经有 try/catch + `usageRecordFailures` + `metrics.usageRecordFailure()`（`GatewayRequestHandler.java:646-665`）——它不会外抛；
- 但 `onComplete` 第一段 `loadRelease.run()`（`:601-607`）没有任何保护，它抛 `RedisUnavailableException` 就会**跳过**后续记账与事件，这是真实缺口；
- `publishTraffic`（`:609-614` → `AbstractGatewayRequestTemplate.java:209-219`）同样裸调；
- `ProxyStreamingFlux.java:137-153` 里 `tee` 有 try/catch，**`usageSink.accept` 与 `onComplete.run()` 没有**——usageSink 抛异常会连带吃掉 onComplete，这一条巡检没写；
- 构造期窗口：`streamResponse` 在 `:594` 调 `prepareStreaming` 时 `releaseDeferred` 已被置 `true`（`:352`），候选 Mono 的 `doFinally`（`:388-396`）会跳过释放 → 泄漏到 TTL。仍然成立。

**改法**

1. `GatewayRequestHandler` 加一个收尾隔离器 + 计数（与现有 `usageRecordFailures` 同型）：

   ```java
   private final AtomicLong streamCompletionFailures = new AtomicLong();

   /** 收尾三段互不阻断：某一段失败只打点，不得吃掉后面的记账与事件。 */
   private Runnable isolated(String step, Runnable action) {
       return () -> {
           try {
               action.run();
           } catch (RuntimeException e) {
               long total = streamCompletionFailures.incrementAndGet();
               if (metrics != null) {
                   metrics.streamCompletionFailure(step);
               }
               log.error("Streaming completion step failed: step={} total={}", step, total, e);
           }
       };
   }
   ```

2. `streamResponse` 把三段显式拆开（顺序不变：释放 → 记账 → 事件）：

   ```java
   Runnable completion = isolated("load-release", () -> { if (loadRelease != null) loadRelease.run(); });
   completion = chain(completion, isolated("usage-accounting",
           () -> recordStreamingUsage(context, routing, terminalUsage.get())));
   completion = chain(completion, isolated("traffic-event",
           () -> publishTraffic(context, exchange, terminalUsage.get(), firstTokenWriter.elapsedMillis(), null)));
   ```
   `chain(a, b)` 就是「跑完 a 再跑 b」的 `Runnable`。保留现有两段式写法的可读性即可，**不要**把三段塞进一个 try 里（那等于没隔离）。

3. 构造期归还：把 `prepareStreaming` 之后到 `return` 的构造体包起来：

   ```java
   try {
       ... 现有构造 ...
   } catch (RuntimeException e) {
       // 延迟释放已经置位、doFinally 不会再来兜底；releaseLoad 自身 CAS 幂等，重复归还无副作用
       if (loadRelease != null) loadRelease.run();
       throw e;
   }
   ```

4. `ProxyStreamingFlux.doFinally`（`:137-153`）把 `usageSink` 与 `onComplete` 各自包 try/catch，失败 `log.warn` 不阻断——与它上面 `tee` 的写法保持一致。

5. `GatewayMetrics` 新增常量 `knot.gateway.stream.completion.failure` + 带 `step` tag 的计数器方法（与 `UPSTREAM_FAILURE` / `USAGE_RECORD_FAILURE` 同风格）。

**探针（先红后绿）**

- 新增 `GatewayRequestHandlerStreamCompletionIsolationTest`：
  - `loadRelease` 抛 `RedisUnavailableException` → 断言 usage 与 traffic **都执行了**、`streamCompletionFailures()==1`；
  - `usage` 抛异常 → 断言 traffic 仍执行（顺序敏感性）；
  - 三段都正常 → 断言顺序为 release → usage → traffic。
  实现方式：把三段组装抽成 **package-private** 方法（例如 `Runnable streamingCompletion(...)`）直接驱动，不启容器、不 mock 具体类（JDK 25 限制）。
- `ProxyStreamingFluxTest` 加一例：`usageSink` 抛异常 → `onComplete` 仍被调用、流正常结束。
- 构造期：用 `RecordingHttpExchange` 让 `prepareStreaming` 抛异常（若它没有注入开关，加一个），断言 `releaseLoad` 被调用**恰好一次**（CAS 语义顺带验证）。

**验收**：定向 `-pl knot-gateway -am -Dtest=GatewayRequestHandlerStreamCompletionIsolationTest,ProxyStreamingFluxTest,GatewayRequestHandlerLoadReleaseTest,GatewayRequestHandlerStreamingTrafficTest -Dsurefire.failIfNoSpecifiedTests=false`。
