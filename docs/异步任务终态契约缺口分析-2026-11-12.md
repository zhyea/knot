# 异步任务终态契约缺口分析（2026-11-12）

结论先行：**三个现象是同一个根因**——异步任务在「提交之后」走的是一条自建的平行链路
（poller → 裸 WebClient 查询 → 结算 → 回调），它没有经过主代理链路
`GatewayRequestHandler` / `UpstreamProxyClient`，因此主链路上的三个副作用出口被整体跳过：

| 主链路副作用 | 出口位置 | 异步平行链路是否复用 |
|---|---|---|
| `knot_extend` 注入 | `GatewayRequestHandler#applyUsageAccounting` | ❌ 不复用，另起一套「测试头」门禁 |
| 上游 `usage`/`cost` 原文透出与记录 | 同一处 + `UsageAccounting.rawUsage` → Kafka | ❌ 只留原文，不做结构化、不对外 |
| 插件 dispatch（含日志插件） | `AbstractGatewayRequestTemplate` + `UpstreamProxyClient` | ❌ 一次都没调 |

按 `docs/standards/rules/00-core.md` 铁律 11：异步对外契约无外部消费方，可一次做干净，不做兼容兜底。

---

## 一、`knot_extend` 缺失

链条上有**三个独立拦截点**，任何一个都足以让普通客户端拿不到：

1. **提交响应（202 信封）刻意不带**
   `knot-gateway/.../runtime/GatewayRequestHandler.java:567-575`：`submitIfAsync` 命中后直接 `return accepted`，
   并把占位用量摘掉（`exchange.proxyResult(result.withoutUsage())`），跳过后面的
   `shouldReturnUsageDetail` → `KnotExtendPayload` 注入（:579-599）。注释写明「本次响应只是任务已提交，不是终态」。
   **这一条是设计意图，不是缺陷。**

2. **终态查询只认测试头，不认消费者配置**
   - `GatewayTaskController.java:57-59` 只透传 `X-Knot-Test-Return-Usage`；
   - `AsyncTaskLookupRunner.java:86-89` → `GatewayHeaders.testReturnUsageRequested(headerValue)` → `withEvidence`；
   - `AsyncTaskViewSupport.java:45-54`：`withEvidence ? settlementOf(task) : null`。
   同步链路的开关是 `routing.returnUsageDetail() || 测试头`（`GatewayRequestHandler.java:530-532`），
   **异步侧漏了 `return_usage_detail` 这一半**：消费者后台开了用量明细，异步查询仍然拿不到。
   且 `AsyncTaskContext`（:14-28）没有存这个布尔值，查询侧想按消费者配置判定也拿不到。

3. **回调恒定不带**
   `AsyncTaskDeliveryRunner.java:86` 调的是 `AsyncTaskViewSupport.toResponse(task)` 无参重载，
   `AsyncTaskViewSupport.java:34-43` 明示「回调投递恒传 false」。
   理由是「回调推的就是轮询会返回的那一份」，但这个约定只在两边都不带时才成立。

**数据其实算出来了**：`AsyncTaskRunner.java:458-467` 在终态时把 `KnotExtendPayload.of(usage)`
写进 `kb_async_tasks.settlement_json`（与同步 `knot_extend` 同形），
`AsyncTaskViewSupport#settlementOf` 也读得回来。缺的是**下发开关**，不是账目。

## 二、上游返回的 `cost` 没有记录

### 2.1 概念先分清

- `NormalizedUsage.totalCost` / `detail[].cost`：knot 按自有计费规则算出的**售价**，已在结算里。
- 「上游返回的 cost」：供应商响应里 `usage.cost`（或 `total_cost`）这类**成本口径**，
  代码里唯一读它的地方是 `BillingFactAssembler.java:133-152` `extractUpstreamCost`，
  仅用于管理端路由调试抽屉的 JEV 裁判（`UPSTREAM_COST_DEVIATION` 检查），**不参与计费**
  （`knot-adapter/.../extractor/DecisionsUsageTest.java:20-21` 也写明「上游口径，不参与 knot 计费」）。

### 2.2 落点逐项核对

| 出口 | 现状 | 证据 |
|---|---|---|
| `kb_async_tasks` 表列 | 只有 `terminal_body`（上游原文 LONGTEXT）、`settlement_json`（knot 自算 usage+billing），**无上游 cost/usage 列** | `knot-admin/src/main/resources/db/schema.sql:499-543` |
| `settlement_json` 内容 | `KnotExtendPayload` 只有 `usage` + `billing` 两个分量 | `AsyncTaskRunner.java:458-467`、`KnotExtendPayload.java:23-24` |
| Kafka 流量事件 | 有 `upstream_usage` 字段，来源是 `usage.rawUsage()`；空对象归一成 null 后整段省略 | `GatewayTrafficMsgDto.java:104, 248, 274-280` |
| 对终态响应体 | `AsyncTaskQueryResponse` 无并列 `usage` 字段；同步规范是 `knot_extend` **+ 并列 `usage`** 成对输出 | `AsyncTaskQueryResponse.java:47-71`、`docs/knot_extend-输出规范-2026-10-04.md:12-13, 54-59` |

### 2.3 为什么会丢

`AsyncTaskCompletion.java:75-92` 的 `charge` 把查询响应原文交给
`UsageExtractorRegistry.extract(queryBody, upstreamContext)`，
其中 `rawUsage = UsageRawReader.readUsage(rawBody)`（`UsageExtractorRegistry.java:113`）。

`UsageRawReader.readUsage`（:91-119）**只认顶层 `usage`，或 `response.usage`（Responses 协议兜底）**；
`MediaUsageReaders.rawUsage`（:23-29）同样只取顶层 `usage`。

而视频查询响应普遍把用量/cost 嵌在 `data.*`（如可灵 `data.task_status_msg` /
`data.task_result.*`，见 `AsyncTaskSpec.java:20-23` 对 errorMessagePath 的说明；
方案文档 `docs/视频异步任务轮询拉取技术方案-2026-10-26.md:21-24` 也写了 MiniMax / Kling 的 query 体形态）。
顶层 `usage` 取不到 → `rawUsage = null` → Kafka `upstream_usage` 缺失、
`settlement_json` 里也没有上游 cost、`AsyncTaskQueryResponse` 更没有并列 `usage`。

**唯一还留着的证据是 `terminal_body` 原文**（`AsyncTaskRunner.java:420` 与终态同一条 CAS 落库），
但它非结构化、只在测试头 `withEvidence` 下以 `upstream_body` 对外（`AsyncTaskViewSupport.java:68-71`），
离线对账要自己再解一遍原文。

⚠ **未验证**：本次是静态代码分析，没有真实 Key 抓取查询响应。上游实际是否回 `cost`、
回在哪个 JSON 路径，需要一次端到端实测确认（复核报告
`docs/代码质量巡检复核-2026-11-11.md:475` 亦记录「异步任务链路至今没跑过真实数据」）。

## 三、日志插件没有输出

### 3.1 插件 dispatch 的全部入口（全库仅两处）

| 入口 | 阶段 | 证据 |
|---|---|---|
| `AbstractGatewayRequestTemplate#dispatchGatewayPlugin` | `GATEWAY_REQUEST` / `GATEWAY_RESPONSE` / `GATEWAY_ERROR` | `:161, :193, :213`，dispatch 实现 `:301-327` |
| `UpstreamProxyClient#dispatchPlugin` | `UPSTREAM_REQUEST` / `UPSTREAM_RESPONSE` / `UPSTREAM_ERROR` | `:123, :126, :129`，dispatch 实现 `:208-234` |

六个内置日志插件（`knot-plugin/.../builtin/*LoggingPlugin.java`）全部按
`extensionPoint + stageCode + capabilityCode` 匹配绑定（`DefaultPluginDispatcher.java:43-55, 63-80`），
**没有任何 dispatch 调用就没有日志，跟后台有没有配绑定无关**。

### 3.2 异步链路覆盖情况

| 阶段 | 走的类 | 是否 dispatch |
|---|---|---|
| 客户端发起创建（提交） | `GatewayControllerSupport` → `GatewayRequestHandler` → `UpstreamProxyClient` | ✅ 有，那一次 create 调用会出日志 |
| N 次轮询查询上游 | `AsyncTaskQueryClient#query` 裸 `WebClient`（:100-117） | ❌ 无 |
| 终态判定 / 计费 / Kafka 事件 | `AsyncTaskRunner` / `AsyncTaskCompletion` | ❌ 无 |
| 客户端查询任务 | `GatewayTaskController` 只做鉴权 + 投影（`AsyncTaskLookupRunner`） | ❌ 无（不经 `GatewayRequestHandler`） |
| 回调推送 | `AsyncTaskCallbackClient#deliver` 裸 `WebClient`（:33-47） | ❌ 无 |

所以「执行过程中没有日志」准确说是：**只有提交那一拍有插件日志，占绝大多数的查询/终态/回调全程没有**。
现有 `AsyncTaskScheduledPoller` / `AsyncTaskRunner` 里的都是 slf4j 应用日志
（WARN/ERROR/INFO，且成功查询路径不打日志），不是插件日志，格式与落点都不同，不能互相替代。

## 四、修复建议（待 robin 拍板，本次未改代码）

### P0 契约对齐（一次做干净，不留兼容）

1. **下发开关对齐**：把 `context.routing().returnUsageDetail()` 快照进 `AsyncTaskContext`
   （提交点 `AsyncTaskSupport.java:244-257`），查询侧按「消费者配置 || 测试头」算 `withEvidence`，
   与 `GatewayRequestHandler#shouldReturnUsageDetail` 同口径。
2. **补并列 `usage`**：`AsyncTaskQueryResponse` 增加与 `knot_extend` 平级的
   `usage`（上游原文），终态时由结构化证据填充，兑现同步侧 `knot_extend-输出规范` 的成对契约。
3. **回调同形**：`AsyncTaskViewSupport` 已把「回调 = 轮询」定为红线。
   要么两边一起带账目，要么明确「回调不带」并写进契约文档 —— **这是需要 robin 先定的决策点**，
   不能只改轮询侧，否则恰好破坏现有收敛。
4. **上游 cost 结构化**：给档案加一条可配的 `usage_path`（MVEL，与现有
   `statusPath` / `resultPath` / `errorMessagePath` 同机制），异步结算按它取上游 usage 对象，
   再作为 `rawUsage` 交给 `UsageExtractorRegistry`。这样 Kafka `upstream_usage` 自动带 cost，
   不必新增表列；若还需要离线可对账的独立数值，再评估加 `upstream_cost` 列
   （⚠ `schema.sql` 加列必须同步迁移脚本，见 `AGENTS.md` 红线）。

### P1 插件日志接入

5. 在 `AsyncTaskQueryClient#exchange` 前后显式
   `pluginDispatcher.dispatch(UPSTREAM_EXCHANGE, UPSTREAM_REQUEST/RESPONSE/ERROR, new UpstreamPluginContext(...))`，
   终态/回调同理补 `GATEWAY_*`。**只复用 dispatch 原语，不接管调用链**。
   - ⚠ 层次别混：failover / retry / ejection / 摘除 / 限流在 `GatewayRequestHandler#proxyWithFailover`
     （:178）→ `attemptCandidates`（:250）→ `invokeWithRetry`（:464），**不在** `UpstreamProxyClient`。
     方案 §5.4 第 2 点禁的正是这一层（`attemptCandidates` 候选 failover）。
     `UpstreamProxyClient.proxy(context)`（:119-132）只是单次调用门面：算 URL + 三次插件 dispatch + 执行器。
     方案原文写「固定 GET」也与当前代码有偏差：`AsyncTaskDefaults.QUERY_METHOD="GET"` 只是默认，
     档案 `queryMethod` 可配（`AsyncTaskQueryClient:97` 用 `HttpMethod.valueOf`）；「单尝试 + 自身退避」仍成立。
   - **真正不能直接拿来当查询客户端的是四处硬冲突**：
     ① URL 带 `{task_id}` 占位（`AsyncTaskQueryClient:94-97`），而 `UpstreamAdapter#resolvePath`（:39-41）
     只取 `binding.apiPath` / 协议默认路径，`UpstreamRequestContext` 里没有上游任务 ID 这个位置；
     ② 查询超时必须 `queryTimeoutMs < claimTtlMs`，proxy 链用的是生成请求的 `responseTimeout`
     （`AbstractUpstreamProtocolExecutor:353-358`），超出租约会让别的节点重领同一行；
     ③ `adapter.handleResponse` 会改写响应（:154），而 `terminal_body` 要求原文零改动；
     ④ `executeBuffered` 每次响应都跑 `usageExtractorRegistry.extract`（:159），
     中间态也会被算钱、且可能与去兜底策略冲突，终态还会与 `settlementPort.charge` 双份算账。
   - 现成判例：`AsyncTaskCompletion#charge`（:84-91）只调 `buildModelRequestContext` 构造上下文，
     **不调** `proxy` —— 「复用原语、不复用编排」在这一层已有先例。
6. ⚠ 边界先定：`DefaultPluginDispatcher` 刻意不吞异常（:26-28），同步插件在主链路上抛错本意是打断链路。
   挂到轮询线程后，日志插件抛错会打断任务推进。需明确「仅日志类插件 fail-open」的实现位置，
   不要改 dispatcher 全局语义。

## 五、判据与尺子（按 `80-code-review.md`）

这不是「三处各修一个 bug」，而是**一条平行链路漏接了主链路的三个横切关注点**。
判据是「换掉 HTTP 框架这段逻辑还要不要」（薄壳边界）与「同一契约是否只有一个投影出口」：
`AsyncTaskViewSupport` 已经把投影收成唯一出口，`GatewayTrafficMsgDto.of` 已经是唯一事件装配点，
`PluginDispatcher` 已经是唯一插件入口 —— 缺的是**把异步链路接到这些既有出口上**，
而不是在 poller 里另写三套解析/日志/投影（那正是 `docs/视频异步任务轮询拉取技术方案` §5.5
「禁止在 poller 内另写字段解析」要防的漂移）。

## 六、实施落地（2026-11-12）

结论：三处缺口按「**接到既有出口上**」收口，没有在 poller 里另起第二套解析 / 投影 / 日志。
四个决策点由 robin 拍板，按推荐全做。

### 6.1 拍板口径

| 决策点 | 结论 | 判据 |
|---|---|---|
| `knot_extend` / 并列 `usage` 下发条件 | **终态 + consumer 配置**；测试头保留叠加 | 账目在终态结算时才写进 `settlement_json`，在途下发只会给客户端一个空账；consumer 开关与同步链路 `return_usage_detail` 同源 |
| 回调 body | **两边都带，保持同形** | `AsyncTaskViewSupport` 是唯一投影出口；回调没有请求头所以测试头不叠加 —— 这是唯一有意差异 |
| 上游 usage / cost 结构化 | **档案加可配 `usage_path`** | 真实响应路径未实测，写死路径等于赌厂商契约；表达式与 `status_path` / `result_path` 同机制，新增一家上游只加一行档案 |
| 插件异常 | **调用侧 fail-open** | `DefaultPluginDispatcher` 刻意不吞异常（主链路敏感词插件依赖冒泡打断）；故障隔离只在异步查询调用侧做，不改全局语义 |

### 6.2 改动分布

| 批次 | 范围 | 关键文件 |
|---|---|---|
| A 上游用量贯通 | DB + svc + gateway 快照 | `schema.sql` 加 `usage_path` 可空列 + 两份幂等迁移脚本；`AsyncTaskProfileEntity` / `AsyncTaskProfileMapper.xml` / 三个 DTO-VO / `AsyncTaskConverter`（3 处）/ `AsyncTaskProfileSupport`（normalize + validate + compile）/ `AsyncTaskExpressionSupport#object` / `AsyncTaskSpec#usagePath` / `AsyncTaskSpecRules#usageOf` / `AsyncTaskCompletion#queryBodyForUsage` / `AsyncTaskContext#returnUsageDetail` / `AsyncTaskSupport` 提交快照 |
| B 终态下发 | 投影唯一出口 | `AsyncTaskQueryResponse` 加并列 `usage`；`AsyncTaskViewSupport` 按「终态 + 配置 + 测试头」投影；`AsyncTaskLookupRunner` / `AsyncTaskDeliveryRunner` 语义对齐；守门 `AsyncTaskViewSupportTest`（6 例） |
| C 查询侧插件 | 只接原语不接管编排 | `AsyncTaskQueryClient` 在 `UPSTREAM_REQUEST/RESPONSE/ERROR` 三阶段 dispatch，调用侧 fail-open；`UpstreamProxyClient` 的 `UpstreamPluginContext` 构造抽成 `UpstreamPluginContextSupport.of(...)`（构造签名不变，3 个既有 6 参测试不受影响）；守门 `AsyncTaskQueryClientTest`（6 例） |

### 6.3 几条刻意守住的边界

- **`terminal_body` 原文零改动**：`AsyncTaskCompletion#queryBodyForUsage` 只加工「交给提取器的输入」，
  终态落库的仍是 `polling.rawBody()`。原文失真会让离线重算与线上口径分叉。
- **`usage_path` 取对象不走 `text()`**：新增 `object()`，不放宽 `text/scalar` 语义 ——
  后者还服务状态文本与产物地址，放宽会让「取到 Map」变成合法标量，静默污染终态判定。
- **旧快照不回填**：`poll_spec_json` / `context_json` 是提交时口径快照，新增可空字段由 Jackson 填
  null / false，不写数据迁移、不动在途任务（铁律 11：无消费方，不做兼容兜底）。
- **`upstream_body` 不随 consumer 配置下发**：消费者开用量明细只该拿账目，
  不该连上游响应原文一起收到。
- **回调与轮询同形**：`AsyncTaskViewSupport` 一处投影、两处调用，不复制。

### 6.4 顺带发现（已按 robin 决策处理：清理，不修）

新增的两份迁移脚本照抄 `2026-10-29-async-task-profile-admin.sql` 模板时，else 分支写成
`'SELECT ''...'' AS skipped);` —— **字符串未闭合且 `IF` 未闭合**，MySQL 会报语法错
（正确写法 `AS skipped');`，见 `2026-10-29-async-task-callback.sql:68`）。本次两个新脚本已修。

全库审计发现**历史脚本另有 14 处同类写法、分布在 6 个文件**（`2026-10-29` / `2026-10-30` /
`2026-11-02` 三批各带 rollback）。因为加列分支通常只走一次，**幂等重跑才会命中 else 分支**，
所以一直没暴露。

**处置（2026-11-12 20:10，robin 拍板）**：不逐处修补，直接清理历史脚本。库形态的唯一标准是
`schema.sql`（结构）+ `data.sql`（种子），`docs/database/migration/` 只保留**未上线批次**的脚本，
上线执行完即删——这 14 处语法错随文件一并消失，也不再有「照抄老模板」的传染源。
本目录现只留本次两份 `2026-11-12-async-task-profile-usage-path{,-rollback}.sql`，
约束写进 `AGENTS.md` 红线速记。
