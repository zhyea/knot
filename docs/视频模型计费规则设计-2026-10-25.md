# 视频模型计费规则设计（2026-10-25）

> 输入：豆包 Seedance 2.5 / MiniMax Hailuo / Kling 可灵 4.0 三张价格截图 + Vidu Open Platform `pricing.md`。
> 目标：归纳业界计费方案，找出 knot 现有视频计费的能力缺口，给出可落地的设计。

---

## 0. 结论先行

| 项 | 结论 |
|---|---|
| 业界共性 | 视频计费 = **「量」×「价」×「结构」×「扣除策略」** 四轴正交，各家只在每轴选型不同 |
| knot 现状 | 已实现 Q1（输出秒数）× P1/P2 半残（只有分辨率一维）× S1（线性） |
| **最严重缺陷** | `VideoUsageExtractor` 已提取 `sound` / `reference` 两个维度，**但计价链路完全没消费**——豆包的核心定价维度是死数据 |
| **次严重缺陷** | 命中分辨率价后**绕过** `PricingPlan` 链路（代码注释自标「风险 ①」），VIDEO 拿不到错峰/阶梯 |
| 设计要点 | **不新开第四层**。非线性阶梯用 `tierMode=PROGRESSIVE` 复用现有 `tier` 结构解决 |

## 1. 业界方案分类归纳

### 1.1 四轴定义

一次视频计费可以完整拆成四个正交轴，每轴各选型别，各家差异全部落在这个格子里：

| 轴 | 问的问题 | 型别 |
|---|---|---|
| **Q 计费量** | 按什么收 | Q1 输出秒数 / Q2 合成量 / Q3 多对象求和 / Q4 Token 化 |
| **P 单价** | 一单位多少钱 | P1 固定 / P2 维度分档 / P3 用量阶梯 / P4 时段相位 |
| **S 金额结构** | 怎么累加 | S1 线性单项 / S2 分段累加 / S3 附加费 |
| **D 扣除策略** | 何时不收 | D1 免费额度 / D2 失败不扣 / D3 取整规则 |

### 1.2 四家定位表

| 厂商 | Q | P | S | D | 计费单位 |
|---|---|---|---|---|---|
| **豆包 Seedance 2.5** | Q4 Token 化 | P2 二维分档（分辨率 × 是否含视频输入） | S1 线性 | — | 元/百万 token |
| **MiniMax Hailuo** | Q3 多对象求和 | P2 分档（模型档 × 分辨率） | S1 + S3 | D1（前 5 张图免费） | 元/秒 + 元/张 |
| **Kling 可灵 4.0** | Q2 合成量 | P2 分档（分辨率） | S1 线性 | — | 积分/秒 |
| **Vidu** | Q1 输出秒数 | P2 全维度分档（能力×版本×时长×分辨率×风格） | **S2 分段累加** + S3 | D2 + D3 | 积分/秒 |

### 1.3 各轴要点

**Q 轴 —— 计费量怎么定**

- **Q1 输出秒数**：最朴素，直接按产出视频时长。Vidu Q3/Q4 走这条。
- **Q2 合成量**（Kling）：计费量不是物理量，是**公式算出来的合成秒数**：
  - 无视频输入：`总时长 = 输出时长`
  - 有输入且 输入 ≤ 输出：`总时长 = 输出时长 × 2`
  - 有输入且 输入 > 输出：`总时长 = 输入时长 + 输出时长`
  - 注意：第三种是线性相加，第二种是**翻倍惩罚**——同"有输入"两种算法，说明厂商在按「输入是否被完整消费」区分定价。
- **Q3 多对象求和**（MiniMax）：输出视频按秒、输入视频按秒、输入图片按张，三路各自计价后求和。⚠ 这是**跨量纲求和**（秒 + 张）。
- **Q4 Token 化**（豆包）：视频模型但不按秒，折成 token 按 `元/百万token`。分辨率退化成**分档键**而非计费量。

**P 轴 —— 单价怎么定**

- **P2 维度分档**是绝对主流，区别只在维度数量：
  - 豆包：2 维（分辨率 × 含视频输入）
  - Vidu：5 维（能力类型 × 模型版本 × 时长 × 分辨率 × 风格）
- **P4 时段相位**（Vidu 错峰）：标准价一半，小数**向上取整**。这就是 knot `PEAK_OFF_PEAK` 的现实原型。
  - Vidu 的限制很具体：Q3 的 pro/turbo **仅在 `audio=true` 时**支持错峰；Q3-mix 不支持。说明相位可适用范围是 per-配置而非全局。

**S 轴 —— 金额结构（最容易被忽略的一轴）**

- **S2 分段累加**是 Vidu Q2 全系的非线性结构，实际有三种形态：
  - 两段式：`第1秒 6，之后每秒 +2`（Q2-turbo 540P）
  - 三段式：`第1秒 8，第2秒 10，第3秒起 +10`（Q2-turbo 720P）
  - 两段式高价：`第1秒 15，之后 +10`（Q2-pro 720P）
  - ⚠ **这不是阶梯价（P3）**：阶梯是「总量落档后统一单价」，分段是「第 N 秒本身价格不同」。混淆二者会算错钱。
- **S3 附加费**（Vidu）：直出音频/视频在任务基础上 **+15 积分**；微调模型每次推理 +40；声音克隆 300/音色。附加费与量无关，是**常数项**。

**D 轴 —— 扣除策略**

- **D1 免费额度**（MiniMax）：输入图片前 5 张免费，超出按张。相当于分段函数的首段单价 = 0。
- **D2 失败不扣**（Vidu）：生成失败不消耗积分，**含内容审核拒绝**。
- **D3 取整**（Vidu）：错峰半价小数向上取整。⚠ 这是**积分域（整数）**行为，金额域不需要。

## 3. 设计方案

### 3.1 总原则

knot 已有 **「模式（决定量） × 方案（决定价）」** 两层正交结构。视频计费的所有复杂度**必须落进这两层**，
不得再开「video 特例枚举」这类第三层——每开一层，模式 × 方案的组合矩阵就翻一倍，且无法验证完整性。

### 3.2 Q 轴：给 `VideoBillingUsage` 补两个分量

```java
public record VideoBillingUsage(TokenBillingUsage tokens,
                                long durationSeconds,       // 输出视频秒数（主计费量）
                                long inputDurationSeconds,  // NEW 输入视频秒数（合成量用）
                                long imageCount,            // NEW 输入图片张数
                                long pixels, long width, long height,
                                boolean sound, boolean reference)
```

- `inputDurationSeconds`：请求体 `duration` 之外的输入视频时长，别名待定（见 §3.6 决策点）
- `imageCount`：请求体里图片 URL / 文件数组的**元素个数**，非布尔
- ⚠ **跨量纲求和（MiniMax 的 秒 + 张）不在模式层做**——那是「一次调用命多条规则」的编排层职责。本批只做同量纲（秒 + 秒）的合成

### 3.3 P 轴：把分辨率价收进方案层（修风险 ①）

**现状问题**：`VideoBillingModeCalculator.resolveUnitPrice()` 命中 `resolutionPrices` 后直接 return，
完全绕过 `PricingPlan`，导致 VIDEO 拿不到 `PEAK_OFF_PEAK` / `TIERED`。

**设计**：给 `PricingPlan` 接口加一个「维度键取价」方法，让分辨率价走和 basePrices 同一条链：

```java
public interface PricingPlan {
    PricingPlanEnum plan();
    BigDecimal resolvePrice(PriceKind kind, PricingContext context, BigDecimal fallback);
    BigDecimal resolveDefaultPrice(PricingContext context, BigDecimal fallback);

    /** NEW 维度键取价：dimensionPrices[key] -> basePrices -> defaultUnitPrice -> fallback，再过方案倍率 */
    BigDecimal resolveDimensionPrice(String dimensionKey, PricingContext context, BigDecimal fallback);
}
```

- `resolutionPrices` 保留字段名（DB 兼容），但解析改走 `resolveDimensionPrice`
- 维度键从「单一分辨率」扩成「组合键」：`720P` / `720P:REFERENCE` / `720P:REFERENCE:AUDIO`
  - 生成规则：分辨率 → `+":REFERENCE"`（有参考输入）→ `+":AUDIO"`（有声音）
  - 未命中组合键时**逐级降级**（`720P:REFERENCE:AUDIO` → `720P:REFERENCE` → `720P` → default）
  - 这样豆包的「分辨率 × 是否含视频输入」二维定价天然可表达，且老配置（只有 `720P`）零改动继续生效

**放开方案到媒体模式**：

```java
TIERED("阶梯价", BillingModeEnum.TOKEN, BillingModeEnum.IMAGE, BillingModeEnum.AUDIO, BillingModeEnum.VIDEO),
PEAK_OFF_PEAK("高低峰价", BillingModeEnum.TOKEN, BillingModeEnum.IMAGE, BillingModeEnum.AUDIO, BillingModeEnum.VIDEO);
```

⚠ 放开 PEAK_OFF_PEAK 到 VIDEO 依赖 §3.3 的修复，顺序不能颠倒。

### 3.4 S 轴：非线性分段累加 —— `tierMode`

Vidu Q2 的「首秒阶梯」是**分段函数**，不是阶梯价：

| 型 | 语义 | 公式 |
|---|---|---|
| `PER_REQUEST`（现有，默认） | 整笔用量落一个档，全量按该档单价 | `cost = 量 × 档单价` |
| `PROGRESSIVE`（新增） | 逐单位判定所属档位，单价逐单位累加 | `cost = Σ(i=1..n) tierPriceAt(i)` |

配置形态：

```json
{
  "tierMode": "PROGRESSIVE",
  "tier": [
    { "condition": {"from": 1, "to": 1}, "unitPrices": {"input": 8} },
    { "condition": {"from": 2, "to": 2}, "unitPrices": {"input": 10} },
    { "condition": {"from": 3},          "unitPrices": {"input": 10} }
  ]
}
```

**验算**（Q2-turbo 720P，8 秒）：`8 + 10 + 10×6 = 78` — 与 Vidu 官方口径一致 ✅
**验算**（Q2-pro 720P，5 秒）：`15 + 10×4 = 55` ✅
**验算**（Q2-turbo 540P，10 秒）：`6 + 2×9 = 24`

**明细单价口径（需定）**：PROGRESSIVE 下不存在唯一单价。约定 `detail[].unitPrice` 报**本笔单位均价**
（`totalCost ÷ amount`），并在 `detail[].type` 带 `PROGRESSIVE` 后缀，防止下游按「量 × 单价」复算时对不上。

**免费额度**（D1）用同一机制表达：首档 `unitPrices.input = 0`。

### 3.5 S3 附加费

```json
{
  "surcharges": [
    { "code": "AUDIO",   "amount": 15 },
    { "code": "FINETUNE","amount": 40 }
  ]
}
```

- 命中条件：请求侧布尔（`sound` / `reference`）或上游返回标志
- 与量无关的**常数项**，直接加进 `totalCost`
- ⚠ 币种与单价一致，不做换算

### 3.6 决策点（robin 2026-10-25 已拍板）

| # | 决策点 | 拍板 | 落地形态 |
|---|---|---|---|
| 1 | 跨量纲求和（MiniMax 秒+张） | **单规则多分量** | 一条 VIDEO 规则内部算三路求和，`VideoConfig` 承载分量价；不引入「规则组」 |
| 2 | 输入时长字段别名 | 请求侧读取 | `input_duration_seconds` / `input_video_seconds` / `input_duration` / `input_video_duration` / `source_*`；图片张数取数组长度优先 |
| 3 | PROGRESSIVE 明细单价口径 | **均价 + type 后缀** | `unitPrice` = 总额÷量，`type` 加 `:PROGRESSIVE`（注意 `detail.price` 仍是既有的「每百万单位」口径） |
| 4 | 附加费触发来源 | **仅请求侧** | `sound` / `reference` 两个请求侧布尔；响应侧不可预检 |
| 5 | D2 失败不扣 | **不做** | 异步任务模型，属计费触发时机，另开单 |

### 3.7 实施结果（2026-10-25 已落地）

| 批次 | 落地内容 | 验证 |
|---|---|---|
| A | `PricingPlan.resolveDimensionPrice` 新增；`VideoBillingModeCalculator` 消费 `sound`/`reference` 生成组合键 `720P:REFERENCE:AUDIO` 并逐级降级；`PricingPlanEnum` 放开 TIERED/PEAK_OFF_PEAK 到 IMAGE/AUDIO/VIDEO | `VideoBillingModeCalculatorTest` 4 例分档 + 2 例错峰回归 |
| B | `VideoBillingUsage` 补 `inputDurationSeconds`/`imageCount`；`MediaUsageReaders` 加读取口径；合成量三口径 + 多分量求和 | Kling 三档验算（5/10/13）、MiniMax 三路求和 7.60 |
| C | `tierMode=PROGRESSIVE` 逐单位累加；`surcharges` 常数项；免费额度走首档扣减 | Vidu 78 / 55 / 8 三例 |

**两处实施中发现的真问题**（设计阶段未预见，靠测试暴露）：

1. **合成量公式边界**：`OUTPUT_PLUS_MAX` 写成 `输出 + max(输入, 输出)` 时，无输入（输入=0）会算成 `输出×2`。
   必须显式判 `inputSeconds > 0`。已修并留验算注释。
2. **分量价被全局默认价抢先**：输入图片分量走 `resolveDimensionPrice` 时，键未命中会回落到
   `defaultUnitPrice`（那是**输出视频**的价），把「0.20/张」算成「0.50/秒」，MiniMax 三路多算 1.5。
   新增 `resolveComponentPrice` 把「分量自带默认价」与「规则全局默认价」两条回落链分开声明。

## 5. 风险登记

| 风险 | 说明 | 处置 |
|---|---|---|
| 组合键爆炸 | 分辨率 × 参考 × 声音 = 最多 档数 × 4 组合 | 用**逐级降级**，未配组合自动回落，不要求配全 |

| 异步任务计费时机 | 视频是「创建任务 → 轮询」，knot 现按 HTTP 响应计费 | **明确不在本批范围**，需另开单 |

## 6. 前端页面设计

### 6.1 分区结构（`BillingModeVideoConfig.vue`）

视频模式配置页按「先定基准价 → 再按维度分档 → 最后声明量的口径」五段排布，
每段自上而下收窄：下一段永远是上一段的补充而非并列，避免用户面对一堆平级输入框。

| # | 分区 | 承载的配置 | 关键交互 |
|---|---|---|---|
| 1 | 默认单价 | `defaultUnitPrice` | 所有未命中的维度组合都回落到这里；标签随单位变（每秒 / 每百万 Token） |
| 2 | **分辨率档位** | `resolutionPrices[{档位名}]` | **可增删行编辑器**，档位名可下拉选常用值也可自由输入 |
| 3 | 含参考输入时的单价 | `resolutionPrices[{档位名}:REFERENCE]` | 与第 2 段**同一行**的不同列，回显时按键后缀合并 |
| 4 | 计费量口径 | `video.quantityMode` | 下拉 + 实时口径说明；Token 量纲下整段隐藏 |
| 5 | 输入侧分量 | `video.inputVideoPerSecond` / `inputImagePerImage` / `freeInputImages` + `surcharges` | 留空即该分量不启用 |

#### ⭐ 分辨率档位为什么必须可配置（2026-10-26 修）

**厂商档位名不可枚举**：MiniMax 用 `768P / 2K / 480P`，Vidu 用 `540P`，豆包用 `480p / 720p / 1080p`，
还有各种自造名。此前前端硬编码 6 个固定输入框（480P/540P/720P/1080P/2K/4K）——
**MiniMax 的 768P 根本没地方填**，配了价也吃不到。

对应的后端问题同样真实：`resolution: "768P"` 走「宽高反推档位名」时，
768P 不在标准尺寸表里，会退化成裸串甚至空值。故后端也改为
**请求体声明的档位名优先**，宽高反推只作兜底，未识别的写法原样大写返回（不做白名单过滤）。

常用档位下拉（`480P / 540P / 720P / 768P / 1080P / 2K / 4K`）**只是建议不是白名单**——
`el-select` 开了 `allow-create`，任何自造档位名都能填。

### 6.2 三条 UI 纪律

1. **0 与「未启用」必须可区分**：分量价输入框留空 = 该分量不计费，填 0 = 免费。
   两者在 JSON 上分别是「字段缺失」与「值为 0」，不能靠 `!= null` 之外的判断混淆。
2. **参考输入价不复用分辨率输入框**：组合键 `{分辨率}:REFERENCE` 与 `{分辨率}` 是两张价，
   若共用输入框，回显时无法判断用户填的是哪个，必然丢配置。
3. **`video` 段只在有实质配置时才落库**：默认的「仅输出秒数」不写进 JSON——
   写了会污染老配置的 `config_json`，也让「默认行为」在库里多一份可漂移的副本。

### 6.3 阶梯区（`PricingPlanTieredConfig.vue`）

新增「累计方式」单选（`PER_REQUEST` / `PROGRESSIVE`），**仅 VIDEO / AUDIO / IMAGE 显示**
（TOKEN 整笔落一档即可，放开只会让语义变模糊）。切换后提示文案整体替换，因为两者档位含义不同：

| | 整笔落一档 | 逐单位累加 |
|---|---|---|
| 档位区间填的是 | **本笔用量总量** | **第几个单位**（第 1 秒填 `1~1`） |
| 金额 | 量 × 单价 | Σ 各单位单价 |
| 8 秒（8/10/10） | 80 | **78** |

明细单价在 PROGRESSIVE 下报**本笔均价**（78 ÷ 8 = 9.75），`type` 带 `:PROGRESSIVE` 后缀，
提示下游不要按「量 × 单价」复算。⚠ 注意 `detail.price` 仍是既有的**每百万单位**口径（9.75 → `9750000.00`）。

## 7. 配置参考：四家厂商对照

### 7.1 Kling 可灵 4.0（合成量）

```json
{
  "defaultUnitPrice": 1.0,
  "resolutionPrices": {"720P": 0.6, "1080P": 0.9},
  "video": {"quantityMode": "OUTPUT_PLUS_MAX"}
}
```
一条 `OUTPUT_PLUS_MAX` 覆盖三档：无输入=输出 / 输入≤输出=输出×2 / 输入>输出=输入+输出。

### 7.2 MiniMax Hailuo（多分量求和 + 非标档位 768P）

```json
{
  "defaultUnitPrice": 0.50,
  "resolutionPrices": {"768P": 0.50, "2K": 0.80},
  "video": {
    "inputVideoPerSecond": 0.50,
    "inputImagePerImage": 0.20,
    "freeInputImages": 5
  }
}
```
输出 10 秒 + 输入视频 4 秒 + 输入图片 8 张（768P）→ `5.00 + 2.00 + 0.60 = 7.60`。

⚠ 768P 是 MiniMax 自己的档位名，**不在标准尺寸表里**。请求体必须声明 `resolution: "768P"`；
若只给宽高（1366x768），后端也能反推到 `768P`，但声明优先。

### 7.3 Vidu Q2（PROGRESSIVE 分段累加，`pricingPlan=TIERED`）

```json
{
  "tierMode": "PROGRESSIVE",
  "tier": [
    {"condition": {"from": 1, "to": 1}, "unitPrices": {"input": 8, "output": 0, "cacheRead": 0, "cacheWrite": 0, "cacheWrite5m": 0, "cacheWrite1h": 0}},
    {"condition": {"from": 2, "to": 2}, "unitPrices": {"input": 10, "output": 0, "cacheRead": 0, "cacheWrite": 0, "cacheWrite5m": 0, "cacheWrite1h": 0}},
    {"condition": {"from": 3},               "unitPrices": {"input": 10, "output": 0, "cacheRead": 0, "cacheWrite": 0, "cacheWrite5m": 0, "cacheWrite1h": 0}}
  ]
}
```
8 秒 → `8 + 10 + 10×6 = 78`，与官方口径一致。

### 7.4 Vidu Q3-pro（维度分档 + 错峰，`pricingPlan=PEAK_OFF_PEAK`）

```json
{
  "defaultUnitPrice": 24,
  "resolutionPrices": {"540P": 9, "720P": 20, "1080P": 24},
  "pricing": {"rateMode": "MULTIPLIER", "timezone": "UTC+8", "phases": [ ... ]}
}
```
错峰半价靠相位倍率实现——**前提是分档价必须过方案层**（本次修复的风险 ①）。

### 7.5 豆包 Seedance 2.5（已完整对齐，2026-10-26）

**规则头**：`billingMode=VIDEO`、`unit=1M_TOKENS`、`pricingPlan=FIXED`

```json
{
  "defaultUnitPrice": 70,
  "resolutionPrices": {"720P": 70, "720P:REFERENCE": 42, "1080P": 77, "1080P:REFERENCE": 46}
}
```

| 场景 | 量 | 分档键 | 金额 |
|---|---|---|---|
| 480p/720p，输入不含视频 | 1,000,000 token | `720P` | `70` |
| 480p/720p，输入含视频 | 1,000,000 token | `720P:REFERENCE` | `42` |
| 1080p，输入不含视频 | 1,000,000 token | `1080P` | `77` |
| 1080p，输入含视频 | 1,000,000 token | `1080P:REFERENCE` | `46` |

**对齐方式**：量纲由规则单位声明——`unit=1M_TOKENS` 时取内嵌 token 量（总量优先、其次输出量），
`unit=PER_SECOND` 时取秒。**没有新增 `quantitySource` 一类字段**：
「一单位收多少钱」的分母是什么，本身就已经回答了「按什么收」，再开字段等于同一件事写两遍，必然漂移。

⚠ **两条约束**（已在代码注释与 UI 提示中双写）：
1. **Token 量纲下输入侧分量不启用**：一条规则只有一个单位基数（分母），
   秒 / 张分量会被同一个分母除错，故只出输出分量一条明细。
2. **合成量模式在 Token 量纲下不适用**：量直接取上游 token，不按秒折算。
