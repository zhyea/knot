## 4. 根因归并：4 条阻断其实是 3 个独立缺陷 + 1 个幻象

```
① .gitignore 用 *.json 通配（🔴-1）
   → 测试夹具不入库 → 干净 checkout 9 个用例红

② .gitignore 忽略 */package-lock.json + *.json（🔴-2）
   → 干净 checkout npm ci EUSAGE（已复现）
   → 只能改走 npm install 重解析 ^ 范围 → 依赖版本漂移
   → 这大概率就是原报告观测到 4 个 TS2345 的环境（🔴-3）
   → 但锁文件入库 + npm ci 重装后，4 个 TS2345 无法复现

③ unplugin 声明被 *.d.ts 忽略 + CI「类型检查 → 构建」顺序（🔴-4）
   → 干净 checkout 首跑 35 个 TS7006（已精确复现）
   → 与锁文件无关：锁死后依然复现，只有先构建才消失
   → 且被一个未跟踪的残留 src/components.d.ts 长期掩盖
```

结论修正：**🔴-4 有独立根因，不能归到 🔴-2 名下**（我第一轮把它并进锁文件链是错的）；🔴-3 才是依赖漂移的产物，且已随锁文件消失。原报告的问题不是"拆得太细"，而是**把 3 个独立缺陷与 1 个环境幻象混在同一层级**，读者无法判断哪条该改代码、哪条该改基础设施。

## 5. 原报告的方法学问题

1. **环境指纹与实际不符**：报告的 JDK 27.0.1 / Maven 3.10.0 / Node 26.13.0 / npm 11.20.0 在本机不存在（只有 25.0.3 / 3.9.15 / 22.22.2 / 10.9.7）。既然后端 1529、前端 592 这些数字与本机逐一对得上，说明命令是真实执行过的——问题出在**没有把"哪次测量在哪个环境"写清楚**，导致环境差异被当成代码缺陷上报。
2. **"本地也不存在该目录"是事实性错误**：夹具在，4492 字节，11-01 创建。正确表述应是"本地存在但未入库；干净导出后缺失"。
3. **把根因与环境幻象混在同一层级**：🔴-1/🔴-2/🔴-4 是三个独立缺陷，🔴-3 是依赖漂移现象，报告用同一种"阻断"口径并列，导致修复顺序无法判断。
4. **判据强度不均**：`*.json` 这条通配的实际影响面（会连带吞掉任何未来的测试夹具/样例配置）只给了"加否定规则"的方向，没给可执行规则，例如 `!knot-server/**/src/test/resources/**/*.json`。
5. **没往下追"为什么本地能过"**：若追一步就会发现 `src/components.d.ts` 这个残留（§3.4），也就不会把 🔴-4 写成"干净环境才有"的偶发。

原报告值得保留的优点也应记一笔：**行号级引用几乎全中**（`GatewayRequestHandler`、`GatewayConfigCacheService`、`ProxyStreamingFlux`、`RoutingResolver` 的引用逐行对得上），§7"已排除的误报"主动对照既有规范，避免了一批"看起来像违规"的噪声——这部分不需要返工。
