## 3. 必须修订的三项

### 3.1 P0-2 的实现形态会把"修 P0"变成"造 P0"

**事实**：`dispatch` 有两个调用点，线程上下文完全不同。

| 调用点 | 位置 | 执行线程 |
|---|---|---|
| Gateway 阶段 | `AbstractGatewayRequestTemplate.java:144/176/196`，位于 `handleMap` 同步段 | **Netty event loop** |
| Upstream 阶段 | `UpstreamProxyClient.java:120/123/126`，由 `GatewayRequestHandler.java:299` 的 attempt supplier 托底 | `Schedulers.boundedElastic()` |

原方案 §5.2 要求「每个 binding 独立提交、`Future.get(timeoutMs)` 等待」——在 Gateway 阶段等同 **event loop 阻塞**，直接违反 `10-backend-java` 已立下的红线（"event loop 禁止 `block()`；调度一律 `boundedElastic`"）。这是在修一个未复现的缺陷时引入一个必然发生的生产故障。

**修订方向**：

1. `PluginDispatcher.dispatch` 改为返回 `Mono<Void>`，由**调用点**决定 compose 还是 block：
   - Gateway 阶段：直接在 Reactor 链上 compose。
   - Upstream 阶段：`proxy()` 本就是阻塞层，`.block(Duration)` 可接受。
2. 每个 binding 用 `Mono.fromRunnable(...).subscribeOn(...).timeout(Duration.ofMillis(ms))`。
3. **不要自建 virtual thread executor / 信号量 / 手动 MDC 透传**——已存在 `knot-gateway/.../runtime/MdcContextSupport`（`subscribeOn` + MDC，兜底 `Schedulers.boundedElastic()`），直接复用即可拿到超时、调度和 traceId 透传。
4. 保留原方案里站得住的部分：`PluginFailurePolicy` 枚举、`PluginDescriptor.failurePolicy()`、上下文关闭协议、`timeoutMs<=0` 取默认配置 + 上限。

**失败策略名单（8 个 handler 已全枚举，可直接使用）**：

| 策略 | 插件 |
|---|---|
| `FAIL_CLOSED` | `SensitiveWordRequestPlugin`、`SensitiveWordResponsePlugin`（超时不得绕过审核） |
| `FAIL_OPEN` | 6 个 builtin：`GatewayRequest/Response/Error` + `UpstreamRequest/Response/Error` Logging |

### 3.2 §6.3 下半段与 2026-10-23「计费去兜底」立规反向

**现状**：`UsageExtractorRegistry.resolveExtractorCode` 的优先级是
`binding 显式配置 → ANTHROPIC provider 特例 → protocol if 链 → 默认 TOKEN`。
源码注释自陈：

> 这与「配置驱动」原则相悖，彻底移除需改为绑定配置驱动，见方案 §12 第 4 项。

而 `docs/standards/rules/60-business-rules.md` §8（2026-10-23 立规）明确：**禁止启发式猜协议语义；消解点是 per-binding 提取器绑定**。

原方案提议把 protocol→extractor 挂进 `ModelApiProtocolEnum.usageExtractorCode()`：形式上删了 if 链，实质是把「按协议猜」从 if 提升为官方契约。这与方案自身 §3.1「继续围绕 `UsageExtractor` 收敛」自相矛盾。

**同一数字的第二个内部矛盾**：§6.3 第 7 条要删 `canonical()`（恒等函数），但 `canonical()` 恰恰是"协议别名归一"的正当归位——两者必须二选一。

**修订方向**（拆成两件事）：

- **(a) 赞成**：抽 `UsageExtractorResolver`（`Resolver` 在后缀白名单），消灭 `RoutingTestBillingVerdictService:144` 对网关 registry 的手抄镜像。这是真正的双份真相。**建议提前执行**。
- **(b) 改方向**：protocol 猜测的收敛目标是**移除**（改为绑定配置驱动），不是搬进枚举。

## 6. 第 5 项决策的详细依据

### 6.1 问题形态（比"字段不一致"更严重）

HTTP 出口的 `GatewayErrorResponse.ErrorBody` **根本没有 `stage` 字段**（只有 `message/type/code/detail/upstreamStatus/upstreamMessage`）。所以真实差异是：

| 出口 | type | http_status | stage |
|---|---|---|---|
| HTTP 响应 | `timeout_error` | **504** | 无此字段 |
| Kafka 流量事件 | `upstream_error` | **500** | `internal` |

同一个请求：调用方看到"超时"，数仓记成"上游故障"。这是**性质误判**，不是格式差异。

### 6.2 为什么"只统一代码、不改值"不算修复

原方案 §10 风险表写「保持现有 `type/code/stage` 值」，与 P0-3 目标自相矛盾：只要 Kafka 侧仍输出 `upstream_error`，两出口就仍不一致，抽 descriptor 只是"两个地方用同一份错的值"。

四条支撑论据：

1. **可直接观测的数据畸形**：`GatewayTrafficMsgDto:242` 的 `statusOf()` 把 `upstream_error` 映射成 `status=upstream_error`；而契约规定上游失败率须过滤 `attempts[].counted_for_ejection`。总超时不产生任何 attempt 失败行 → 数仓会出现"request 级标上游失败、attempts 为空"的记录。这是当前缺陷的可取证证据。
2. **超时与真未知异常共用出口**：`ErrorMsgDto:89` 兜底同时承接 NPE 类未知异常与总超时，值完全相同，事后无法区分"代码炸了"和"慢"。
3. **把 timeout 拎出来，第 2 条自动消解**：不需要给未知异常改 type（那是更大的破坏性变更）。分离后兜底出口只剩真正的未知异常，`500/upstream_error/internal` 语义自然干净。
4. **数仓契约当前处于漂移状态**：`gateway-warehouse-kafka-message-protocol-2026-10-17.md` §3 声明 stage 为八值，含 `routing_resolve`；代码 `ErrorMsgDto.Stage` 却是另一个八值——**缺 `routing_resolve`、多 `internal`**。两边已漂且无人校验，说明此处改动自由度很高，但也意味着**改完必须回写文档**。

### 6.3 三个选项

| | Kafka 侧输出 | 契约改动 | 语义准确度 | 判定 |
|---|---|---|---|---|
| A 不改值 | `upstream_error`/500/`internal` | 0 | ✗ 超时仍算作供应商故障 | ❌ 未真正修复 |
| B 对齐 type+status，stage 复用 `upstream_call` | `timeout_error`/504/`upstream_call` | 契约表 +1 行 | △ 位置对、性质不明 | 保守备选 |
| **C 对齐 type+status，新增 `stage=timeout`** | `timeout_error`/504/`timeout` | 契约表 +1 行 + 八值→九值 | ✓ 最精确 | **推荐** |

**推荐 C**：总超时是网关自身的 request budget，覆盖整条链路（路由解析、插件、上游等待均可能触发），`upstream_call` 会误导，"卡在 upstream"不是它的语义。既然这一行的 type/status 无论如何都要改，一次做干净；**零历史包袱前提下该选项已无成本项**。

### 6.4 选 C 的落地面（5 项）

1. `ErrorMsgDto.Stage`（或新抽的 `GatewayErrorStageEnum`）+1 值 `TIMEOUT("timeout")`；顺带对齐 `routing_resolve` / `internal` 的文档漂移（先确认哪个为准）。
2. `docs/gateway-warehouse-kafka-message-protocol-2026-10-17.md` §3：类型对照表加一行 + 八值清单改九值。
3. `GatewayErrorDescriptor.of()` 中 timeout 分支落 `504 / timeout_error / timeout`。
4. 新增 `GatewayErrorMappingTest`，参数化覆盖 8 类异常，HTTP 与 Kafka 双出口成对断言。
5. 原方案提到的"历史数据口径说明"——**未部署前提下不需要**。
