### 0.4 预算与键序（已定策）

`PluginLogSupport` 的 512 预算由整份快照**共享**（`truncateTree` 用 `int[]{512}` 引用传递），
`responseSnapshot` 里谁排前面谁留正文。两个 body 共存后，长响应下必然只有一个能读全 —— **留原文**：
`upstreamResponseBody` 不可再生（适配会丢掉供应商侧的 id / 时间戳 / 原始 usage 形态），
`responseBody` 在 `gateway-response-log` 里另有一份可查。键序由
`UpstreamProxyClientTest#wireOriginalComesBeforeAdaptedBody` 钉死。

副作用仍在：`usage` 排在最后，长响应下 `rawUsage` 的文本字段（以及 `rawBody` 那份整包副本）会被截断；
数字字段不受影响（`truncateTree` 只动 textual）。要两个 body 都读全，只能临时切 `knot.plugin.log.body=full`。

## 1. 结论

用户观察到的“上游返回信息被修改过”，需要拆成三类不同问题：

| 层次 | 实际发生了什么 | 是否影响客户端响应 |
|---|---|---|
| 协议适配层 | `adapter.handleResponse` 把供应商响应转换成网关侧协议形状 | 是，属于既定设计 |
| 日志投影层 | 日志把响应体当字符串、按预算截断，并包进快照对象 | 否，只影响日志可读性 |
| 流式路径 | 流式响应体在 `Flux` 中，当前上游响应日志没有正文 | 否，属于日志缺口 |
| 客户端最终响应 | `knot_extend` 注入 / 流式 usage 事件（`GatewayRequestHandler:576-600`） | 是，这才是客户端真正收到的；`UPSTREAM_RESPONSE` 日志记的是它**之前**的适配结果 |

> ⚠ 表中「日志投影层」容易被读成「日志 = 客户端响应」。实际是**三层**，见 §0 修正 1。

因此：

- 如果日志里的 `id`、`created`、`model`、`finish_reason`、`usage` 等字段与供应商原文不同，根因是 **`AbstractUpstreamProtocolExecutor` 在构造 `ProxyResult` 前执行了 `adapter.handleResponse`**。
- 如果日志正文尾部出现 `...(truncated)`，根因是 **`PluginLogSupport` 默认的 512 字符截断策略**，不是上游或客户端响应被改。
- 如果流式请求的日志里 `responseBody` 为 `null`，根因是 **流式分支的 `ProxyResult.responseBody` 本来就是 `null`**，正文由 `UpstreamStreamResponse` 持有。
- 上游请求日志和上游异常日志也存在同类保真缺口，见 §3.5、§3.6。

## 2. 问题现象对照

| 观察到的现象 | 所属层 | 直接原因 | 建议判断 |
|---|---|---|---|
| 响应结构变成另一种协议形状 | 协议适配 | `adapter.handleResponse` 在日志分发前执行 | 正常情况下是协议适配；若日志定位为“上游原文”，则是缺陷 |
| `id` / `created` / `model` / `finish_reason` / usage 与供应商不同 | 协议适配 | 适配器重建响应字段 | 同上 |
| `response.responseBody` 是带转义的字符串 | 日志投影 | 快照里的 body 是 `String`，`JsonKit.toTree` 不会把内层字符串再解析成树 | 日志不可直接寻址，排障需要二次解析 |
| 响应尾部出现 `...(truncated)` | 日志投影 | 默认 `truncated` 模式，整份正文共享 512 字符预算 | 日志脱敏策略，不是数据面修改 |
| 流式请求 `responseBody=null` | 流式日志缺口 | `ProxyResult.responseBody` 在流式路径固定为 `null` | 当前日志不记录流式正文 |
| 上游 4xx/5xx 日志没有上游错误体 | 异常日志缺口 | `UpstreamErrorPayload` 没有错误体字段 | ✅ 已补（§0.3）：现带 `httpStatus` 与 wire 错误体 |

## 3. 证据链

### 3.1 响应在进日志前已经被协议适配

证据链路：

1. `knot-server/knot-gateway/src/main/java/org/chobit/knot/gateway/upstream/protocol/AbstractUpstreamProtocolExecutor.java:154`
   先执行 `adapter.handleResponse(buffered.body(), context)`，把上游原文转换为网关侧响应。
2. 同文件 `:155-163` 用转换后的 `handledResponseBody` 构造 `ProxyResult`，原始 `buffered.body()` 不再保留。
3. `knot-server/knot-gateway/src/main/java/org/chobit/knot/gateway/upstream/UpstreamProxyClient.java:126`
   在 `UPSTREAM_RESPONSE` 阶段分发插件。
4. 同文件 `:252-261` 的 `responseSnapshot` 把 `result.responseBody()` 放进日志快照。
5. `knot-server/knot-plugin/src/main/java/org/chobit/knot/plugin/builtin/UpstreamResponseLoggingPlugin.java:64-72`
   直接把 `context.responseSnapshot()` 转成 payload 输出。

典型改写示例：

- `knot-server/knot-adapter/src/main/java/org/chobit/knot/adapter/support/anthropic/AnthropicMessagesResponseSupport.java:119-125`
  重新生成 `id`（`chatcmpl-<uuid>`）、填当前 `created`、映射 `finish_reason`，并转换 usage。
- `knot-server/knot-adapter/src/main/java/org/chobit/knot/adapter/protocol/ChatCompletionsToMessagesUpstreamAdapter.java:65`
  和 `MessagesToChatCompletionsUpstreamAdapter.java:70` 都通过 `handleResponse` 做双向协议转换。
- `knot-server/knot-adapter/src/main/java/org/chobit/knot/adapter/protocol/AwsBedrockChatCompletionsToConverseUpstreamAdapter.java:53`
  Bedrock Converse 响应同样在适配器里转成 OpenAI 形状。

契约问题：

- `knot-server/knot-plugin/src/main/java/org/chobit/knot/plugin/log/UpstreamResponsePayload.java:7`
  Javadoc 写的是“原始响应 JSON”，但代码实际记录的是适配后的响应。
- 这意味着日志消费者如果把该字段当作供应商原文，会得到错误结论。

### 3.2 日志里的响应体是字符串，不是可寻址的 JSON 树

- `UpstreamProxyClient.java:252-261` 把 `responseBody` 以 `String` 放入快照。
- `UpstreamResponseLoggingPlugin.java:69` 使用 `JsonKit.toTree(context.responseSnapshot())`。
- `JsonKit.toTree`（`knot-server/knot-common/src/main/java/org/chobit/knot/common/util/JsonKit.java:233-242`）
  只是把 `Map` / POJO 转成树，不会把 `Map` 里的 `String` 再解析成 JSON。
- 结果是日志里出现 `"responseBody": "{\"id\":...}"` 这样的转义字符串，而不是可直接按字段寻址的对象。

### 3.3 默认 512 字符截断

- `knot-server/knot-plugin/src/main/java/org/chobit/knot/plugin/log/PluginLogSupport.java:40`
  默认正文预算 `BODY_BUDGET = 512`。
- 同文件 `:53` 默认模式为 `truncated`，模式在类加载时从系统属性解析一次。
- 同文件 `:104-113` 对文本节点截断并追加 `...(truncated)`。
- 预算由整份 payload 的所有文本值共享；`responseBody` 很长时会消耗掉预算，后面的 `usage` 文本字段也可能被截断。
- 这是日志安全策略，不是数据面修改。系统属性 `knot.plugin.log.body` 支持 `none` / `truncated` / `full`，但 `full` 会落完整 prompt / 模型输出，仅适合短时排障。

### 3.4 流式响应没有正文日志

- `AbstractUpstreamProtocolExecutor.java:242-250` 流式分支构造 `ProxyResult` 时 `responseBody` 为 `null`。
- 正文由 `UpstreamStreamResponse` 持有的 `Flux<DataBuffer>` 承载。
- `UpstreamProxyClient.java:259` 因此只能记录 `responseBody=null` 和元数据。
- 如果观察到的是流式请求，当前行为不是“上游响应被改”，而是“上游响应日志没有抓流式正文”。

### 3.5 上游请求日志同样不是实际出站请求

- `UpstreamProxyClient.java:123` 在执行器之前分发 `UPSTREAM_REQUEST`，日志读取的是 `context.requestBody()`。
- 真正的出站请求体由 `AbstractUpstreamProtocolExecutor.java:413` 的 `adapter.buildRequestBody(context)` 生成。
- 因此跨协议绑定时，请求日志展示的是客户端协议请求，不是供应商实际收到的请求。
- `knot-server/knot-plugin/src/main/java/org/chobit/knot/plugin/log/UpstreamRequestPayload.java:7`
  同样写的是“原始请求 JSON”，与当前实现存在相同偏差。

### 3.6 上游异常日志缺上游错误体与状态码

- `knot-server/knot-gateway/src/main/java/org/chobit/knot/gateway/exception/GatewayUpstreamException.java:7-9`
  持有 `httpStatus`、`responseBody`、`retryAfterMs`。
- 同文件 `:74-80` 提供 `httpStatus()` / `responseBody()` 访问器。
- `knot-server/knot-plugin/src/main/java/org/chobit/knot/plugin/builtin/UpstreamErrorLoggingPlugin.java:67-75`
  只输出 `errorType` / `errorMessage`，没有使用异常里的 `httpStatus` 和 `responseBody`。
- `knot-server/knot-plugin/src/main/java/org/chobit/knot/plugin/log/UpstreamErrorPayload.java:15-22`
  也没有对应的 `httpStatus` / `upstreamResponseBody` 字段。
- 结果是上游 4xx/5xx 的真实错误体和状态码在插件日志里缺失。

### 3.7 同步与异步查询日志语义不一致

- 异步查询路径 `knot-server/knot-gateway/src/main/java/org/chobit/knot/gateway/async/AsyncTaskQueryPluginDispatcher.java:58-62`
  记录的是查询响应原文。
- 同步代理路径记录的是 `adapter.handleResponse` 产物。
- 同一个“上游响应日志插件”，两条链路的 body 语义不同，排障时容易误判。

## 4. 影响

| 影响 | 说明 |
|---|---|
| 供应商对账失真 | 用同步上游响应日志对比供应商后台时，看到的是网关适配后的字段，不是供应商原文 |
| 排障证据不足 | 上游错误体、HTTP 状态码、流式正文缺失，无法单靠插件日志还原上游行为 |
| 误判数据面 | 512 字符截断和 JSON 字符串化容易被误认为响应内容被网关修改 |
| 契约误导 | payload Javadoc 写“原始响应 / 原始请求”，与实现不一致 |

需要明确：**客户端收到的协议适配响应是既定行为**。`docs/gateway-output-message-protocol-2026-10-17.md` 已把 `adapter.handleResponse` 定位为协议适配；问题在于“上游日志”是否应该记录同一份适配后响应。

## 5. 候选解决方案

> 以下方案均未实施，需 robin 先确认“上游日志”的目标语义，再决定改动范围。

### 方案 A：让上游日志恢复 wire 级证据（推荐，若日志用于供应商对账）

核心原则：**同一份日志只记录一个明确来源，原始响应和网关适配响应分开命名，不能继续混用 `responseBody`。**

候选改动点：

1. 数据模型
   - 在 `ProxyResult` 增加上游原始响应字段，例如 `upstreamResponseBody`；现有 `responseBody` 继续表示
     **适配后响应**（它是客户端响应的上游来源，但客户端还会叠加 `knot_extend` / 流式 usage 事件，
     两者仍不同源——「客户端最终收到」用 `gateway-response-log` 看）。
   - 或者在 gateway 侧引入独立的 `UpstreamExchangeSnapshot`，把 `upstreamRequest` / `upstreamResponse` / `gatewayResponse` / `usage` 分开。
2. 响应采集点
   - `AbstractUpstreamProtocolExecutor.executeBuffered` 在 `adapter.handleResponse` 之前保存 `buffered.body()`。
   - `UpstreamProxyClient.responseSnapshot` 的 `responseBody` 改为读取原始响应；如仍需要客户端形态，新增 `gatewayResponseBody` 字段。
3. 请求采集点
   - 在 `buildRequestBody` 之后获取实际出站体，或在请求上下文里增加 `upstreamRequestBody` 快照。
   - 需要避免重复调用 `buildRequestBody` 造成转换结果不一致。
4. 异常日志（✅ 已实施，但取值路径与原方案不同）
   - `UpstreamErrorPayload` 增加 `httpStatus`、`upstreamResponseBody`。
   - ⚠ **不能让插件判断 `error instanceof GatewayUpstreamException`**：`knot-plugin` 不能反向依赖
     `knot-gateway`（会成环）。实际做法是 `UpstreamPluginContextSupport`（网关侧）解出值，
     以 `UpstreamPluginContext.httpStatus()` / `upstreamResponseBody()` 两个普通字段传入，
     插件只读值、不认类型。
5. 流式日志
   - 先明确是否记录流式正文；若不记录，至少增加 `streaming=true` / `contentType` 标记，避免“body 丢失”的误解。
   - 若必须记录，设计有界 tee / buffer，只保留前 N 字节，且不得阻塞转发、不得改变 `Flux` 的取消与背压语义。
6. 契约与文档
   - 修正 `UpstreamResponsePayload` / `UpstreamRequestPayload` 的 Javadoc。
   - 明确 `bodySource=UPSTREAM_RAW` / `GATEWAY_ADAPTED` 之类的来源标记，避免消费者猜。

优点：日志与插件名称一致，能直接对比供应商原文。
代价：改动 `ProxyResult`、插件上下文、payload record、请求分发时机；需要同步更新测试与文档。

### 方案 B：保留现语义，但把契约改准确（最小改动）

核心原则：承认日志记录的是网关侧 payload，不再声称“原始”。

候选改动点：

1. `UpstreamResponsePayload` / `UpstreamRequestPayload` 的 Javadoc 改为“网关侧请求 / 响应快照”。
2. 字段可改名为 `gatewayRequestBody` / `gatewayResponseBody`，或增加 `bodySource=GATEWAY_ADAPTED`。
3. 文档补充“跨协议绑定时，上游日志展示的是适配后形状”。

优点：改动小、无原始 body 存储与泄露面。
缺点：仍无法用该日志核对供应商原文；只解决“名字误导”。

### 方案 C：只解决截断和字符串化

适用于确认“结构没变，只是日志尾部被截断”的场景。

候选改动点：

1. 临时排障：启动参数增加 `-Dknot.plugin.log.body=full`，用完改回。
2. 长期方案：增大预算、按阶段配置预算，或把合法 JSON body 解析成 `JsonNode` 后再进日志；非 JSON / SSE 回落为字符串。
3. 不建议把默认改成 `full`：会落完整 prompt、模型输出和业务数据，PII / 密钥风险不可接受。

### 方案 D：流式日志单独定策

1. 最小方案：明确“流式上游响应不落正文”，payload 增加 `streaming=true` 和 `contentType`，避免误判。
2. 完整方案：对 `Flux<DataBuffer>` 做有界 tee，仅保留前 N 字节用于日志；日志写入必须在流完成后进行，不能反向施加背压，也不能吞掉异常或改变取消语义。

### 方案 E：错误日志补齐（低风险，可独立实施）

- `UpstreamErrorPayload` 增加上游 HTTP 状态、原始错误体、`retryAfterMs`（如果需要）。
- `UpstreamErrorLoggingPlugin` 从 `GatewayUpstreamException` 读取这些字段。
- 这条与响应/请求保真是独立问题，可以先做。

## 6. 方案对比

| 方案 | 能解决“日志不是上游原文” | 能解决“截断/转义” | 改动面 | 泄露风险 | 适合场景 |
|---|---|---|---|---|---|
| A 原始 + 适配分离 | 是 | 可同时处理 | 中 | 原始 body 需继续套用 `PluginLogSupport` 策略 | 供应商对账、工单排障 |
| B 改名/标注 | 否，只消除误导 | 否 | 小 | 低 | 只关心客户端响应 |
| C 截断/结构优化 | 否 | 是 | 小 | `full` 风险高 | 日志可读性排障 |
| D 流式策略 | 部分 | 部分 | 中 | 取决于是否落正文 | 流式排障 |
| E 错误日志补齐 | 部分 | 否 | 小 | 低 | 上游 4xx/5xx 排障 |

## 7. 建议判断顺序

1. 先确认观察到的是哪一类现象：
   - 结构/字段变化 → 走方案 A 或 B；
   - `...(truncated)` → 走方案 C；
   - 流式 `responseBody=null` → 走方案 D；
   - 上游错误日志没有错误体 → 走方案 E。
2. 如果“上游日志”的定位是“与供应商对账 / 提工单”，推荐方案 A；如果只是内部观察客户端响应，方案 B 更克制。
3. 不建议先改 `PluginLogSupport` 的默认策略，先确认日志保真层级，再决定是否调整预算。
