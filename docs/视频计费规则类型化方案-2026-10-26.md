## 0. 修订说明（v2）

v1 提了「新增形状分类轴 `BillingRuleTypeEnum`」。robin 拍板修正：

- **不新增形状分类轴**；
- **直接扩充 `PricingPlanEnum`**；
- **默认规则类型不需要新增枚举值**（默认即沿用既有 `FIXED`，代表字节/豆包型维度计费）。

故 v2 方案：**在 `PricingPlanEnum` 新增一个值 `VENDOR_MINIMAX`（厂商定制 / 进阶方案特例），MiniMax 归为此类；其余厂商仍走 `FIXED`/`TIERED`/`PEAK_OFF_PEAK`，其中 `FIXED` 即默认（字节/豆包型）。**

> 修正后的好处：无需新列、无需新 VO 字段、无需 schema 迁移；改动收敛到「枚举 + 工厂 + 校验 + 前端下拉 + MiniMax 形状校验」，且无存量回填（data.sql 无 MiniMax 规则种子）。

## 1. 问题：视频计费缺少「厂商定制」这一档

现状（`kb_billing_rule_versions` 表的 `pricing_plan` 列 + `PricingPlanEnum`）：

| 值 | 语义 | 视频可用性 |
|---|---|---|
| `FIXED` | 固定价（默认方案） | ✅ |
| `TIERED` | 阶梯价 | ✅（VIDEO 已放开） |
| `PEAK_OFF_PEAK` | 高低峰价 | ✅（VIDEO 已放开） |

三家维度型厂商（豆包 / Kling / Vidu Q2 / Vidu Q3-pro）都能用上述三值表达，**但 MiniMax 的「多分量独立计价 + 附加费」形状没有对应的方案档位**——
它现在只能勉强塞进 `FIXED`（§7.2 实测即如此），系统无从识别「这是厂商定制型规则」。

robin 的拍板把这件事收口为：**在 `PricingPlanEnum` 加 `VENDOR_MINIMAX`，MiniMax 归为此类**；
默认（字节/豆包型）不需要新值，沿用 `FIXED` 即可。

## 2. 类型 = `PricingPlanEnum` 的一个新值

### 2.1 枚举扩值

```java
public enum PricingPlanEnum implements EnumOption {
    FIXED("固定价"),
    TIERED("阶梯价", TOKEN, IMAGE, AUDIO, VIDEO),
    PEAK_OFF_PEAK("高低峰价", TOKEN, IMAGE, AUDIO, VIDEO),
    /**
     * 厂商定制计费规则：进阶定价方案家族中的特例（旗舰 = MiniMax）。
     * 代表视频「多分量独立计价 + 附加费」的厂商定制形状。
     * 取价语义与 FIXED 一致（分量数学在 VideoBillingModeCalculator / config_json，
     * 方案层只决定单价来源），本值仅作为分类标签与落库校验锚点。
     * 仅 VIDEO 模式可用（厂商定制形状目前只在视频域出现）。
     */
    VENDOR_MINIMAX("厂商定制(MiniMax)", VIDEO);
}
```

- `fromCode(blank) -> FIXED` 不变 → **默认类型 = `FIXED` = 字节/豆包型**，无需新值。
- `supports(VIDEO)` 为真；其余模式 `supports` 为假（防止非视频规则误标厂商定制）。
- `isAvailable()` 沿用 `return true` → 能力矩阵默认开放。

### 2.2 取价语义：VENDOR_MINIMAX == FIXED

`PricingPlan` 领域对象由 `BillingConfig.pricingPlan(PricingPlanEnum)` 的 `switch` 构建。
新增 `VendorMiniMaxPricing`，其 5 个取价方法与 `FixedPricing` 完全一致（无阶梯、无相位倍率，
单价直接来自 `config_json` 的 `basePrices`/`defaultUnitPrice`/`resolutionPrices`/分量自带价），
仅 `plan()` 返回 `VENDOR_MINIMAX`。

```java
case VENDOR_MINIMAX -> new VendorMiniMaxPricing(basePrices, defaultUnitPrice, resolutionPrices);
```

> 为什么 VENDOR_MINIMAX 不引入新取价逻辑：真正的「多分量求和」数学在
> `VideoBillingModeCalculator` 里、由 `config_json` 的 `video.inputVideoPerSecond` /
> `video.inputImagePerImage` / `surcharges` 驱动，与 `pricingPlan` 取值无关。
> 所以 `VENDOR_MINIMAX` 在计算器眼里 == `FIXED`，**计算器零改动**；枚举值纯粹是「分类标签 + 校验锚点」。

## 3. 五家厂商映射（直接对齐 §7）

| 厂商（§7） | `billing_mode` | `pricing_plan` | 归类 |
|---|---|---|---|
| 豆包 Seedance 2.5（§7.5） | VIDEO | **FIXED** | 默认型（字节/豆包维度：token 量纲 + 分辨率维度 + `:REFERENCE`） |
| Kling 4.0（§7.1） | VIDEO | **FIXED** | 默认型（OUTPUT_PLUS_MAX + 分辨率维度） |
| Vidu Q2（§7.3） | VIDEO | **TIERED** | 默认型（维度原型 + PROGRESSIVE 累进） |
| Vidu Q3-pro（§7.4） | VIDEO | **PEAK_OFF_PEAK** | 默认型（维度原型 + 高低峰倍率） |
| MiniMax Hailuo（§7.2） | VIDEO | **VENDOR_MINIMAX（新增）** | 厂商定制型（输出秒 + 输入视频秒 + 输入图片张数 + 附加费） |

**结论**：四家落在默认型（FIXED/TIERED/PEAK_OFF_PEAK 任一带维度原型），仅 MiniMax 单列 `VENDOR_MINIMAX`。
「默认类型不新增枚举值」因此自然成立——默认型就是 `FIXED` 等既有值，无需为「默认」造一个新值。

## 4. 落库与默认规则

### 4.1 无 DDL

`pricing_plan` 列与 `pricingPlan` VO 字段**已存在**，直接复用。本次**不需要新列、不需要迁移脚本加列**。

### 4.2 默认取值

- `pricing_plan` 列 `DEFAULT 'FIXED'` → 新建 VIDEO 规则留空即 `FIXED`（= 字节/豆包型默认）。
- 仅当规则是 MiniMax 这类厂商定制形状时，显式选 `VENDOR_MINIMAX`。

### 4.3 存量回填（核查结论：无需回填，无脚本）

经核查 `data.sql`：MiniMax 仅登记为 `model_family`（`('minimax','MiniMax',13)` 行），**不存在任何 MiniMax 计费规则种子**（`kb_billing_rule_versions` / `kb_billing_rules` 无 MiniMax 规则行），因此没有历史 `pricing_plan='FIXED'` 的 MiniMax 规则需要改标。

> 原设想的回填 SQL（下）仅作「若未来运行时插入 MiniMax 规则种子」的**幂等兜底模板**，**本次不创建迁移文件、不执行**：
>
> ```sql
> -- 仅当确认存在 MiniMax 计费规则种子时才需要；2026-10-26 核查无此数据，故跳过
> UPDATE kb_billing_rule_versions
> SET pricing_plan = 'VENDOR_MINIMAX'
> WHERE billing_mode = 'VIDEO'
>   AND pricing_plan = 'FIXED'
>   AND JSON_CONTAINS_PATH(config_json, 'one',
>         '$.video.inputVideoPerSecond', '$.video.inputImagePerImage', '$.surcharges') = 1;
> ```
>
> 守卫条件确保「只有真的带多分量/附加费的 VIDEO 版本」被改标，避免误伤维度型规则。

### 5.1 校验伪码（挂 `validate(PricingPlanEnum)` 内，仿现有 TIERED 分支）

```java
if (resolved == PricingPlanEnum.VENDOR_MINIMAX) {
    return validateVendorMiniMax();
}
// ... 现有 TIERED / PEAK_OFF_PEAK 分支保持不变

private String validateVendorMiniMax() {
    boolean hasComponent = video != null
        && (video.inputVideoPerSecond() != null
            || video.inputImagePerImage() != null
            || (surcharges != null && !surcharges.isEmpty()));
    return hasComponent ? null
        : "VENDOR_MINIMAX requires component fields (inputVideoPerSecond / inputImagePerImage / surcharges)";
}
```

> 与红线一致：单向校验（VENDOR_MINIMAX ⇒ 必须带分量形状），不强制反向（FIXED 带分量字段也允许，
> 避免破坏既有 MiniMax=`FIXED` 的历史配置；改标由 §4.3 回填显式完成）。

## 6. 决策点（全部已拍板，2026-10-26）

1. ~~枚举命名~~ ✅ `VENDOR_MINIMAX`（标签「厂商定制(MiniMax)」）。
2. ~~作用域~~ ✅ **仅 VIDEO**：`VENDOR_MINIMAX(..., BillingModeEnum.VIDEO)`，`supports(VIDEO)` 为真、其余模式为假；前端 `EnumControl` 走数据驱动能力矩阵，仅视频下拉出现该项。
3. ~~校验强度~~ ✅ **强制图片分量**（二次迭代按官方价表收窄）：`validateVendorMiniMax()` 要求 `video.inputImagePerImage` 必填（MiniMax 的识别特征是「输入图片按张计费」）；视频输入价可由输出档位价回落、免费额度默认 5、音频免费，故均不必填。单向校验，不限制 FIXED 带分量字段。
4. ~~回填范围~~ ✅ **无需回填**：`data.sql` 中 MiniMax 仅登记为 `model_family`（`('minimax','MiniMax',13)`），**不存在 MiniMax 计费规则种子**，故无历史 `billing_mode`/规则记录需改标；§4.3 的 UPDATE 脚本仅作「若未来有 MiniMax 规则种子」的幂等兜底模板，本次不执行。

## 8. 专属实现（2026-10-26 二次迭代：独立组件 + 专属计算）

robin 补充 MiniMax H3 官方价表后，为其落了一套独立的前端组件与后端计算分支。

### 8.1 官方价表（来源：robin 截图）

| 模型 | 输出分辨率 | 输出视频/秒 | 输入视频/秒 | 输入图片/张（超出免费后） |
|---|---|---|---|---|
| MiniMax-H3（画质优先） | 2K | ¥0.80 | ¥0.80 | ¥0.20 |
| MiniMax-H3 | 768P | ¥0.50 | ¥0.50 | ¥0.20 |
| MiniMax-H3-Highspeed | 768P | ¥0.40 | ¥0.40 | ¥0.20 |
| MiniMax-H3-Lite | 768P | ¥0.26 | ¥0.26 | ¥0.13 |
| MiniMax-H3-Lite | 480P | ¥0.16 | ¥0.16 | ¥0.13 |

规则：
- **图片输入**：每次任务前 **5 张免费**，超出部分按张计费；单价**不随图片或输出视频分辨率变化**。
- **视频输入**：按**输入时长**及所选模型的**输出分辨率**计费（每档输入价 == 该档输出价）。
- **任务类型**：同一模型、同一分辨率下各任务类型单价相同；**音频输入免费**。

### 8.2 计费公式

```
总价 = 输出秒数 × 档位输出单价
     + 输入秒数 × 档位输入单价        （未单配 INPUT_VIDEO:档位 时回落同档位输出单价）
     + max(0, 输入图片张数 − 免费张数) × 每张固定单价
     （音频输入免费，不收取任何附加费）
```

### 8.3 后端：`VideoBillingModeCalculator#calculateVendorMiniMax`

`calculate()` 在 `usage` 类型校验后按 `context.pricingPlan()` 分流：`VENDOR_MINIMAX` 走专属方法，其余方案走原通用分量路径。专属方法与通用路径的三点**实质差异**（非转发壳）：

1. **输出量只取输出秒，绝不折叠输入秒**：MiniMax 把输入秒当独立分量计费，若走 `quantity(SUM/OUTPUT_PLUS_MAX)` 会与输入分量重复计费。
2. **输入视频单价默认回落同档位输出单价**：`INPUT_VIDEO:档位` 键可单独覆盖（未来某档不同价），未配置时用 `resolveComponentPrice` 的 `componentDefault` 参数把输出档位价传进去。
3. **图片走固定标量价 + 免费额度默认 5 + 音频免费**：图片价不查分辨率键；`freeInputImages` 未配置时按 5 兜底；不收取任何附加费。

### 8.4 前端：`plans/PricingPlanVendorMiniMaxConfig.vue`

- 方案轴独立组件（`componentsByPlan.VENDOR_MINIMAX`），展示计费公式 + 三块输入：**输入图片每张**、**图片免费张数**、**音频输入（免费只读）**。
- `BillingModeVideoConfig.vue` 在 `pricingPlan === VENDOR_MINIMAX` 时：
  - 分辨率表第三列由「含参考输入」切换为「**输入每秒**（留空同输出）」，序列化为 `resolutionPrices["INPUT_VIDEO:档位"]`。**只要用户显式填了就落库，哪怕等于输出价**——不做「等于输出就省略」的隐式去重（MiniMax 官方价表输出/输入本就相等，去重会让刚填的值在 config_json 里凭空消失、重开回显不出，已作为缺陷修正）；留空才不下发 `INPUT_VIDEO` 键，由后端回落同档位输出价；
  - **隐藏**「合成量口径」与「输入侧分量」两块（避免与方案组件重复编辑同一字段，也避免用户误配 SUM 导致双计）。
- `BillingRuleFormDialog.vue`：切换方案时补官方默认（图片 0.20 / 免费 5）；保存前缺图片单价则拦截；`buildBaseConfig` 对 MiniMax 不落 `quantityMode` / `inputVideoPerSecond` / `surcharges`。
