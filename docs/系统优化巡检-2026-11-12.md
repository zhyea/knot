## 3. 本轮优化项

### 🟡-1 四个列表接口存在逐行查询（N+1）

**证据**

- `knot-server/knot-service/src/main/java/org/chobit/knot/svc/service/ModelPoolService.java:60` 使用 PageHelper，`:64-65` 对每条池记录调用 `enrich`；`:205-224` 的 `enrich` 每行执行 `listItemsByPoolCode`，`:229-232` 的 `boundCount` 再执行 `countItemsByPoolCode` 和 `countRoutingTargetsByPoolCode`。
- `knot-server/knot-service/src/main/java/org/chobit/knot/svc/service/AppService.java:57-61` 每行调用 `enrich`；`:159-161` 每行调用 `trafficPolicySupport.load`。
- `knot-server/knot-service/src/main/java/org/chobit/knot/svc/service/support/ResourceTrafficPolicySupport.java:58-63` 的单资源 `load` 先转调 `loadBatch(List.of(resourceId))`；`:69-109` 的一次 `loadBatch` 最多执行 4 条查询（绑定、限流策略、额度绑定、额度策略）。
- `knot-server/knot-service/src/main/java/org/chobit/knot/svc/service/RoutingConsumerService.java:52-56` 每行加载 traffic；`:205-207` 的 `toDto` 每行还执行 `countRulesByConsumerCode`。
- `knot-server/knot-service/src/main/java/org/chobit/knot/svc/service/ProviderProfileService.java:33-39` 每行 `toItem`；`:152-162` 的 `toItem` 每行执行 `countAccountsByProviderCode`。

**查询次数上界（`pageSize=20`，含 PageHelper 的 count 查询与主列表查询）**

| 列表 | 每行附加查询 | 单页上界 |
|---|---:|---:|
| ProviderProfile | 1 次 boundCount | 22 次 |
| ModelPool | 1 次 items + 2 次 count | 62 次 |
| App | 最多 4 次 traffic 查询 | 82 次 |
| RoutingConsumer | 最多 4 次 traffic + 1 次规则计数 | 102 次 |

**影响**

- 管理端单页 20 行即可放大为 62~102 次 DB 往返；列表变慢、连接池占用上升，且随每条关联数据增加而线性恶化。
- `ProviderProfileService` 的分页错误另见 🟡-2，两者需要同一轮修复。

**建议**

- 已有范式和目标形态：`RoutingRuleService.enrichList` 在 `knot-server/knot-service/src/main/java/org/chobit/knot/svc/service/RoutingRuleService.java:194-213` 先批量取目标与 traffic，再在内存组装。
- App、RoutingConsumer 复用 `trafficPolicySupport.loadBatch(resourceType, allIds)`，只调用一次。
- ModelPool 增加按 poolCode 集合的 `listItemsByPoolCodes`、分组 count 查询，或直接把条目数/目标数并进主列表 SQL。
- ProviderProfile 增加按 providerCode 集合的分组 count；列表主查询仍应保留 `Page` 身份。
- 建议补测试：用 Mockito 断言列表路径只调用一次 batch 方法，或通过 MyBatis 查询计数拦截器钉住单页查询次数上界。

### 🟡-2 `ProviderProfileService.list` 的 total 被 `stream().toList()` 丢掉

**证据**

- `knot-server/knot-service/src/main/java/org/chobit/knot/svc/service/ProviderProfileService.java:34-39`：
  - `providerProfileMapper.list(...)` 返回 PageHelper 的 `Page`；
  - 随后 `.stream().map(this::toItem).toList()` 变成普通 `List`；
  - 再 `new PageInfo<>(rows)`。
- PageHelper 6.1.0 的 `PageSerializable` 构造器只有在 `list instanceof Page` 时才取 `Page.getTotal()`，否则直接 `total = list.size()`。已机读源码确认。
- 因此第 1 页 `pageSize=20` 会返回 `total=20`；末页 5 条会返回 `total=5`，分页器会把总页数算错。
- 当前没有 `ProviderProfileService` 的测试文件（`rg` 未命中）。

**影响**

- 不是性能问题，而是**对外结果错误**：前端总条数、总页数、翻页可用性均可能错误。

**建议**

- 保持 `PageInfo<ProviderProfileEntity> pageInfo = new PageInfo<>(providerProfileMapper.list(...))`，再用 `pageInfo.getList()` 做转换；不要先把 `Page` 转成普通集合。
- 同时按 🟡-1 把 `boundCount` 批量化。
- 增加分页契约测试：`25` 行、`pageSize=10`，断言 `page1.total=25 / list=10`，`lastPage.list=5`。

### 🟡-3 操作日志列表入口无分页/无上限

**证据**

- `knot-server/knot-admin/src/main/java/org/chobit/knot/admin/controller/OperationLogController.java:60-87` 暴露 3 个返回 `List` 的 GET：按 module、operator、entity 查询。
- `knot-server/knot-service/src/main/java/org/chobit/knot/svc/service/OperationLogService.java:72-76` 直接调用 `operationLogMapper.listByModule`，没有 `PageRequest`。
- `knot-server/knot-dal/src/main/resources/mapper/OperationLogMapper.xml:19-40` 只有过滤与 `order by created_at desc`，没有 `limit`。

- 另外 `GET /api/system/enums/operation-logs/{category}` 仍在用，且同样无上限：`EnumConfigController.java:57-59`、`OperationLogService.java:125-131`、`OperationLogMapper.xml:94-106`；前端调用点 `knot-front/src/api/enums.ts:20`。

**建议**

- 枚举分类日志改为 POST + 分页查询，或复用 `/api/operation-logs/list` 的分页与前缀过滤能力。
- 即使保留，也必须加服务端 `limit`（例如 200）并在响应中明确截断；不要仅依赖前端 `pageSize`。
- 补测试：断言每个日志查询入口最多返回配置上限，且无权限绑定的旧路径返回 404/403。

### 🟡-4 定时任务：业务 handler 在事务内执行，分布式锁先于事务提交释放

**证据**

- `knot-server/knot-admin/src/main/java/org/chobit/knot/admin/service/schedule/ScheduledTaskExecutor.java:53` 在 `execute` 整体标 `@Transactional`。
- `:64` 获取 `GET_LOCK`，`:70` 调用 `executeLocked`，`:71-74` 在 `finally` 中释放锁；Spring 事务代理要等方法返回后才提交。
- `:101` 的 `handler.execute()` 位于该事务内；实际 handler 会走外部 HTTP，例如 `OpenRouterModelSyncHandler.java:25-26` → `ExternalModelService.sync` → 外部模型同步抓取。

**影响**

- 外部 HTTP 等待期间占用数据库连接和事务，长任务会拉长事务、增加连接池耗尽风险。
- 锁在事务提交前释放：另一节点可在第一节点尚未提交时进入同一任务，形成并发窗口。若 handler 的写操作尚未提交，第二节点可能读到旧状态并重复执行。
- 这是静态推演；没有做两节点并发集成实验。`ScheduledTaskExecutor` 当前也未发现专属测试文件。

**建议**

- 把锁生命周期从业务事务中拆出：handler 执行不要包在 `@Transactional` 内；运行记录插入、完成回调等短写操作各自使用独立事务。
- 若继续用 MySQL `GET_LOCK`，必须确保获取/释放使用同一条会话连接，并在业务处理完成后、且不跨外层事务时释放；也可改为数据库租约（claim/lease）并让释放发生在明确的短事务中。
- 增加并发测试：两个执行器 + 两个连接同时执行同一 taskCode，断言 handler 不重叠；并覆盖「handler 抛异常」和「提交前释放锁」的时序。

### 🟡-5 外部模型同步/导入：事务语义、部分成功和 N+1 不一致

**证据**

- `knot-server/knot-service/src/main/java/org/chobit/knot/svc/service/external/AbstractExternalModelSyncProvider.java:29-58` 对每个模型执行 `getItemByModelId` 再 `insert/update`，N 个模型是 2N 次 DB 往返；`:50-57` 仅 `failed++`，没有日志或失败原因聚合。
- `knot-server/knot-service/src/main/java/org/chobit/knot/svc/service/ExternalModelService.java:162-191` 的 `createLogicalModels` 整体 `@Transactional`，循环内 `createLogicalModel(...)`，`:185-190` catch `Exception ignored` 后继续下一项。
- `createLogicalModel` 标了 `@Transactional`（`ExternalModelService.java:128-129`）；它调用 `logicalModelService.create`（`LogicalModelService.java:118-119` 也是 `@Transactional`）。在 Spring 默认 REQUIRED 传播下，内层事务抛出运行时异常会把外层事务标为 rollback-only；外层 catch 后再提交，可能触发 `UnexpectedRollbackException`，使「部分成功」变成整批回滚且摘要仍声称部分成功。
- 该路径的 `failed` 也没有保存具体 itemId/异常原因，排障只能看到计数。

**影响**

- 外部模型目录同步可能变慢；失败原因不可观测。
- 批量导入的失败语义不可靠：调用方看到的是计数，但事务结果可能完全不同，容易误判「已导入 N 个」。

**建议**

- 明确语义：要么全有或全无（移除循环内 catch，让异常明确失败）；要么部分成功（移除外层事务，逐个走独立事务，并记录失败项）。
- 同步侧增加按 modelId 集合的批量查询与批量 upsert；至少把单条失败改成带 `modelId` / `syncHash` 的 WARN 日志，并返回失败明细或可定位的汇总。
- 补测试：3 条记录中第 2 条冲突，断言最终事务结果与摘要一致；另补同步侧 N 条记录的查询次数上界测试。

### 💭-5 异步任务轮询跳拍的观测性偏弱

1. **先修错误结果与查询放大**：`ProviderProfileService` total + 四个列表 N+1；这是用户可见与 DB 压力双重收益。
