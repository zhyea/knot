# 问题分析：后端重启后首次进入模型池被登出

- **分析日期**：2026-09-22
- **问题模块**：前端认证状态、模型池页面
- **问题性质**：疑似旧 Token 请求返回 401 后误清理新登录态
- **当前结论**：高概率为前端全局 401 处理与旧请求返回时序之间的竞态，尚需浏览器 Network 日志确认

---

## 一、问题现象

复现步骤：

1. 输入用户名和密码，完成登录。
2. 进入首页，访问正常。
3. 点击左侧菜单“模型池”，页面提示“已登出”，自动退出登录并返回登录页。
4. 再次输入用户名和密码，登录成功。
5. 再次点击“模型池”，可以正常访问。

复现前提：

- 之前曾成功登录过；
- 后来执行过退出登录；
- 后端服务随后重启；
- 前端页面或浏览器标签页未必被刷新。

该问题具有明显的一次性特征：第二次登录后通常可以正常访问模型池。

---

## 二、相关代码链路

### 2.1 Token 持久化

文件：`knot-front/src/composables/useAuth.js`

- Token 通过 `localStorage` 持久化；
- 应用重新加载时会从 `localStorage` 恢复 `knot_token`；
- 登录成功后写入新 Token；
- 退出登录时清理 Token、用户信息和授权信息。

### 2.2 请求携带 Token

文件：`knot-front/src/api/http.js`

请求拦截器从 `useAuth()` 读取当前 Token，并统一写入：

```http
Authorization: Bearer <token>
```

### 2.3 401 全局处理

文件：`knot-front/src/api/http.js`

当前逻辑对非登录请求的 HTTP 401 统一执行：

1. `logout()`
2. 跳转 `/login`
3. 提示“登录已过期，请重新登录”

当前逻辑没有校验：

- 该 401 请求实际使用的是哪个 Token；
- 返回 401 时前端当前保存的是哪个 Token；
- 该请求是否属于旧会话。

### 2.4 模型池页面

文件：`knot-front/src/views/ModelPoolManageView.vue`

进入页面后会加载模型池列表，调用：

```http
POST /api/model-pools/list
```

如果该请求返回 401，或者在它之前已有其他请求返回 401，都会触发全局退出逻辑。

---

## 三、最可能的根因

### 3.1 旧 Token 在后端重启后失效

退出登录前曾经使用过旧 Token A。由于 Token 会持久化在浏览器中，页面中可能仍存在：

- 尚未完成的旧请求；
- 页面初始化请求；
- 路由切换触发的懒加载请求；
- 退出登录前已经发出的请求。

后端重启后，旧 Token 可能因以下原因失效：

- JWT 签名密钥在启动过程中发生变化；
- 服务端保存的会话、Token 黑名单或认证缓存被清空；
- 用户授权版本或相关认证状态重新加载；
- 旧 Token 本身已过期。

### 3.2 旧请求返回 401，误清理新登录态

可能的时间顺序如下：

```text
旧 Token A 请求发出
        ↓
后端重启，Token A 失效
        ↓
用户重新登录，前端保存新 Token B
        ↓
旧请求 A 才返回 401
        ↓
全局响应拦截器执行 logout()
        ↓
Token B 被清除，页面跳转登录页
```

这可以解释以下现象：

- 登录接口本身成功；
- 首页最初可以访问；
- 点击模型池时突然被登出；
- 第二次登录后没有旧请求继续返回 401，因此可以正常访问。

### 3.3 为什么模型池本身不是首要怀疑对象

模型池列表接口使用统一 HTTP 客户端和统一认证拦截器。当前没有证据表明模型池接口存在独立的登录状态处理。

如果是稳定的模型池权限配置错误，第二次登录后通常仍会失败；而当前表现是第一次失败、第二次成功，更符合旧请求竞态或认证状态残留。

---

## 四、需要重点核对的另一种可能

还需要排查后端重启是否导致**权限数据或授权缓存短暂不一致**：

1. 登录接口生成新 Token；
2. 前端登录成功后请求 `/api/me/authorizations`；
3. 后端授权数据尚未完全加载或权限绑定不一致；
4. 该请求返回 401 或错误的未授权响应；
5. 前端把它当成登录过期并执行退出。

项目中曾出现过“接口级权限错误被错误映射为 401，前端因此登出”的问题，相关记录见：

`docs/修复记录-登录后被401踢回登录页-2026-09-22.md`

因此，本次问题需要区分：

- **旧 Token 请求返回 401**；
- **新 Token 请求因权限或授权初始化问题返回 401/403**。

两者在前端表现相同，但修复位置不同。

---

## 五、建议的验证方法

打开浏览器开发者工具：

1. 切换到 Network；
2. 勾选 Preserve log；
3. 清空现有请求；
4. 按问题步骤重新复现；
5. 检查第一次被踢出前的所有 401 请求。

重点记录：

| 项目 | 需要确认的内容 |
|---|---|
| 请求 URL | 是 `/api/model-pools/list`，还是其他接口 |
| 请求发生时间 | 是登录前、登录中还是登录后 |
| 请求 Authorization | 携带旧 Token A 还是新 Token B |
| 401 响应消息 | `未登录或 token 无效`、`token 已过期或无效`，还是权限相关消息 |
| 是否存在并发请求 | 是否有多个请求同时返回 401 |
| 登录接口结果 | 登录接口是否成功返回新 Token |
| 授权接口结果 | `/api/me/authorizations` 是否成功返回 200 |

建议临时在 `knot-front/src/api/http.js` 的 401 分支增加诊断日志：

```js
const { token } = useAuth();

console.warn("401 diagnostic", {
  url: error.config?.url,
  requestAuthorization: error.config?.headers?.Authorization,
  currentToken: token.value
});
```

如果发现：

```text
requestAuthorization = Bearer Token-A
currentToken = Token-B
```

并且随后执行了 `logout()`，即可确认旧请求误清理新会话。

## 六、推荐修复方案

### 6.1 401 处理前比较请求 Token 与当前 Token

请求发出时保存实际使用的 Token：

```js
http.interceptors.request.use((config) => {
  const { token } = useAuth();

  if (token.value) {
    config.authToken = token.value;
    config.headers.Authorization = `Bearer ${token.value}`;
  }

  return config;
});
```

401 处理时只允许当前会话对应的请求触发退出：

```js
const { token, logout } = useAuth();
const requestToken = error.config?.authToken;

if (error.response?.status === 401 && !isLoginRequest) {
  if (requestToken && requestToken === token.value) {
    await logout();
    router.push("/login");
    ElMessage.error("登录已过期，请重新登录");
  }

  return Promise.reject(error);
}
```

### 6.2 登录和退出时取消旧请求

可以为请求增加 `AbortController` 或 Axios cancel token：

- 退出登录时取消旧会话请求；
- 开始新登录时取消上一会话的未完成请求；
- 防止旧请求在新会话建立后继续影响全局状态。

### 6.3 区分 401 和 403

建议保持以下语义：

- 401：未登录、Token 无效或 Token 过期；
- 403：已登录但没有接口权限。

前端只应在真正的 401 上清理登录态。权限不足不应清除 Token。

### 6.4 避免使用全局 `logout()` 处理过期响应时覆盖新会话

如果一个请求的 Token 与当前 Token 不一致，该响应只应作为普通请求失败处理，不应清除当前用户的认证状态。

---

## 七、结论与当前状态

### 当前判断

最可能的根因是：

> 后端重启使旧 Token 失效，旧 Token 对应的请求延迟返回 401；前端全局 401 拦截器未判断请求 Token 是否仍是当前 Token，直接清理了新登录态。

### 尚未确认的事实

- 第一个 401 请求的具体 URL；
- 该请求携带的是旧 Token 还是新 Token；
- 是否由 `/api/me/authorizations` 权限问题触发；
- 后端重启时 JWT 密钥、授权缓存或会话状态是否发生变化。

### 建议优先级

1. 先通过浏览器 Network 日志确认第一个 401 请求；
2. 给前端 401 处理增加请求 Token 与当前 Token 比较；
3. 补充旧请求取消机制；
4. 检查后端重启后的 JWT 密钥和授权数据初始化策略；
5. 增加“旧会话 401 不得清除新会话”的前端回归测试。
