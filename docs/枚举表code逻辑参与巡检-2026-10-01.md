## 二、与既有记忆的偏差

记忆「仍在 DB 字典的分类只剩 `model_pool_selection_strategy` / `status` / `billing_unit`」**已过时**：
实际参与逻辑的分类是上表 8 个（含 `billing_currency`、`plugin_extension_point`、`plugin_stage_code`、`model_family`、`logical_model_visibility`）。
其中 8/9/23/24/25 的逻辑由**平行代码枚举**接管，DB 行退化为展示副本。

## 三、需关注的风险点

1. **双源漂移（高）**：分类 8/9/23/24/25（及 12 部分）的 code 同时存在于 `ks_enum_configs` 与代码枚举。逻辑走代码枚举，DB 行若被管理员增删/改名，代码枚举不会同步 → 展示与逻辑不一致。建议：要么以 DB 为唯一源（逻辑改读 `EnumConfigService`），要么废弃这些 DB 行。
2. **`status` 下拉源用错（中）**：前端 `PluginFormDialog`/`ProviderDiscountFormDialog`/`SecurityPolicyView` 用 `category="status"`（DB 分类 15 = ONLINE/RUNNING/DRAFT/GENERATED/SUCCESS/FAILURE/FAILED），却 `include-codes=['ENABLED','DISABLED']/['ACTIVE','INACTIVE']`——这些属 `EntityStatusEnum` 代码枚举，不在分类 15 内 → 下拉会被过滤为空（坏）。应改用 `useEnumOptions('EntityStatusEnum')`。
3. **`plugin_fail_mode` 未接线（中）**：failMode 已存库但无分支，失败策略不生效。要么补 `PluginDispatcher` 分支，要么明确「默认放行」并去掉该枚举避免误导。
4. **折扣逻辑疑似缺失（待核）**：`discount_type`/`scope_type` 仅存字段，service/gateway 均未发现折扣应用代码，需确认折扣是否真正落地。
5. **孤儿分类 `app_type`（低）**：已种子化但无任何消费，建议从 `ks_enum_configs` 清理或补消费点。

## 四、前端侧专项结论

前端对 DB 枚举的 all 使用均为展示：`EnumSelect`/`useEnums(category)` 取选项 + `v-model` 绑定 + `resolveEnumLabel` 回显。
唯一对 code 的 `===` 比较均为**标签配色**（`row.status==='SUCCESS'?'success':'danger'`，操作日志态）或 **EntityStatusEnum 代码枚举**（`ENABLED`/`DISABLED`），**没有任何 DB 枚举分类 code 进入前端业务逻辑分支**。
