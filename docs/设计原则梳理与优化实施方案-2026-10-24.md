## 1. 文档目标

本文不重复介绍 SOLID 等基础概念，而是把第二轮代码梳理结果整理成可执行的实施计划：

1. 先修会影响真实行为或造成错误运维判断的问题。
2. 再把重复的协议、错误、计费语义收敛到单一来源。
3. 最后拆分职责过宽的服务和前端组件。
4. 每个改动都给出文件边界、测试方式和回滚思路，避免"为了拆而拆"。

本轮使用的主要判断原则：

| 原则 | 在本项目中的判断方式 |
|---|---|
| SRP | 一个类是否同时承担管理面 CRUD、运行时执行、外部 I/O、展示状态等多个变化原因 |
| OCP | 新增协议、异常、计费模式时，是否必须修改多处 `if/switch` 集合 |
| DIP | `adapter` 是否反向依赖 `dal`，业务类是否直接创建外部客户端 |
| ISP | 插件上下文、服务上下文是否把大量无关字段塞进同一个宽接口 |
| DRY / 单一真相 | 同一业务规则是否在多个模块、多个出口各自维护 |
| KISS / YAGNI | 是否存在假成功、空实现、死代码、恒等抽象 |
| 可测试性 / 可观测性 | 关键链路是否有特征测试、超时/失败是否有明确日志和指标 |

## 2. 优先级口径

| 级别 | 定义 | 处理要求 |
|---|---|---|
| P0 | 已存在的行为缺陷，或会把错误结果当成成功结果暴露给用户/数仓 | 立即修复，先于结构性重构 |
| P1 | 高概率回归、明显双份真相、后续变更成本持续增加 | 本迭代安排，先补测试再重构 |
| P2 | 规范债、死代码、可读性和防御性问题，当前没有明确故障证据 | 随手清理或排入后续迭代 |

## 3. 现状结论

### 3.1 值得保留的设计

- `AbstractGatewayRequestTemplate.handleMap` 已经固定了网关主链路骨架：鉴权、路由解析、请求插件、代理、响应插件、终态错误处理都有明确阶段。
- 协议执行器、鉴权器、请求适配器、用量提取器通过 Spring `List<T>` 收集，扩展点方向是正确的。
- `PluginDispatcher`、`PluginHandler`、`PluginBindingProvider` 的契约分层清晰，插件实现没有反向依赖网关运行时。
- `RoutingRuleTestDrawer` 的 `verdictToken` 已经处理了连续测试导致裁判结果串台的问题，这个设计应保留。
- `PeakOffPeakResolver` 被管理端试算复用，避免管理端另写一套高低峰判定，是"单一真相"的正确做法。
- `UsageExtractor` 已经是计费用量的领域模型，后续应继续围绕它收敛，而不是让适配器重新承担计费语义。

### 3.2 当前最需要纠正的认知

"类太大"不是第一优先级。真正需要先处理的是：

1. 对账接口在没有任何真实比对的情况下返回 `DONE`，前端还显示"对账完成"。
2. `PluginBindingView.timeoutMs` 从数据库传到 dispatcher 后没有被消费，配置是死配置。
3. `TimeoutException` 在 HTTP 出口是 `504/timeout_error`，在 `ErrorMsgDto` 出口会落到 `500/upstream_error`，同一请求存在两套错误语义。

## 5. P0 实现方案

### 5.1 P0-1：对账接口假成功

#### 现状

- `knot-server/knot-service/src/main/java/org/chobit/knot/gateway/service/BillingService.java:397` 的 `reconcile()` 直接返回 `new ReconciliationResultDto(providerCode, billDate, 0, 0, "DONE")`。
- `knot-server/knot-admin/src/main/java/org/chobit/knot/gateway/controller/BillingController.java:168` 暴露 `POST /api/billing/reconciliation`。
- `knot-front/src/views/billing/ReconciliationView.vue:29` 调用接口后直接 `ElMessage.success("对账完成")`。
- `knot-front/src/api/billing.ts:49` 已经封装了 `runReconciliation`。

#### 推荐决策

如果没有明确的"外部供应商账单/对账文件"数据源，**先下线，不保留假成功**。对账属于财务动作，返回 `DONE` 但没有比对数据，比暂不提供功能更危险。

#### 方案 A：下线未实现功能

后端：

1. 删除 `BillingController.reconcile()` 及 `POST /api/billing/reconciliation`。
2. 删除 `BillingService.reconcile()`。
3. 检查 `ReconciliationResultDto`、`ReconciliationResult`、`BillingConverter.toReconciliationVO()` 是否只服务于该接口；无其他引用则一并删除。
4. 不直接改权限三表或 `ks_`/`kx_` 表；先 grep 权限绑定、菜单种子和前端路由引用，再决定是否清理运营配置。

前端：

1. 删除 `knot-front/src/views/billing/ReconciliationView.vue`。
2. 删除 `knot-front/src/api/billing.ts` 中的 `runReconciliation`。
3. 删除 `knot-front/src/router/index.ts` 的 `billing-reconciliation` 路由。
4. grep i18n 的 `reconciliation` key，确认是否还有菜单或其他页面引用；不要误删仍被其他计费页面使用的文案。

验收标准：

- 前端菜单和路由不再出现"对账管理"。
- 直接访问旧路由不会进入可执行页面。
- 后端不再返回 `DONE/0/0` 形式的假结果。
- `rg "reconciliation|runReconciliation|ReconciliationView"` 无业务调用残留。

#### 方案 B：保留接口，实现真实对账

如果该功能必须保留，先定义清楚以下内容，再写代码：

1. **内部账数据源**：网关计费明细/Kafka 落库表/请求流水表。
2. **外部账数据源**：供应商 API、CSV 导入、人工上传或线下账单。
3. **匹配键**：`requestId`、上游请求 ID、模型、时间窗口、金额、币种、计费规则版本。
4. **比较规则**：金额精度、汇率、时区、四舍五入、缺失行、重复行、负金额/退款。
5. **状态语义**：`PENDING`、`MATCHED`、`DIFF`、`FAILED`，不能没有实际比对就返回 `DONE`。
6. **权限与审计**：谁能执行对账、谁看差异、是否写操作日志。
7. **幂等性**：同一 `providerCode + billDate` 重复执行的结果是否覆盖、追加还是拒绝。

实现建议：

- 新建 `BillingReconciliationService`（顶层 `@Service`）承载编排。
- 新建只读查询和差异比较组件，避免把外部账单 I/O 塞进 `BillingService`。
- 返回值至少包含 `comparedRows`、`diffRows`、`status`，并增加 `startedAt`、`finishedAt` 或失败原因。
- 在得到真实比对结果前，接口不得返回成功状态。

#### 测试

- 方案 A：删除后跑编译；前端 grep 旧路由。
- 方案 B：覆盖完全匹配、金额差异、缺失行、重复行、非法日期、非法供应商和重复执行。

### 5.2 P0-2：插件超时配置落地

#### 现状链路

```text
kb_plugin_instances.timeout_ms
  -> PluginInstanceEntity.timeoutMs
  -> PluginService.toBindingView()
  -> PluginBindingView.timeoutMs
  -> DefaultPluginDispatcher.dispatch()
  -> 未消费
```

证据：

- `knot-server/knot-plugin-api/src/main/java/org/chobit/knot/gateway/plugin/PluginBindingView.java:12` 定义 `timeoutMs`。
- `knot-server/knot-service/src/main/java/org/chobit/knot/gateway/service/PluginService.java:113` 已把实体字段传入视图。
- `knot-server/knot-plugin-api/src/main/java/org/chobit/knot/gateway/plugin/runtime/DefaultPluginDispatcher.java:28` 只在循环中直接调用 `handler.handle()`。
- `docs/standards/rules/40-plugin.md:8` 说明 SYNC 插件在请求线程内联执行，dispatcher 当前没有 try/catch。

#### 设计目标

1. 每个绑定项拥有独立超时预算，而不是整条插件链共用一个模糊 deadline。
2. 超时行为可配置：安全插件失败关闭，日志/可观测插件失败开放。
3. 超时不能只返回给调用方，还必须阻止超时任务继续修改共享上下文。
4. 保留绑定顺序、异常冒泡和现有插件扩展点。

#### 推荐实现

1. 新增 `PluginFailurePolicy` 枚举：
   - `FAIL_CLOSED`：超时或执行异常中断请求，适合敏感词审核等安全能力。
   - `FAIL_OPEN`：记录日志后继续下一插件/主链路，适合日志、审计等非阻断能力。
   - 默认值由插件实现显式声明，不在 dispatcher 里按 capability 字符串硬编码。

2. 扩展 `PluginDescriptor`：
   - 当前是 `capabilityCode + extensionPoint + stageCode`。
   - 增加 `PluginFailurePolicy failurePolicy`，保留三参数构造器的重载，避免一次性改所有插件。
   - `PluginHandler` 可以提供默认 `FAIL_CLOSED`，日志类插件显式声明 `FAIL_OPEN`。

3. 新增 `PluginExecutionSupport`（`plugin-api` 的 `runtime` 包）：
   - 使用 Java 21 virtual thread executor 或受控有界线程池，每个 binding 独立提交。
   - 用信号量限制并发插件任务数，防止大量请求同时创建任务。
   - 通过 `Future.get(timeoutMs)` 等待；超时后 `cancel(true)`，并记录 binding、capability、stage、耗时和 traceId。
   - 线程内要透传 trace/MDC 上下文；否则日志中的 traceId 会与实际请求脱节。

4. 超时默认值：
   - `timeoutMs == null || timeoutMs <= 0` 时读取配置，例如 `knot.plugin.default-timeout-ms`。
   - 设置上限，避免数据库误配置成几分钟。
   - 不要让 dispatcher 自己维护一个魔法数字。

5. 上下文关闭协议：
   - 在 `PluginDispatchContext` 增加关闭标记和 `close()`。
   - 超时后标记关闭；`putAttribute()` 对已关闭上下文拒绝或忽略写入。
   - 逐步把 `requestBody`、`responseSnapshot` 等共享 Map 改为不可变视图；handler 只能读取，不能修改。
   - 这一步必须明确：仅靠 `Future.cancel()` 不能保证阻塞任务立即停止，必须有"超时后不再接收写入"的防线。

6. 失败处理：
   - `FAIL_CLOSED`：抛出 `PluginTimeoutException`，由现有网关异常处理链转成明确错误；敏感词插件应保持失败关闭，不能因超时绕过审核。
   - `FAIL_OPEN`：记录 WARN/指标并继续后续插件。
   - 无论哪种策略，都要保留原始异常和超时标记，方便日志排查。

#### 伪代码

```java
for (PluginBindingView binding : bindings) {
    PluginHandler<T> handler = resolveHandler(binding, context);
    if (handler == null) {
        continue;
    }
    long timeoutMs = resolveTimeout(binding.timeoutMs());
    try {
        PluginExecutionSupport.run(handler, binding, context, timeoutMs);
    } catch (PluginTimeoutException ex) {
        if (handler.descriptor().failurePolicy() == FAIL_CLOSED) {
            throw ex;
        }
        log.warn("plugin timeout, fail-open: binding={}, capability={}, stage={}, timeoutMs={}",
                binding.bindingId(), binding.capabilityCode(), binding.stageCode(), timeoutMs);
    }
}
```

#### 测试

新增 `DefaultPluginDispatcherTest` 或 `PluginExecutionSupportTest`：

- 正常 handler 按 `orderNo` 执行。
- `timeoutMs = null` 使用默认值。
- `timeoutMs <= 0` 不产生无限等待。
- handler 阻塞超过预算时触发超时。
- `FAIL_CLOSED` 抛出异常并停止后续插件。
- `FAIL_OPEN` 记录后继续后续插件。
- 超时后调用 `putAttribute()` 不污染主链路上下文。
- 已验证 traceId 能穿透到插件执行线程。

注意：项目使用 JDK 25 + Mockito 时不能 mock 具体类，测试替身应使用子类覆写或接口 mock。

### 5.3 P0-3：错误映射单一来源

#### 现状

- `knot-server/knot-gateway/src/main/java/org/chobit/knot/gateway/controller/GatewayExceptionHandler.java:200` 将 `TimeoutException` 映射为 `504/timeout_error`。
- `knot-server/knot-gateway/src/main/java/org/chobit/knot/gateway/kafka/msg/ErrorMsgDto.java:46` 的异常链没有 timeout 分支，最终落入 `:89` 的 `500/upstream_error`。
- `knot-server/knot-gateway/src/main/java/org/chobit/knot/gateway/kafka/msg/GatewayTrafficMsgDto.java:143` 会调用 `ErrorMsgDto.of(error)`，因此同一个异常会进入两套语义。

#### 推荐实现

1. 新增 `GatewayErrorDescriptor`（`Descriptor` 在规范白名单内）：

```java
public record GatewayErrorDescriptor(
        String type,
        String code,
        int httpStatus,
        String stage
) {
    public static GatewayErrorDescriptor of(Throwable error) { ... }
}
```

2. 把 `ErrorMsgDto` 内部的私有 `Stage` 提取为 `GatewayErrorStageEnum`：
   - 现有值保持不变，避免影响数仓。
   - 为 timeout 增加独立 stage，例如 `TIMEOUT("timeout")`。
   - 如果数仓暂时不接受新枚举，可先复用 `INTERNAL`，但必须由 descriptor 统一决定，不能两个出口各自猜。

3. `GatewayErrorDescriptor.of()` 负责异常族到 `type/code/httpStatus/stage` 的唯一映射：
   - `GatewayUpstreamException`
   - `GatewayTrafficRejectException` / quota / rate limit
   - `RedisUnavailableException`
   - `GatewayAuthException`
   - `GatewayInvalidRequestException`
   - `GatewayBadRequestException`
   - `BusinessException`
   - `TimeoutException`
   - 其他异常兜底

4. `GatewayExceptionHandler` 使用 descriptor 决定状态码和响应体：
   - 429 的 `Retry-After`、`TrafficRejectDetail` 继续在 handler 里处理。
   - 上游异常的 `upstreamStatus`、`upstreamMessage` 继续在 handler 里处理。
   - 不再在 handler 与 `ErrorMsgDto` 各写一棵异常类型树。

5. `ErrorMsgDto.of()` 使用同一 descriptor：
   - `type/code/httpStatus/stage` 直接取 descriptor。
   - 上游详情和 429 详情仍各自构造成 `UpstreamErrorMsgDto`、`TrafficRejectMsgDto`。

#### 测试

新增 `GatewayErrorMappingTest` 或参数化测试：

| 异常 | HTTP 期望 | ErrorMsgDto 期望 |
|---|---|---|
| `TimeoutException` | 504 / `timeout_error` | 504 / `timeout_error` |
| `GatewayUpstreamException` | 502 / `upstream_error` | 502 / `upstream_error` |
| `GatewayRateLimitException` | 429 / `rate_limit_error` | 429 / `rate_limit_error` |
| `GatewayQuotaException` | 429 / `quota_error` | 429 / `quota_error` |
| `RedisUnavailableException` | 503 / `storage_unavailable` | 503 / `storage_unavailable` |
| `GatewayAuthException` | 401 / `auth_error` | 401 / `auth_error` |
| `BusinessException` | 400 / `invalid_request_error` | 400 / `invalid_request_error` |
| 未预期异常 | 500 / `upstream_error` | 500 / `upstream_error` |

## 6. P1 实现方案

### 6.1 `RoutingRuleService` 拆分

#### 现状

`knot-server/knot-service/src/main/java/org/chobit/knot/gateway/service/RoutingRuleService.java` 共 1128 行，同时包含：

- 路由规则 CRUD、编码校验、目标保存、限流策略保存。
- 调试协议白名单和提示文案。
- 调试目标解析、协议解析、模型池协议并集计算。
- 调试请求体构造、curl 构造、multipart 处理。
- `RestClient` 创建和网关调试调用。

此外，`RoutingRuleService.java:138` 注入的 `routingRuleConverter` 当前没有实际使用。

#### 目标结构

| 类 | 职责 | 位置 |
|---|---|---|
| `RoutingRuleService` | CRUD、校验、目标装配、事务边界 | `service` 顶层，`@Service` |
| `RoutingRuleDebugService` | 调试入口编排、能力下发 | `service` 顶层，`@Service` |
| `RoutingRuleDebugProtocolResolver` | 调试目标解析、协议放行、模型池协议并集 | `service.support` |
| `RoutingRuleDebugRequestSupport` | 请求体、curl、multipart 构造 | `service.support` |
| `RoutingRuleDebugRunner` | `RestClient` 生命周期和 HTTP 调用 | `service.support` |

#### 迁移顺序

1. 先移出纯函数：`buildGatewayTestPath`、`buildTestCurl`、`buildMultipartCurl`、`appendMultipartFields`、`promptFieldOf`。
2. 再移出协议解析：`resolveTestTarget`、`resolveTestProtocol`、`supportedProtocolsForTarget`、`supportedProtocolsForModel`、`fallbackProtocolsForModelType`、`getPrimaryTarget`。
3. 最后移出调试编排和 `RestClient`：`testInvoke`、`streamTestInvoke`、`prepareTestInvocation`。
4. `RoutingRuleController` 的 CRUD 路由继续注入 `RoutingRuleService`；调试路由改为注入 `RoutingRuleDebugService`。
5. 删除 `routingRuleConverter` 注入和 import。
6. 更新 `RoutingRuleStreamControllerTest.StubRoutingRuleService`：如果调试方法迁移，测试替身应继承或替换 `RoutingRuleDebugService`，不要为了保留旧测试结构而把调试方法留在原服务。

#### 约束

- `@Transactional` 只留在负责写库的 `RoutingRuleService`，不要散落到 debug support。
- 新类后缀必须符合 `Service / Resolver / Support / Runner` 白名单。
- 非 `@Service` 的协作者统一进 `service.support`。
- 先补特征测试，再移动代码，避免"拆分 + 行为修改"同时发生。

#### 验证

- CRUD 创建/更新/状态切换/目标保存仍走原事务。

### 6.3 协议能力与用量提取器单一来源

#### 推荐实现

1. 在 `ModelApiProtocolEnum` 增加声明式元数据：
   - `debuggable`
   - `executorCode` 或 `protocolFamily`
   - `usageExtractorCode`
   - `streamSupported`
   - 可选：`displayPath`、`promptField`

6. 前端只消费后端 `/api/common/enums` 和 `/api/models/types`；前端保留展示文案和表单归一化，但不要自己维护协议能力集合。

#### 测试

- 参数化测试覆盖"协议 → 执行器 → extractor → 可调试性"。
- 新增协议时，测试应只新增枚举行和一个用例，不需要改多个集合。
- 前端协议下拉与后端能力接口对齐；不要在测试里复制后端协议全集。

### 6.5 缓存边界

#### 现状

`knot-server/knot-gateway/src/main/java/org/chobit/knot/gateway/service/GatewayDataService.java:58` 维护 16 个 Caffeine 缓存。`listApiBindingsByModelId()` 在 `:223` 直接返回缓存 List；`listCache` 在 `:309` 只做了 `List.copyOf`，元素仍是可变 Entity。

#### 风险

- 列表容器不可变，但实体字段仍可被调用方 `set`，会污染后续请求。
- 当前静态搜索未发现实际修改缓存实体的调用，因此不是已复现故障，属于防御性设计缺口。
- 管理面更新后依赖 TTL/refresh 生效，需要明确一致性 SLA。

#### 推荐实现

1. 先做静态审计：对每个 `getXxx()` 调用点 grep `set` 和可变 Map 操作。
2. 热点实体改成只读 DTO/record；冷路径至少明确"缓存 Entity 只读"契约并加测试。
3. 为管理面写操作提供主动失效入口，例如 `evictModelCode()`、`evictProviderCode()`、`evictRoutingRule()`。
4. 补 `GatewayDataService` 缓存命中、刷新、失效和可变性测试。
