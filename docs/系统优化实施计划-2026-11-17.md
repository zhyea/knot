### B2 四个列表批量化（N+1）

**目标**：单页查询次数从 22/62/82/102 降到个位数。

**范式**：`RoutingRuleService.enrichList:194-213` —— 先批量取关联数据，内存按 code/id 分组后组装。

| 列表 | 现每行查询 | 改成 | 需要新增的 Mapper 方法 |
|---|---|---|---|
| App | `trafficPolicySupport.load` ×4 | 一次 `loadBatch(APP, ids)` | 无（`loadBatch:67` 已存在） |
| RoutingConsumer | `load` + `countRulesByConsumerCode` | 一次 `loadBatch` + 一次分组计数 | `countRulesByConsumerCodes(List<String>)` |
| ProviderProfile | `countAccountsByProviderCode` | 一次分组计数 | `countAccountsByProviderCodes(List<String>)` |
| ModelPool | `listItemsByPoolCode` + 2×count | 一次 `listItemsByPoolCodes` + 一次分组 count（items 数用 size） | `listItemsByPoolCodes(List<String>)`、`countRoutingTargetsByPoolCodes(List<String>)` |

**注意**

- `loadBatch` 在 `bindings.isEmpty()` 时提前返回（`ResourceTrafficPolicySupport:73-75`），批量化的真实收益是「4 次固定查询」而不是「4×N」。
- `countRulesByConsumerCode` 是 3 段子查询之和（`RoutingConsumerMapper.xml:57-64`），批量版用 3 次 group by 求和，别硬拼 UNION。
- `ModelPoolMapper.listItemsByPoolCode` 的 SQL 自带 2 个关联子查询（`:106-118`），批量化后单条 SQL 仍可能放大，本轮不重写该 SQL，只降调用次数。
- 空集合必须短路，禁止 `List.of()` 直接进 `<foreach>` 生成 `in ()`。

**新增测试**：每个列表 1 个「单页只调用一次批量方法」的断言（Mapper 接口 + Mockito `verify(..., times(1))`，并显式断言不再调用逐行方法 `never()`）。

**验收**：`pageSize=20` 下单页查询次数 ≤ 5（可用 MyBatis Interceptor 计数，或仅靠 mock 调用次数断言）；返回数据与改动前逐字段一致。

### B4 定时任务事务边界与锁（高风险，方案已定）

**现状**：`ScheduledTaskExecutor:48 @Transactional` 包住 `:59` 抢锁、`:96 handler.execute()`、`:66-69` finally 释放锁。

**⚠ 巡检报告的建议单独实施会引入更严重缺陷**：`GET_LOCK` / `RELEASE_LOCK` 是**会话级** MySQL 用户锁（`ScheduledTaskMapper.xml:127-133`），且 `ScheduledTaskService` 全部方法都没有 `@Transactional`。当前两句 SQL 能碰上同一条连接，**唯一原因就是执行器外层那个事务**。若照报告「把 handler 移出事务」直接删 `@Transactional`，抢锁与释放会落到不同池化连接上：`RELEASE_LOCK` 返回 0，锁挂在原连接上直到连接关闭——Hikari 连接长期存活 = **该任务永久不再执行**。比现在的「提交前释放造成并发窗口」严重一个量级。

**已拍板：改数据库租约**（放弃 `GET_LOCK`）。

**表结构**（`ks_scheduled_tasks` 现有 12 列，见 `schema.sql:161-178`，加 2 列 + 1 索引）

```sql
ALTER TABLE ks_scheduled_tasks
  ADD COLUMN lock_owner VARCHAR(128) DEFAULT NULL COMMENT '持有租约的节点 id，NULL 表示空闲',
  ADD COLUMN lease_until DATETIME(3) DEFAULT NULL COMMENT '租约到期时刻，过期为可抢',
  ADD KEY idx_scheduled_tasks_lease (lease_until);
```

`schema.sql` 与 `docs/database/migration/2026-11-17-scheduled-task-lease.sql` 同步写；迁移脚本用 `information_schema` 判列存在，幂等可重跑（`schema.sql` 的 `CREATE TABLE IF NOT EXISTS` 不会给既有表补列）。

**抢锁 / 释放 SQL**

```sql
-- 抢：影响行数 = 1 才算抢到；口径与异步任务 claim 一致（<= now(3) 为可抢）
update ks_scheduled_tasks
   set lock_owner = #{owner},
       lease_until = date_add(now(3), interval #{leaseMinutes} minute)
 where task_code = #{taskCode}
   and (lock_owner is null or lease_until is null or lease_until <= now(3));

-- 放：只清自己的租约，避免误清别人的
update ks_scheduled_tasks
   set lock_owner = null, lease_until = null
 where task_code = #{taskCode} and lock_owner = #{owner};
```

**租约时长**：固定 30 分钟（与本项目异步任务默认 `timeout_minutes=30` 同口径），**不做续租**。约束写进 javadoc：单个 handler 的墙钟耗时不得超过租约时长，否则会被另一节点抢跑。若将来出现超 30 分钟的任务，再补心跳续租，本轮不加。

**执行器改法**
- `ScheduledTaskExecutor.execute` 去掉 `@Transactional`；`insertRun` / `finishRun` / `updateTaskFireTime` 各自独立短事务（在 `ScheduledTaskService` 上显式标 `@Transactional`，不靠执行器兜）。
- 抢不到租约 → `log.info` 跳过（保持现语义：不排队、不补跑）。
- `BROADCAST` 模式不加租约，语义不变。
- `ScheduledTaskService.acquireLock/releaseLock` 改签名带 `nodeId`；`NodeIdentity` 已在执行器注入（`:37`）。

**测试**（不能 mock 具体类，用子类覆写 + 调用记录 record）
- 双执行器 + 同一 taskCode：断言 handler 只被调用一次。
- handler 抛异常：断言 run 记录落 FAILURE 且租约被清、下一次仍能执行。
- 租约过期：把 `lease_until` 手工置为过去，断言另一节点可抢到。
- 断言 `execute` **不再**有 `@Transactional`（反射或源码扫描），防回退。

### B5 外部模型导入语义

**现状**：`ExternalModelService.createLogicalModels:156-190` 外层事务 + 循环内 `catch (Exception ignored)`；内层 `createLogicalModel:122` 是 REQUIRED，异常会把外层标 rollback-only，**提交阶段抛 `UnexpectedRollbackException`，摘要回不到调用方**（巡检报告写的「摘要仍声称部分成功」不成立，需按此修正测试断言：期望抛异常而不是期望摘要）。

**另一处需修正的事实**：`AbstractExternalModelSyncProvider:50-57` 的 catch 不止 `failed++`，还会把该条落 `FAILED(3)`；真实缺口只剩「没有失败原因、无日志」。

**已拍板：部分成功。**

**⚠ 关键陷阱（自调用让内层事务失效）**：`createLogicalModels` 里的 `createLogicalModel(item.getId())` 是 `this.` 自调用（`:180`），一旦去掉外层 `@Transactional`，内层 `@Transactional` 走不到代理，等于**完全没有事务**——`logicalModelService.create`（另一个 bean，事务仍在）会先提交，随后 `updateItemLogicalModel`（`:152`）若失败，就留下「逻辑模型已建、外部条目未回填」的脏数据。所以不能只删注解。

**改法**
- 新增 `knot-service/.../service/support/ExternalModelImportRunner`：单条导入 + `@Transactional(propagation = REQUIRES_NEW)`，把 `createLogicalModel` 的现有实现搬进来（`ExternalModelService` 保留同名单条入口给 `ExternalModelController:63`，内部委托 runner）。
- `createLogicalModels` 去掉 `@Transactional`，循环里 `try { runner.importOne(id) } catch (Exception e) { failed++; failures.add(...) }`，每条独立提交。
- `ExternalModelSyncResult` 增 `List<ItemFailure> failures`（record `ItemFailure(String itemId, String modelCode, String reason)`，上限 50 条，超出只计数并标注截断）；`failed` 与 `failures` 必须自洽。
- 失败原因落 `log.warn`：`itemId` + `modelCode` + 异常 message（当前 `catch` 只有计数，`ExternalModelService:182` 是 `catch (Exception ignored)`）。

**测试**
- 3 条记录、第 2 条 conflict：断言 `created=2 / failed=1 / failures.size()=1`，且库里恰好 2 条逻辑模型、第 2 条外部条目的 `logical_model_id` 仍为空。
- 反向探针：把 runner 改回 `REQUIRED` 并给外层加回 `@Transactional`，同一测试必须变红（证明测的是「逐条提交」而不是「碰巧成功」）。
- 空 ids / 全重复：断言 `inserted=0` 不产生新模型。

**同步侧 N+1**：`getItemByModelId` 逐条查询是 2N 次往返。批量 upsert 改动较大，本轮只做「按 modelId 集合一次查回」+ 内存判存，写仍逐条；失败项同样补 WARN + `failures`。若坚持一次做净，另开批次。
