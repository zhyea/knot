# 任务协议绑定方案（供应商模型 × 接口协议 × 任务协议）

> 2026-10-28。范围：让「异步任务」这件事在**模型 API 绑定**这一步就能一次配完，并让非法组合不可表达。
> 仅方案，不含实现。

## 0. 结论先行

**在模型表单的「接口协议」卡片里加一列「任务协议」，与接口协议同一次保存落库；任务协议只能选 `protocol` 与本行协议相等的已启用档案。不一致的组合在服务端被 400 拒掉，在前端被过滤掉——因此它不可表达。**

现状是断裂的：`kb_model_api_bindings.async_profile_code` 列存在、网关会读、迁移脚本会写，但 **DTO / VO / 保存逻辑 / 前端全都没有它**。也就是说今天想配一个异步模型，唯一的办法是手写 SQL。本方案补的正是这条断链。

四个决策点（建议已填，待拍板）：

| # | 决策点 | 建议 | 理由 |
|---|---|---|---|
| 1 | 任务协议做成「协议枚举的一种」还是「绑定行的一列」 | **绑定行的一列** | §2：协议管「怎么发」，任务协议管「发完怎么收」，两个维度 |
| 2 | 流式协议能否配任务协议 | **不能，400** | 一条请求只有一条终态；轮询与流式互斥，同时存在则计费口径说不清 |
| 3 | 网关侧要不要也校验 `profile.protocol` | **校验 + `log.error` + 回落同步** | 迁移脚本可以绕过管理面写库，运行时这是唯一防线 |
| 4 | 前端如何知道「本行协议不能配任务协议」 | **后端在 options 里给 `disabled`，前端不硬编码流式协议集合** | 否则前端要复制一份 `streamSupported` 事实 |

## 1. 现状：四处断链

| 层 | 现状 | 后果 |
|---|---|---|
| DB | `kb_model_api_bindings.async_profile_code`（null=同步） | 有列 |
| DAL | `ModelApiBindingEntity.asyncProfileCode` + xml 全列读写 | 通 |
| **Service** | `ModelApiBindingDto` / `ModelApiBindingItem` **没有这个字段**；`ModelApiBindingSupport#toEntity` 不赋值、`changed` 不比较 | 保存时该列恒被写 null；即使别处写了，改别的字段保存一次也会被抹掉 |
| **Admin** | 无档案相关端点 | 前端拿不到候选 |
| **Front** | `knot-front/src` 里 `asyncProfileCode` 零命中 | 无入口 |
| Gateway | `AsyncTaskSupport#profileCodeOf` 读该列；`loadSpec` 只按 code 取档案，**不校验 protocol、不看 status** | 停用档案照样生效；协议不匹配照样用 |

第三条最危险：**它不只是"不能配"，而是"会静默抹掉"**。任何一次在界面上编辑模型并保存，都会把这行已配好的异步档案清空——而这在界面上看不出任何痕迹。

顺带解释上一轮报告的「流式 × 异步静默跳过」：因为该组合从来没人配得出来（配不出来，也就没人发现它无意义）。补完入口之后，这条必须一并堵上（决策点 2）。

---

## 2. 关键判断：任务协议不是协议

- **接口协议**（`ModelApiProtocolEnum`）= 客户端与上游之间的**接口形状**：路径、请求体、是否流式。它是「怎么发」的唯一事实。
- **任务协议**（`kb_async_task_profiles` 的一行）= 同一形状下的**收尾方式**：提交即终态，还是先拿 `task_id` 再轮询。它决定「发完怎么收」。

判据一句话：**协议决定怎么发，任务协议决定发完怎么收。** 两者正交，所以任务协议挂在绑定行上。

把异步做成协议枚举变体（`VIDEO_GENERATIONS_TASK`）为什么不行：

1. **同一上游端点既可能同步也可能异步**——Kling 的 `/v1/videos/generations` 就是同一个 path，只是响应里多一个 `task_id`。让协议承担这个区分，等于让 path 与协议名打架。
2. **枚举翻倍**：可异步的协议 ×2，还要处理 `CUSTOM`。
3. **并没有省掉那个下拉**：一家上游一套查询口径（Kling 与可灵同协议不同 path），仍然要选档案。多出来的只有一个维度污染。
4. 与既有结论冲突：**「异步与否是绑定属性，不是协议属性」**（`docs/Kling3.0Turbo对接方案-2026-10-27.md` §3）。除非推翻它，否则不该走这条路。

## 3. 方案对比

| 方案 | 形态 | 优点 | 致命点 | 结论 |
|---|---|---|---|---|
| **A** | 绑定行加一列「任务协议」，值 = 档案 `profile_code` | 与既有列/既有结论一致；改动集中在一条数据通路 | 表单多一个下拉 | **推荐** |
| B | 协议枚举加异步变体 | 少一个字段 | §2 的四条 | 否决 |
| C | 档案绑到供应商账户上，绑定行只写协议 | 最"一步" | 同一账户下不同模型可能要用不同档案；跨账户共用档案无法表达；迁移面最大 | 后置（若将来档案真的按账户收敛，再从 A 迁移到 C，A 是它的前置） |

A 与 C 不冲突：A 是"把档案挂在能落到模型粒度的地方"，C 是"把粒度上移到账户"。先做 A，等档案数量涨到需要按账户复用时再谈 C。

## 4. 后端设计（方案 A）

### 4.1 契约补字段

`knot-server/knot-service/src/main/java/org/chobit/knot/svc/dto/model/ModelApiBindingDto.java`
`knot-server/knot-service/src/main/java/org/chobit/knot/svc/vo/model/ModelApiBindingItem.java`

两个 record 各加一个字段，位置紧跟 `protocol`（语义相邻，读的人一眼看到"协议 × 任务协议"是一对）：

```java
public record ModelApiBindingDto(Long id,
                                 String protocol,
                                 String asyncProfileCode,   // 新增：任务协议编码；null = 同步
                                 String apiPath,
                                 ...) {
}
```

`ModelApiBindingItem` 再加一个**只读派生字段**供列表展示（见 §4.5）：

```java
String asyncProfileLabel   // 档案 profile_code；null 表示同步。不参与写入
```

### 4.2 `save` 的 diff 必须比较新字段

这是本方案最容易漏的一处，且**漏了在界面上完全看不出来**。

`ModelApiBindingSupport#changed` 现在是逐字段 `Objects.equals`，加字段必须同步加一行：

```java
return !Objects.equals(existing.getProtocol(), desired.getProtocol())
        || !Objects.equals(existing.getAsyncProfileCode(), desired.getAsyncProfileCode())
        || ...;
```

判例（本仓库已发生过同型）：diff 少比较一个字段 → 用户改了但没写库 → 保存成功、列表还显示旧值 → 排查时先怀疑缓存。所以这条要进测试（§7 第 2 例），不能只靠 code review。

同时 `toEntity` 补 `entity.setAsyncProfileCode(blankToNull(binding.asyncProfileCode()))`。**空串必须折成 null**，否则 `''` 会被当成一个不存在的档案编码，然后被 §4.3 的"档案不存在"校验拦下，报错信息却很莫名。

### 4.3 四条校验（放在 `toEntity`，唯一写入点）

`toEntity` 已经是"协议合法性 + 模型类型支持性"的唯一校验点，任务协议就长在它旁边，不另开一层：

```java
String profileCode = blankToNull(binding.asyncProfileCode());
if (profileCode != null) {
    AsyncTaskProfileEntity profile = profileMapper.getByProfileCode(profileCode);
    if (profile == null || !EnabledStatusEnum.isEnabled(profile.getStatus())) {
        throw new BusinessException(ErrorCode.VALIDATION_ERROR, "任务协议不存在或已停用：" + profileCode);
    }
    if (!protocol.matches(profile.getProtocol())) {
        throw new BusinessException(ErrorCode.VALIDATION_ERROR,
                "任务协议 " + profileCode + " 属于协议 " + profile.getProtocol()
                        + "，不能绑定到协议 " + protocol.code());
    }
    if (protocol.streamSupported()) {
        throw new BusinessException(ErrorCode.VALIDATION_ERROR,
                "协议 " + protocol.code() + " 是流式协议，提交即终态，不能绑定任务协议");
    }
}
```

注意顺序：先存在性、再协议匹配、最后流式互斥。顺序影响报错可读性——用户选错档案时最该看到的是"这个档案属于别的协议"，不是"你是流式"。

第四条（流式互斥）之所以放最后：它是否决性最强的规则，但只在"档案本身合法"时才有意义。

**依赖注入**：`ModelApiBindingSupport` 现有依赖只有 `ModelApiBindingMapper`。加 `AsyncTaskProfileMapper` 属于同层（svc → dal），不破坏分层；但要更新构造器——**改构造器前先 `grep "new ModelApiBindingSupport("`**（本仓库踩过：加参数导致 4 处测试 `new X(一堆 null)` 编译失败）。

### 4.4 读侧：一个 options 端点，一次装载、前端按行过滤

按仓库既有约定（`OptionItem` + `POST /options` + `vo.common.meta` 强类型 meta）：

`POST /api/system/async-task-profiles/options`

```java
// 入参：空请求体即可（档案总量是个位数，不做服务端分页/过滤）
public record AsyncTaskProfileOptionMeta(String protocol,       // 所属接口协议，前端按行过滤用
                                         String queryMethod,     // 回显用
                                         String queryPath,       // 回显用
                                         Integer pollIntervalMs, // 回显用
                                         Long timeoutMs) {       // 回显用
}
```

返回 `List<OptionItem<AsyncTaskProfileOptionMeta>>`，其中：

| 字段 | 取值 |
|---|---|
| `value` | `profile_code` |
| `label` | `profile_code`（表里没有 display_name，`remark` 当前为空；等真需要展示名再加载荷，不提前造） |
| `disabled` | `ModelApiProtocolEnum.fromCode(profile.protocol).streamSupported()` —— **决策点 4**：把"流式协议不可用"这条事实算一次，前端不复制 |
| `meta` | 上面那个 record |

**为什么一次返回全部、前端按行过滤，而不是按协议请求**：模型表单里可能同时有多条协议行，按行请求会打出 N 个 XHR、换协议时还要再请求一次。档案总量小，一次拉全、本地过滤最省事，换协议立即生效。

**为什么不复用 `/api/enum-options`**：档案是数据不是枚举，它会随运维增删。

### 4.5 列表页展示

`ModelApiBindingItem.asyncProfileLabel` 由 `ModelApiBindingSupport` 在装配 VO 时从档案批量取（与 `mapByModelIds` 同一次调用里带出，避免 N+1）：

- 在 `listByModelIds` / `listByModelId` 的 SQL 里 `LEFT JOIN kb_async_task_profiles`，直接带出 `remark` 或 `profile_code`；
- 不允许在 Java 侧循环调 `getByProfileCode`——列表页一次几十行，会变成 N 次查询。

### 4.6 运行时兜底（决策点 3）

管理面校验只能保证"从界面进来的写是合法的"。但**迁移脚本是我们的合法写入路径**（Kling P3 的落库 SQL 就显式写了 `async_profile_code`），所以运行时仍要一条防线。

`AsyncTaskSupport#loadSpec` 目前只按 code 取，补两件事：

```java
if (!EnabledStatusEnum.isEnabled(profile.getStatus())) {
    log.error("Async task profile is disabled but referenced by a binding: {}", profileCode);
    return null;   // → 调用方回退同步链路
}
if (!protocolMatches(protocol, spec)) {  // 传入本次协议
    log.error("Async task profile {} belongs to protocol {}, but binding says {}; fallback to sync",
            profileCode, spec.protocol(), protocol.code());
    return null;
}
```

回落到同步而不是抛错，理由是**请求本身没坏**（上游已成功、响应体在手上），只是这次不计费为异步；抛 500 会让一个纯配置错误变成用户可见故障。但日志必须是 `error` 级别并带齐三方信息（档案、协议、绑定），否则运维只能猜。

### 4.7 权限绑定登记

新端点 `/api/system/async-task-profiles/options` 属于管理面 `/api/**`，会被 `AdminAuthorizationInterceptor` 扫到，**必须登记接口级授权**，否则运行期 403。判据仍是"拦截器扫不扫得到"——网关的 `/openai/**` 不用管，管理面的 `/api/**` 必须管。

## 5. 前端设计

改动集中在两个文件：`knot-front/src/components/model/ModelFormDrawer.vue`（编辑）+ `knot-front/src/views/model/ModelManageView.vue`（展示）。

### 5.1 落点：协议卡片第 2 行

现在每张协议卡片是三行：

```
[ 接口协议 (8) ] [ 请求适配器 (10) ] [ 启用 (6) ]
[ 上游路径 (24) ]
[ Usage (12) ] [ 流式Usage (12) ]
```

改为（**只动第 2 行，其余不动**）：

```
[ 接口协议 (8) ] [ 请求适配器 (10) ] [ 启用 (6) ]
[ 任务协议 (8) ] [ 上游路径 (16) ]
[ Usage (12) ] [ 流式Usage (12) ]
```

理由：上游路径与任务协议都是"这一行怎么打到上游"的事实，放同一行；协议与任务协议虽相邻，但塞进第 1 行会挤成 3 个窄下拉，读起来更差。

### 5.2 控件形态

```vue
<el-col :span="8">
  <el-form-item label="任务协议">
    <el-select v-model="binding.asyncProfileCode" clearable filterable
               placeholder="同步（提交即终态）" style="width: 100%">
      <el-option v-for="item in taskProtocolOptions(binding)"
                 :key="item.value"
                 :label="item.label"
                 :value="item.value"
                 :disabled="item.disabled" />
    </el-select>
    <div v-if="taskProtocolHint(binding)" class="async-profile-hint">
      {{ taskProtocolHint(binding) }}
    </div>
  </el-form-item>
</el-col>
```

- `clearable`：清空 = 同步，是合法且最常见的取值，不能让它只能通过删除整行来表达。
- `placeholder="同步（提交即终态）"`：默认态要自解释，而不是"请选择"。
- **不要**用 `EnumControl`：档案不是枚举。

### 5.3 联动规则（四条，都要写进组件）

| # | 触发 | 行为 |
|---|---|---|
| 1 | 打开抽屉 / 加载档案 | 一次拉 `POST /api/system/async-task-profiles/options`，结果存 `taskProfileOptions` |
| 2 | `binding.protocol` 变化 | 若当前 `asyncProfileCode` 的 `meta.protocol` ≠ 新协议 → 置空 + `ElMessage.warning("已清空任务协议：它属于协议 X")`。**静默清空是禁止的**——用户看不出自己丢了配置 |
| 3 | 渲染选项 | `taskProtocolOptions(binding)` = 全部档案中 `meta.protocol === normalizeProtocolCode(binding.protocol)` 的那些 |
| 4 | 未选接口协议 | 任务协议下拉 `disabled`，避免先选任务协议再选协议导致的来回清空 |

选项的 `disabled` 由后端给（决策点 4），前端**不要**维护 `STREAM_PROTOCOLS` 常量：那是把 `ModelApiProtocolEnum.streamSupported` 抄了第二份，改一处漏一处。

### 5.4 选中后的只读回显

用户必须能看清"我到底绑了个什么"，否则这个下拉就是一个黑盒编码：

```
任务协议  [ KLING_TASK ▼ ]
          GET /v1/videos/generations/{task_id} · 首次轮询 5s · 超时 30min
```

`taskProtocolHint` 取 `meta` 里的 `queryMethod / queryPath / pollIntervalMs / timeoutMs` 拼一行灰字（12px，`#909399`）。**不显示档案的全部内部细节**（退避参数、JSON 路径），那是排障信息不是配置信息。

### 5.5 列表页展示

`ModelManageView.vue` 的协议列：

```
VIDEO_GENERATIONS   [任务]        ← 有 asyncProfileCode
CHAT_COMPLETIONS                  ← 同步
```

`[任务]` 用 `el-tag size="small" type="warning"`，`title` 提示 `任务协议：KLING_TASK`。判断依据是 `asyncProfileCode != null`，**不要用 truthy 判空**（本仓库定式：状态 0 / 空串都是合法值，`if (x)` 会误判）。

### 5.6 类型与默认值

`knot-front/src/components/model/ModelFormDrawer.vue` 里的本地 `type ApiBinding`：

```ts
asyncProfileCode: string;   // '' 表示同步；提交时后端折成 null
```

- 新增行的默认值 `asyncProfileCode: ""`（与既有 `apiPath: ""` 同款口径）。
- 组装提交体时**不要**自己 `|| null`：`''` 与 `null` 由后端 `blankToNull` 统一处理，前端再造一套是第二份口径。
- 回填时 `source.asyncProfileCode || ""`（受控组件不能把 `null` 直接给 `v-model`，Vue 会警告）。

## 6. 数据与迁移

- **无 DDL**：`kb_model_api_bindings.async_profile_code` 已在 `schema.sql` 与迁移脚本 `docs/database/migration/2026-10-27-async-task-tables.sql` 中就位。
- **一致性体检**（补进同一个迁移脚本末尾，幂等、只读）：

```sql
-- 应当返回 0 行；非 0 说明有绑定行引用了协议不匹配的档案（多为手写 SQL 造成）
SELECT b.model_code, b.protocol, b.async_profile_code, p.protocol AS profile_protocol, p.status
FROM kb_model_api_bindings b
         JOIN kb_async_task_profiles p ON p.profile_code = b.async_profile_code
WHERE p.protocol <> b.protocol
   OR p.status <> 1;
```

- 存量影响：当前 `async_profile_code` 全为 null（只能手写），故**预期 0 行**；Kling P3 落库脚本执行后仍是 0（t2v/i2v 都是 `VIDEO_GENERATIONS`）。

## 9. 实施顺序

| 步 | 内容 | 依赖 |
|---|---|---|
| P1 | 契约补字段 + `toEntity` 赋值 + `changed` 比较 + 四条校验 + 单测 1~5 | 无 |
| P2 | options 端点（Controller + Mapper 查询 + meta）+ 权限登记 | P1（共用校验口径） |
| P3 | 前端抽屉（下拉 + 联动 + 回显）+ 单测 7~10 | P2 |
| P4 | 列表页 tag + `loadSpec` 运行时兜底 + 单测 6 + 迁移体检 SQL | P1 |

P1 完成后「能用 SQL 之外的方式配异步」这件事就成立了；P2/P3 是把它变成可操作界面；P4 收口展示与运行时防线。
