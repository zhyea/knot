## 4. 关键坑（下次别再踩）

1. **`configOf` 必须 `static`**：`TokenBillingModeCalculator.planOf` 是 static，实例方法会编译失败（无法从静态上下文引用）。
2. **日志脱敏不能把正文压成字符串**：`PluginLogPayloadSerializationTest` 断言 `requestBody.vendor_only_field` 可寻址——压成字符串会把它打红（4 Errors）。正确做法是**保留结构、按预算截断文本值**。
3. **`vite build` 必须带 `--emptyOutDir false`**：不带会 `emptyDir/prepareOutDir` 失败 EXIT 1（项目约定，不是缺陷）。
4. **改 Java 用脚本按字节替换**：主源码是 CRLF，多行 `Edit` 易失败；脚本带「未命中即非零退出 + 幂等跳过」，并重跑校验。
5. **Maven 日志含 `\000`**：先 `tr -d '\000'` 落干净文件再 grep，否则 grep 报「binary file matches」而看不到错误。

## 10. 4.6 admin 面引入 response VO 层（拍板后落地）

**为什么这件事不是一个「漏改」**：实测 36 个 admin 控制器里 **0 个**走 `model.vo.response`、28 个方法直返 `*Entity`。这是管理面的统一风格，单改一处只会制造第三种风格。robin 拍板「引入」后才动手。

**做法：字段逐字平移，不改对外契约。**

| 批次 | 控制器 | 新增 svc 载体 | Converter |
|---|---:|---|---|
| ① 授权 | 5 | `AdminApiBindingItem` / `AdminMenuDetailItem` / `AdminModuleDetailItem` / `AdminPermissionItem` / `AdminRoleItem` | `AuthorizationConverter`（5 类资源 Entity↔Item 双向，**刻意不设中间 Dto**：两侧字段同名，多一层只会多一处漂移点） |
| ② 日志 / 枚举 / 模型族 | 3 | `OperationLogDetailItem` / `EnumConfigItem` / `EnumCategorySummaryItem` / `ModelFamilyItem` | `OperationLogConverter.toDetailItem`（新增，跳过 Dto）/ `EnumConfigConverter` / `ModelFamilyConverter` |
| ③ 外部模型 | 1 | `ExternalModelSourceItem` / `ExternalModelItem` | `ExternalModelConverter` |

合计新增 **15 个文件**（11 个载体 + 4 个转换器），改 9 个控制器 + 7 个 svc 服务。

**契约零变更的证据（机械比对，不是"看了一遍"）**：脚本逐字段提取 10 组「`dal.entity` ↔ `svc.vo` record」的字段名集合并求差集，**全部相等**（record 既不缺也不多）→ 对外 JSON 字段集合不变 → 前端零改动：

```
OK   AdminApiPermissionBindingEntity    record缺=-  多=-
OK   AdminMenuEntity / AdminModuleEntity / AdminPermissionEntity / AdminRoleEntity   同上
OK   OperationLogEntity / EnumConfigEntity / ModelFamilyEntity                       同上
OK   ExternalModelItemEntity / ExternalModelSourceEntity                             同上
```

**四处容易翻车的地方**：

1. **装响应的壳是最隐蔽的外泄点**：`OperationLogListResult` 里塞着 `List<OperationLogEntity>`。把 controller 返回类型改了、壳里还留实体，grep 控制器是看不出问题的。判据只有一条：改完在**整个 admin 主源码** grep `dal.entity` 必须为空。
2. **record 的 SpEL 必须用访问器形式**：`ExternalModelController` 原本写 `entityNameAfter = "#result.modelName"`（该方法返回 record）。切面对 SpEL 失败是**静默兜底**的（`parseSpel` 返回表达式原文），于是审计日志的 `entityName` 会存成字面量 `#result.modelName`，不报错不告警。**顺着这条线索回查了全仓**，同族共 **5 处**：`ExternalModelController` 1 处、`PluginController` 2 处（`PluginItem` 是 record）、`NotificationController` 2 处（`NotifyTemplate` 也是 record）。全仓复扫（排除注释）已 **0 处**无括号的属性访问。
3. **一个方法被两种用途共用**：`ExternalModelService.getItem` 既是 detail 接口的数据源，又是 `@OperationLog(oldValueSpel = "@externalModelService.getItem(#p0)")` 的取值入口，内部还会 enrich 后回写数据库。直接改返回类型会让回写拿不到实体 → 拆成私有 `requireEntity`（保留 enrich 回写，唯一允许吐实体的出口）+ 对外 `getItem`（吐 record）。`requireEntity` **故意不标** `@Transactional`：它只在内部自调用，Spring 代理不介入，标了是假承诺；事务由两个调用方提供。
4. **缓存值类型**：`EnumConfigService.listByCategory` 的 `@Cacheable` 值从 `List<EnumConfigEntity>` 变成 `List<EnumConfigItem>`。admin 用 Caffeine（堆内、重启即空）→ 无反序列化兼容问题；**哪天换 Redis 必须先加缓存版本号**。

**测试连带**：`EnumConfigCacheTest` / `EnumConfigServiceUpdateTest` 补 `EnumConfigConverter` 构造器参数，入参从 `EnumConfigEntity` 改 `EnumConfigItem`。转换器用 `Mappers.getMapper(...)` 拿真实现，**不 mock** ——mock 掉会让 record 恒为 null，断言照样绿但链路没测到。

## 16. B 类三项：大小写归一 / 档位枚举 / 未命中抛异常（2026-10-31，robin 直接下指令）

### 16.1 三项的原始缺陷

### 16.8 判据沉淀

1. **⚠⚠ 行尾破损会让 `git diff` 把整个文件当成重写**。`BillingRuleFormDialog.vue` 出现 1029/1032 全文件 diff，根因是上一轮删 scoped 规则时留下的**孤立 CR**（`}\r\n\r\r\n</style>`：CR=1030 但 CRLF=1029）。git 判定「混合行尾」后放弃 CRLF 归一化，逐字比较 → 全文件差异。**判据**：`d.count('\r') - d.count('\r\n') != 0` 即破损；修掉后 diff 立刻从 1029/1032 变成 0/3。
2. **「行尾规则」不能按语言一刀切**。本轮实测：`EnumOptionRegistry.java` 与 `EnumOptionRegistryTest.java` 是 **LF**，同模块的 `BillingConfig.java` 是 CRLF；`useAuth.ts` 是 CRLF，`billingTier.ts` 是 LF。唯一可靠判据是**逐文件数**，且看 `git diff --numstat` 有没有出现「全文件行数级」的改动。
3. **严格化要按「谁是业务口径、谁是容错兜底」划线，不按「同名就一起改」**。分量价的 `componentDefault` 承载 MiniMax 官方口径，收紧它就是改业务。
4. **`-pl` 多模块 + 探针必须关心 reactor 的 SKIPPED**。失败模块的下游不会跑，`-fae` 不解决，要 `-Dmaven.test.failure.ignore=true`。
5. **改前端单选/输入控件的取值来源时，先数定义点**。档位名原本 4 处各写一份（后端 switch + 前端常量 + prop 默认值 + 局部别名），任一处漏改都是「界面上选不到、计费侧认」。
