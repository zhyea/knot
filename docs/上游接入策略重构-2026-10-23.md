- 日期：2026-10-23
- 状态：**已实施并通过门禁**（后端 833 例全绿、前端 `vue-tsc` + `vite build` 全绿）
- 范围：上游请求链路、模型/供应商账户配置、前端模型表单、数据库迁移
- 前置讨论：本文件取代 `docs/AWS模型账户对接方案-2026-10-21.md`、`docs/上游curl命令方案-2026-10-22.md` 中关于「上游 URL 来源」的描述

## 0. 结论先行

1. `UpstreamAuthApplier` 新增 `prepare()`，一次产出生效 **base URL + 静态鉴权头**（`UpstreamAccess`）；
   执行器每请求只 `resolve` 一次策略（改造前 `requestSpec` 与 `withBody` 各 resolve 一次）。
2. `UpstreamRequestAdapter` 删除 `resolveBaseUrl` 及其 AWS import——通用协议接口不再认识任何供应商。
3. 模型级 `kb_models.base_url` → `base_path`（只保留路径前缀）；上游 host 唯一来源是
   `kb_provider_accounts.base_url`。
4. AWS 端点推导收口到 `AwsSigV4AuthApplier.baseUrl()`，通过 `requiresBaseUrl()` 声明「可以不给地址」。
5. `signsRequestBody()` 更名为 `requiresFinalizedPayload()`（语义澄清，非行为变更）。
6. 端点缺失从「拼出相对 URI 后莫名失败」改为请求前 `UPSTREAM_ENDPOINT_NOT_CONFIGURED`，且不重试。

## 2. 设计

### 2.1 接口形态

```java
// UpstreamAuthApplier
default UpstreamAccess prepare(UpstreamRequestContext context) {
    HttpHeaders headers = new HttpHeaders();
    apply(headers, context);
    return new UpstreamAccess(baseUrl(context), headers);
}

/** 默认只认 provider_account.base_url，零供应商特例。返回 null = 配置缺失。 */
default String baseUrl(UpstreamRequestContext context) {
    return context == null || context.provider() == null ? null : context.provider().getBaseUrl();
}

/** 该策略是否要求账户显式配置 base URL；AWS 覆写为 false。 */
default boolean requiresBaseUrl() { return true; }

default boolean requiresFinalizedPayload() { return false; }
```

`UpstreamAccess(String baseUrl, HttpHeaders headers)`：`headers` 构造时转
`HttpHeaders.readOnlyHttpHeaders(...)`，防止策略之外偷偷改鉴权头。

### 2.2 分层收口（重要）

`ProxyErrorCodeEnum` 在 `knot-common`，`GatewayUpstreamException` 在 `knot-gateway`，
而 `prepare()` 住在 `knot-adapter`。**adapter 不得抛 gateway 的异常**（否则反向依赖）。

因此：`baseUrl()` 只返回可空 `String`，**判空 + 抛 503 由执行器负责**。
错误消息带上 `providerAccount=<code>`，避免只看到一句「端点未配置」却不知道是哪个账户。

### 2.3 执行时序

1. `adapter.resolvePath()` 取协议路径（绑定 `api_path` 优先，缺省协议默认路径）；
2. `authApplierCatalog.resolve()` **一次**，`applier.prepare()` **一次**；
3. `access.baseUrl()` 判空 → 空则 `UPSTREAM_ENDPOINT_NOT_CONFIGURED`；
4. `path = joinPath(model.basePath, protocolPath)`；
5. 组装 `RequestTarget(baseUrl, path, contentType, access, applier)`；
6. `adapter.buildRequestBody()`；
7. 请求头 = traceparent + `X-Request-Id` + `access.headers()`；
8. `requiresFinalizedPayload()` 为真时：请求体序列化成 `byte[]` → 用**同一个 URL 字符串**与
   **同一份字节**签名 → 发出同一份字节；
9. 响应处理不变。

`RequestTarget` 内部 `url()` 只算一次，签名与发送共用一个字符串——这是 SigV4 的第二雷区。

## 3. URL 拼接规则

```text
path = joinPath(model.base_path, protocol_path)
url  = joinUrl(provider_account.base_url, path)
```

### 3.1 `joinPath`

| base_path | protocolPath | 结果 |
|---|---|---|
| `""` / `"/"` / 空白 | `/v1/chat/completions` | `/v1/chat/completions` |
| `/ep-123` | `/v1/chat/completions` | `/ep-123/v1/chat/completions` |
| `/ep-123/` | `/v1/chat/completions` | `/ep-123/v1/chat/completions` |
| `/ep-123` | `v1/chat/completions` | `/ep-123/v1/chat/completions` |

### 3.2 `joinUrl` 的「路径段级重叠吸收」

账户 `base_url` 允许带路径（如 `https://openrouter.ai/api/v1`），协议默认路径又以 `/v1` 开头。
直接相加会得到 `/api/v1/v1/decisions`。规则：把 base 的路径段与 path 的段逐段比较，**从尾部与头部
向中间找连续相等的段**并消除；path 至少保留最后一段。

| base | path | 结果 | 说明 |
|---|---|---|---|
| `https://api.openai.com` | `/v1/chat/completions` | `https://api.openai.com/v1/chat/completions` | 无重叠 |
| `https://openrouter.ai/api/v1` | `/v1/decisions` | `https://openrouter.ai/api/v1/decisions` | 吸 1 段 |
| `https://host/v10` | `/v1/chat` | `https://host/v10/v1/chat` | 按段比较，`v10 ≠ v1` |
| `https://host/v1` | `/v1` | `https://host/v1/v1` | path 不允许被吸空 |

**禁止**在该工具里做任何 URI 编解码 / `normalize()`：Bedrock 路径含已编码的 `%3A`，
任何规范化都可能让签名覆盖的路径与实际发出的路径不一致。

### 3.3 模型级 `base_path` 校验

空串 = 无前缀（常态）。非空时：
- 必须 `/` 开头，末尾 `/` 去掉；
- 拒绝 `scheme://`、`?`、`#`、`//`（连续斜杠）；
- 字符集白名单 `^/[A-Za-z0-9._~\-/]*$`（刻意不含 `%`，避免与 Bedrock 已编码路径混淆）；
- 长度 ≤ 255（对齐列宽）。
