# 统一视频用量模型（VideoBillingUsage v2）

> 日期：2026-10-27　范围：`knot-adapter` 用量提取层 / 计费计算器 / `ModelUsageNormalizer`
> 前置结论：`BillingUsage` 是计费唯一量来源，`ModelUsage` 是它的**单向投影**，
> 永远不进 `Calculator`（详见上一轮辨析）。因此本方案**只改源**，投影随源自动收敛。
> 上游盘点：`docs/视频计费规则不足盘点-2026-10-27.md`
>
> ⚠ **同日傍晚追加（robin 拍板，见 §五之六）**：投影「随源自动收敛」不成立——
> `ModelUsage` 原先只有输出侧计量，D1 新增的 4 个维度与输入侧两轴**没有出口**。
> 已把 `ModelUsage` 扩容为「归一化用量 + 计费属性（`attributes`）」并补齐投影，
> Kafka 消息同时新增同级 `upstream_usage`（上游原文）。原「对外 JSON 一行不改」的结论**已撤销**（§七）。

## 0. 结论先行

v1 的 `VideoBillingUsage` 是 9 个扁平字段，隐含三个错误假设（下表是对已实施批次的复盘；
当前 HEAD 已是 **11 字段**：B+C 收敛到 7，D1 再补 4 个价格维度）：

| 错误假设 | 表现 | 后果 |
| --- | --- | --- |
| **「时长」用 `long` 秒就够** | `MapNumberUtils.longValue` 直接截断 | 5.9s→5s 少收 15%；0.5s→0→兜 1s 多收 100% |
| **「有参考」是一个布尔** | 一个 `reference` 同时承载参考图/参考视频/输入视频 | 图生视频误命中 `:REFERENCE` 档；同一 `reference_images` 又喂了张数（A4） |
| **「一次请求 = 一个完整响应」** | 无阶段概念 | 提交型厂商回 `{task_id}` 被静默计 1 秒（A2） |

v2 目标：**时长毫秒化、输入侧事实拆开、按六家官方价目表补齐维度原料**。
`pixels` 与宽高合并为档位名（9 → 7），再按价目表补 4 个维度字段（7 → **11**），每个字段都有唯一语义。

> ### ⚠ 修订（2026-10-27 晚间，robin 拍板）
>
> 初稿把宽高当 `long`、并加 `stage` 阶段位，两处都被推翻：
>
> 1. **宽高改字符串 `outputResolution`** —— *「`long outputWidth`、`long outputHeight` 与事实不符，
>    改成字符串，直接用 resolution 就好」*。厂商声明的就是**档位名**（`768P`、`540P`、`2K`、`4K`
>    乃至自造名），不是像素尺寸；宽高是「由档位名反推」的中间产物，而反推只认标准尺寸表，
>    `768P` 这类非标档会退化成裸串或空值，配了价也吃不到。三个字段（`width`/`height`/`pixels`）
>    因此合并为一个 `outputResolution`，`outputPixels()` 派生方法一并删除。
> 2. **删 `VideoUsageStage`** —— *「和数据提取有关，但和计费无关，也去掉」*。
>    **计费模型只回答「量是多少、按哪一档」，不回答「这份量该不该出账」**；阶段是提取层的判定，
>    放进计费 record 就是让一个纯量模型承载策略。随之删掉的还有 Calculator 的阶段闸门与
>    `shouldNotChargeWhenTaskOnlyAccepted` 一例。
>
> 净结果：B+C 阶段 v2 字段数 **7**（`tokens` / `outputVideoMillis` / `inputVideoMillis` / `inputImageCount` /
> `outputResolution` / `sound` / `referenceVideo`），比 v1 的 9 个更少且每个都有唯一语义。
> 批次 D 再补 4 个价格维度字段，见下方「收敛说明」。

**收敛说明（批次 D 修订）**：B+C 阶段曾把 `outputAspectRatio` / `outputSegmentCount` 搁置，
理由是「没有消费方，加了就是长期为 0 的死字段」。robin 随后给出六家官方价目表，
要求**按计费规则补齐字段**，判据随之改为「至少一家把它当价格维度，且无法从其他字段推出来」，
于是补 4 个：

| 新字段 | 价目表依据 | 为什么推不出来 |
| --- | --- | --- |
| `outputAspectRatio` | 阿里云「部分模型按输出视频画幅定价（1:1 / 3:4 异价）」 | 画幅与分辨率正交；且它自带 `:`，与维度键分隔符冲突，须由 Calculator 转义 |
| `outputMode` | 阿里云标准·专业（`wan-std` / `wan-pro`）；Kling 动作控制（数字人 / 对口型同类） | 是同一 Model ID 下的**请求参数**，靠模型绑定区分不了。⚠ Kling 的「有声 / 无声」不占此档，由 `sound` 承担 |
| `outputVideoCount` | Veo「US$0.40 / 1 count（每条视频）」 | 按条计价的量就是条数；这类响应可以没有时长字段 |
| `voiceSpecified` | Kling 2.6 有声 × 指定音色 1.2 vs 有声 × 未指定 1.0 | 与「是否有声」正交，同一有声档再分两价 |

反之**不设字段**：输入音频时长（六家均不单独计价：Grok 1.5 收音频输入但不计费，
Kling 音频生成是独立功能、按次收费）、时长套餐（可由毫秒派生档位）、免费额度（属规则配置）、
帧率（无按帧计价）。

**字段前缀规则**：所有输出侧带 `output` 前缀、输入侧带 `input` 前缀。`width`/`height` 这类裸名在
record 里读不出方向——这是改名的唯一理由，不是洁癖。

## 二、v2 定义（最终落地形态）

```java
public record VideoBillingUsage(TokenBillingUsage tokens,
                                long outputVideoMillis,
                                String outputResolution,   // 档位名，如 "720P" / "768P" / "2K"
                                String outputAspectRatio,  // "16:9" / "1:1" / "3:4"，空串=未声明
                                String outputMode,         // "wan-std" / "wan-pro" / 功能档，空串=未声明
                                long outputVideoCount,     // 产出条数，0=未上报
                                long inputVideoMillis,
                                long inputImageCount,
                                boolean sound,
                                boolean voiceSpecified,
                                boolean referenceVideo) implements BillingUsage {

    public VideoBillingUsage {
        tokens = tokens == null ? TokenBillingUsage.empty() : tokens;
        outputResolution  = trimmed(outputResolution);
        outputAspectRatio = trimmed(outputAspectRatio);
        outputMode        = trimmed(outputMode);
        outputVideoMillis = Math.max(outputVideoMillis, 0L);
        outputVideoCount  = Math.max(outputVideoCount, 0L);
        inputVideoMillis  = Math.max(inputVideoMillis, 0L);
        inputImageCount   = Math.max(inputImageCount, 0L);
    }

    /** 输出时长（秒，向上取整）：计费与展示的唯一口径 */
    public long outputSeconds() { return ceilSeconds(outputVideoMillis); }

    /** 输入时长（秒，向上取整） */
    public long inputSeconds()   { return ceilSeconds(inputVideoMillis); }

    /** 按条计价的量：0 表示未上报，按 1 条兜底（否则相乘得 0 元） */
    public long billedVideoCount() { return outputVideoCount <= 0 ? 1L : outputVideoCount; }

    /** ⭐ 有无输入视频的唯一判据（维度键 / 分量 / 附加费 / Kling 分支共用） */
    public boolean hasInputVideo() { return inputVideoMillis > 0 || referenceVideo; }

    @Override
    public boolean isEmpty() {
        // 只认「量」：token / 输出时长 / 分辨率档 / 产出条数。
        // 属性字段（画幅 / 模式 / 声音 / 音色 / 参考）不得参与——它们只能描述「怎么出的」，
        // 不能证明「出了东西」；否则提交态回执会被判成非空，破坏 UsageExtractorRegistry 的 MISMATCH 语义（A2）。
        return tokens.isEmpty()
                && outputVideoMillis <= 0
                && outputResolution.isBlank()
                && outputVideoCount <= 0;
    }

    /** 逐项合并：数值取 max、字符串取先出现的非空值、布尔取或 */
    @Override
    public VideoBillingUsage mergeMax(BillingUsage other) { /* ... */ }

    private static long ceilSeconds(long millis) {
        return millis <= 0 ? 0L : (millis + MILLIS_PER_SECOND - 1) / MILLIS_PER_SECOND;
    }
}
```

**为什么画幅 / 模式是字符串而不是枚举或宽高**：画幅是厂商声明的价目表档名（`16:9` / `1:1` / `3:4`），
与分辨率正交；模式档各家命名体系互不相通（阿里云 `wan-std`/`wan-pro`，Kling 用「动作控制」「数字人」），
枚举化会把「新增一档」变成改代码。字符串原样保存事实，键的规范化与转义归 Calculator。

**为什么没有 `outputPixels()`**：宽高不是事实，像素数更不是。厂商声明的档位名已是计费所需的全部信息，
再用「档位名 → 标准尺寸表 → 面积」反推一个数字，只会把非标档（`768P`）变成 `0`，
而真正按像素计价的厂商一个都没有。

**为什么没有 `stage`**：见第一节修订说明。判定「这份量该不该出账」属于提取层，
计费模型一旦承载它，就同时拥有了「配价」和「闸门」两种权责，改任何一侧都会牵连另一侧。

## 三、五个关键决策

### D1 时长用 `long` 毫秒，不用 `BigDecimal` 秒

| 方案 | 评价 |
| --- | --- |
| **`long` 毫秒（采纳）** | 无精度损失；`mergeMax` 直接 `Math.max`；record 的 `equals` 稳定；字段名自带单位防误读。出口单点换算成秒 |
| `BigDecimal` 秒 | `1.0` 与 `1.00` 不 `equals`，会让 `assertEquals(VideoBillingUsage.empty(), ...)` 这类既有断言随 scale 抖动；且时长不是金额，不需要 `DECIMAL128` 语义 |
| 保留 `long` 秒 + 加小数位字段 | 两个真值源，必然长期不一致 |

⚠ **配套约束：明细 `quantity` 仍是 `long`**（`NormalizedUsageDetail.quantity`，对外契约）。
**修正（实施时定稿）**：初稿想「成本用毫秒精确算、quantity 展示取整秒」，实际放弃——
因为 `PROGRESSIVE`（Vidu 首秒阶梯）必须按秒序号落档，毫秒进不去，两套口径会分叉。
最终统一为 **毫秒只作存储精度，计费与展示一律经 `outputSeconds()` 向上取整到秒**：

| 真实时长 | v1（`long` 秒截断） | v2（毫秒 → 向上取整） |
| --- | --- | --- |
| 5.9s | 5s（少收 15%） | 6s ✅ |
| 0.5s | 0（再被兜成 1s，多收 100%） | 1s ✅ 与旧值一致 |
| 10s | 10s | 10s |

向上取整让金额方向恒定（宁可多 1 秒也不漏收），且不引入第二套量纲。

### D2 `width`/`height`/`pixels` 三个字段合并为一个 `outputResolution`

旧字段唯一作用是让 `isEmpty()` 在「无时长」时返回非空——而这个副作用正是 A2 灾难的成因
（提交态永远非空 → 不打 warn → 计 1 秒）。v2 把这个「非空」职责交给 `outputResolution`（档位名非空即算拿到了产出口径），
但 `pixels` 这个派生值彻底删掉——**没有一家厂商按像素计价**，留着它只会诱导后人去反推。

⚠ **档位名归一化只做一遍，在提取层**：`MediaUsageReaders.normalizeResolution` 把
`768p` / `768 P` / `768-P` / `768_p` / `1366x768` / `2K` / `uhd` 统一成同一个键，
Calculator 直接消费归一化后的字符串，**不再做第二遍解析**。
反推标准尺寸（`1366x768 → 768P`、`1920x1080 → 1080P`）也在这里，因为它读的是请求体的 `resolution`/`size`/`dimensions`——
那本来就是提取层的活。

> 反面判据：`VideoBillingModeCalculator` 曾自带 `resolutionOf` / `declaredResolution` / `normalizeResolution`
> 三件套 + `REQUEST_SIZE_KEYS` 常量去读请求体。这是**归属错误**——计算器的入参只有 `BillingUsage`，
> 它不该回头去翻请求体。三个方法全部迁往 `MediaUsageReaders`，计算器里只剩一行
> `String resolution = video.outputResolution();`。

### D3 「有无输入视频」拆成两个独立事实

- `inputVideoMillis > 0`：**知道时长**（可按秒计价 / 可算合成量）
- `referenceVideo == true`：**知道存在但可能不知道时长**（Kling 传 URL / video_id，请求体里根本没有秒数）

二者不可合并。旧的 `hasInputVideo = inputDuration > 0 || reference` 保住了「取哪一档价」，
但「量是多少」这条轴在缺时长时仍然只能退化——v2 让这个退化**可见**（`referenceVideo && inputVideoMillis == 0`
即「有参考视频但时长未知」，交由 Calculator 决定退化为输出秒还是报错）。

**提取侧配套**：判断「有没有提供某素材」必须用 `MediaUsageReaders.present`，
`flag` 只用于布尔开关（详见盘点文档 A6 —— `flag` 对 String 走 `Boolean.parseBoolean`，
**任何 URL 字符串判 false**，旧键表里所有「传 URL」的键从未命中）。

### D4 ~~阶段位三值，默认 `UNKNOWN`~~ —— 已撤销

理由见第一节修订：阶段是**提取层**的判定，与「怎么计价」无关。计费模型只回答「量是多少、按哪一档」。
删除 `VideoUsageStage` 后，围绕它建立的 Calculator 阶段闸门与 `shouldNotChargeWhenTaskOnlyAccepted`
一例一并移除；「提交态不出账」这个问题回到提取层解决（A2 仍待 A1 决策确定后处理）。

### D5 厂商键表靠「模板方法基类 + 差异钩子」，不扩 `extractUsage` 签名

> **⚠ 2026-10-28 修订（robin 指令）：钩子形态已被推翻，改为「一个类、一次解析」。**
> 「每个档位一个 `protected` 钩子」的问题不是命名，是结构：同一份请求体被扫十遍，
> 且「视频有哪些档位」这个清单散在十个签名里——加一维要动基类 + 每个子类 + 组装点，
> 漏任一处的表现是**少一路钱且不报错**。
> 现行形态：`AbstractVideoUsageExtractor#facts`（唯一取数入口）→ `VideoUsageFacts`
> （10 个分量的记录，`of(body, requestBody)` 一次取齐，`toBuilder()` 供厂商局部改）。
> 决策的其余部分（模板方法固定组装、身份声明留在子类、零签名改动、子类同包）**不变**。
> 规范条款：`60-business-rules.md` §8.13。下面的表格与钩子清单保留为**当时**的判断记录。

`VideoUsageExtractor.extractUsage(body, requestBody)` 的签名里没有厂商/协议身份，
这是 A1（Kling 输入秒取不到）的结构性原因。三条路：

| 方案 | 评价 |
| --- | --- |
| **模板方法基类 `AbstractVideoUsageExtractor` + 子类覆写钩子（采纳，已实施；⚠ 钩子形态 2026-10-28 已被 `VideoUsageFacts` 取代）** | 组装流程固定（取 6 个事实 → 构造 → 投影），「字段从哪儿取」留 5 个 `protected` 钩子；通用键表是默认值。厂商子类只声明身份 + 覆写差异钩子。**零签名改动、零架构新增** |
| 把厂商键表继续堆进单一实现 | 提取器会随接入厂商线性膨胀，且每加一家都要改公共类（回归面持续扩大） |
| 扩签名加 `UpstreamContext` | 撞所有 extractor + 所有测试，收益只是「少注册几个 bean」 |
| 键表塞进 `BillingConfig` | 违反分层：键表是**协议语义**，不属于计费规则；换厂商要改规则配置 |

**当时的钩子清单（默认实现 = 通用键表，已于 2026-10-28 全部并入 `VideoUsageFacts.of`）**：
`outputSeconds` / `inputSeconds` / `inputImageCount` / `soundEnabled` / `referenceVideoProvided`。
分辨率**不设钩子**——通用 `sizeOf` 够用，不为「将来可能」先加抽象（真需要时再加，成本一样）。

⚠ 子类须与本类**同包**：钩子依赖包内共享的 `MediaUsageReaders`（刻意不对外暴露）。
厂商提取器增多导致包拥挤时，再把 `MediaUsageReaders` 提为 `public` 并分包——那是以后的决策。

## 五之六、批次 M1 + M2 实施记录：对外用量视图扩容（2026-10-27 傍晚，已实施）

> 触发：robin 追问「`ModelUsage` 是不是需要和 `BillingUsage` 合并——提供 `ModelUsage` 的本意
> 是下游可以据此完成自己的计费，那计费相关信息也要入 `ModelUsage`，这样就与 `BillingUsage` 重叠了」。
> 讨论后**不合并**，但承认原设计有实质缺陷：投影是**有损**的。

### 结论：不合并，但投影必须无损

| 维度 | `BillingUsage`（sealed 四变体） | `ModelUsage`（对外单形状） |
| --- | --- | --- |
| 角色 | 内部计费事实，Calculator 的唯一输入 | 对外契约（`knot_extend.usage` + Kafka `usage`） |
| 形状 | 按计费模式分型，字段随厂商价目表演进 | 一份形状服务所有模式，下游按字段缺席判定语义 |
| 稳定性 | 内部可随时改 | 改一次要通知数仓与所有调用方 |
| 合并语义 | `mergeMax` 逐字段 | 必须**同规则**，否则两视图分叉 |

判据（写进规范，见 §60-business-rules）：**`ModelUsage` 是 `BillingUsage` 的无损投影**——
计费事实的每个字段都要能在 `ModelUsage` 里找到出口，判据是「能否只凭 `ModelUsage` 重建计费」。
合并两类类型会同时丢掉「按模式分型的强契约」与「对外单一形状」，两头都吃亏。

### robin 拍板（2026-10-27）

1. `ModelUsage` 的定位是**对上游 `usage` 的归一化**（不是「计费结果的展示」）。
2. Kafka 消息内**补上游原文 usage**（`upstream_usage`），与 `usage` **同级**（不嵌进 `usage`）。
3. **不提供计费规则给数仓**——所以下游要复算，分档键必须随用量给出。
4. 下游会**转卖 token**：既有重算价格的需求，也有成本分摊与毛利核算的需求。
5. 排版三问的回答：段名用 **`attributes`**；`upstream_usage` 与 `usage` **同级**；六家视频维度**全进**
   （追问「图片 `pixels`/`width`/`height` 是否也进」→ 同样**全进**）。

由此定下**用量三视图，单向派生**：

```
upstream_usage（上游原文，只透传）
      ↓ 归一化 + 补请求侧计费属性
usage（ModelUsage：input / output / attributes / total_tokens）
      ↓ 按本网关规则计价（规则内容不下发）
billing（NormalizedUsage：金额与明细）
```

### 6.3 字段之外的两处缺口（不补则字段形同虚设）

#### 缺口一：没有「按条」这个计费单位

**现状**：`BillingUnitEnum` 七个码（`1K_TOKENS` / `1M_TOKENS` / `PER_TOKEN` / `PER_REQUEST` /
`PER_IMAGE` / `PER_SECOND` / `CUSTOM`），`BillingModeEnum.VIDEO.supportedUnits()` 只放
`PER_SECOND` + token 三档。Veo 的价目表是 **count 计价**，现有任何单位都表达不了：
选 `PER_SECOND` 会拿秒乘「每条价」，选 `PER_REQUEST` 又不在 VIDEO 支持集内（会被
`normalizeUnit` 悄悄纠正成 `PER_SECOND`），两种都是 100 倍量级的错账。

**方案**：

| 改动 | 内容 |
| --- | --- |
| `BillingUnitEnum` | 新增 `PER_VIDEO("PER_VIDEO", "按视频条数")`；`unitSize()` 显式返回 `1`（**必须加 case**，否则落到 `default -> throw`） |
| `BillingModeEnum.VIDEO` | `supportedUnits` 追加 `PER_VIDEO`；默认单位仍是 `PER_SECOND`（老规则零影响） |
| `CUSTOM` | **不加**。`CUSTOM` 绑视频提取器时本来就走默认价、不分档，加进去只会多一条没有消费方的组合 |

**计算器侧（关键）**：现在的量纲判断是 `tokenQuantity(rule, mode)` 一个布尔，
再加一个布尔就会退化成「两套判断各写一份」——而这正是 `AbstractBillingModeCalculator`
注释里警告过的资损路径（换一次提取器绑定就换一套算法，编译与单测全绿）。改为
**单位 → 量纲** 的单点映射，三条腿：

| 量纲 | 判定 | 输出分量取值 |
| --- | --- | --- |
| `SECONDS` | 其余（默认） | `outputAmountSeconds(video, videoConfig)`（今天的路径：`quantityMode` 折叠 + 至少一秒） |
| `TOKENS` | `unit.tokenBased()` | `tokenAmount(video.tokenUsage())` |
| `COUNT` | `unit == PER_VIDEO` | `video.billedVideoCount()`；**忽略 `quantityMode`** |

`COUNT` 下另外两条硬约束：

1. **输入秒 / 输入图分量必须关闭**——与 token 量纲同理，一条规则只有一个分母（`unitSize`），
   秒 / 张分量会被「每条」的分母除错。附加费是常数项，保留。
2. **明细 `quantity` 是条数**（`NormalizedUsageDetail.quantity` 仍是 `long`，无需改契约）。

**校验与门禁**：

- `BillingUnitEnumTest.everyUnitSizeIsPowerOfTen` 会遍历新常量并调用 `unitSize()`——
  忘了加 case 时它会立刻抛异常变红，这条既有测试就是守卫，不用另写。
- 新增 1 例：`VIDEO` 支持 `PER_VIDEO`、`TOKEN` 不支持；`normalizeUnit("PER_VIDEO")` 在 `TOKEN` 下仍回落 `1M_TOKENS`。
- `BillingService.validateModeAndUnit` 由 `supportsUnit` 自动放行，无需改。

#### 缺口二：维度键语法只装得下 2 个布尔

**现状**：键形如 `档位[:REFERENCE][:AUDIO]`。三处硬约束同时存在：

| 位置 | 现状 |
| --- | --- |
| `VideoBillingModeCalculator.dimensionKeys`（:305） | 只生成 4 条候选（`档位`、`:REFERENCE`、`:AUDIO`、`:REFERENCE:AUDIO`），逐级去尾 |
| `BillingConfig.SUPPORTED_DIMENSION_SUFFIXES`（:119） | 保存期白名单只有这 4 种，新维度**存不进去** |
| 前端 `billingResolution.ts` + 档位表 | 4 个价格列一一对应这 4 种后缀 |

**为什么不能「加列」**：画幅 × 模式 × 音色 × 参考 × 有声，列数按 2ⁿ 增长；
Kling 一次请求就可能同时命中「有声 + 指定音色 + 参考视频 + 功能档」四维。
再加列等于让运维手工填 16～32 个格子，配错格子就是错价。

**方案：固定顺序 + 值前缀，老键零改动**

```
档位[:MODE=值][:ASPECT=值][:REFERENCE][:AUDIO][:VOICE]
```

| 规则 | 说明 |
| --- | --- |
| 段顺序固定 | `MODE` → `ASPECT` → `REFERENCE` → `AUDIO` → `VOICE`，且每段至多一次 |
| 值带前缀 | `MODE=` / `ASPECT=` 消除位置歧义——否则 `720P:AUDIO` 里的 `AUDIO` 无法区分是「模式名」还是「有声开关」 |
| 冒号转义 | 画幅自带的 `:` 转成 `X`：`16:9` → `16X9`、`1:1` → `1X1`；转义在 Calculator 做，record 里存原始事实 |
| 全大写 | 键空间统一大写（`dimensionPrice` 虽兼容三种大小写，但配置与候选应同形，避免靠兜底命中） |
| 值只允许 ASCII | `MODE=` / `ASPECT=` 的值限定 `A-Z0-9_-`：中文档名（动作控制 / 数字人）由厂商子类映射成 `MOTION_CONTROL` / `DIGITAL_HUMAN`，配置里不出现中文键 |
| 老键不变 | `720P` / `720P:AUDIO` / `720P:REFERENCE:AUDIO` 全部仍是合法键、语义不变 |

示例（每一行都是真实价目表需求）：

| 价目表 | 键 |
| --- | --- |
| 阿里云图生动作 标准 / 专业 | `720P:MODE=WAN-STD` / `720P:MODE=WAN-PRO` |
| 阿里云部分模型按画幅 | `1080P:ASPECT=16X9` / `1080P:ASPECT=1X1` |
| Kling 2.6 有声 × 指定音色 | `720P:AUDIO:VOICE` |
| Kling 3.0 动作控制 | `720P:MODE=MOTION_CONTROL` / `1080P:MODE=MOTION_CONTROL` |
| Kling 有声 + 参考 + 音色 | `720P:REFERENCE:AUDIO:VOICE` |
| Seedance 离线推理 | `720P:MODE=OFFLINE`（token 单价不同，键相同） |

**候选链改为「声明维度的全部子集」，不再逐级去尾**：

- 逐级去尾只能删最右一段，会漏掉「请求声明了 MODE，但价格只按 AUDIO 配」的键
  （`720P:MODE=WAN-PRO:AUDIO` 去尾得到 `720P:MODE=WAN-PRO`，永远轮不到 `720P:AUDIO`）——
  而这两种配置在真实价目表里并存（阿里云按模式、Kling 按声音）。
- 子集生成：至多 5 维 → 最多 **32 条**候选，纯内存循环，不是配置爆炸。
  排序为「段数降序 → 固定维度优先级（MODE > ASPECT > REFERENCE > AUDIO > VOICE）」，
  保证确定性（同段数时不会因集合遍历顺序不同而取到不同价）。
- 候选里天然包含老键：请求带 mode + audio 时，子集里仍有 `720P:AUDIO`，老配置继续命中。

**配置校验**：`SUPPORTED_DIMENSION_SUFFIXES` 白名单（`BillingConfig:119`）换成
**语法解析器**（同文件 `validateDimensionTiered:1007`）：剥掉 `INPUT_VIDEO:` / `INPUT_IMAGE:`
前缀后，首段必须非空档位名，其余段按上表顺序匹配，违规报错信息带上「期望顺序」。
**输入侧分量键不开放新维度**：`INPUT_VIDEO:` 后只允许老的 4 种形状，配了新维度直接拒绝——
计算器不会为输入分量生成这些键，放行等于让运维配一个永不命中的价。

**前端**：

- 必需：`constants/status.ts` 的 `BillingUnit` 补 `PER_VIDEO`；`utils/billingPrice.ts` 的
  `UNIT_LABELS` 补「每条单价」（否则回落成「每秒单价」，用户按秒填每条价）。
- **不阻塞**：`config_json` 页已可编辑任意键，且 `parseResolutionRows` 对未匹配后缀的键
  **整串保留为档位名**（`BillingRuleFormDialog.vue:640-647`），保存不会丢配置——
  实测结论是「新键能存能回显，只是在档位表里显示成一行长名字」。
- 暂不做「高级维度键」专用编辑器：现有两条路（表格 + config_json）够用，
  等真的有人天天手填再补 UI（YAGNI）。

### 6.4 第二轮对 §五之四 的三处修订

| 项 | §五之四原方案 | 第二轮修订 | 理由 |
| --- | --- | --- | --- |
| `outputMode` 默认钩子 | `""`（只留给厂商子类） | 读 `video_mode` / `output_mode` / `mode` | 阿里云图生动作 / 换人绑的是通用提取器，默认 `""` 会让模式档永远取不到；键带 `MODE=` 前缀，误读（如 `mode=async`）只会配不上价、回落默认价，不会错命中 |
| `outputVideoCount` 默认钩子 | 只取 `data` 数组长度 | `data` / `videos` 数组长度，或存在单个视频对象 → 1 | Veo 回 `videos`，只认 `data` 会让 `isEmpty()` 判空 → MISMATCH（A2 同类问题） |
| `outputAspectRatio` 默认钩子 | 通用键表不猜 | 只读 `aspect_ratio` | 语义明确的键才读；`size` / `ratio` 语义含糊（可能是像素尺寸），交给厂商子类按实际请求参数覆写 |

`voiceSpecified` 默认仍是 `false`（Kling 专属，D3 覆写），无修订。

### 6.7 已拍板：两个字段解决不了的计费口径（robin，2026-10-27）

| # | 问题 | 证据 | 拍板结论 |
| --- | --- | --- | --- |
| 1 | **输入秒上限** | 阿里云「万相-参考生视频」：计费时长 = 输入视频时长（上限 5 秒）+ 输出视频时长；Wan3.0 / 视频编辑则是全量输入秒 | **不约束**：输入时长由调用方决定，网关无法控制，不在计费侧加 `inputVideoCapSeconds`。`SUM` 口径按上游实报的全量输入秒计，>5s 的差额接受（见 §6.8 第一条风险） |
| 2 | **token 取数方向** | Seedance 明示「actual consumption = `completion_tokens`」；`tokenAmount()` 目前总量优先（`totalTokens`），若上游同时回 `total_tokens = prompt + completion`，会把提示 token 算进视频价 | **归 Calculator 层**：不新增字段、不在提取器按厂商特判，`firstAmount` 保持为 Calculator 内的唯一取数出口。取数顺序（输出优先 / 总量优先）只在此一处调整，改前先用真实响应核对 `total_tokens` 是否含提示 token |

### 6.8 残余风险（本轮不解决，登记在案）

| 风险 | 表现 | 处理 |
| --- | --- | --- |
| 阿里云参考生视频**输入秒 >5s 会多收** | 价目表只计前 5 秒，而网关不约束输入时长（§6.7 拍板），`SUM` 按上游实报的全量输入秒计 | 接受；需要对账精确的规则可把该模型改成「只计输出」（`VideoConfig.billsInputVideo=false`），由运营按模型权衡 |
| Kling 传 URL 时**输入时长未知** | `referenceVideo=true` 但 `inputVideoMillis=0`，`OUTPUT_PLUS_MAX` 退化为「只计输出」→ 少收输入段 | 不加字段；Calculator 在「`OUTPUT_PLUS_MAX` + 有参考 + 输入秒为 0」时打 warn，让少收在日志里可见 |
| 阿里云画幅定价**未列具体模型** | 本页只在通用说明里写「部分模型按画幅定价（1:1 / 3:4）」，没有可直接对照的表格 | 字段先落地；D3 接入具体模型时按该模型请求参数核对键名（`aspect_ratio` 或别名） |
| Kling 数字人 / 对口型**归属未核实** | 若它们是独立 Model ID 而非同模型请求参数，`outputMode` 就用错了层（应走规则绑定） | D3 接入前先核 Kling 模型清单与请求参数；本轮只据价目表把它们登记为同类功能档 |
| 维度候选数随维数 2ⁿ 增长 | 现在是 32 条上限 | 出现第 6 维时改结构化键（`Map<Segment, …>`），不再扩子集 |
| `PER_VIDEO` 与 `PROGRESSIVE` 组合 | 技术上可配，语义是「第 N 条起不同价」 | 不禁止、不推荐；文档标注，配错由配置审查兜住 |

## 七、明确不做（避免后续重复讨论）

| 项 | 理由 |
| --- | --- |
| `declared` vs `delivered` 双时长 | 当前所有目标厂商均按**请求声明时长**计费；请求体 duration 键表尚未收齐，加字段只会多一个长期为 0 的死字段。等出现真正按实际出片时长计费的厂商再加 |
| 时长套餐（B3）字段 | 「5s/10s 包价」本质是档位，可由 `outputVideoMillis` 派生档位名，不需要新字段 |
| 免费额度 / 周期配额（C2） | 计费域整体缺口，不属视频模型范畴，另开单 |
| 「每 5 秒」非 10ⁿ 单位（C1） | `BillingUnitEnum` 的单位语义，与用量模型无关 |
| ~~改 `ModelUsage` 对外 JSON 形状~~ —— **已撤销（2026-10-27 傍晚）** | 原判「契约稳定压倒一切」，但实测投影是**有损**的：D1 的 4 个维度与输入侧两轴在对外用量里没有出口，视频条数还会被误标成图片张数。robin 拍板扩容 + Kafka 补 `upstream_usage`，已实施，见 §五之六 |
| 把 `ModelUsage` 与 `BillingUsage` 合并成一个类型 | 两者形状 / 稳定性 / 演进速度 / 合并语义四点都不同（§五之六开头的对比表）；真正的问题是**投影有损**，不是类型数量。合并会同时丢掉「按模式分型的强契约」与「对外单一形状」 |
| 把价格或计费规则内容放进 `ModelUsage` / Kafka 消息 | 价格只在 `NormalizedUsage`；规则内容不下发数仓（robin 拍板）。下游要复算，靠的是「量 + 分档键 + `upstream_usage` 原文」，不是规则本身 |
| `attributes` 里做键空间归一（统一大小写、`16:9` → `16X9`） | 原样保留厂商写法；网关一替下游猜档位名，两侧就会各猜一套。归一化是 Calculator 取价时的内部动作 |
| 输入时长的**取数补强**（响应侧兜底、多认请求键） | robin 2026-10-27 拍板暂不处理：输入时长网关既控制不了也未必拿得到；`inputVideoMillis` 已在 record 里，缺的只是 URL 场景的取值来源。等有真实响应证据再评估，风险已登记 §6.8 |
