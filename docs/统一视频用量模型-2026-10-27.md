# 统一视频用量模型（VideoBillingUsage v2）

> 日期：2026-10-27　范围：`knot-adapter` 用量提取层 / 计费计算器 / `ModelUsageNormalizer`
> 前置结论：`BillingUsage` 是计费唯一量来源，`ModelUsage` 是它的**单向投影**，
> 永远不进 `Calculator`（详见上一轮辨析）。因此本方案**只改源**，投影随源自动收敛。
> 上游盘点：`docs/视频计费规则不足盘点-2026-10-27.md`

---

## 0. 结论先行

v1 的 `VideoBillingUsage` 是 9 个扁平字段，隐含三个错误假设（下表是对已实施批次的复盘；
当前 HEAD 已是 7 字段，D1 的 11 字段仍在方案阶段）：

| 错误假设 | 表现 | 后果 |
| --- | --- | --- |
| **「时长」用 `long` 秒就够** | `MapNumberUtils.longValue` 直接截断 | 5.9s→5s 少收 15%；0.5s→0→兜 1s 多收 100% |
| **「有参考」是一个布尔** | 一个 `reference` 同时承载参考图/参考视频/输入视频 | 图生视频误命中 `:REFERENCE` 档；同一 `reference_images` 又喂了张数（A4） |
| **「一次请求 = 一个完整响应」** | 无阶段概念 | 提交型厂商回 `{task_id}` 被静默计 1 秒（A2） |

v2 目标：**时长毫秒化、输入侧事实拆开、按六家官方价目表补齐维度原料**。
`pixels` 与宽高合并为档位名（9 → 7），再按价目表补 4 个维度字段（7 → **11**），每个字段都有唯一语义。

> ### ⚠ 修订（2026-10-27 晚间，robin 拍板）
>
> 初稿把宽高当 `long`、并加 `stage` 阶段位，两处都被推翻：
>
> 1. **宽高改字符串 `outputResolution`** —— *「`long outputWidth`、`long outputHeight` 与事实不符，
>    改成字符串，直接用 resolution 就好」*。厂商声明的就是**档位名**（`768P`、`540P`、`2K`、`4K`
>    乃至自造名），不是像素尺寸；宽高是「由档位名反推」的中间产物，而反推只认标准尺寸表，
>    `768P` 这类非标档会退化成裸串或空值，配了价也吃不到。三个字段（`width`/`height`/`pixels`）
>    因此合并为一个 `outputResolution`，`outputPixels()` 派生方法一并删除。
> 2. **删 `VideoUsageStage`** —— *「和数据提取有关，但和计费无关，也去掉」*。
>    **计费模型只回答「量是多少、按哪一档」，不回答「这份量该不该出账」**；阶段是提取层的判定，
>    放进计费 record 就是让一个纯量模型承载策略。随之删掉的还有 Calculator 的阶段闸门与
>    `shouldNotChargeWhenTaskOnlyAccepted` 一例。
>
> 净结果：B+C 阶段 v2 字段数 **7**（`tokens` / `outputVideoMillis` / `inputVideoMillis` / `inputImageCount` /
> `outputResolution` / `sound` / `referenceVideo`），比 v1 的 9 个更少且每个都有唯一语义。
> 批次 D 再补 4 个价格维度字段，见下方「收敛说明」。

**收敛说明（批次 D 修订）**：B+C 阶段曾把 `outputAspectRatio` / `outputSegmentCount` 搁置，
理由是「没有消费方，加了就是长期为 0 的死字段」。robin 随后给出六家官方价目表，
要求**按计费规则补齐字段**，判据随之改为「至少一家把它当价格维度，且无法从其他字段推出来」，
于是补 4 个：

| 新字段 | 价目表依据 | 为什么推不出来 |
| --- | --- | --- |
| `outputAspectRatio` | 阿里云「部分模型按输出视频画幅定价（1:1 / 3:4 异价）」 | 画幅与分辨率正交；且它自带 `:`，与维度键分隔符冲突，须由 Calculator 转义 |
| `outputMode` | 阿里云标准·专业（`wan-std` / `wan-pro`）；Kling 无声·有声·动作控制·数字人·对口型 | 是同一 Model ID 下的**请求参数**，靠模型绑定区分不了 |
| `outputVideoCount` | Veo「US$0.40 / 1 count（每条视频）」 | 按条计价的量就是条数；这类响应可以没有时长字段 |
| `voiceSpecified` | Kling 2.6 有声 × 指定音色 1.2 vs 有声 × 未指定 1.0 | 与「是否有声」正交，同一有声档再分两价 |

反之**不设字段**：输入音频时长（六家均不单独计价：Grok 1.5 收音频输入但不计费，
Kling 音频生成是独立功能、按次收费）、时长套餐（可由毫秒派生档位）、免费额度（属规则配置）、
帧率（无按帧计价）。

**字段前缀规则**：所有输出侧带 `output` 前缀、输入侧带 `input` 前缀。`width`/`height` 这类裸名在
record 里读不出方向——这是改名的唯一理由，不是洁癖。

## 二、v2 定义（最终落地形态）

```java
public record VideoBillingUsage(TokenBillingUsage tokens,
                                long outputVideoMillis,
                                String outputResolution,   // 档位名，如 "720P" / "768P" / "2K"
                                String outputAspectRatio,  // "16:9" / "1:1" / "3:4"，空串=未声明
                                String outputMode,         // "wan-std" / "wan-pro" / 功能档，空串=未声明
                                long outputVideoCount,     // 产出条数，0=未上报
                                long inputVideoMillis,
                                long inputImageCount,
                                boolean sound,
                                boolean voiceSpecified,
                                boolean referenceVideo) implements BillingUsage {

    public VideoBillingUsage {
        tokens = tokens == null ? TokenBillingUsage.empty() : tokens;
        outputResolution  = trimmed(outputResolution);
        outputAspectRatio = trimmed(outputAspectRatio);
        outputMode        = trimmed(outputMode);
        outputVideoMillis = Math.max(outputVideoMillis, 0L);
        outputVideoCount  = Math.max(outputVideoCount, 0L);
        inputVideoMillis  = Math.max(inputVideoMillis, 0L);
        inputImageCount   = Math.max(inputImageCount, 0L);
    }

    /** 输出时长（秒，向上取整）：计费与展示的唯一口径 */
    public long outputSeconds() { return ceilSeconds(outputVideoMillis); }

    /** 输入时长（秒，向上取整） */
    public long inputSeconds()   { return ceilSeconds(inputVideoMillis); }

    /** 按条计价的量：0 表示未上报，按 1 条兜底（否则相乘得 0 元） */
    public long billedVideoCount() { return outputVideoCount <= 0 ? 1L : outputVideoCount; }

    /** ⭐ 有无输入视频的唯一判据（维度键 / 分量 / 附加费 / Kling 分支共用） */
    public boolean hasInputVideo() { return inputVideoMillis > 0 || referenceVideo; }

    @Override
    public boolean isEmpty() {
        // 只认「量」：token / 输出时长 / 分辨率档 / 产出条数。
        // 属性字段（画幅 / 模式 / 声音 / 音色 / 参考）不得参与——它们只能描述「怎么出的」，
        // 不能证明「出了东西」；否则提交态回执会被判成非空，破坏 UsageExtractorRegistry 的 MISMATCH 语义（A2）。
        return tokens.isEmpty()
                && outputVideoMillis <= 0
                && outputResolution.isBlank()
                && outputVideoCount <= 0;
    }

    /** 逐项合并：数值取 max、字符串取先出现的非空值、布尔取或 */
    @Override
    public VideoBillingUsage mergeMax(BillingUsage other) { /* ... */ }

    private static long ceilSeconds(long millis) {
        return millis <= 0 ? 0L : (millis + MILLIS_PER_SECOND - 1) / MILLIS_PER_SECOND;
    }
}
```

**为什么画幅 / 模式是字符串而不是枚举或宽高**：画幅是厂商声明的价目表档名（`16:9` / `1:1` / `3:4`），
与分辨率正交；模式档各家命名体系互不相通（阿里云 `wan-std`/`wan-pro`，Kling 用「动作控制」「数字人」），
枚举化会把「新增一档」变成改代码。字符串原样保存事实，键的规范化与转义归 Calculator。

**为什么没有 `outputPixels()`**：宽高不是事实，像素数更不是。厂商声明的档位名已是计费所需的全部信息，
再用「档位名 → 标准尺寸表 → 面积」反推一个数字，只会把非标档（`768P`）变成 `0`，
而真正按像素计价的厂商一个都没有。

**为什么没有 `stage`**：见第一节修订说明。判定「这份量该不该出账」属于提取层，
计费模型一旦承载它，就同时拥有了「配价」和「闸门」两种权责，改任何一侧都会牵连另一侧。

## 三、五个关键决策

### D1 时长用 `long` 毫秒，不用 `BigDecimal` 秒

| 方案 | 评价 |
| --- | --- |
| **`long` 毫秒（采纳）** | 无精度损失；`mergeMax` 直接 `Math.max`；record 的 `equals` 稳定；字段名自带单位防误读。出口单点换算成秒 |
| `BigDecimal` 秒 | `1.0` 与 `1.00` 不 `equals`，会让 `assertEquals(VideoBillingUsage.empty(), ...)` 这类既有断言随 scale 抖动；且时长不是金额，不需要 `DECIMAL128` 语义 |
| 保留 `long` 秒 + 加小数位字段 | 两个真值源，必然长期不一致 |

⚠ **配套约束：明细 `quantity` 仍是 `long`**（`NormalizedUsageDetail.quantity`，对外契约）。
**修正（实施时定稿）**：初稿想「成本用毫秒精确算、quantity 展示取整秒」，实际放弃——
因为 `PROGRESSIVE`（Vidu 首秒阶梯）必须按秒序号落档，毫秒进不去，两套口径会分叉。
最终统一为 **毫秒只作存储精度，计费与展示一律经 `outputSeconds()` 向上取整到秒**：

| 真实时长 | v1（`long` 秒截断） | v2（毫秒 → 向上取整） |
| --- | --- | --- |
| 5.9s | 5s（少收 15%） | 6s ✅ |
| 0.5s | 0（再被兜成 1s，多收 100%） | 1s ✅ 与旧值一致 |
| 10s | 10s | 10s |

向上取整让金额方向恒定（宁可多 1 秒也不漏收），且不引入第二套量纲。

### D2 `width`/`height`/`pixels` 三个字段合并为一个 `outputResolution`

旧字段唯一作用是让 `isEmpty()` 在「无时长」时返回非空——而这个副作用正是 A2 灾难的成因
（提交态永远非空 → 不打 warn → 计 1 秒）。v2 把这个「非空」职责交给 `outputResolution`（档位名非空即算拿到了产出口径），
但 `pixels` 这个派生值彻底删掉——**没有一家厂商按像素计价**，留着它只会诱导后人去反推。

⚠ **档位名归一化只做一遍，在提取层**：`MediaUsageReaders.normalizeResolution` 把
`768p` / `768 P` / `768-P` / `768_p` / `1366x768` / `2K` / `uhd` 统一成同一个键，
Calculator 直接消费归一化后的字符串，**不再做第二遍解析**。
反推标准尺寸（`1366x768 → 768P`、`1920x1080 → 1080P`）也在这里，因为它读的是请求体的 `resolution`/`size`/`dimensions`——
那本来就是提取层的活。

> 反面判据：`VideoBillingModeCalculator` 曾自带 `resolutionOf` / `declaredResolution` / `normalizeResolution`
> 三件套 + `REQUEST_SIZE_KEYS` 常量去读请求体。这是**归属错误**——计算器的入参只有 `BillingUsage`，
> 它不该回头去翻请求体。三个方法全部迁往 `MediaUsageReaders`，计算器里只剩一行
> `String resolution = video.outputResolution();`。

### D3 「有无输入视频」拆成两个独立事实

- `inputVideoMillis > 0`：**知道时长**（可按秒计价 / 可算合成量）
- `referenceVideo == true`：**知道存在但可能不知道时长**（Kling 传 URL / video_id，请求体里根本没有秒数）

二者不可合并。旧的 `hasInputVideo = inputDuration > 0 || reference` 保住了「取哪一档价」，
但「量是多少」这条轴在缺时长时仍然只能退化——v2 让这个退化**可见**（`referenceVideo && inputVideoMillis == 0`
即「有参考视频但时长未知」，交由 Calculator 决定退化为输出秒还是报错）。

**提取侧配套**：判断「有没有提供某素材」必须用 `MediaUsageReaders.present`，
`flag` 只用于布尔开关（详见盘点文档 A6 —— `flag` 对 String 走 `Boolean.parseBoolean`，
**任何 URL 字符串判 false**，旧键表里所有「传 URL」的键从未命中）。

### D4 ~~阶段位三值，默认 `UNKNOWN`~~ —— 已撤销

理由见第一节修订：阶段是**提取层**的判定，与「怎么计价」无关。计费模型只回答「量是多少、按哪一档」。
删除 `VideoUsageStage` 后，围绕它建立的 Calculator 阶段闸门与 `shouldNotChargeWhenTaskOnlyAccepted`
一例一并移除；「提交态不出账」这个问题回到提取层解决（A2 仍待 A1 决策确定后处理）。

### D5 厂商键表靠「模板方法基类 + 差异钩子」，不扩 `extractUsage` 签名

`VideoUsageExtractor.extractUsage(body, requestBody)` 的签名里没有厂商/协议身份，
这是 A1（Kling 输入秒取不到）的结构性原因。三条路：

| 方案 | 评价 |
| --- | --- |
| **模板方法基类 `AbstractVideoUsageExtractor` + 子类覆写钩子（采纳，已实施）** | 组装流程固定（取 6 个事实 → 构造 → 投影），「字段从哪儿取」留 5 个 `protected` 钩子；通用键表是默认值。厂商子类只声明身份 + 覆写差异钩子。**零签名改动、零架构新增** |
| 把厂商键表继续堆进单一实现 | 提取器会随接入厂商线性膨胀，且每加一家都要改公共类（回归面持续扩大） |
| 扩签名加 `UpstreamContext` | 撞所有 extractor + 所有测试，收益只是「少注册几个 bean」 |
| 键表塞进 `BillingConfig` | 违反分层：键表是**协议语义**，不属于计费规则；换厂商要改规则配置 |

**钩子清单（默认实现 = 通用键表）**：`outputSeconds` / `inputSeconds` / `inputImageCount` /
`soundEnabled` / `referenceVideoProvided`。分辨率**不设钩子**——通用 `sizeOf` 够用，
不为「将来可能」先加抽象（真需要时再加，成本一样）。

⚠ 子类须与本类**同包**：钩子依赖包内共享的 `MediaUsageReaders`（刻意不对外暴露）。
厂商提取器增多导致包拥挤时，再把 `MediaUsageReaders` 提为 `public` 并分包——那是以后的决策。

`flag()` 对字符串走 `Boolean.parseBoolean`，所以**任何 URL 字符串都被判成 `false`**：

这是**「一个方法承担两种语义」**的典型缺陷：`generate_audio`（布尔开关）与 `video_url`（存在性）

## 五之四、批次 D1 设计定稿（2026-10-27，未实施）

**字段集（11 个）**：`tokens` / `outputVideoMillis` / `outputResolution` / `outputAspectRatio` /
`outputMode` / `outputVideoCount` / `inputVideoMillis` / `inputImageCount` / `sound` /
`voiceSpecified` / `referenceVideo`。字段顺序按「输出侧 → 输入侧 → 生成属性」重排。
⚠ 构造点改动量取决于批次 E 是否先落地：**E 先做则本节实施时构造点零改动**（只需在记录内补字段），
否则要同步补 16 处测试构造 + 提取器 + `empty()` / `mergeMax()`（见五之五）。

**两个口径决定**

1. **`isEmpty()` 纳入 `outputVideoCount`**：按条计价的响应可以没有时长字段，
   `data` / `videos` 数组长度就是产出本身。属性字段（画幅 / 模式 / 声音 / 音色 / 参考）一律不参与，
   否则提交态回执会被判成非空，A2 的 MISMATCH 语义会被重新破坏。
2. **`billedVideoCount()` 把 0 兜成 1**：按条计价的乘数是条数，0 会算出 0 元；
   「未上报」的现实含义是「一条」，与「至少一秒」同一口径。

**提取钩子（默认值 / 留给厂商子类）**

| 钩子 | 默认实现 | 说明 |
| --- | --- | --- |
| `outputAspectRatio` | `""` | 通用键表不猜画幅；只有阿里云部分模型按画幅定价 |
| `outputMode` | `""` | 模式档是厂商命名（`wan-std` / 动作控制…），由子类覆写 |
| `outputVideoCount` | `data` 数组长度 | OpenAI 风格；Veo 的 `videos` 由子类覆写 |
| `voiceSpecified` | `false` | Kling 2.6 的音色字段由子类覆写 |

**实施时新增测试**：`VideoBillingUsageTest` 补「条数兜底 / `isEmpty` 含条数 / `mergeMax`」三组

## 五之五、批次 E 设计定稿：构造方式改 `@Builder`（2026-10-27，未实施）

### 问题：11 个位置参数的两个真实痛点

| 痛点 | 表现 | 是否需要立刻解决 |
| --- | --- | --- |
| **顺序不可见** | `long inputVideoMillis` 与 `long inputImageCount` 相邻；`sound` / `voiceSpecified` / `referenceVideo` 三个 `boolean` 相邻。调换顺序**编译通过**，单测也可能通过，账单直接错 | ✅ 是（静默错单） |

生产侧「只有 1 处构造、参数都是自解释的方法调用」不足以反驳上述判断——第二家厂商提取器一多，
位置调用就会重新成为错单源头，只是把问题推迟。

### 方案对比

尺子：SOLID 主尺，DRY / KISS / YAGNI 辅尺（`80-code-review.md` §1）。

| 方案 | 写点改动 | 读点改动 | 新增字段波及 | 同型调换 | 代价 |
| --- | --- | --- | --- | --- | --- |
| A 维持位置构造 | — | — | 19 处全断 | ❌ 静默 | 0 |

### 三条实施口径

1. **`mergeMax()` 保留位置构造**：合并不是「建值」，每个字段的合并策略（`Math.max` / 先出现的非空串 /
   布尔或）必须逐行写出来，改成 builder 只是把同一段逻辑劈成两半。
2. **`empty()` 改 `builder().build()`**：全零 / 空默认值经紧凑构造器归一后恰好就是空用量，
   字段再增也不用回来补参数。
3. **`@Builder` 生成器必须走规范构造器**：紧凑构造器里的归一化（`tokens` 空值兜底、分辨率 `trim`、
   负数夹零）要由测试钉住。builder 若绕过归一化，既有测试全绿也发现不了——这是新增测试的唯一职责。
