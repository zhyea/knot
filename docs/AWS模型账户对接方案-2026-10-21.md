## 0. 结论先行

Bedrock 接入**不需要新表、不需要新端点、不需要动路由/计费/频控主干**。knot 的扩展点体系（凭据类型 → 鉴权策略 → 请求适配器 → 用量提取器，四族 Catalog 注册制）就是为这类供应商准备的，`ProviderCredentialTypeEnum` 里 `AWS_AUTH` 已预留（`knot-common/.../ProviderCredentialTypeEnum.java:12`）。

需要动的只有 **8 个后端文件 + 1 个迁移脚本 + 种子数据 + 1 个前端小改动（可砍）**：

| 层 | 文件 | 动作 |
|---|---|---|
| common | `ProviderCredentialTypeEnum.java` | `AWS_AUTH.requiredFields` 补 `sessionToken`（D5） |
| adapter | `AwsSigV4AuthApplier.java` | 新增，code=`AWS_SIGV4` |
| adapter | `AwsSigV4Support.java` | 新增，纯函数 SigV4 签名器 |
| adapter | `UpstreamAuthApplier.java` | 加 `sign(...)` 默认空方法（签名钩子） |
| adapter | `BedrockConverseRequestAdapter.java` | 新增，code=`BEDROCK_CONVERSE` |
| adapter | `BedrockConverseUsageExtractor.java` | 新增，code=`BEDROCK_CONVERSE` |
| adapter | `UpstreamRequestAdapter.java` | 加 `streamSupported` 默认方法 |
| gateway | `AbstractUpstreamProtocolExecutor.java` | body 序列化提前 + 调签名钩子 + 流式委托 adapter |

**外部协议零变化**：客户端照发 `/v1/chat/completions`，Bedrock 的差异全部消化在适配器与签名器里。

## 1. 现状盘点（扩展点地图）

证据链（`文件:行`）：

- 凭据类型枚举 `ProviderCredentialTypeEnum`（knot-common）——`AWS_AUTH("aws-auth", requiredFields=[accessKey, secretKey, region])` 已存在，但**全仓零实现**（grep 仅命中枚举本体 + 两个单测）。
- 鉴权策略族 `UpstreamAuthApplier`（knot-adapter）+ Catalog（按 code/类名解析，空回退 Bearer）。现有三策略：`BEARER`、`ANTHROPIC_API_KEY`、`NONE`。`apply(HttpHeaders, UpstreamRequestContext)` 只碰头、不碰客户端类型——**SigV4 需要 URL + body hash，这是唯一需要动契约的地方**。
- 请求适配器族 `UpstreamRequestAdapter`（`buildRequestBody` / `handleResponse` / `resolvePath` / `extractUsage`）。现有 `OPENAI_COMPATIBLE` / `ANTHROPIC` / `PASSTHROUGH`。
- 用量提取器族 `UsageExtractor` + Catalog；`TokenBillingUsage.from()` 只认 snake_case（`input_tokens`/…），**不认 Bedrock 的 camelCase（`inputTokens`/…）** → 必须做专用提取器。
- 协议执行器 `AbstractUpstreamProtocolExecutor`（WebClient，阻塞到响应头就绪；流式走 `toEntityFlux`）。`TextGenerationProtocolExecutor` 管四个文本协议。
- 上下文 `UpstreamRequestContext`（protocol/requestBody/model/provider/authConfig/binding/authApplier），`UpstreamProxyClient` 组装。
- 选项下发全数据驱动：`ProviderController` → `authApplierCatalog.definitions()`（`ProviderService.java:138`）、`ModelController` → adapter/extractor definitions（`ModelService.java:183/199`）——**新增策略自动出现在前端下拉**。
- 前端表单 `ProviderAccountFormDrawer.vue` 按 credentialType 的 requiredFields 动态渲染字段（`:94-95`），鉴权方式按 credentialTypes 过滤（`:213`）。

**顺带发现（存量缺陷，不在本方案范围）**：`data.sql:641-642` qwen-image 两个 binding 的 `request_adapter='QWEN'` 在代码里不存在（全仓 grep 无 `QwenRequestAdapter`），运行期被 `UpstreamRequestAdapterRegistry` 静默兜底成 `PASSTHROUGH`。建议另开单修。

## 2. Bedrock 与现有供应商的技术差异

| 维度 | OpenAI / Anthropic 直连 | AWS Bedrock |
|---|---|---|
| 端点 | 固定 base_url + 固定 path | `bedrock-runtime.<region>.amazonaws.com/model/<modelId>/converse`，region 与 modelId 都进 URL |
| 鉴权 | 静态头（Bearer / x-api-key） | **SigV4**：`Authorization` 头是对 `(method, URI, headers, body-hash)` 的 HMAC 签名，带时间窗 |
| 请求体 | OpenAI / Anthropic 原生格式 | **Converse** 统一格式（`messages[].content[]` 块状、`system[]`、`inferenceConfig{}`） |
| 响应体 | OpenAI / Anthropic 原生格式 | `output.message.content[]` + `stopReason` + `usage{camelCase}` |
| 流式 | SSE 文本 | **AWS EventStream 二进制帧**（不是 SSE），usage 在 metadata 事件 |
| 错误 | HTTP status + JSON | status + `x-amzn-ErrorType`（ThrottlingException 429 等） |
| 用量口径 | usage 对象 snake_case | camelCase `inputTokens/outputTokens/totalTokens/cacheReadInputTokens/cacheWriteInputTokens` |

## 3. 总体设计

关键路径：

1. 客户端 CHAT_COMPLETIONS 请求 → 路由选中 Bedrock 模型（`kb_models`，`upstream_model = anthropic.claude-...-v1:0`）。
2. `UpstreamProxyClient` 组装 `UpstreamRequestContext`（`binding.requestAdapter = BEDROCK_CONVERSE`，`credential.authApplier = AWS_SIGV4`）。
3. `TextGenerationProtocolExecutor` → `BedrockConverseRequestAdapter.buildRequestBody`（chat→converse）+ `resolvePath`（`/model/{upstream_model}/converse`）。
4. **改造点**：executor 先把 body 序列化为 `byte[]`（SHA-256 得 payloadHash），再走签名钩子 → `AwsSigV4AuthApplier` 产出 `Authorization` + `X-Amz-Date`（+ `X-Amz-Security-Token`）。
5. WebClient 发出 → Bedrock。
6. 响应 → `adapter.handleResponse`（converse→OpenAI chat.completion）→ `BedrockConverseUsageExtractor`（camelCase→TokenBillingUsage）→ 计费/频控照旧。

## 4. 决策点（等 robin 拍板）

| # | 决策 | 建议 | 理由 |
|---|---|---|---|
| D1 | Converse vs InvokeModel | **Converse 为主**（一个适配器覆盖全部模型族）；Anthropic 模型可选 InvokeModel 复用 `ANTHROPIC` 适配器（binding 级配置，不写码） | Converse 是 AWS 统一入口；InvokeModel 绑定随时可加，零开发 |
| D2 | 鉴权路径 | **SigV4（AK/SK）为主**；Bedrock API Key（Bearer）零开发即可用（credential type 选 api-key + applier BEARER），写进运维文档 | enum 已预留 aws-auth；API Key 是较新的快路径 |
| D3 | 流式分期 | **P1 不支持流式**：adapter `streamSupported=false` → executor 降级整包 → **合成单 chunk SSE 回给客户端**（D3a）；P2 做 eventstream 解码 | EventStream 是二进制帧，解码 + SSE 桥接是独立工作量；降级要保外部契约（stream 请求必须回 SSE） |
| D3a | 降级形态 | 合成单 chunk SSE（推荐） vs 直接回 JSON（违约） vs 400 拒绝（不友好） | 外部契约优先 |
| D4 | region 单一事实源 | **authConfig.region**；`model.base_url` 留空→按 region 推导；填了→必须与 region 一致（保存时校验） | 签名 region 与端点 region 必须一致，双事实源必漂移；留 base_url 兼容 VPC endpoint / 代理 |
| D5 | sessionToken | 加为**可选字段**（前端小改 ~10 行） | 支持 STS 临时凭据；不要混进自定义 JSON 区（易错） |
| D6 | executor 签名钩子形态 | `UpstreamAuthApplier` 加 `default void sign(UpstreamSignableRequest, HttpHeaders, ctx)` 默认空实现；body 由 executor 统一序列化 | 三个现有 applier 零改；保持「不碰客户端类型」既定边界 |
| D7 | embedding | P3：Titan（有 inputTextTokenCount）/ Cohere（响应无 usage→计费 0 或估算，**待运营确认口径**） | 先保文本对话主线 |
| D8 | 错误映射 | 落一张映射表（Throttling→429 可 failover、AccessDenied→403 不重试、Validation→400、ResourceNotFound→404、ModelError/Internal→5xx）；executor 现有 `upstreamFailure` 已带 status+body，**不改重试/failover 主干** | 错误体解析（message 字段）仅用于排障日志 |
| D9 | 权限绑定 | **零新增端点**→零权限绑定改动 | provider/model/binding/credential 全是既有 CRUD |
| D10 | 测试策略 | SigV4 用 **botocore 离线交叉验证**（管理 venv 装 botocore，假 AK/SK 签同一 canonical request 对拍）；链路用假上游；**未经真实 AWS 环境**（本机无账号）如实标注 | 签名错一位全站 403，必须交叉验证 |
| D11 | 种子凭据 | data.sql 放**占位 AK/SK**（与既有 `ENC:` 密文同流程生成，注明必须换） | 与 JEV 占位密钥先例一致 |

## 5. 详细设计

### 5.1 凭据与签名

凭据（`kb_provider_credentials.encrypted_config`，AES-GCM 密文，解密后 JSON）：

```json
{"accessKey":"AKIA...","secretKey":"...","region":"us-east-1","sessionToken":"(可选)"}
```

requiredFields 已含前三者；sessionToken 见 D5。

`AwsSigV4AuthApplier`（code=`AWS_SIGV4`，credentialTypes=`{AWS_AUTH}`）：

- `sign(UpstreamSignableRequest req, HttpHeaders headers, ctx)`：
  - `X-Amz-Date: <yyyyMMdd'T'HHmmss'Z'>`（UTC，每次请求实时取——签名时间窗 5 分钟，不能缓存）
  - sessionToken 非空 → `X-Amz-Security-Token`
  - canonical request（method/uri/query/headers/payloadHash）→ string to sign（scope = `<date>/<region>/bedrock/aws4_request`）→ signing key（HMAC 链）→ `Authorization: AWS4-HMAC-SHA256 Credential=.../..., SignedHeaders=host;x-amz-date, Signature=...`
  - 时钟源：`Instant.now()`，**必须 UTC**（踩坑点：`LocalDateTime.now()` 会带本地时区）
  - 编码：URI 路径段 RFC3986 编码（`/` 保留）；query 按 key 排序

`AwsSigV4Support`（纯静态函数族，无 Spring 依赖，便于单测）：

- `canonicalRequest(...)` / `stringToSign(...)` / `signingKey(...)` / `authorizationHeader(...)`
- SHA-256 + HMAC-SHA256（`javax.crypto`，JDK 自带，**零新依赖**）

executor 改造（`AbstractUpstreamProtocolExecutor`，最小侵入）：

- `execute()` 里先算 `url = joinUrl(baseUrl, path)`；
- `withBody()`：JSON 路径先把 body 用 ObjectMapper 序列化成 `byte[] payload`，算 `sha256Hex(payload)`，构造 `UpstreamSignableRequest(POST, url, payloadHash)` 交给 `applier.sign(...)`；multipart 路径不签名（Bedrock 无 multipart，保持原样）；
- 发出时用 `BodyInserters.fromValue(payload)`——**必须字节级一致**（hash 什么发什么），这是签名验证的第一雷区；
- `supportsStreaming` 增加 adapter 委托：`adapter.streamSupported(context)` 默认 true，Bedrock 适配器返回 false → 走整包 → 合成 SSE（D3a）。

`UpstreamSignableRequest` record（adapter.upstream 包）：`(String httpMethod, String url, String payloadHash)`——纯值类型，不引任何 HTTP 客户端类型，守住既定边界。

### 5.2 请求适配器 BEDROCK_CONVERSE

| 钩子 | 行为 |
|---|---|
| `resolvePath` | `/model/{RFC3986(upstream_model)}/converse`（`upstream_model` 来自 `kb_models.upstream_model`，如 `anthropic.claude-sonnet-4-20250514-v1:0` 或推理配置 `us.anthropic.claude-...`） |
| `buildRequestBody`（入参 chat.completions 语义） | messages→converse messages：system 角色→`system[0].text`；user/assistant→`content[0].text`（P1 仅文本）；`max_tokens`/`max_completion_tokens`→`inferenceConfig.maxTokens`（缺失默认 1024，与 ANTHROPIC 适配器同口径）；`temperature`/`top_p`→inferenceConfig；`stop`→`stopSequences`；**丢弃** `n`/`stream`/`model`/`penalties`/`response_format`；`top_k` 等透传 `additionalModelRequestFields` |
| `handleResponse` | converse→OpenAI：`output.message.content[]` 文本块拼接为 `choices[0].message.content`；`stopReason` 映射（end_turn/stop_sequence→stop，max_tokens→length，tool_use→tool_calls，content_filtered/guardrail_intervened→content_filter）；补 `id`（Bedrock 不回 id，用 `chatcmpl-<uuid>`）、`created`、`object`、`model=<upstream_model>` |
| `extractUsageFromBody` | usage camelCase → TokenBillingUsage；`cacheReadInputTokens`→cacheReadTokens、`cacheWriteInputTokens`→cacheWriteTokens；缓存加回输入总量（与 Anthropic 口径一致，Converse 的 inputTokens **不含**缓存读写——待实测确认，见风险 R2） |
| `streamSupported` | false（P1） |
| `protocol()` | `{CHAT_COMPLETIONS, MESSAGES, RESPONSES, COMPLETIONS}`（与 ANTHROPIC 适配器对齐） |

### 5.3 用量提取器 BEDROCK_CONVERSE

- `TokenBillingUsage.from()` 不认 camelCase → 专用提取器：`usage.inputTokens/outputTokens/totalTokens/cacheReadInputTokens/cacheWriteInputTokens` → TokenBillingUsage；`billingModes = {TOKEN}`，`calculator = TokenBillingModeCalculator`（照 AnthropicUsageExtractor 模板）。
- Anthropic-on-Bedrock 若走 InvokeModel 绑定：响应是 Anthropic 原生格式 → 直接用 `ANTHROPIC` 提取器，**零新码**。

### 5.4 错误映射（D8）

| Bedrock 错误 | HTTP | 网关处理 |
|---|---|---|
| ThrottlingException | 429 | 现有 UPSTREAM_ERROR + retry/failover 主干照旧（Retry-After 解析已有） |
| AccessDeniedException | 403 | UPSTREAM_ERROR；**不可重试**（签名/权限问题重试无意义）——需确认 failover 判定是否只看 5xx/429 |
| ValidationException | 400 | UPSTREAM_ERROR；适配器保证必填后应极少见 |
| ResourceNotFoundException | 404 | UPSTREAM_ERROR（modelId 写错） |
| ModelErrorException / InternalServerException | 4xx/5xx | UPSTREAM_ERROR + failover |
| ServiceQuotaExceededException | 429/402 | 同 Throttling |

说明：executor 的 `upstreamFailure` 已把 status+body+requestId 带齐，错误体 `message` 字段仅进排障日志，不改主干（`x-amzn-ErrorType` 头解析为可选增强）。

## 8. 风险与未验证项

- **R1** 签名时间窗：网关时钟漂移 >5min → 全量 403。建议 P1 加启动自检（仅文档告警，或发一次 `ListFoundationModels`）。标注未验证。
- **R2** Converse 的 `inputTokens` 是否含缓存读写——影响计费口径，**待真实环境实测**（P1 用假上游无法回答）。
- **R3** 本机无 AWS 账号/凭证：全部链路验证走假上游 + botocore 离线对拍；**未经真实 AWS 环境验证**，上线前须用真实 AK/SK 跑一次连通性冒烟。
- **R4** Cohere embedding 无 usage 回传 → 计费 0 或估算，口径待运营拍板（D7）。
- **R5** P1 流式降级为单 chunk SSE：长响应 TTFT 体验差（整包等完才出首字节），P2 必须补流式。
- **R6** Bedrock 区域可用性：模型×region 矩阵由运营维护，`upstream_model` 填错 → ResourceNotFoundException 404，排障依赖错误体 message。
