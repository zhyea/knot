## 0. 结论先行

**总评：骨架完整度约 85%，网关主链设计质量高（契约钉得死、无 TODO 堆积、无注释尸体），但存在 2 个 P0 级"代码能跑但结果是错的"缺陷，以及 3 个看起来有实际为空壳的能力域。**

| 维度 | 定级 | 一句话 |
|---|---|---|
| 功能能力矩阵 | **B+** | 13 项网关能力 11 项可用；计费主链扎实但**折扣域整体空壳、计费结果零落库** |
| 非功能与性能容量 | **C+** | 全链路同步阻塞在 Tomcat 线程、退避用 `Thread.sleep`；无全局请求超时；无连接池配置落地 |
| 架构成熟度与技术债 | **A-** | 模块边界干净（plugin 红线合规）、命名纪律好、零 TODO/FIXME；债集中在 **knot-dal 零测试 + 24 个 Service 零覆盖** |
| 生产就绪度 | **C** | 零 Dockerfile/零 CI、监控指标**完全不存在**、默认 `KNOT_SQL_INIT_MODE=ALWAYS`、明文默认密钥仅告警 |

## 2. 维度二：非功能与性能容量

| 项 | 现状 | 证据 | 评价 |
|---|---|---|---|
| 并发模型 | **全链路同步阻塞**（Tomcat 线程） | `AbstractGatewayRequestTemplate.java:100-150` | 流式请求在写完前**一直占线程**，长流会耗尽线程池 |
| 重试退避 | **`Thread.sleep` 睡在请求线程** | `GatewayRequestHandler.java:353-363`：JEV `JevBillingJudge.java:125` 同款 | 重试期间线程不可复用；并发 × 退避 = 线程雪崩 |
| DB 读放大 | 1 次请求最多 5 次 Caffeine miss，每个 miss 是**请求线程上的同步 DB 读** | `GatewayDataService.java:93,305-320`（`refreshAfterWrite` 同步刷新） | 冷启动/缓存过期期 DB 压力大 |
| 连接池 | Apache HttpClient 5，建连 5s / 取连接 5s / 读 120s / 总 200 / 每路由 50 | `GatewayUpstreamClientProperties.java:23-59` | **配置合理但 yml 零落地**，运维无从感知与调优 |
| 全局请求超时 | **无**。读超时是"相邻包静默"非整包（注释自陈 `:31-34`）；唯一整体约束 `spring.mvc.async.request-timeout: 600s` | `application.yml:10` | 慢上游可占线程 10 分钟 |
| 存储选型 | `knot.traffic.store` / `knot.load.store`，仅 caffeine/redis 两档，**怪值启动失败** | `StoreModeResolver.java:33-40`、yml `:67,:75` | **合规且设计正确** |
| Redis 策略 | redis 档 fail-hard（503 + STORAGE_UNAVAILABLE） | `RedisCache.java:84-101,129` | 符合 2026-10-15 拍板；但 ERROR 无节流 |
| 异步旁路 | Kafka fire-and-forget，不阻塞链路；残留风险 `max.block.ms=1000` | `KafkaPublisher.java:18-21,74`、`KafkaConfiguration.java:39` | 设计正确 |
| 内存放大 | 插件上下文每个 upstream stage 整份 copy 响应体 | `UpstreamProxyClient.java:199-209` | QPS 高时放大明显；流式恒含 null body 却照样构造 |

**容量结论**：未做压测，无法给 QPS 上限。结构性瓶颈是**线程模型**（同步阻塞 + sleep 退避 + 无全局超时），而非连接池或缓存。按默认 200 连接池与 Tomcat 默认 200 线程估算，**并发长流请求是首要风险**。
