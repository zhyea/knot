# 视频路由规则调试（异步任务链路 + 结算证据）

> 2026-10-30。范围：让路由规则测试抽屉能真正「调试完」一次视频调用——提交拿到任务句柄、轮询到终态、看到产物与失败原因、并对这一次的账做校验。
> 仅设计，未动代码。决策记录见 §9。

## 0. 结论先行

**现状是「发得出去、收不回来」：抽屉能提交视频任务，但拿到的 202 被当最终结果展示，计费校验对视频恒为 skipped。**

设计分三条：

| # | 内容 | 关键判断 |
|---|---|---|
| 1 | **异步链路进抽屉**：识别 202 信封 → 轮询任务 → 终态产物/失败原因 + 时间线 | 识别靠**响应形状**，不靠协议名硬编码；以后别的异步协议自动支持 |
| 2 | **结算落库，让「被告账」存在**：终态结算写 `kb_async_tasks.settlement_json`；查询端点在测试头下回 `knot_extend` | 现在这笔账**只存在于 Kafka 事件里**，任何地方都查不到 → 没有被告，计费校验不可能成立 |
| 3 | **计费校验分族**：verdict 契约补 `upstreamBody`（视频上游响应不是 `{usage}` 形状）；JEV 题组按**计费模式**分族 | 视频上游常不报 usage，token 题组问它「归一化是否正确」会得到无意义答案 |

轮询通道按 2026-10-30 二次拍板走**网关查询端点**（`POST {gateway}/openai/v1/tasks/{task_code}`）：抽屉扮演真实客户端，验证的是自己发出去的那套契约（`Authorization` + `Rule` + `query_url`），与提交同源。

新增一条自检项 `ASYNC_SETTLEMENT_CONSISTENCY`（终态成功 ⟺ 有账），同步链路 SKIP。

## 1. 现状与缺口（实证）

| # | 事实 | 位置 |

**结论：缺口不在「能不能发」，而在「发完之后什么都没有」——状态、产物、账，三样都缺。**

## 2. 目标与非目标

### 2.1 目标

1. 一次视频调试能看到完整生命周期：提交 → 每次轮询 → 终态 → 产物/失败原因。
2. 能区分「异步生效」与「回落同步」两类结果，并指路到根因（档案 / `task_id_path` / 绑定）。
3. 终态后能回答这次调用**是否计费、算了多少、算得对不对**，与同步链路同一套三区（事实 / 自检 / 裁判）。
4. 关抽屉即停：不留后台轮询、不留悬挂请求。
5. 调试走的是**客户端同一条路**——轮询用的是 202 回执里的 `query_url` 与同一套头，契约问题在调试时就能暴露。

### 2.2 明确不做

| 项 | 理由 |
|---|---|
| 在抽屉里改/重试任务 | 属运维动作，异步任务页已有 cancel / retry；调试只看不动 |
| 回调（`callback_url`）调试 | 回推是另一条链路，验证它要把任务与本地接收器配对，独立批次 |
| 视频转码 / 下载 / 预览代理 | 抽屉只给地址与内嵌播放，产物治理不在这里 |
| 改同步链路的 verdict 行为 | `upstreamBody` 是新增可选字段，同步仍走 `{usage}` 口径 |
| 按协议名硬编码异步能力 | 异步是绑定属性（`async_profile_code`），不是协议属性（`任务协议绑定方案-2026-10-28.md §2`） |
| 让普通客户端看到结算账 | 只有带测试头才回 `knot_extend` / `upstream_body`；不加头键不出现 |

## 3. 链路总览

```
① 抽屉提交（Authorization + Rule [+ X-Knot-Test-Return-Usage]）
        │
        ├─ 200 上游体  → 「未拿到任务句柄」：档案没命中 / task_id_path 取不到 → 回落同步
        │                 （抽屉直接指路，这是最高频的配置错误）
        └─ 202 {task_id, status:"queued", query_url}
                │
                ▼
② 轮询 POST {GATEWAY_BASE_URL}{query_url}（同 Authorization / Rule，无 body）
        │   间隔 3s → ×1.5 → 上限 15s；本地上限 10min；关抽屉即 abort
        │   带测试头时，终态响应额外含：
        │     knot_extend  {usage, billing}      ← 被告账（settlement_json）
        │     upstream_body {…上游终态原文…}     ← 重算基准（terminal_body）
        ▼
③ 终态 completed → 产物（result_url / result_urls）+ 耗时
   终态 failed    → error{code,message}；**本任务不计费**（状态机 SETTLE）
        │
        ▼
④ 计费校验（仅 completed 且有 knot_extend 时）
   POST /api/routing-rules/{id}/test/billing-verdict
   { protocol, targetCode, requestBody, upstreamBody, knotExtend, taskStatus, stream:false }
        │
        ▼
   影子重算（VIDEO 提取器，读 upstream_body.usage + request 维度）
   → 自检八项（含 ASYNC_SETTLEMENT_CONSISTENCY）
   → JEV（VIDEO 题组）→ 三区
```

## 4. 后端设计

### 4.1 结算与上游终态双落库

`kb_async_tasks` 加两列（`result_json` 之后）：

```sql
terminal_body   LONGTEXT DEFAULT NULL
  COMMENT '上游终态查询响应原文（计费复现与排障依据；SETTLE_BILLED / POLL_FAILED 时写）',
settlement_json JSON     DEFAULT NULL
  COMMENT '终态结算快照：knot_extend 同形（usage + billing）；失败/超时不计费故为 NULL'
```

**为什么两列都要**：

- `settlement_json` 是**被告**（网关当次算出的账）；
- `terminal_body` 是**重算基准**。视频提取器从**上游响应**取输出时长与产物数（`VideoUsageFacts.of(body, requestBody)` 的 `body` 参数），请求体只提供分辨率 / 声音 / 参考图等维度。这份响应此前用完即弃（只进 Kafka），**不落它，影子重算就没有输入**——`COST_FORMULA_MATCH` 与 `GATEWAY_RECOMPUTE_MATCH` 只能恒 SKIP，「校验」名不副实；
- 附带收益：上游终态原文可事后复核（换供应商 / 字段漂移时，第一现场不再只存在于 Kafka 里），计费校验也不再依赖「抽屉当时是否在场」。

**为什么与 `result_json` 分开放**：`result_json` 是**客户端契约**（轮询 / 回调原样吐出 `result`），结算账与上游原文都不能混进去——否则每个普通客户端都会看到内部账目，并破既有 `result` 形状。

**写入点唯一：`AsyncTaskRunner.finish`**，且与终态**同一条 UPDATE**（`AsyncTaskMapper.complete` 增加两列）：

- 先算钱再落终态的顺序不变（`charge` 抛异常 → 不落终态 → 下一轮重试），已付费的那次不会因为写失败而丢账；
- 若拆成「complete 后再 UPDATE 一次」，就会出现**终态已落、账没落**的窗口，重试也不会补——这是资损方向；
- `SETTLE_BILLED`：两列都写；`SETTLE`（失败/超时/取消）：`terminal_body` 写（有响应时）、`settlement_json` 传 null，不写假账。

序列化 `settlement_json` 直接复用 `KnotExtendPayload.of(usage)`（knot-adapter），保证与同步链路 `knot_extend` **同形**——前端提取逻辑、JEV state 组装都不用分叉。

### 4.2 读侧：网关查询端点，测试头下附两段

| 层 | 改动 |
|---|---|
| `AsyncTaskQueryResponse` | 加 `@JsonInclude(NON_NULL) @JsonProperty("knot_extend") KnotExtendPayload knotExtend`；加 `@JsonInclude(NON_NULL) @JsonProperty("upstream_body") Map<String,Object> upstreamBody` |
| `GatewayTaskController.query` | 多读一个 header（`X-Knot-Test-Return-Usage`）传进 Runner；仍只做「绑定入参 + 委托 + 404 翻译」 |
| `AsyncTaskLookupRunner.lookup` | 增 `boolean returnDetail`；为 true 且行上有值时填充两字段 |
| `AsyncTaskViewSupport` | 两段的解析放这里（对外投影的唯一出口，与轮询/回调共用纪律） |
| `AsyncTaskDto` / Mapper `TaskColumns` / `AsyncTaskConverter` | 加两列（详情投影已有全列查询，补映射） |

**为什么 `upstream_body` 用 `Map`**：它是上游动态 payload，形状由供应商决定，属 `10-backend-java.md §5.1` 明确允许的三类场景。`knot_extend` 是本项目定义的结构，用 record。

**头不加会怎样**：两个键都不出现（`NON_NULL`），普通客户端契约零变化。这与同步链路既有行为完全一致——`X-Knot-Test-Return-Usage` 本来就是「我要消费详情」的开关。

**为什么不用管理端查库**（2026-10-30 二次拍板前的备选，记下来避免反复）：查库能顺手拿到 `attempts` 与计费规则版本，但代价是**调试绕开了客户端真实路径**——`query_url`、对外状态词、Rule 归属 404 全都不经过，正是这次要验证的东西。选网关后，`attempts` 要回到异步任务页看，这是明确取舍。

**体积**：两段只在测试头下出现；视频查询响应通常 < 10KB，轮询每 3~15s 一次不构成压力。终态之后两段恒定，前端不再重复渲染历史值。

### 4.3 verdict 契约：补 `upstreamBody` 与 `taskStatus`

`RoutingBillingVerdictRequest` 加两个可选字段：

| 字段 | 来源 | 用途 |
|---|---|---|
| `Map<String,Object> upstreamBody` | 查询响应的 `upstream_body` | 视频的产物/时长都在这里，是影子重算的输入；同步链路为空则退回 `{usage}` 口径 |
| `String taskStatus` | 查询响应的 `status`（对外词 `completed/failed/…`） | 支撑 §4.4 的一致性自检；同步链路为空 |

编排层一行收敛：

```java
// 同步链路：body 只有 usage 对象；异步视频：整包查询响应（时长/产物/usage 都在里面）
Map<String, Object> upstreamRawBody = req.upstreamBody() != null
        ? req.upstreamBody()
        : Map.of("usage", upstreamUsage);
```

`BillingFactAssemblyInput` / `BillingFactAssembler` 已经是通用入参，**不需要改**（§1 事实 10）。

`stream` 固定 `false`：异步任务没有流式。

> `taskStatus` 用**对外词**判断，不用库里的 0~5 码：抽屉拿到的就是对外词，再造一份码表等于把 `AsyncTaskViewSupport.displayStatus` 抄第二遍。

### 4.4 自检第 8 项：`ASYNC_SETTLEMENT_CONSISTENCY`

| 项 | 判据 | 失败含义 |
|---|---|---|
| `ASYNC_SETTLEMENT_CONSISTENCY` | `completed` ⟺ 有被告账；`failed` ⟺ 无被告账 | 成功没落账（漏收）或失败落了账（错收），两个方向都是资损 |

- 输入：`BillingFactSubject` 加可空 `taskStatus`；`queued/processing/unknown` 与同步链路（null）一律 **SKIP**，不充 PASS；
- 现状语义是「失败不计费」（`EXPIRED/CANCELLED` 对外都投影成 `failed`），写死在这一项里；将来若改为失败也计费（算力已消耗），**只改这一处**并扩测试。

### 4.5 JEV 题组按计费模式分族

现有四题是按 token 写的（`usage_parse_ok` 里明确对照 `completion_tokens` 等）。视频上游多数**根本不报 usage**，用同一套题会得到「依据不足 / 瞎猜」的答案。

| 计费模式 | 题组 |
|---|---|
| TOKEN / EMBEDDING | 现状四题，不动 |
| VIDEO | `usage_parse_ok`（对照上游查询响应的产物/时长，不套 token 公式）、`rule_match_ok`（同名同选项）、`cost_plausible`（时长 × 分辨率 × 声音档位与账是否相称，语义嗅探）、`risk_level` |

分族依据取 `BillingFactRuleRef.billingMode()`，**不取协议名**：IMAGE/AUDIO 后续接入时按同一判据扩展，避免「协议 × 题组」的笛卡尔积。

`state` 里 `requestAttributes` 只放计费维度键（`duration` / `size` / 生成声音开关 / 是否带输入视频），不放整个请求体（§6.6 体积纪律）。

### 4.6 校验与边界

| 项 | 口径 |
|---|---|
| 视频请求体带 `stream: true` | `ModelApiProtocolEnum.streamSupported()==false` → 提交前后端 400 / 前端拦，不进流式分支 |
| 轮询地址 | 只信 202 回执的 `query_url`（相对路径），前端不拼 `/openai/v1/tasks/...`（唯一来源 `AsyncTaskAcceptedResponse.TASKS_PATH`） |
| 轮询鉴权 | 与提交同源：`Authorization` + `Rule`；规则不匹配定位不到任务 → 404，抽屉按「规则不一致 / 句柄失效」提示 |
| 测试头 | `X-Knot-Test-Return-Usage: true` 复用既有常量；它是「回消费详情」的开关，与同步链路同一语义，不新增头 |
| `terminal_body` 体积 | 不做压缩、不做截断（截断会让重算结果漂移）。将来若出现超大响应，加长度上限并**在自检里显式 SKIP**，不得静默截断 |
| 命名 | 无新 Controller；投影落 `AsyncTaskViewSupport`；composable 名 `useAsyncTaskPolling` |

## 5. 前端设计

### 5.1 提交响应的三态分流

`runBufferedTest` 拿到响应后按**形状**判：

| 形状 | 分流 |
|---|---|
| `stream:true` 请求体 | 既有流式链路，不变 |
| 202 + `task_id` + `query_url` | 异步链路（新增） |
| 其他 | 既有同步链路，不变 |

判定函数 `isAsyncTaskAccepted(status, body)` 放 `utils/routingTestPayload.ts`，纯函数、可单测。

**「未拿到句柄」提示**：协议为 `VIDEO_GENERATIONS` 且响应不是 202 信封时，在概览区给一条可执行提示——

> 本次未生成任务句柄，请求按同步返回。检查：① 模型该协议的绑定是否选了任务协议（`async_profile_code`）；② 档案的 `task_id_path` 是否能在上游创建响应里取到 ID（可在「异步任务档案 → 试跑」验证）。

判据只有「协议是视频 + 无 task_id」两条，不猜上游字段。

### 5.2 新 composable：`useAsyncTaskPolling`

**只抽状态与定时，不抽编排**（与 `useStreamBuffer` 同一纪律）：发请求、判错误、触发裁判仍留在抽屉。

```ts
useAsyncTaskPolling({
  taskCode: () => string | null,               // 202 回执里的 task_id
  queryUrl: () => string | null,               // 202 回执里的 query_url（相对路径）
  buildHeaders: () => Record<string,string>,   // 复用 buildRequestHeaders（含测试头）
  queryTask: (url, headers, signal) => Promise<{status, data}>,  // 注入，便于单测替换
  onTerminal: (payload) => void,               // 抽屉在这里触发计费校验
})
```

| 状态/动作 | 说明 |
|---|---|
| `taskStatus` | 直接用响应里的对外词 `queued/processing/completed/failed/unknown` 展示（中文提示文案按对外词写），**不建码表** |
| `pollCount` | 本次调试发起的查询次数（外部词：`attempts` 只有管理端任务详情有，这里不冒充） |
| `elapsedMs` | 从提交时刻起算，1s 刷新 |
| `timeline` | `{at, status, elapsedMs, error?}[]`，每次查询一行 |
| `result` / `error` | 响应里的 `result`（`result_url` / `result_urls`）与 `error{code,message}` |
| 退避 | 首查 1.5s，之后 3s 起 ×1.5，cap 15s |
| 本地上限 | 10min 到点停止，置 `localTimeout`，文案「任务仍在运行，可稍后在异步任务页查看」+ 句柄 |
| 令牌 | `pollToken` 自增，新测试/关抽屉后到达的响应一律丢弃（同 `verdictToken`） |
| 终止条件 | `completed` / `failed` / 404 / 401·403 / 本地超时 / 用户停止 |
| 可重试错误 | 网络错误与 5xx 不停，记 `lastError` 后按退避继续 |

**资源释放走既有唯一入口**：`disposeTestResources()` 增调 `disposeAsyncPolling()`（清 timer + abort in-flight）；`@closed` 与 `onBeforeUnmount` 都只走它，不各抄一遍。

### 5.3 响应区新增「异步任务」页签

仅当本次提交返回 202 时出现，排在「概览」之后：

| 区块 | 内容 |
|---|---|
| 状态条 | 对外状态 + 已用时 + 本次调试查询 N 次 + 「立即查询」/「停止」 |
| 时间线 | 提交 T0 → 每次查询（状态、耗时）→ 终态（总耗时） |
| 产物 | 内嵌 `<video controls>`（首个产物）+ 全部 URL 列表（多产物逐个可复制） |
| 失败 | `error.code` + `error.message` + 「本任务不计费」 |
| 计费校验 | 复用 `RoutingBillingVerdictPanel`（三区不变） |

「请求预览」区补一行**轮询 curl**（用回执里的 `query_url` 拼，带测试头），排障时可直接贴给别人。

### 5.4 计费校验的触发点

- 只在 `completed` 且 `knot_extend` 在场时发起；`failed` 不发起（本就不计费，硬跑校验只会得到「无被告」的噪音）；
- `requestBody` 传**本次提交给网关的原始体**（不是上游转换体）；
- `knotExtend` = 终态响应的 `knot_extend`（`captureKnotExtend` 直接复用——形状与同步链路同构）；
- `upstreamBody` = 终态响应的 `upstream_body`；`taskStatus` = 响应 `status`；
- `protocol` 传当前协议，`stream:false`。

### 5.5 降级文案（三态，不许混）

| 情形 | 文案 |
|---|---|
| 终态无 `knot_extend` | 「本次响应未返回结算账目（任务早于本版上线 / 关掉了「临时返回消费详情」），计费校验不可用」 |
| 终态有账但校验请求失败 | 现有 error 态 + 具体原因 |
| 本地超时未到终态 | 「任务仍在运行，计费在终态才发生，暂无法校验」 |

### 8.1 P1 实测记录（2026-10-30）

九条用例里 1~5 已落成测试，实测中发现三处设计稿没写到的事，按「代码为准、回写文档」处理：

1. **两个相邻 `String` 会传反**：`complete(...)` 原本要加 `terminalBody` / `settlementJson` 两个参数，两者都是可空字符串，写反了不报错，只是静默变成「这笔任务从来没有账」。改成打成一个 `AsyncTaskTerminalDto`（`terminalBody` + `settlementJson` + `EMPTY` + `isEmpty()`），调用方拿不到「位置」就没有传反的机会。
2. **空账会落成字面量 `"null"`**：`KnotExtendPayload.of(usage)` 在 `usage.isEmpty()` 时返回 `null`，直接 `JsonKit.toJson(payload)` 得到 4 个字符的字符串，写进 JSON 列后读出来是「有账目字段、内容为 null」——被第 8 项自检读成「有账」，与「这次不该收钱」的结论正好相反。现修为 `payload == null ? null : toJson(payload)`，并用 `emptyAccountingWritesSqlNull` 钉住。
3. **控制器参数顺序按 Runner 对齐**：`query(authorization, rule, taskCode, testReturnUsage)`——路径参数在可选头之前。原先写反，`GatewayTaskControllerTest` 三条用例直接以「参数错位」的形式红了（`seenTaskCode == null`），说明这类壳层测试确实在起作用。

### 8.2 P2 实测记录（前端）

1. **`isAsyncTaskAccepted` 改成 `parseAsyncTaskAccepted`**：设计稿写的是布尔谓词，但调用方真正需要的是 `task_id` + `query_url` 两个值——先判 true 再各取一次，等于把「202 且字段齐全」这个判据写两遍。改成一个函数直接返回 `{taskCode, queryUrl} | null`，没有句柄就没有对象。
2. **`postGatewayJson` 增加可选 `signal`**：设计稿写「abort in-flight」，而 XHR 通道原本没有中止能力——那样「已停止」只是界面文案，网关上仍有一串查询在跑。补 4 行（`signal.addEventListener("abort", () => xhr.abort())` + `xhr.onabort` 抛 `AbortError`），不去编造「已经中止」。
3. **网关基址导出为 `gatewayBaseUrl()`**：`query_url` 是相对路径，只有网关基址能补成绝对地址。原本基址是 `useTestRequestComposition.ts` 的模块私有常量，自己再读一次 env 就会得到第二份基址。导出后 `requestUrl` / curl 预览 / 轮询三处共用一份。
4. **轮询 curl 放在异步页签内**，不是「请求预览区再加一段」：预览区那段是**提交**用的 curl，两段 curl 相邻会让人分不清哪个才是当前该跑的。
5. **`requestBody` 传的是剥离 `model` 之后的网关体**：与发送时同一份（`stripModelField`），而不是模板原文——否则裁判看到的请求体与实际发出去的不是同一个。
6. **预设只补了 `builtin-video-generations-kling`**，没有再加一条 `builtin-video-generations`：后者与既有的 `builtin-video-generations-basic` 完全重复。**也没有种子化异步任务档案**——档案的 `task_id_path` / 轮询 MVEL 与上游地址强绑定，凭空种一份等于给用户一个必然跑不通的档案，比没有更糟。

### 8.3 P3 实测记录（JEV 题组）

- 分族依据取 `BillingFactRuleRef.billingMode()`，不取协议：`VIDEO_GENERATIONS` 协议下若错配了一条 TOKEN 规则，该问的是「规则配错了」，按协议分族会把这个信号盖掉。
- 选项键两族完全一致（`CORRECT` / `INCORRECT` / `INSUFFICIENT_EVIDENCE` 等），只有 `instructions` 变——响应解析与摘要生成因此不必分叉。
- `requestAttributes` 对视频**多放行分辨率与声音开关**（分档键），但**不放 `video` / `image`**：它们的值是带签名的产物地址，放进来等于把上游 URL 送进第三方模型。「有没有输入视频」的权威仍是 `state.produced.usage.input.video_seconds`（唯一推导入口 `VideoUsageFacts`），没有在裁判里算第二遍。
- 视频 `cost_plausible` 明确写「不要试图反推或编造单价」：裁判手里没有价目表，让它算单价只会得到编出来的数字。

## 10. 风险

1. **两列会被清理任务一起带走**：清理按终态 + 保留窗口删行，账与上游原文随行删——与今日 `result_json` 同命。若将来要对账，应在清理前归档（本方案不扩范围，登记为缺口）。
2. **测试头是「看账」的开门条件**：任何持有消费者密钥的调用方带该头就能看到**自己这次**的账与上游原文——与同步链路现状一致（同步也只看这个头），不是新增暴露面；但它确实比「只给管理端看」宽。若日后要求收窄，正确做法是给测试头加管理端专用凭据，而不是在这条链路上打补丁。
3. **长任务（>10min）在抽屉里看不到终态**：本地超时是刻意的（不把抽屉变成后台监控），文案给句柄 + 异步任务页出口。
4. **视频上游不报 usage 的模型**：输出时长只能来自请求体或上游响应其他字段，`USAGE_NOT_EMPTY` 可能判 0 —— 属提取器口径问题，不是调试链路问题；冒烟要用真实模型族验证一次（Kling / ARK 各一）。
5. **`terminal_body` 存上游原文**：可能含上游内部字段与带签名的产物地址。它只在测试头下出现（不对外、不进 `result`），敏感级别等同 `result_json`；写入前不脱敏，因为脱敏会让重算口径失真——要脱敏就得连影子链一起改，不做。
6. **假上游冒烟不能证明真实字段**：真实 Key 下需复核 `result_urls` 多产物、`outputSeconds` 取值与账目是否自洽（登记为上线后第一批）。
