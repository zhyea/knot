## 0. 结论先行

| # | 结论 |
|---|---|
| 1 | **两张表，不是一张**：`kb_async_task_profiles`（「怎么查上游」的模板，一家上游一行）+ `kb_async_tasks`（一次提交一行）。新增异步上游 = 加一行档案 + 绑定引用，**不改表、不改代码**。 |
| 2 | **DB 为唯一真相源**，不再以 Redis/Caffeine 为主存储。原方案「Redis 不可用即 503」会把上游可用性问题放大成网关不可用；落表后任务可查、可恢复、可归档 —— 契合「数据不丢失高于性能」的红线。Redis 退为可选加速。 |
| 3 | **任务类型用 `protocol` 表达，不另设 `task_type`**：protocol 已是「这次调用是什么能力」的唯一事实，再加一列就是同一件事写两遍，必然漂移。 |
| 4 | **轮询口径在提交时快照进 `poll_spec_json`**：档案后续改了也不影响在途任务，保证「同一笔任务无论何时完成，算法与口径可复现」。 |
| 5 | **调度用 Spring `@Scheduled` + cron**（robin 2026-10-27 定调、2026-10-28 改为 cron）：cron 只决定扫描节拍，行级 `next_poll_at` 决定真实节奏；cron 不保证串行，故每个节拍方法带一次性守卫跳过重叠拍；多节点靠 DB 原子 claim，不引中间件。 |
| 6 | **状态转移收成一张表，不散在 if 链里**：9 事件 × 6 状态 → `AsyncTaskStateMachine`（纯函数，可穷举）。两条硬规则——终态冻结、只有成功计费——由 `AsyncTaskStateMachineTest` 8 例守门，**不靠 review**。见 §3.1。 |
| 7 | **一笔任务发 1 + N 条流量事件，不压成 1 条**（robin 2026-10-28 拍板路 B）：上游真实开销就是 1 次提交 + N 次查询，压成 1 条等于把 N-1 次调用、每次查询时刻、中间失败全部从数仓里抹掉。语义落在事件的 `task_phase` / `task_terminal` / `task_query_seq` 上，模板层**零判断**。Kafka 留事实、数仓裁视图——单向，只能往多留事实的方向选。见 §3.2。 |

## 1. 为什么拆成「档案 + 实例」两层（通用性的根）

异步任务的差异全在「怎么查上游」，一件都不能硬编码：查询方法、路径模板（`/v2/query/.../{task_id}` vs `/tasks?task_ids={task_id}`）、状态取值（`succeeded` vs `completed` vs `SUCCESS`）、产物位置（`content.url` vs `data[0].outputs[0].url`）、产物时效（30 天 / 7 天 / 24 小时）。

若把这些塞进任务表每一行 → 冗余且无法复用；若塞进 `kb_model_api_bindings`（按 model×protocol）→ 同一家上游的文生/图生两条绑定要各写一遍。故独立成**档案表**，以 `profile_code` 被多条绑定引用。

**异步与否是「绑定」的属性，不是协议的属性**：同为 `VIDEO_GENERATIONS`，MiniMax H3 异步、其它模型可能同步 → 判定开关放在 `kb_model_api_bindings.async_profile_code`（为空 = 同步，存量行语义不变）。

## 2. 表结构

### 2.1 `kb_async_task_profiles`（查询口径档案）

| 列 | 作用 | 备注 |
|---|---|---|
| `profile_code` | 档案编码（唯一） | Kling 建议 `KLING_TASK`，MiniMax 建议 `MINIMAX_VIDEO_TASK` |
| `protocol` | 所属协议，用于绑定一致性校验 | 不是主键，允许同协议多档案（Kling / MiniMax 都在 `VIDEO_GENERATIONS`） |
| `query_method` / `query_path` | 查询方法与路径模板 | 唯一占位符 `{task_id}`，可出现在 path 或 query 段；拼装仍走 `UpstreamUrlSupport`（唯一 URL 工具）。⚠ 曾有的 `{external_task_id}` 已于 2026-10-28 废除，档案里再写它会**直接抛**而不是静默查不到 |
| `task_id_path` | create 响应取上游任务 ID 的 **MVEL 取值表达式** | `data.id`；取不到回 `null` → 回退同步链路 |
| `status_path` / `status_succeeded` / `status_failed` / `status_running` | 终态判定：一个取状态 + 三个 **MVEL 布尔表达式** | 变量 `status`（`status_path` 取到的文本）与 `body`（整个查询响应）。多值写 `['a','b'] contains status`（MVEL **没有** `in (...)` 元组语法）；`status_running` 为空 = 除成功/失败外一律非终态 |
| `result_path` | 终态产物 URL 的 **MVEL 取值表达式** | `data[0].outputs[0].url` |
| `result_expires_days` | 产物有效期 | Kling 30 / MiniMax 7 / Sora 1 |
| `poll_interval_ms` / `poll_backoff_base_ms` / `poll_backoff_max_ms` / `max_attempts` / `timeout_ms` | 轮询参数 | 与 `BackoffCalculator` 同口径；两个上限先到先生效 |

### 2.2 `kb_async_tasks`（任务实例）

| 组 | 列 | 说明 |
|---|---|---|
| 身份 | `task_code`（唯一，对外句柄）、`profile_code`、`protocol` | 客户端只认 `task_code` |
| 上游 | `upstream_task_id` | create 响应里取到的上游任务号，查询只用它。**不再存自造的外部 ID**（2026-10-28 删 `external_task_id`：任务行本来就在本表，DB 丢了反查也没处回填） |
| 状态机 | `status`（整型码，见 §2.3）、`attempts`、`next_poll_at`、`last_polled_at` | 见 §3 |
| 并发 | `claim_id`、`claim_expires_at` | 见 §4.2 |
| 快照 | `request_json`、`poll_spec_json`、`context_json` | **三者缺一不可**：请求体是提取器的唯一输入；口径快照保证可复现；上下文用于重建计费与发 Kafka |

### 2.3 两处刻意的取舍

- **状态用 `TINYINT` 存 `AsyncTaskStatusEnum.code()`**（2026-10-28 由 `VARCHAR(24)` 存 `name()` 翻案）：
  0-PENDING 1-POLLING 2-SUCCEEDED 3-FAILED 4-EXPIRED 5-CANCELLED。
  原取舍「字符串自解释、省一层字典」依然成立，翻案是因为另外两条更硬：
  ① `idx_async_tasks_due(status, next_poll_at)` 是轮询扫描入口且 status 是首列，`'PENDING'` 连长度前缀
  9 字节、TINYINT 1 字节，同 buffer pool 下索引页能装近两倍条目；② 全库其它状态列都是 TINYINT，
  两种存法并存让人要记两套规则。
  ⚠ **整型的真风险不是「不可读」，而是「撞 code」**——两个常量给同一个号，数据写进去就不可区分、
  不可恢复。四道护栏：code 显式声明且**只增不改、不复用废号**；**禁用 `ordinal()`**；
  `AsyncTaskStatusEnumTest` 钉死 0~5（唯一钉数值的地方）；DB 加 `CHECK (status BETWEEN 0 AND 5)`。
  SQL 里的「在途态」谓词由 Java 传 `inFlightCodes` 参数，**不写魔法数字**（写了就没人会回来改）。
  ⚠ 迁移顺序：**先转数据再 MODIFY 列类型**，反了会把 SUCCEEDED 截断成 0=在途 → 重新轮询 → 重复计费。
- **上下文整体进 `context_json`，不铺 12 个列**：凡是不进 `WHERE`/`ORDER BY`/索引的，一律不占列 —— 路由快照、命中快照、追踪信息随协议演进而变，铺列会让每次加字段都要改表。

## 3. 状态机（通用，与业务无关）

```
                 ┌────────── 上游瞬时失败 / 非终态 → 退避，attempts++，推 next_poll_at
                 │                                    （超过 max_attempts 或 expires_at → EXPIRED）
create 成功 ──► PENDING ──► POLLING ────────────────► SUCCEEDED  （终态：计费 + 发一条流量事件）
                  │            │
                  │            └──────────────────► FAILED     （终态：不计费 + 发错误事件）
                  │                                  EXPIRED    （终态：同上，error=TASK_TIMEOUT）
                  └──► CANCELLED（客户端主动取消 / 上游任务已不可查）
```

- `PENDING` 与 `POLLING` 分开：运维一眼能分辨「创建后从未被轮询过」（poller 未接手）与「正在轮询」。
- 终态后 `next_poll_at` 置 `NULL`，天然退出扫描集。
- **终态转换必须 CAS**：`UPDATE ... SET status=? WHERE id=? AND status IN (:inFlightCodes)`，影响行数 = 1 才发 Kafka 事件 —— 这是「一条任务一条终态事件」的幂等闸门。

### 3.1 落地形态：`AsyncTaskStateMachine`（2026-10-28）

改造前「哪些转移合法」这件事散在四处：`AsyncTaskStatusEnum#inFlight()`、三条 SQL 里各写一遍的
`status IN (:inFlightCodes)`、以及 `AsyncTaskPoller#process` 的 if 链。想回答「哪些事件会落终态」
要顺读 40 行；加一个事件（比如取消）要同时改判断、改码、改话术，漏一处**没有任何编译期提示**。

现在收成一个纯函数 + 一张表：

```java
AsyncTaskTransition transition(AsyncTaskStatusEnum from, AsyncTaskEvent event)
// → record AsyncTaskTransition(from, event, to, Action{RESCHEDULE|SETTLE_BILLED|SETTLE|REJECT})
```

| 事件 | 错误码 | 去向 | 动作 |
|---|---|---|---|
| `POLL_RUNNING` | — | `POLLING` | `RESCHEDULE` |
| `QUERY_ERROR` | — | `POLLING` | `RESCHEDULE` |
| `POLL_SUCCEEDED` | — | `SUCCEEDED` | **`SETTLE_BILLED`** |
| `POLL_FAILED` | `UPSTREAM_TASK_FAILED` | `FAILED` | `SETTLE` |
| `RESULT_MISSING` | `UPSTREAM_RESULT_MISSING` | `FAILED` | `SETTLE` |
| `SNAPSHOT_INVALID` | `TASK_SNAPSHOT_INVALID` | `FAILED` | `SETTLE` |
| `ATTEMPTS_EXHAUSTED` | `TASK_TIMEOUT` | `EXPIRED` | `SETTLE` |
| `TIMEOUT` | `TASK_TIMEOUT` | `EXPIRED` | `SETTLE` |
| `CANCEL` | `TASK_CANCELLED` | `CANCELLED` | `SETTLE` |

**两条硬规则**（都由穷举测试守门，不是靠 review）：

1. **终态冻结**：`from == null || !from.inFlight()` 一律 `REJECT`。`PENDING` 与 `POLLING` 共享同一张表
   （差别只是首次查询后提升为后者），所以表只有 9 行。这条与 SQL 的终态 CAS 是**同一事实的两层执行**：
   状态机管「不该发这个事件」，CAS 管「两节点同时发时只有一个赢」。实测印证了两层互为冗余——
   去掉 `inFlight()` 守卫后 `AsyncTaskPollerTest` 14 例**全绿**（CAS 已挡在前面），只有穷举测试能咬住。
2. **只有成功计费**：`SETTLE_BILLED` 只挂 `POLL_SUCCEEDED`。多挂一条 = 资损，少挂一条 = 漏收。
   `AsyncTaskStateMachineTest#onlySuccessBills` 断言 `EnumSet.of(POLL_SUCCEEDED)`；
   `#errorCodeMatchesAction` 是第二道不变量——**计费动作不该携带错误码**。

**构造期校验**：`rules()` 遍历 `AsyncTaskEvent.values()`，缺规则直接抛 `IllegalStateException` →
**漏登记会启动失败**，而不是运行到那个事件时悄悄落个错状态。

**错误码挂在事件上**，不挂在分支里：`finish(..., event.errorCode(), ...)` 一处取值，杜绝「同一个超时
在两个分支里写两个码」。

⭐ **超时也走状态机**（本次顺带修掉的真缺口）：`expireTimedOut()` 原先是批量 `UPDATE ... SET status='EXPIRED'`，
**绕过状态机与 `finish`** → 超时任务不发终态事件 → 「超时」这个结局在数仓里完全不存在。
改为 `store.listExpired(now, limit)` 取行 + 逐条 `apply(..., TIMEOUT)`。代价是牺牲一次性 `UPDATE` 的吞吐，
换来「任何进入终态的行都恰好发过一条终态事件」。

⚠ **一处已知残留**：`SNAPSHOT_INVALID`（`context_json` 都解析不出来）时 `finish` 里的 `context == null` 分支会
直接返回——行落库了（`error_code=TASK_SNAPSHOT_INVALID`），但**发不出终态事件**。这不是遗漏而是边界：
流量事件信封需要 `traceparent` / 规则 / 消费者，全部来自 `AsyncTaskContext`，没有它连事件都构造不出来。
所以这类任务只能靠 `SELECT ... WHERE error_code='TASK_SNAPSHOT_INVALID'` 排查，**不要指望数仓里能看到它**。
根因在写快照那一刻（序列化失败），不在终态侧。

### 3.2 流量事件：一笔任务发 1 + N 条（路 B，robin 2026-10-28 拍板）

**为什么改**。一次异步请求在上游的真实开销是 **1 次 create + N 次 query**（N 由产物耗时 ÷ 轮询间隔决定，
视频任务可达数百）。原方案在提交时**抑制**流量事件，只由轮询器发一条终态——等于把「1 + N」压成「1」：

| 丢掉的事实 | 后果 |
|---|---|
| 提交那次 create 调用 | 上游调用总量少算 1 次；提交侧错误（如 task_id 解析失败）无法归因 |
| 中间 N-1 次 query | 上游调用总量少算 N-1 次；**上游稳定性对异步链路全盲**（「重试 5 次才成功」与「一次成功」长得一样） |
| 每次查询的时刻 | 产物延迟分布算不出来，只有「最终耗时」一个数 |

路 A / 路 B 的分野就在这：

| | 路 A（抑制） | **路 B（采用）** |
|---|---|---|
| 模板层 | 需要钩子 `suppressesTrafficEvent` + 唯一出口里的判断 | **零判断**，钩子整体删除 |
| 事件条数 | 1 条 | 1 + N 条 |
| 语义在哪 | 网关的分支判断里 | **数据里**（`task_phase` / `task_terminal` / `task_query_seq`） |
| 加新阶段（取消 / 续期） | 改判断、改码、改话术 | 只加一个枚举值，模板层不动 |
| 数仓成本 | 低 | 高（中间事件也要落） |

**为什么接受数仓成本**：Kafka 保留的是**原始事实**，粒度取舍是数仓的事——真嫌多，一句
`where task_terminal = true` 就能退回路 A 的视图；反过来路 A 丢掉的中间事实，事后无论用什么 SQL 都补不回来。
「事实可丢、视图可裁」是单向的，只能往「多留事实」的方向选。

**落地形态**（`GatewayTrafficMsgDto.TaskTrace`，走 context 属性传递）：

```java
TaskTrace.submit(taskCode)                  // 提交：phase=submit, terminal=false, seq=null
TaskTrace.query(taskCode, seq, terminal)     // 查询：phase=query, seq=k, terminal 由状态机结果决定
```

| 事件 | 谁发 | 带 usage | `task_terminal` |
|---|---|---|---|
| 提交（202） | `GatewayRequestHandler.applyUsageAccounting` → 模板 `publishTraffic` | 否 | `false` |
| 中间查询（还在跑 / 查询失败重试） | `AsyncTaskPoller.apply` 的 `RESCHEDULE` 分支 | 否 | `false` |
| 终态查询（成功 / 失败 / 超时） | `AsyncTaskPoller.finish` | 仅成功那次 | `true` |

**标记归属：写在 `AsyncTaskSupport.submitIfAsync` 里，不在请求链路上**（2026-10-28 收口）。

一开始这三行写在 `GatewayRequestHandler` 里（`envelope` → 取 `task_id` → `putAttribute`），
结果是同步链路为了发一条埋点，必须 `import GatewayTrafficMsgDto` 并认识 `TaskTrace` 的形状。
搬进 `submitIfAsync` 之后：

- `GatewayRequestHandler` 对事件格式**零感知**，它对异步的全部认知是「`submitIfAsync` 返回非 null 就回 202」；
- 提交标记与轮询侧发的查询 / 终态标记出**同一个包**，口径不可能漂移；
- 请求链路为异步做的事从「判定 + 落库 + 打标」降到「判定 + 落库」。

⚠ 换句话说：路 B 省掉的不只是模板层的钩子，**还有请求链路对事件格式的依赖**。这两笔要一起算，
否则容易得出「路 B 只是把 3 条压成 1+N 条」的错误结论。

守门 `AsyncTaskSubmitStampTest`（2 例）：正向验「提交成功 → context 上带 `phase=submit`，
且 `task_code` 与回给客户端的信封同一个」；反向验「判定不成立 → 不留任何标记」。
后者是必须的——标记漏到同步请求上，数仓按 `task_phase is null or = 'submit'` 统计客户端请求数会静默算错。

⚠ **`REJECT` 不发事件**：那行已由别的节点发过终态，我们的查询属重复劳动，记了会让上游调用数虚高。
宁可少记一次，也不让同一个 `task_code` 出现两条终态。

⚠ **schema 升 1.1**：字段层面纯追加，但消息基数变了——按 `count(*)` 当请求数写的消费逻辑会静默放大。
数仓聚合口径（客户端请求数 / 上游调用数 / 计费 / 失败率）见
`docs/gateway-warehouse-kafka-message-protocol-2026-10-17.md` §2.1，那四条**必须**照着写。

**追踪坐标：1 + N 条共用同一个 `(trace_id, span_id)`**（robin 2026-10-28 追加要求）。

这看着像「偷懒不给每次查询单独开 span」，实际是把语义放对地方：W3C traceparent 第 3 段是
「发起这次调用的父 span」，N 次查询本就都是**提交那次 span 的子调用**。所以正确做法不是
「给每次查询生成新 span」，而是**回到提交那次**。

| | `fromTraceparent(String)` | `replay(String traceparent, String requestId)` |
|---|---|---|
| 语义 | 解析入站 trace + 为**本次**请求生成新 span | 回到**已经发生过**的那次请求 |
| `spanId` | `randomHex(8)`，每次调用都变 | 取 traceparent 第 3 段（即原 span） |
| `requestId` | 恒新生成 | 沿用入参；null 才生成（脏数据兜底） |
| 适用 | 网关入口（`GatewayTraceFilter`） | 异步任务重建上下文 |

⚠ **踩过的坑**：`AsyncTaskCompletion.publish` 原先每发一条事件就调一次 `fromTraceparent`，
于是同一笔任务的 1 + N 条拿到 N 个不同 `span_id` —— `trace_id` 一致掩盖了问题，数仓按
`(trace_id, span_id)` 聚不到一组，等于白留了 trace。

⭐ **测试分层的一个实例**：`replay` 的 4 例单元测试（`GatewayTraceContextTest`）在任何实现下都绿，
因为它们测的是 `replay` 自己；真正会红的是 `AsyncTaskCompletionTraceTest`（跑真实 `publish`）。
所以「单元测试全绿」在这里**不能**当作「集成路径用对了」的证据——两个类都得有。

### 3.3 产物转储扩展点（2026-10-28）

供应商给的产物地址有两处硬伤：**带有效期**、常在境外且跨域限速。今天能用是因为拿到就消费掉了；
一旦要给客户回看历史、或者供应商换了域名/下线了模型，旧地址就是一堆死链。
所以留一个扩展点，「有条件时」把产物搬到自己可控的位置。

```java
public interface ArchiveStore {
    String archive(ArchiveAsset asset);   // 输入供应商地址，输出客户端最终下载地址
}
```

| 项 | 约定 |
|---|---|
| 输入 | `ArchiveAsset`：`taskCode` / `upstreamTaskId` / `sourceUrl` / `modelCode` / `upstreamModelCode` / `providerAccountCode` / `ruleCode` / `completedAt` |
| 输出 | **非空白**的最终下载地址 |
| 默认实现 | `PassthroughArchiveStore` 原样返回 `sourceUrl`（`knot.gateway.archive.type=passthrough`，缺省即此） |
| 换实现 | 新实现标 `havingValue="s3"` 且**不写** `matchIfMissing`，与默认实现天然互斥，不需要 catalog |
| 调用点 | `AsyncTaskPoller.apply` 的 `SETTLE_BILLED` 分支，**一次任务一次**，在 `finish` 落库之前 |
| 失败 | 回退 `sourceUrl` + ERROR 日志；任务**照样 `SUCCEEDED`、照样计费、照发终态事件** |

四条关键取舍：

1. **转储失败不推翻终态**。它挂在「上游已成功、URL 已取到」之后，此时钱必然要算。
   为一个可以事后补搬的旁路去否定整个终态，等于把「地址将来会过期」升级成「这次调用彻底失败」。
2. **先算钱再搬文件**。两者互不依赖，但顺序反了会出现「文件已搬、计费抛异常、下次重查又搬一遍」。
   按 `taskCode` 幂等本不该产生副本，但没必要给实现方出这种题。
3. **接口不放 `knot-adapter`**。转储与厂商协议无关，Kling 之外的厂商、乃至图片/音频产物走的是同一套
   「临时地址 → 长期地址」。放进某个 adapter 子包，第二个厂商就会复制一份。
4. **`result_json` 只存最终 `result_url`**。原始供应商地址只进日志——`result_json` 是给客户端的交付物，
   不是运维台账；多存一份会让 passthrough 与真转储两种情形产生不同形状。

⚠ 三个类型名不带 `Video`（2026-10-28 由 `VideoArchiveStore` / `PassthroughVideoArchiveStore` / `VideoAsset`
改名）：**留 `Video` 前缀会让人以为图片/音频不适用**，而它本来就不限视频。配置键同步由
`knot.gateway.video-archive.type` 改为 `knot.gateway.archive.type`（旧键不留兼容，项目未上线）。

⚠ `ArchiveAsset` 刻意**不带** `contentType` / `sizeBytes`：查上游任务状态拿不到这两个事实，
留成字段只会变成永远为 null 的属性，下一个人得逐个查「为什么它是空的」。实现方真需要，自己 HEAD 一次。

⚠ 实现必须**幂等**（同一 `taskCode` 返回同一地址）且**线程安全**（轮询器按 `concurrency` 并发调用）：
节点在 `finish` 前宕机、终态重放、手动补搬，都会让同一个任务被搬第二次。

守门：`AsyncTaskPollerTest` 4 例（正常转储 / 抛异常回退 / 返回空白回退 / 上游失败不转储）
+ `PassthroughArchiveStoreTest` 2 例（逐字不改写、查询参数不解码）。

## 4. 调度：Spring `@Scheduled` + cron

### 4.1 节拍与节奏分离

```java
@Scheduled(cron = "${knot.gateway.async-task.tick-cron:0 * * * * *}")
public void tick() { /* 扫描 + claim + 处理一批 */ }

@Scheduled(cron = "${knot.gateway.async-task.cleanup-cron:0 0 * * * *}")
public void archive() { /* 删保留窗口之前的终态行 */ }
```

| 项 | 决策 | 理由 |
|---|---|---|
| **cron 而非 fixedDelay**（robin 2026-10-28 定调） | 节拍按墙钟对齐，配置即 cron 表达式 | 想改成「每 5s」「每 10min」只改配置，不用换算毫秒 |
| **必须配节拍守卫** | 每个节拍方法一个 `AtomicBoolean`（`compareAndSet`），拿不到就**跳过**这一拍 | ⚠ `@Scheduled` 对同一方法<b>不做互斥</b>；`fixedDelay` 时代靠「跑完再计时」天然串行，换 cron 后这个性质消失。不补守卫 → 同一批任务被两拍同时扫（DB claim 保证不重复处理同一行，但会产生无谓 UPDATE 与日志噪音，且 `blockLast` 把两个线程都占住） |
| 跳过而不是排队 | 拿不到就 `log.debug` 返回 | 排队会让欠账越滚越大；跳过则下一拍照常扫，效果与 fixedDelay 等价 |
| tick 默认 **每分钟**（`0 * * * * *`，2026-10-28 由每秒改来） | **真实节奏由行上的 `next_poll_at` 决定**，节拍只是下限 | 改轮询间隔不必重启；不同任务可有不同退避。⚠ 节拍是**下限**：档案写 `poll_interval_ms=5000` 的任务实际最早也要等下一个整分才查，于是「单次查询间隔 ≥ 60s、吞吐上限 = `batch-size`/分钟（100/min ≈ 1.7/s）」，`max_attempts`(360) 几乎永不生效，实际由 `timeout_ms`(30min) 先到 |
| `TaskScheduler` 线程池 | 必须自定义（默认单线程），当前 `async-task-` 池大小 2 | 单线程下任一 tick 卡住会连带停掉其它定时任务；池 2 让 tick 与 archive 互不阻塞 |
| 阻塞 HTTP | 提交到 `Schedulers.boundedElastic()` / 专用 `asyncTaskPollExecutor` | 红线：阻塞段不进 event loop；`@Scheduled` 线程也不是 event loop，仍需隔离 |

⚠ cron 表达式由 Spring 在**启动期**解析，写错直接起不来（fail-fast，不会静默跑一个错误节奏）。

### 4.2 多节点：DB 原子 claim，无中间件

```sql
-- ① 普通抢占：只挑「到期 + 未超时 + 无有效占位」的行
UPDATE kb_async_tasks
   SET claim_id = :claimId, claim_expires_at = :claimExpire, last_polled_at = NOW(3)
 WHERE status IN (:inFlightCodes)
   AND next_poll_at <= NOW(3)
   AND expires_at > NOW(3)                              -- 已超时的行交给 ②，两路互斥
   AND (claim_id IS NULL OR claim_expires_at < NOW(3))
 ORDER BY next_poll_at
 LIMIT :batchSize;

SELECT * FROM kb_async_tasks WHERE claim_id = :claimId;

-- ② 超时回收的抢占：只挑「已过 knot 侧超时」的行，其余条件同 ①
UPDATE kb_async_tasks
   SET claim_id = :claimId, claim_expires_at = :claimExpire
 WHERE status IN (:inFlightCodes)
   AND expires_at <= NOW(3)
   AND (claim_id IS NULL OR claim_expires_at < NOW(3))
 ORDER BY expires_at
 LIMIT :expireBatchSize;
```

- `claim_id = <nodeId>-<uuid>`：既做占位，又留下排查线索（只看 UUID 只能知道「不是我」，看不出是哪台机器卡住）。
- **不显式释放**：节点宕机后 `claim_expires_at` 到期自动可回收。优雅停机无需额外钩子。
- 吞吐控制：`batchSize`（默认 100）× tick 间隔；单节点足够，多节点天然分摊。

#### 4.2.1 ⭐ 占位是租约，不是锁：每次写都要带着它（2026-10-28 补）

抢到只说明「这一轮由我来做」，**不说明之后还能写**。若 `scheduleNext` / `complete` 不带
`claim_id` 条件，占位过期后原节点仍能写库：它把新主人刚立的占位抹成 `NULL`，第三个节点随即
再领一次同一行——重复处理就这么滚起来，而且每一环单独看都「成功」了。

```sql
... WHERE id = :id AND claim_id = :claimId AND status IN (:inFlightCodes)
```

`claim_id` 是与 `claim` 配对的 **fencing token**：写不进就代表这行已不归我，调用方**不得再报数**。

六道防线，缺一不可（判据是「哪种失守由谁兜」）：

| # | 机制 | 挡住什么 | 守门 |
|---|---|---|---|
| 1 | `claim` / `claimExpired` 的 `claim_id is null or claim_expires_at < now(3)` | 两个节点同时处理同一行 | DB 行锁 + 探针 ⑭ |
| 2 | `claim` 的 `expires_at > now(3)` / `claimExpired` 的 `expires_at <= now(3)` | 一条行同时被「轮询」和「超时回收」两条路挑中（不依赖两个节拍的先后顺序） | 探针 ⑭ |
| 3 | `scheduleNext` / `complete` 的 `claim_id = :claimId` | 租约过期后原节点仍能写库、抹掉新主人的占位 | 探针 ⑮ |
| 4 | `complete` 的 `status in (:inFlightCodes)` | 已经被落过终态的行被再落一次（终态事件唯一性） | `AsyncTaskPollerTest` |
| 5 | `attempts` 只在 `scheduleNext` 里 +1（且被 ③ 拦住） | 同一行被两个节点各加一次 → 退避跳档 | 同 ③ |
| 6 | 每行一次 CAS，不做批量 `UPDATE` 收超时 | 超时任务绕过状态机与事件发布 | `AsyncTaskPollerTest#expireTimedOutClaimsThenSettles` |

`scheduleNext` / `complete` 返回 `false` 时才有的两种处理：

- **不报查询事件**：这一行的 `task_query_seq` 已归新主人报。两边都报会让数仓按
  `(task_code, task_phase, task_query_seq)` 去重时无从判断哪条是真的；少记一次由 WARN 里的
  `taskCode` 兜底补账。
- **不发终态事件**：终态事件的口径是「一条任务一条」，由真正落定的人发。

#### 4.2.2 时间预算：`claim_ttl` 必须覆盖一轮处理

| 配置 | 默认 | 含义 |
|---|---|---|
| `query-timeout-ms` | 30 000 | 单次「查任务状态」的超时 |
| `claim-ttl-ms` | 180 000 | 占位有效期 = **一轮处理的时间预算上限**（查询 + 产物转储 + 落终态） |

⚠ 这两个数**同值不同义**的坑要注意：档案侧的退避封顶 `poll_backoff_max_ms` 默认也是 30 000，
但它与 `query-timeout-ms` 毫无关系。所有默认值已收敛到 `AsyncTaskDefaults`（2026-10-28），
每个数按「一个事实」独立命名，**禁止按数值合并常量**。

⚠ **不复用 `knot.gateway.upstream.response-timeout`**（默认 120s）：那是给生成型请求的（等模型吐字），
而查一次任务状态是亚秒级 GET。改造前正是拿它当查询超时，配上 60s 占位——**默认配置本身就是错的**：
查询只要慢过 60 秒，别的节点就会重领同一行。

校验位置：`AsyncTaskPoller#init`（`@PostConstruct`，配置绑定之后）断言
`claim-ttl-ms > query-timeout-ms > 0`，不满足直接拒绝启动。收益全在误配的那一天：
症状是「偶发少算上游调用数」，事后按日志几乎还原不出来。默认值另有 `AsyncTaskPropertiesTest`
在 CI 守（改错默认值不该等到部署才炸）。

#### 4.2.3 实测（2026-10-28，真实 MySQL，事务内 rollback，零残留）

12 条断言全绿，覆盖 ①②③④ 四道 DB 级防线：

| 断言 | 结果 |
|---|---|
| `claim` N1 拿到到期行 / N2 抢不到（N1 租约有效） | 1 / 0 |
| `scheduleNext`、`complete` 用**错**占位号 | 0 / 0 |
| 行仍在途且仍属 N1 | `POLLING?PENDING\|N1` |
| `scheduleNext` 用**对**占位号 → 占位被释放 | 1 / `POLLING\|null` |
| `claimExpired` 遇**有效**租约 | 0 |
| 普通 `claim` 遇到已超时行（两路互斥） | 0 |
| `claimExpired` 遇**过期**租约 | 1 |
| 原持有者 X 落终态 / 回收者 E1 落终态 | 0 / 1 |

同时用真实启动 + `AsyncTaskMapper` 的 SQL 日志确认两个语句都在 MySQL 上跑通：
`claimExpired` 带 `limit 200`（`expire-batch-size`）、`claim` 带 `limit 100`（`batch-size`），
`claim_expires_at` 恰为调用时刻 +180s，`claim_id` 前缀是本机主机名、每次调用一个新 UUID。

⚠ **仍未覆盖**：真正的并发交错（两个 JVM 同一毫秒抢同一行）没有自动化用例——
靠的是 InnoDB 对 `UPDATE ... ORDER BY ... LIMIT` 的行锁与 current-read 语义。
这里只验证「单条语句的判据在真实库上是对的」，没验证「两个事务同时跑」。

### 4.3 一次轮询的处理流程

流程被切成三段，中间那段是**唯一**会产生副作用的地方：

```
process(task)                                    // ① 取数：只读，不落库不发事件
  ├─ 反序列化 poll_spec_json / context_json 失败 → event = SNAPSHOT_INVALID
  ├─ attempts = 行上 attempts + 1
  ├─ attempts > max_attempts                    → event = ATTEMPTS_EXHAUSTED
  ├─ queryClient.query(...) 抛异常              → event = QUERY_ERROR（退避重试）
  └─ 否则 event = pollEventOf(queryBody, spec)  // ② 判语义：唯一入口
         terminalOf(queryBody) → RUNNING        → POLL_RUNNING
                               → FAILED         → POLL_FAILED
                               → SUCCEEDED      → resultUrlOf 为空 ? RESULT_MISSING : POLL_SUCCEEDED

apply(Polling, event)                            // ③ 执行：唯一出口，严格按 Action 分派
  ├─ REJECT         → log.warn，返回
  ├─ RESCHEDULE     → nextDelayMs(attempts, spec)
  │                   → scheduleNext(id, claimId, now + delay)
  │                       落库成功才 publishQuery；失败 = 租约易主，只留 WARN
  ├─ SETTLE_BILLED  → completion.account(...) → archive(...) → finish(SUCCEEDED, resultUrl, usage)
  └─ SETTLE         → finish(to, null, event.errorCode(), messageOf(event))
```

拆成「取数 / 判语义 / 执行」三段的意义：

- `pollEventOf` 是**语义判定的唯一入口**，`apply` 是**副作用的唯一出口**。加事件只改一处。
- `messageOf` 只管话术（`POLL_FAILED` 取上游 message、`ATTEMPTS_EXHAUSTED` 拼 maxAttempts），
  不参与决策——话术变不会改行为。
- `REJECT` 分支保留 `return`（而非抛异常）：此刻任务已被别的节点落终态，属于正常竞态，不是故障。

⭐ **计费逻辑零改动**：终态仍走 `UsageExtractorRegistry.extract` + 各模式 Calculator，只是触发点从请求线程换到 `@Scheduled` 线程、输入体从 create 体换成 query 体。禁止在 poller 内另写字段解析（口径漂移红线）。

## 7. 代码侧骨架（2026-10-28 落地 P0~P5；2026-10-29 三轮调整后定稿）

> ⭐ **2026-10-29 分层结论（中途改过三版，以本段为准）**：编排（`process` / `apply` / `finish` /
> 转储 / 退避）从 496 行的 `AsyncTaskPoller` 里**拆成独立的编排类**，并因消费方只有 gateway

### 7.1 落地时补上的五个判断（骨架阶段没写清）

1. **202 需要一个载体**：`applyUsageAccounting` 只能返回 `Object`，直接返回 `Map` 会被当成 200 响应体。故用 `AsyncTaskAcceptedResponse`（record，兼作控制信号），`GatewayControllerSupport.respond()` 里 `instanceof` 判出后走 `ResponseEntity.accepted()`。⚠ 2026-10-29 订正：**载体内部不再用 `Map` 装字段**——`task_id` / `query_url` 是蛇形 wire 名，改由 `@JsonProperty` 钉住，键名漂移由 `AsyncTaskAcceptedResponseTest` 守门（原版 `record AsyncTaskAccepted(Map<String, Object> envelope)` 全靠调用方手写字符串，键名写错编译期零信号）。
2. **权限绑定不需要登记**：`ks_api_permission_bindings` 只约束管理面 `/api/**`（`AdminAuthorizationInterceptor` 在 knot-admin，扫不到 knot-gateway 的控制器）。网关 `/openai/v1/**` 沿用主链路的 `Authorization` + `Rule` 头部校验，规则不匹配一律 **404**（不是 403 —— 不泄漏句柄是否存在）。
3. **归档清理不共用轮询节拍**：`archive()` 用独立的 `cleanup-cron`（默认 `0 0 * * * *`，即每小时整点）。清理是后台家务，同频只会让一张持续被扫的表再多一类写压力。
4. **只看 `Bearer ` 前缀等于没鉴权**（2026-10-28 补）：查询端点最初只校验 `Authorization` 以 `Bearer ` 开头，于是任意字符串都能拿任意 `taskCode` 去查——任务句柄是可枚举的 32 位十六进制，等于全库可读。修法不是新写一套校验，而是把 `RoutingResolver` 里「key 形态 → consumer 存在且启用 → rule 属于该 consumer → app 存在且启用」这条链原样抽出为 `resolveAccess`，再暴露 `public void requireRuleAccess(secretKey, ruleCode)`；`resolveByRule` 与查询端点共用同一实现，避免两条鉴权路径日后漂移。`GatewayExceptionHandler` 的 advice 范围随之从 `{GatewayControllerSupport}` 扩到 `{GatewayControllerSupport, GatewayTaskController}`，否则 401 / 400 的响应体形状会和主链路不一致（无 advice 时走 Spring 默认错误页）。
5. **「一次请求一条事件」这个前提本身被推翻了**（2026-10-28，v3 定稿）：这条经历过三个阶段，记全是因为每一步都踩了坑。
   - **v1（错）**：异步提交后只把抑制判断挂在非流式成功这一个出口上。于是任务行已落库、202 已构造，若随后 `dispatchGatewayPlugin(GATEWAY_RESPONSE)` 抛异常，异常出口会照发一条错误事件，轮询器稍后还会发终态事件——一次请求两条。
   - **v2（对但方向错）**：把判断下沉进 `publishTraffic` 并做成 `protected final`，三个出口都走它，`final` 防第四个；删掉子类重复的 `eventPublisher` / `trafficTopic`（它存在的唯一理由是让 `streamResponse` 自己 publish，即第二个出口）。这一步技术上是对的——**但抑制这件事本身是错的**（见 §3.2）：它把「1 次提交 + N 次查询」压成 1 条，上游调用数与延迟分布在数仓里全没了。
   - **v3（现行）**：抑制整体废除，钩子 `suppressesTrafficEvent` 删除，`publishTraffic` 只剩 `eventPublisher == null` 这一个开关。异步语义改由事件自带的 `task_*` 字段表达，模板层**完全不知道异步的存在**。
   - 教训：**「修好一个错误的机制」不等于「做对了事」**。v2 的探针是有效的（去掉判断恰好 3 例红），但它验证的是「抑制有没有生效」，而没人问「抑制该不该存在」。守门测试随之整体重写为 `AsyncTaskTrafficEventTest`（9 例），旧类删除——**能力搬家时测试必须跟着搬，否则删了能力测试还绿**。
6. **超时不能绕过状态机**（2026-10-28 补，状态机改造的连带收获）：`expireTimedOut()` 原先是批量 `UPDATE`，不发终态事件，于是「超时」这个结局在数仓里完全不存在。详见 §3.1 末段。

⑨ 是这一轮最值得记的一条：**单元测试绿了不代表集成路径用了它**。`replay` 本身无论怎么测都是对的，
错的是「`publish` 没调它」。这类错口只有端到端的那个类能咬住——所以不能拿 `GatewayTraceContextTest`
的绿替代 `AsyncTaskCompletionTraceTest`。

⑩ 则说明两条断言各自承重：spanId 与 requestId 是**两个独立的不变量**，不是一个的推论。
（`replay` 里 requestId 传 null 会静默新生成，编译期和 spanId 断言都看不出来。）

② 的结果是本次最有价值的一条：**控制器侧的用例是接线测试，抓不到鉴权实现退化**（它的 `RecordingRoutingResolver` 覆写了 `requireRuleAccess`，只能证明「被调用、传的是去掉 `Bearer ` 的裸 key」）。真正咬住鉴权语义的是 ③——所以两层都不能省，且**不能把「控制器绿了」当成鉴权正确**。

⑥ 同理印证了「终态冻结是两层执行」：poller 侧的 SQL claim 已经带 `status IN (:inFlightCodes)`，终态行根本不会进入 `process()`，所以轮询器测试**结构上摸不到**那条守卫。这类冗余不是浪费——CAS 管并发抢，状态机管「不该发」；但**只有穷举测试能验证后者还活着**。

⑯ 是补「假绿」的那一条：单测里 `store` 是 mock，`any()` 什么参数都能过。把占位号换成 `null`
立刻 9 例红，说明那些 `eq(CLAIM_ID)` 不是摆着好看的——**没有这条探针，就没法排除「断言写宽了」**。

⚠ 但单测层的绿**证明不了 SQL 条件是对的**：mock 的 `store` 根本不含 `where` 子句。
这一层只能靠 §4.2.3 的真实 DB 探针（12 条断言）+ 真启的 SQL 日志。两层的分工要分清：
单测守「调用方有没有把租约传下去」，DB 探针守「传下去之后 SQL 认不认」。

⭐ **2026-10-28 补上了中间一层（此前判为「静态不可判」）**：`<foreach>` 这类动态节点
**不需要数据库就能验证**——mybatis 3.5.x 自带 shaded 的 `org.apache.ibatis.ognl`
（外部 ognl 是 `optional` 依赖、不传递，fat jar 里没有它），所以 `Configuration` +
`XMLMapperBuilder` 解析 XML 后取 `MappedStatement#getBoundSql(params)` 即可拿到展开后的 SQL
（`AsyncTaskMapperSqlTest`，4 例）。实测 claim 展开结果是 `where status in ( ? , ? )`。
⚠ 断言只盯 `status in (...)` 那对括号：写成「整条 SQL 不许出现数字」会被 `now(3)`（毫秒精度）立刻误报。
ℹ 仍然判不了的（列名、join、`now(3)` 时区口径、`order by ... limit` 方言合法性）仍归真库。
于是三层分工变成：**BoundSql 守卫守「参数有没有真的展开」→ DB 探针守「展开后数据库认不认」→ 真启守「启动期能解析」**。

与 `docs/视频异步任务轮询拉取技术方案-2026-10-26.md` 的差异：**存储层换 DB、配置层抽成档案表、端点通用化、调度换 `@Scheduled`**；其余（202 信封、终态发一条事件、失败不计费）保持不变。

## 11. 回调交付（`callback_url`）：与 `task_status` 正交的独立维度（2026-10-29）

> 迁移：`docs/database/migration/2026-10-29-async-task-callback.sql`
> 代码：`AsyncTaskDeliveryRunner` / `AsyncTaskCallbackClient` / `AsyncTaskCallbackUrlSupport` / `AsyncTaskViewSupport`

### 11.1 一句话结论

**交付不是状态机的第 N 个状态，而是一条独立的链路。** `task_status` 答「任务成没成」，
`delivery_status` 答「结果有没有送到客户的 `callback_url`」。两者可任意组合——
「生成成功 + 回调失败」是合法状态，且**不是任务失败**。

### 11.2 为什么必须正交（参考设计踩过的坑）

见 `gateway_multi_modal_task` 式状态机里的 `13 = 最终失败`：它表示「Webhook 连续失败 3 次」，
注释却写着「不代表生成一定失败」。一旦客户按这个终态做业务判断，就会把一批**已经生成成功**的
任务当成失败重跑——既有资损，也让「成功率」永远算不准。根因是把「交付失败」塞进了业务终态枚举。

本方案的判据：**任何会被客户用来判断「有没有货」的字段，只能由业务维度决定**；
交付维度只回答「通知到了没」，放弃了也不改 `status`。

### 11.3 表结构（`kb_async_tasks` 追加 8 列）

| 列 | 含义 |
|---|---|
| `callback_url` | 提交时从**原始请求体**提取并落库；不转发给上游 |
| `delivery_status` | 0 无需回调 / 1 待回调 / 2 成功 / 3 失败（`AsyncTaskDeliveryStatusEnum`） |
| `delivery_attempts` | 已尝试次数（含失败重试） |
| `next_delivery_at` | 下次投递时刻；`NULL` = 不在扫描集 |
| `delivered_at` | 成功送达时刻 |
| `delivery_error` | 最近一次失败原因摘要 |
| `delivery_claim_id` / `delivery_claim_expires_at` | 交付**独立租约**（与轮询的 `claim_id` 分开） |

索引：`idx_async_tasks_delivery (delivery_status, next_delivery_at)`。

### 11.4 三条借鉴原则的落点

| 原则 | 落地方式 | 为什么 |
|---|---|---|
| **独立维度** | 进度只写 `delivery_*`，从不改 `status` | 保证「成功+回调失败」可表达；放弃不改任务结论 |
| **可崩溃恢复（检查点）** | 进度全在库里；租约到期由下一拍重新抢占续投 | 节点宕机不需要补偿任务，也不会永久漏回调 |
| **正向包含扫描** | `delivery_status IN (待回调)` | 「排除成功/失败」会让新增子态被静默扫不到 |

### 11.5 流转

1. **提交**：`AsyncTaskSupport` 从原始请求体提取 `callback_url` → SSRF 校验 → 落草稿；
   有地址则 `delivery_status = 1`，否则 `= 0`。
2. **终态**：`mapper#complete` 在同一条 CAS SQL 里**原子武装**交付
   （`delivery_status → 1`、`next_delivery_at → 此刻`）。放进同一条 SQL 是为了避免
   「已终态、却永远不会回调」且无报错的半截状态。
3. **投递**：`@Scheduled` 的 `deliver()` 抢占 → `AsyncTaskCallbackClient` POST
   （body 与轮询响应**同形**，见 §11.6）→ 成功落 `2` / 失败退避 / 到上限落 `3`。
4. **重试**：`min(cap, base × 2^(n-1))`，默认上限 3 次。

### 11.6 回调 body 就是轮询响应

`AsyncTaskViewSupport` 是唯一投影：轮询（`AsyncTaskLookupRunner`）与回调（`AsyncTaskDeliveryRunner`）
共用 `AsyncTaskQueryResponse`。于是「轮询拿到什么」与「回调收到什么」永远同形，客户端只写一套解析。
字段：`task_id / status / created_at / completed_at / result_expires_at / result / error`。

### 11.7 与轮询的边界（两套预算，互不拖累）

| 维度 | 轮询 | 交付 |
|---|---|---|
| 租约字段 | `claim_id` | `delivery_claim_id` |
| 预算 | `claim-ttl-ms` > `query-timeout-ms` | `delivery-claim-ttl-ms` > `delivery-timeout-ms` |
| 节拍 | `tick-cron` | `delivery-cron` |
| 失败后果 | 重复调上游 | 重复回调客户（对外可见） |

两条独立租约的理由：交付发生在终态之后，轮询租约此时已释放；复用一个字段会把
「这一行的轮询由谁负责」与「投递由谁负责」两个事实混在一起。

### 11.8 安全：`callback_url` 是出站目标

原先这个地址被整体剥掉（计费完整性 + 不让客户端指定出站目标）。现在支持回调，就必须守 SSRF：

- 只允许 `http/https`；
- **一律拦截**回环 / 私网 / 链路本地 / CGNAT / 保留地址（IPv4 与 IPv6）；
- 可选白名单 `knot.gateway.async-task.callback-allowed-hosts`（后缀匹配）。

⚠ 残余风险已登记：本类不做 DNS 解析后的 IP 复核，**DNS rebinding 仍可绕过**；
对公网开放回调的部署应配白名单。

### 11.9 已知边界

- **至少一次，不是恰好一次**：投递发出与写回成功之间有崩溃窗口，会重发；
  客户端须按 `task_id` 幂等。`completeDelivery` 的 CAS 只保证「不重复记账」，不保证「不重复发送」。
- **管理端重试会产生第二次回调**：`complete` 每次都重新武装交付（若行上有地址），
  于是重开→新终态会再推一次。这是刻意的——客户需要知道重试后的新结果。
  但**重开本身必须把交付维度归零**（`delivery_status→0`、`attempts→0`、`next_delivery_at`/
  `delivered_at`/`delivery_error`/`delivery_claim_*` 全清空，`callback_url` 保留）：
  否则停在待回调的行被重开后，交付节拍会先拿已清空的 `result_json` 推一次空结果，
  新终态到达再武装一次——**同一个任务两次回调，且第一次是错的**。复位与 `status` 的归零在
  同一条 UPDATE 里完成（`reopen`），不能分两步：中间态会被另一节点抢到。
- **交付失败不影响清理，但「待回调」会挡住清理**：`cleanup` 的谓词是
  `status not in (inFlightCodes)` ∪ `delivery_status not in (deliverableCodes)` ∪ `completed_at < before`。
  已送达成功 / 已放弃的终态行照常按保留窗口删；**仍欠客户端一次结果**的行不删——
  只看 `status` 就把结果连同 `result_json` 一起静默丢弃，客户端既收不到回调也查不到轮询，
  而且没有任何报错。保留期（默认 30 天）远大于 3 次退避总时长，正常不会长期堆积；
  真要堆积，说明回调目标长期不可达，这本身就是该告警的信号而不是该删的数据。
