# 视频异步任务轮询拉取技术方案（knot-gateway）

> 状态：技术方案设计，待 robin 批准分批实施
> ⚠ **已被 `docs/异步任务表与通用轮询方案-2026-10-27.md` 取代**：端点路径与 HTTP 方法以那份为准（现为 `POST /openai/v1/tasks/{task_code}`，通用而非仅视频；2026-10-29 由 GET 改 POST，见 `docs/standards/rules/10-backend-java.md §5.2`）。本文保留设计过程，勿照此实现。
> 日期：2026-10-26
> 范围：`knot-server/knot-gateway`（及 `knot-adapter` 提取/计费管线的复用）
> 触发：MiniMax H3 视频生成走「创建任务 → 轮询 → 取产物/用量」异步模型，而网关当前是同步计费链路。本方案为「网关视频统一采用定时轮询远程拉取」整理实现设计。

## 0. 结论先行

1. **行业共识**：视频生成是异步任务——`create` 立即返回 `task_id` + 挂起态，**用量与计费所需字段只在终态 `query` 响应里返回**，不在 create 响应里。轮询是基线，webhook 是加速可选。knot 必须为此在「创建响应即终态」与「异步任务挂起」之间插入一条分支。
2. **计费逻辑零改动**：异步只是把「触发点」从请求线程挪到轮询完成线程、把「输入体」从 create 体换成 query 体。终态仍走现有 `UsageExtractorRegistry.extract` + `VideoBillingModeCalculator`，复杂度量继续收敛在 `BillingMode × PricingPlan` 两层（见 `docs/视频模型计费规则设计-2026-10-25.md`）。
3. **客户端轮询 knot，不轮询供应商**：网关新增自有查询端点，返回 knot 任务句柄的当前状态/产物/用量；网关 poller 在后台定时查上游并终态计费。供应商被抽象在 knot 之后，计费集中可控。
4. **不建自建队列**：待轮询任务集即存储（Redis/Caffeine），调度即扫描 —— 契合「不在网关建消息队列、Kafka 走原生 async」的既有哲学（见 `docs/gateway-warehouse-kafka-message-protocol-2026-10-17.md` §4）。
5. **数据不丢失红线**：任务存储生产默认 Redis（fail-hard，不可用即 503，不静默丢失）；上游查询窗口（MiniMax 7 天）提供节点重启后的恢复宽限。

## 1. 行业视频模型产出方案对比

| 厂商 | 创建 | 状态查询 | 终态产物 | 用量返回位置 | 计费点 | webhook |
|---|---|---|---|---|---|---|
| **MiniMax H3**（用户提供） | `POST /v2/video_generation` → `task_id` | `GET /v2/query/video_generation/{task_id}`（窗口 `[T-7d, T)`） | `content.url` | query 体 `usage`（total/input/output_seconds、input_image_count、total_tokens…） | 完成按实际量 | 支持 `callback_url` 推送 |
| **OpenAI Sora** | `POST /videos` → `id`，`status:queued/in_progress` + `progress` | `GET /videos/{id}`（建议 10–20s 间隔、指数退避） | `GET /videos/{id}/content` 下载 MP4 | 终态 task 对象（已 deprecated，仅历史参考） | 完成按实际量 | `video.completed`/`video.failed` 事件 |
| **Runway** | `POST /generations/text-to-video` → `id` | `GET /generations/{id}`（轮询至 `completed`） | `video_url` | 终态 task | 完成按实际量（credit 计费） | SDK `waitForTaskOutput` 等价轮询 |
| **Kling 可灵** | `POST …/video/…` → `task_id` | `GET /tasks?task_ids=`（submitted/processing/succeeded/failed） | `outputs[].url`（30 天后清理） | query 体 `usage`；官方按秒计费（输出/输出×2/输入+输出） | **两派并存**：代理式「创建即扣、失败退」vs 官方「完成按实际量」 | 无（依赖轮询） |
| **Luma Dream Machine** | `POST /generations` → `id` | `GET /generations/{id}`（`completed`/`failed`） | `assets.video` | 终态 generation | 完成按实际量 | 支持 `callback_url`（每次状态变更 POST，失败重试 3 次） |
| **Google Veo**（经 Runway） | `POST /text_to_video` → task id | `GET /tasks/{id}` | `output[]` | 终态 task | 完成按实际量 | 同 Runway |

**横向结论**：
- **轮询是基线，webhook 是加速可选**：6 家里 4 家明确支持轮询、3 家支持 webhook（MiniMax/Luma/Sora）。webhook 需要 knot 暴露入站回调端点并做鉴权，反而把计费触发点打散到不可控的外部网络，故本方案**以轮询为主、webhook 列为未来增强**。
- **用量只在终态返回**：create 响应里只有 `task_id` + 挂起态，没有任何计费字段。这正是同步链路会误计为零账的根因。
- **计费点有分歧**：Kling 代理式「创建即扣、失败退」与官方/其余「完成按实际量」并存。knot 选**完成按实际量**——与现有 `VideoUsageExtractor` 读 query 体、`allowsEmptyUsage` 兜底语义天然一致，且失败天然不扣（见 §5.5 / §8 D2）。

## 2. knot 现状链路（改造前）

```
GatewayVideoController.generations()                      [controller/GatewayVideoController.java]
   └─ GatewayRequestHandler.handle(...)
        └─ AbstractGatewayRequestTemplate.handleMap
             ├─ resolveRouting
             ├─ proxy → proxyWithFailover → attemptCandidates
             │     └─ UpstreamProxyClient.proxy → MediaProtocolExecutor(VIDEO_GENERATIONS)
             │           └─ AbstractUpstreamProtocolExecutor.executeBuffered
             │                 └─ UsageExtractorRegistry.extract(responseBody, context)  ← 计费输入
             └─ onProxyResult → applyUsageAccounting → publishTraffic (终态 Kafka 事件)
```

问题：MiniMax H3 `POST /v2/video_generation` 返回 `200 {task_id, status:"queued"}`。当前链路把它当作**成功缓冲响应**，用 `VideoUsageExtractor` 解析 → query 体字段全无 → 合法零用量 → `VideoBillingModeCalculator` 算出 **0 金额** → 发一条「成功但零账」的 `GatewayTrafficMsgDto`。任务实际还在上游排队，网关已终态，**漏计 + 误报**。

## 3. 设计目标与非目标

**目标**
1. 视频异步任务（尤 MiniMax H3）走「创建→轮询→终态计费」，计费与同步路径**同一套**提取/计费管线。
2. 客户端通过 knot 自有端点查询任务状态与产物，不直接接触供应商轮询地址。
3. 多节点部署下不重复轮询、不丢任务、不静默降级。
4. 触发点迁移不引入第二套用量解析（禁止 poller 内另写字段映射）。

**非目标**
- 不改 `BillingModeEnum` / `PricingPlanEnum` / `VideoBillingModeCalculator` 的计价语义（见 `docs/视频模型计费规则设计-2026-10-25.md`）。
- 不在本方案做 webhook 入站端点（列为未来增强，见 §9）。
- 不引入新的消息队列中间件；不改动 Kafka 单条流量事件协议（`knot.gateway.traffic/1.0`）。

## 4. 总体架构

```
客户端                                      knot-gateway
  │  POST /openai/v1/videos/generations
  │  (Authorization / X-Knot-Rule / body: model=MiniMax-H3 …)
  ▼
[VideoAsyncTaskSupport 判定]── asyncTask=false ──► 走既有同步链路（不变）
  │ asyncTask=true
  ▼
UpstreamProxyClient.proxy(VIDEO_GENERATIONS)  ──► 上游 create → {task_id, status:queued}
  │
  ▼
解析 task_id + 存 PendingTask(AsyncVideoTaskStore) + 记录 billingRuleRef / requestBody
  │
  ◄── 202 Accepted { task_id(knot), status:"queued", query_url }
  │
  │  GET /openai/v1/videos/tasks/{knot_task_id}   （客户端轮询 knot）
  ▼
返回 store 中当前状态（queued/processing/completed/failed）+ 产物/用量(终态)

  ┌──────────────── VideoTaskPollScheduler（boundedElastic 定时 tick）────────────────┐
  │  扫 due 任务（Redis 原子 claim / Caffeine 进程内）                                  │
  │   each: 在 gatewayBlockingScheduler 上 GET 上游 query 端点                          │
  │     ├─ 瞬败/非终态 → 指数退避、attempts++、更新 nextPollAt                          │
  │     ├─ succeeded    → TerminalTask → UsageExtractorRegistry.extract(query体)         │
  │     │                   → VideoBillingModeCalculator → GatewayTrafficMsgDto          │
  │     │                   → KafkaPublisher.publish（终态事件）                         │
  │     │                   → 写 store.result(产物URL + usage)                          │
  │     └─ failed/expired → 发 error 流量事件（不计费）                                  │
  └─────────────────────────────────────────────────────────────────────────────────────┘
```

## 5. 关键设计点

### 5.1 异步判定：数据驱动，不靠协议枚举

`VIDEO_GENERATIONS` 既可能异步（MiniMax H3）也可能同步（未来模型），**不能**用协议枚举硬判，否则破坏既有同步视频。

在 `ModelApiBindingEntity` 扩展异步任务字段（复用既有 `api_path` 思路，加 `task_query_path` 等）：

| 字段 | 含义 |
|---|---|
| `async_task` (bool) | 该绑定是否为异步任务模型 |
| `task_query_path` | 上游查询路径模板，含 `{task_id}` 占位（如 `/v2/query/video_generation/{task_id}`） |
| `task_id_json_path` | create 响应取 `task_id` 的 JSON 路径 |
| `task_status_json_path` | query 响应取状态的路径 |
| `task_status_succeeded` / `task_status_failed` | 终态取值（逗号分隔多值） |
| `task_result_url_json_path` | 终态产物 URL 路径（MiniMax `content.url`） |
| `task_error_json_path` | 失败原因路径 |

`VideoAsyncTaskSupport` 读这些字段，把「create 响应 → PendingTask」与「query 响应 → TerminalTask(status, usageBody, resultUrl, error)」两件事做成纯数据映射，不把供应商特例写死在代码里。

### 5.2 客户端契约（knot 自有查询端点）

**创建返回 202**（非 200），信封示例：

```json
{ "task_id": "<knot生成的句柄>", "status": "queued",
  "query_url": "/openai/v1/videos/tasks/<knot_task_id>" }
```

**查询返回**（新增 `GET /openai/v1/videos/tasks/{knot_task_id}`，同 Authorization + Rule 鉴权）：

```json
{ "task_id": "...", "status": "processing", "progress": 33 }
// 终态：
{ "task_id": "...", "status": "completed",
  "result_url": "https://cdn.../x.mp4",
  "usage": { "<knot_extend.usage 同形状>" } }
// 失败：
{ "task_id": "...", "status": "failed", "error": { "code": "...", "message": "..." } }
```

客户端轮询 knot 而非供应商 → 供应商地址/鉴权不外泄、计费集中、未来换供应商客户端无感。

### 5.3 任务存储 `AsyncVideoTaskStore`

接口 `AsyncVideoTaskStore`，两实现复用既有 `StoreMode` / `StoreModeResolver` / `RedisCache`（fail-hard）骨架：

- **Caffeine 实现**：单节点/开发档（`StoreMode.CAFFEINE`），进程内 `ConcurrentMap` + 定时清理。
- **Redis 实现**：生产档（`StoreMode.REDIS`），key=`async-task:{knotTaskId}`，Lua 原子 claim 防多节点重复轮询；Redis 不可用 → 抛 `RedisUnavailableException` → 创建即 503（**不静默丢失任务**，契合 `RedisCache` 的 fail-hard 红线）。

存储内容：`knotTaskId`、`upstreamTaskId`、`providerAccountCode`、`ruleCode`、`stickyKey`、`traceparent`、`requestId`、`billingRuleRef`（序列化）、`requestBody`（供 `VideoUsageExtractor` 取 input 维度/分辨率）、`pollState(nextPollAt, attempts, status)`、`createdAt`、`expiresAt`、`resultPayload`。

**恢复性**：节点重启后 poller 扫 due 任务继续轮询；上游查询窗口（MiniMax 7 天）远大于 knot 侧超时，提供充裕恢复宽限。

### 5.4 Poller：Reactor 调度，无自建队列

`VideoTaskPollScheduler`：单例，在**专用 boundedElastic** 上 `Flux.interval`（间隔 `knot.gateway.async-video.poll-interval-ms`，默认 1500ms）定时 tick。每 tick：

1. 取 `nextPollAt ≤ now` 的任务（Redis 原子 claim / Caffeine 进程内）。
2. 对每个任务：在 `gatewayBlockingScheduler`（`GatewayAsyncConfiguration` 的 `gatewayBlockingScheduler`）上发起上游 query（复用 `UpstreamUrlSupport` + `UpstreamAuthApplier` + WebClient），**不**走 `attemptCandidates` 的候选 failover（query 是固定 GET，单尝试 + 自身退避）。
3. 按响应分支（见 §4 图）。
4. 退避复用 `BackoffCalculator`（与现有重试同源），避免另写一套。

**多节点去重**：Redis `SETNX` 风格 Lua claim，保证同一任务仅一节点轮询；Caffeine 单进程天然无并发。**不建消息队列**——pending 集即存储，扫描即调度。

### 5.5 终态计费（复用现有管线，仅触发点转移）

`succeeded` 时拿 **query 响应体** → `UsageExtractorRegistry.extract(queryBody, context)`：

- `VideoUsageExtractor` 读 `total_seconds` / `input_duration_seconds`（别名 `input_video_seconds` 等）/ `input_image_count` 与 `requestBody` 维度（与同步路径**同一提取器、同一口径**）。
- → `UsageAccounting` → `VideoBillingModeCalculator` → `NormalizedUsage`（金额十进制字符串）。
- 构造 `GatewayTrafficMsgDto`（复用 `of(...)` 工厂，由 poller 提供 `usage` / `ttftMs=null`）→ `KafkaPublisher.publish(trafficTopic, ...)`。

**计费逻辑零改动**；唯一新增是「何时跑（poller 线程）+ 输入体是 query 体」。禁止在 poller 内另写字段解析（口径漂移红线）。

### 5.6 失败 / 过期 / URL 时效

- **failed**：发 error 流量事件（`status=upstream_error`/`gateway_error`，带上游 `code`），**不计费** —— 与「D2 失败不扣」一致（见 `docs/视频模型计费规则设计-2026-10-25.md` §9 待办项）。
- **expired**：超过 knot 侧超时（默认建议 30min，可配，远小于上游 7 天窗口）→ 发错误事件。
- **查询瞬败（429/5xx）**：退避重试，不终态。
- **结果 URL 时效**：MiniMax 7 天窗口、Kling 30 天、Sora 24h。默认**透传 + 文档提示**；「下载转存对象存储」列为未来增强（§9）。

### 5.7 Kafka 流量事件时机调整

| 路径 | 发布点（变更后） |
|---|---|
| 同步/流式 | 既有：非流式 success / catch / 流式 onComplete 三处终态（不变） |
| 异步任务 | create（202）**不**发流量事件（非终态）；poller 在 `succeeded`/`failed`/`expired` 终态发**一条** |

与「单条消息、终态一次」设计完全一致（`docs/gateway-warehouse-kafka-message-protocol-2026-10-17.md` §1）；仅发布点从请求线程移到 poller 线程。

实施影响：`GatewayRequestHandler` 在识别 `asyncTask` 绑定时，抑制 `onProxyResult` 内的 `publishTraffic`，改由 poller 承担。

### 5.8 配置（`knot.gateway.async-video.*`）

对齐 `GatewayUpstreamClientProperties` / `UsageExtractionProperties` 风格（顶层 `knot.gateway.*`，env `KNOT_GATEWAY_*`）：

| key | 默认 | 说明 |
|---|---|---|
| `enabled` | false | 是否开启异步视频轮询 |
| `poll-interval-ms` | 1500 | poller tick 间隔 |
| `max-poll-attempts` | 1200 | 超过标记 expired（≈30min @2s） |
| `poll-backoff-base-ms` | 1000 | 退避基数（复用 `BackoffCalculator`） |
| `poll-backoff-max-ms` | 30000 | 退避上限 |
| `task-timeout-ms` | 1800000 | knot 侧任务超时（默认 30min） |
| `store` | `redis`（prod）/ `caffeine`（dev） | 经 `StoreModeResolver` 归一 |

## 6. 与既有红线/规范的契合

- **计费只落两层**：异步不改，query 体复用 `VideoBillingModeCalculator`。
- **失败不扣（D2）**：failed 任务不跑计费，仅发错误事件。
- **Redis fail-hard / StoreModeResolver**：任务存储直接复用。
- **boundedElastic 阻塞段 / event loop 禁 block**：poller 的 query HTTP 在 `gatewayBlockingScheduler` 执行。
- **Kafka 原生 async / 不建队列**：poller 用存储扫描，无自建队列。
- **数据不丢失**：Redis 持久 + 上游窗口恢复宽限。

## 8. 风险与应对

| 风险 | 应对 |
|---|---|
| 多节点重复轮询 | Redis 原子 claim（Lua）保证单节点轮询；Caffeine 单进程无并发 |
| 任务丢失（Redis 宕） | fail-hard 503，不静默放行；上游查询窗口（7 天）提供恢复宽限 |
| 同步视频被误判异步 | 以绑定 `async_task` 标记驱动，不靠协议枚举 |
| 计费口径漂移 | 复用同一 `UsageExtractorRegistry`，禁止 poller 内另写解析 |
| 上游窗口 ≠ 无限 | knot 侧超时默认 30min（可配），远小于 7 天 |
| 结果 URL 时效 | 默认透传 + 文档提示；下载转存列未来增强 |
| 客户端长轮询占用 | 查询端点无副作用、可缓存；建议客户端指数退避 |

## 9. 待 robin 拍板的决策点

1. **计费点**：完成按实际量（推荐，与现有提取器一致）vs 创建预留+失败退（Kling 代理式）。
2. **客户端契约**：knot 自有 `task_id` 信封（推荐，抽象供应商）vs 直接透传供应商 `task_id`。
3. **轮询 vs webhook**：轮询为主（推荐），webhook 未来增强。
4. **URL 处理**：透传（推荐）vs 下载转存对象存储。
5. **存储**：Redis 生产默认（推荐，fail-hard），Caffeine 仅单节点。
6. **knot 侧任务超时默认值**：建议 30min。
